끝났을 때 할 수 있어야 하는 것

Mental model

file format, table format, catalog, warehouse, compute engine의 책임을 명확히 분리한다.

Metadata forensics

current pointer에서 data/delete file까지 추적하고 query pruning과 commit을 설명한다.

Transactions

optimistic concurrency, atomic pointer swap, isolation, conflict validation의 보장과 실패 창을 말한다.

Evolution

field ID, partition transform/spec, sort order를 사용해 과거·신규 data의 공존을 설계한다.

Operations

small files, manifest growth, delete amplification, snapshot/orphan cleanup을 안전하게 운영한다.

Interview

“Parquet만으로 왜 부족한가?”를 transaction, planning, evolution, delete 관점으로 증명한다.

Iceberg의 핵심은 immutable file을 직접 고치는 것이 아니라 새 table state를 만들고 catalog의 current metadata pointer를 원자적으로 바꾸는 것이다.

큰 그림: metadata tree와 read/write path

실선은 reader가 현재 table state를 찾는 경로다. writer는 새 data/metadata를 만든 뒤, 마지막에 catalog pointer를 compare-and-swap 방식으로 commit한다.

Deep Dive: commit의 선형화 지점과 delete 적용 규칙

Iceberg를 깊게 안다는 것은 metadata 파일 목록을 외우는 것이 아니라, immutable file로 어떻게 일관된 table state를 만들고 concurrent writer를 검증하는지 설명하는 것이다.

1 · Commit linearization

Writer는 base metadata에서 계획하고 새 data/delete/manifest/metadata file을 immutable하게 만든다. 이 파일들은 아직 table state가 아니다. Catalog가 “base pointer가 여전히 current인가?”를 확인하며 새 metadata location으로 원자 교체하는 순간 commit이 선형화된다. 실패 시 파일은 보이지 않지만 storage에 남아 orphan 후보가 된다.

2 · Operation-specific validation

Append는 기존 file을 제거하지 않아 concurrent append를 새 current snapshot 위에 재적용할 수 있는 경우가 많다. 반면 overwrite/rewrite/delete는 계획할 때 본 file·predicate가 여전히 유효한지 검증해야 한다. 충돌 후 무조건 retry하면 새로 들어온 row를 누락하거나 다른 writer 결과를 지울 수 있다.

3 · Two-stage pruning

Manifest list의 partition summary와 counts로 manifest 자체를 제거하고, 남은 manifest의 data file partition tuple·lower/upper bound·null/value count로 file을 제거한다. Planning이 directory listing에 비례하지 않도록 metadata를 분산·재사용하지만 manifest 수와 크기가 커지면 planning latency·client memory가 다시 병목이 된다.

4 · Sequence-number semantics

Delete는 보통 자신보다 오래된 동일 partition data file에 적용된다. Data sequence number는 content의 상대적 나이를 나타내고 rewrite가 content age를 보존해야 하는 경우가 있다. File sequence number는 file이 table에 추가된 snapshot 순서다. 둘을 혼동하면 delete applicability와 incremental processing이 틀어질 수 있다.

5 · v2/v3 delete path

Equality delete는 지정 field 값이 같은 row를, position delete는 file path+row position을 지운다. v3 deletion vector는 한 data file의 deleted position을 bitmap으로 표현하며 snapshot에서 data file당 최대 하나여야 한다. v3 writer는 새 position delete file을 만들지 않지만 업그레이드 table의 기존 position delete는 읽을 수 있어야 한다.

6 · Maintenance race

Compaction은 새 file을 쓰고 old file을 metadata에서 제거하는 또 하나의 transaction이다. Snapshot expiration은 rollback/history reference를 줄이고, orphan cleanup은 metadata에서 참조되지 않는 physical file을 지운다. 장기 writer·branch/tag·다른 engine의 staging file보다 짧은 age threshold를 쓰면 정상 file을 삭제할 수 있다.

기술 리뷰: metadata tree를 근거로 답하기

Metadata review
  1. 현재 snapshot에서 특정 Parquet file까지 어떤 pointer를 따라가는가?
  2. manifest list와 manifest 양쪽에 statistics가 필요한 이유는?
  3. field ID 없이 rename하면 어떤 silent corruption이 가능한가?
  4. partition spec이 다른 old/new file을 한 predicate로 어떻게 pruning하는가?
Transaction review
  1. atomic commit의 선형화 지점은 어디이며 object storage rename이 필수인가?
  2. append retry와 overwrite retry의 conflict validation이 왜 다른가?
  3. commit timeout 후 성공/실패 불명확성을 어떻게 판정하는가?
  4. sequence number가 delete 적용과 incremental scan에 미치는 영향은?
Production review
  1. streaming small files의 원인을 compaction만으로 덮고 있지 않은가?
  2. snapshot expiration이 branch/tag·rollback·active reader를 깨지 않는가?
  3. orphan cleanup threshold가 최장 writer/commit retry보다 충분히 긴가?
  4. 모든 engine의 v2/v3 read/write/maintenance 지원을 자동 검증하는가?
