APACHE ICEBERG · WEEK 3 / DAY 15

field ID와 name mapping

Schema·Partition·Sort Evolution · 예상 학습 30분 + 실습 35분

한 줄 요약
Iceberg에서 column의 정체성은 바뀔 수 있는 이름·순서가 아니라 재사용하지 않는 field ID이며, name mapping은 ID가 없는 이관 file을 위한 명시적 fallback이다.

1. 선수 용어 사전

Identity이름이나 위치가 바뀌어도 같은 대상을 가리키는 안정적인 정체성이다. 주민등록번호와 표시 이름의 차이를 떠올리면 된다.
Field IDSchema의 struct field, list element, map key/value에 부여하는 정수 ID다. Table 안에서 재사용하지 않는다.
ProjectionQuery가 요구한 field ID를 data file의 같은 ID에 연결하고, 원하는 순서와 이름으로 결과 schema를 만드는 과정이다.
Name mappingschema.name-mapping.default에 저장하는 이름→field ID fallback이다. Field ID가 없는 이관 file을 읽을 때만 필요하다.
Writer / reader schemaFile을 쓸 때의 schema와 현재 query가 요청하는 schema다. Schema evolution 뒤 둘은 이름·순서·field 수가 다를 수 있다.
Nested fieldStruct 내부 field, list element, map key/value다. 각각 독립적인 ID를 가지며 dotted name만으로 식별하지 않는다.
Silent corruptionQuery가 실패하지 않고 다른 column의 값을 그럴듯하게 반환하는 오류다. 위치 기반 projection의 가장 위험한 결과다.
Initial defaultOld file에 새 field ID가 없을 때 적용할 수 있는 schema default다. 없으면 partition identity fallback 등을 제외하고 보통 null이다.

2. 왜 중요한가

이름 기반 시스템에서 amount를 gross_amount로 rename하면 old file에는 여전히 amount가 남는다. 다시 amount라는 새 column을 추가하면 문자열 이름만 보는 reader는 old 금액을 새 column으로 잘못 연결할 수 있다. Query는 성공하지만 의미가 바뀌는 silent corruption이다.

Iceberg는 old amount와 renamed gross_amount를 같은 field ID로 연결하고, 새 amount에는 새 ID를 부여한다. 이 identity는 data file projection뿐 아니라 manifest metrics, partition source ID, sort order, equality delete IDs까지 table 전체에 전파된다.

핵심 불변식: 같은 field ID는 같은 논리 field를 뜻하고, 한 번 삭제한 ID는 다른 의미에 재사용하지 않는다. 이름은 사람이 쓰는 label이고 ID가 protocol identity다.

3. 아키텍처 그림과 요청 흐름

① Catalog pointer → metadata JSON
current schema ID · schemas · last-column-id
↓ query name을 current field ID에 bind
② Snapshot → manifest list → manifest
spec source-id · field-ID metrics · equality_ids
↓ candidate data/delete file + projected IDs
③ File schema에 field ID가 있음
ID로 physical column을 선택 · 이름/순서 무관
또는 ↓ ID가 없는 imported file
④ schema.name-mapping.default
명시된 old names → Iceberg field ID fallback
↓ missing ID는 partition/default/null 규칙
⑤ Reader result schema
현재 이름·현재 순서로 값 materialization

Read 요청·응답·상태 변화

  1. SQL analyzer가 현재 schema에서 gross_amount라는 이름을 field ID 2처럼 안정적인 ID에 bind한다. 이후 계획은 이름 문자열이 아니라 ID를 운반한다.
  2. Catalog pointer가 가리키는 metadata JSON과 snapshot을 pin하고 manifest list/manifest를 읽는다. Partition source ID와 metrics key도 동일 ID 공간을 사용한다.
  3. Reader는 file schema에서 ID 2를 찾는다. Old file의 physical name이 amount여도 ID 2라면 현재 결과의 gross_amount로 읽는다.
  4. File에 field ID가 없을 때만 default name mapping에서 file path의 이름을 찾아 ID를 부여한다. Mapping에 없다고 current name을 임의 추측하지 않는다.
  5. Requested ID가 file에 없으면 identity partition 값, name mapping, initial default, null 순서의 spec 규칙으로 해결한다. 새 amount ID 4는 old file에서 null이다.
  6. MOR에서는 equality delete의 field IDs도 같은 identity로 해석한다. Rename이 delete semantics를 바꾸지 않아야 한다. V3 DV는 position 기반이지만 엔진 지원 경계를 확인한다.

Rename commit의 write path

  1. Writer가 base metadata와 current schema를 읽고 amount 이름을 가진 ID 2를 선택한다.
  2. 새 schema version에서 ID 2의 이름만 gross_amount로 바꾼다. Old data file, manifest, snapshot은 rewrite하지 않는다.
  3. 새 metadata JSON을 쓰고 base pointer가 그대로인지 optimistic validation한다. Concurrent schema update가 있으면 ID/name conflict를 병합하거나 실패한다.
  4. Catalog pointer의 atomic swap 성공이 rename의 linearization point다. 이후 새 reader는 current name을 사용하지만 old/new file 모두 ID 2로 읽는다.
  5. 다시 amount를 추가하면 last-column-id보다 큰 새 ID를 할당한다. 삭제된 ID나 rename 전 이름을 재사용하는 것이 아니다.

4. CS 관점의 내부 동작

관점상태 · 불변식 · 비용
Surrogate keyField ID는 mutable name 대신 쓰는 protocol key다. Name과 position을 자유롭게 진화시키는 indirection 비용을 작은 integer metadata로 지불한다.
Type safety동일 ID의 type change는 허용된 promotion 규칙을 따라야 한다. 이름이 같아도 새 ID면 별개 field이므로 old bytes를 읽지 않는다.
Nested identityStruct child, list element, map key/value도 ID를 가진다. a.b 문자열 하나로 nested path를 평탄화하면 literal dot 이름과 충돌할 수 있다.
Index coherenceManifest lower/upper/count map은 field ID로 keyed된다. Rename 뒤에도 pruning synopsis가 같은 logical field에 적용된다.
TransactionSchema는 metadata state 일부다. Pointer swap 전 reader는 old schema, 성공 후 reader는 new schema를 보고 중간 조합은 보지 않는다.
Fallback riskName mapping은 ID 없는 file의 migration debt다. Ambiguous alias, case sensitivity, nested mapping과 엔진 지원을 계속 검증해야 한다.

Column projection 예제

File schema가 1:a int, 2:b string, 3:c double이고 current projection이 3:measurement, 2:name, 4:a라면 결과는 file의 c, file의 b, 그리고 ID 4가 없으므로 null/default다. 이름 a가 old ID 1과 같아도 ID 4를 ID 1의 값으로 채우면 안 된다.

Name mapping은 alias registry가 아니다

Mapping object는 names, optional field-id, nested fields를 가진다. 여러 old name을 한 ID에 연결할 수 있지만, 정상 Iceberg writer가 ID를 기록한 file에는 ID가 우선한다. Migration을 끝낸 뒤에도 current name을 자동으로 추정하거나 모든 engine이 동일 fallback을 구현한다고 가정하면 안 된다.

5. 실무 설계 판단

판단Best practice와 이유
Evolution contractDDL 전 old/new name, field ID, type, required/default, downstream contract를 표로 남긴다. Metadata-safe와 business-semantic-safe를 구분한다.
Migration inventoryImported file format별 field-ID 존재 여부, casing, nested paths와 writer version을 샘플링한다. Name mapping은 증거로 생성하고 추측하지 않는다.
Name reuseDrop/rename 후 같은 이름을 새 의미로 쓸 때 새 ID와 null/default 동작을 canary에서 검증한다. Raw Parquet 소비자는 별도 migration이 필요하다.
Multi-engine gateSpark/Flink/Trino별 rename, nested evolution, case sensitivity, Parquet/Avro/ORC field ID와 name mapping 지원을 old/new file 혼합 table로 테스트한다.
Write serializationSchema change와 대규모 writer/maintenance를 겹치지 않게 운영하거나 conflict를 명시적으로 처리한다. 실패 commit의 metadata file은 current state가 아니다.
ObservabilitySchema ID/field-ID diff, writer/reader version, file schema ID presence, projection plan, null-rate와 metric pruning 변화를 deploy gate에 둔다.

Anti-pattern: 모든 file을 rewrite했으니 field ID가 필요 없다고 생각하거나, current column order와 Parquet physical order가 같다고 가정하는 reader를 운영하는 것이다.

Edge case: Name mapping의 a.b는 nested path가 아니라 점을 포함한 literal name일 수 있다. Struct/list/map child는 mapping의 fields 계층으로 표현해야 하며 case-insensitive fallback은 충돌을 만들 수 있다.

6. 장애 대응 표

상황: Rename/column 추가 후 일부 엔진에서 값이 서로 바뀌거나 null-rate가 급증했다.

증상엔진별 row/value 차이, rename 전 file만 null 또는 다른 값, position reorder 뒤 type mismatch, pruning candidate 급증, equality delete 누락.
먼저 수집할 증거/지표Catalog metadata location·snapshot/schema ID, metadata JSON schemas/last-column-id/name mapping, old/new file physical schema와 IDs, manifest field-ID metrics, spec/sort/equality IDs, query plan, engine/connector version·case mode, null/value distribution.
가능한 가설Name/position 기반 reader, ID 없는 imported file과 누락·오류 mapping, same-name new ID 오인, nested/case collision, stale metadata cache, unsupported type/evolution, equality delete ID 해석 차이, partial writer rollout.
안전한 첫 조치Write와 schema change를 멈추고 문제 snapshot을 pin한다. Old/new file 하나씩 schema·ID를 보존하고 known-good Iceberg reader 결과를 raw-file reader와 비교한다. Catalog cache를 증거 보존 후 refresh한다.
Rollback/복구Bad schema commit이면 retained snapshot/metadata로 catalog-supported rollback한다. ID 없는 file은 검증된 name mapping 또는 controlled rewrite로 보정하고, reader 회귀는 known-good version으로 되돌린다.
하지 말아야 할 조치Metadata JSON의 field ID를 수동 편집·재번호화하지 않는다. Null을 0/빈 문자열로 일괄 채우지 않는다. Raw Parquet name merge를 정답으로 삼지 않는다. 증거 없이 전체 file을 rewrite하지 않는다.

7. 35분 재현 실습

목표: 같은 field ID가 rename 뒤 old/new file을 연결하고, 같은 이름의 새 column은 새 ID로 분리되는 것을 metadata JSON과 query 결과로 증명한다. Raw Parquet name merge의 위험도 비교한다.

사전 조건과 실행 전 예측

  • Docker daemon과 프로젝트 Spark/Iceberg 환경이 준비되어 있고 make smoke가 성공해야 한다.
  • Old amount를 gross_amount로 rename한 뒤 새 amount STRING을 추가하면 old row의 두 결과가 무엇인지 적는다.
  • Iceberg table read와 raw Parquet mergeSchema read 중 어느 쪽이 logical identity를 보존하는지 이유를 적는다.

1단계 · Old file과 최초 field ID 만들기

make smoke

docker compose run --rm spark /opt/spark/bin/spark-sql -e "

DROP TABLE IF EXISTS local.day15.id_lab PURGE;

TBLPROPERTIES ('write.metadata.metrics.column.amount'='full');

"

예상 관찰: 첫 schema에서 id, amount, note는 서로 다른 ID를 갖고 첫 data file에 그 ID가 기록된다.

2단계 · Rename 후 같은 old name을 새 ID로 추가

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
ALTER TABLE local.day15.id_lab RENAME COLUMN amount TO gross_amount;
ALTER TABLE local.day15.id_lab ADD COLUMN amount STRING;

INSERT INTO local.day15.id_lab (id, gross_amount, note, amount)
VALUES (3, CAST(30.25 AS DECIMAL(10,2)), 'new', 'promo');

DESCRIBE TABLE local.day15.id_lab;
SELECT id, gross_amount, amount, note
FROM local.day15.id_lab ORDER BY id;
"

예상 관찰: Old row 1·2의 gross_amount는 10.50/20.00으로 유지되고 새 amount는 null이다. Row 3은 30.25와 promo를 함께 가진다. 이름이 같아졌다는 이유로 old bytes가 새 field에 들어가지 않는다.

SELECT file_path, readable_metrics

"

예상 관찰: Schema history에서 old amount와 gross_amount의 ID는 같고, 새 amount는 더 큰 새 ID다. Metrics도 이름이 아니라 해당 field ID에 연결된다.

실패 주입 · Iceberg를 우회해 raw Parquet 이름 merge

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
CREATE OR REPLACE TEMP VIEW raw_name_view
USING parquet
OPTIONS (
  path 'warehouse/day15/id_lab/data',
  mergeSchema 'true'
);

DESCRIBE raw_name_view;
SELECT * FROM raw_name_view ORDER BY id;
SELECT id, gross_amount, amount
FROM local.day15.id_lab ORDER BY id;
"

예상 관찰: Raw view는 file physical names를 merge하므로 old amount, new gross_amount, 새 amount의 의미를 정확히 복원하지 못하거나 schema conflict를 낼 수 있다. 실패 형태는 Spark/Parquet schema merge 동작에 따라 다르지만 Iceberg 결과가 기준이다.

자주 나는 오류와 해결

  • Warehouse path가 다름: files.file_path와 catalog config로 실제 location을 확인한다. 추측한 path를 수정하지 않는다.
  • Metadata filename sort가 맞지 않음: metadata_log_entries의 latest row에서 exact file path를 얻어 jq에 넘긴다.
  • Raw view path가 container에서 안 보임: Docker Compose volume의 container-side warehouse path로 바꾸되 Iceberg table은 건드리지 않는다.
  • Raw Parquet schema conflict: 이것 자체가 name 기반 merge의 실패 증거다. Type coercion으로 억지 성공시키지 않는다.
  • Rename/Add 문법 차이: 사용 중인 engine의 Iceberg DDL 지원을 확인하고 같은 logical transition을 별도 명령으로 수행한다.
  • Stale DESCRIBE: Catalog/engine cache를 refresh한 뒤 metadata location과 snapshot을 다시 고정한다.

8. 놓치기 쉬운 함정

  1. Field ID는 schema version마다 다시 1부터다. Table 전체에서 identity를 유지하고 재사용하지 않는다.
  2. Rename은 old file column name도 바꾼다. Metadata만 바뀌며 reader가 ID로 old bytes를 연결한다.
  3. 같은 이름이면 같은 field다. Drop/rename 후 새로 추가한 같은 이름은 새 ID일 수 있다.
  4. Name mapping은 모든 file에 적용한다. File ID가 있으면 그것이 우선이며 mapping은 ID 없는 file의 fallback이다.
  5. Column order로 projection해도 type이 같으면 안전하다. 값이 조용히 바뀌는 silent corruption이 더 위험하다.
  6. Nested field는 dotted string 하나면 된다. List/map/struct child mapping과 literal dot 이름을 구분해야 한다.
  7. Rename은 항상 downstream-safe다. Raw Parquet consumer, BI semantic layer, CDC schema registry와 SQL text는 별도 계약이다.
  8. 모든 엔진의 mapping 지원이 같다. Format/file type/connector 버전별 old/new 혼합 canary가 필요하다.

9. 대기업 기술 면접 수준 질문

Q1. Field ID가 왜 필요한지 rename과 drop/add 시나리오로 증명하라.

좋은 답변 구조: 이름·순서의 가변성 → ID 불변식/재사용 금지 → writer/current projection 예제 → old file과 새 same-name field 분리 → metrics/spec/delete에 전파 → name/position 방식의 silent corruption과 migration 대안을 설명한다.

Q2. 5PB Hive Parquet를 rewrite 없이 Iceberg로 이관할 때 name mapping을 어떻게 설계하겠는가?

좋은 답변 구조: File format·기간·writer별 ID/case/nested inventory → canonical field IDs와 aliases → ambiguity 검출/차단 → sampled old/new canary와 engine matrix → null/value checksum → rollback, gradual rewrite와 mapping debt 제거 기준을 수치로 제시한다.

Q3. Schema rename과 streaming writer commit이 동시에 발생할 때 correctness를 설명하라.

좋은 답변 구조: Base metadata/schema ID → writer가 file에 기록한 IDs → optimistic pointer swap·conflict validation → retry 때 current schema 재bind → old/new snapshot reader isolation → 실패 object/orphan과 idempotency → compatibility rollout 방안을 방어한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Iceberg가 O(n) listing을 피한다고 해서 planning이 O(1)은 아닌 이유는?
  2. Manifest list와 manifest는 각각 어떤 후보를 줄이는가?
  3. Rewrite manifests와 rewrite data files의 책임 차이는?
짧은 정답/채점 기준
  1. Root 뒤 M, matching entries, candidate K 비용이 남고 metadata 품질에 따라 커진다고 답하면 정답.
  2. Manifest list summary는 manifest를, manifest partition/field metric은 data/delete file을 줄인다고 답하면 정답.
  3. 전자는 metadata fan-out/locality, 후자는 data file size·clustering/delete merge를 바꾼다고 구분하면 정답.

오늘 내용 확인 3문제

  1. Rename 뒤 old file의 값을 새 이름으로 안전하게 읽을 수 있는 이유는?
  2. Name mapping은 언제 사용하며 언제 사용하지 않는가?
  3. Old 이름과 같은 새 column을 추가했을 때 old row의 값은 어떻게 되는가?
짧은 정답/채점 기준
  1. Old/current schema의 이름은 달라도 같은 field ID로 file column을 projection한다고 답하면 정답.
  2. ID 없는 imported file에서 명시적 이름→ID fallback으로 쓰며, ID가 있는 file에는 file ID가 우선이라고 답하면 정답.
  3. 새 column은 새 ID라 old file에 없으므로 initial default가 없으면 null이며 old bytes를 재사용하지 않는다고 답하면 정답.
