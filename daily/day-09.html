APACHE ICEBERG · WEEK 2 / DAY 09

snapshot, history, refs

Metadata Tree와 Scan Planning · 예상 학습 30분 + 실습 35분

한 줄 요약
Snapshot은 immutable table state node, history는 어떤 snapshot이 main의 current였는지 기록한 전이 log, ref는 snapshot을 이름으로 붙잡는 branch/tag pointer다. 셋을 구분해야 time travel, WAP, rollback과 retention을 안전하게 설계할 수 있다.

1. 선수 용어 사전

Snapshot한 commit이 만든 immutable table state node다. ID, parent, sequence, timestamp, manifest-list와 summary를 가진다.
History어느 timestamp에 어느 snapshot이 main current가 되었는지 나타내는 snapshot-log의 SQL 관찰 창이다. Snapshot 전체 목록과 같지 않다.
Reference(ref)Snapshot ID를 이름으로 가리키는 metadata pointer다. Branch와 tag가 있다.
Branch새 commit에 따라 head가 전진할 수 있는 mutable named ref다. Main과 audit/backfill branch를 분리할 수 있다.
Tag감사·릴리스 기준 snapshot을 이름으로 고정해 읽고 보존하는 ref다. 운영상 immutable label로 다룬다.
AncestorParent pointer를 따라 현재 snapshot 이전에 있는 조상 snapshot이다. Rollback/cherry-pick 후 retained snapshot이 모두 current ancestor인 것은 아니다.
RetentionSnapshot/ref와 참조 file을 얼마 동안 보존할지 정하는 수명 정책이다. Time travel 가능 범위와 storage 비용을 함께 결정한다.

2. 왜 중요한가

Snapshot을 “백업 파일”, history를 “모든 snapshot”, branch를 “data 복사본”으로 이해하면 retention과 복구 설계가 위험해진다. Snapshot은 manifest graph의 root이고, history는 main current 전이 기록이며, ref는 특정 root를 붙잡는 이름이다. 동일한 data/manifest byte를 여러 snapshot과 ref가 공유할 수 있다.

이 모델은 reader isolation, timestamp/snapshot time travel, 감사 tag, WAP(audit branch), backfill과 rollback의 기반이다. 동시에 ref가 붙잡은 snapshot은 expiration에서 보호되어 비용이 늘 수 있고, ref를 잘못 제거하거나 engine별 branch 지원을 오해하면 maintenance race와 multi-engine 불일치가 생긴다.

핵심 불변식: 모든 live ref는 존재하는 snapshot을 가리켜야 하고, ref와 retention 정책이 보호하는 snapshot에서 도달 가능한 manifest·data/delete file은 안전하게 읽을 수 있어야 한다.

3. 아키텍처 그림과 요청 흐름

① Catalog → current metadata JSON
Table root 선택
↓ current-snapshot-id / refs[name]
② Named roots
main → S3 · audit branch → S2 · baseline tag → S1
↓ snapshot-id lookup
③ Snapshot graph
S1 ←parent— S2 ←parent— S3 · 각 node는 manifest-list 보유
↓ history는 main current 전이를 투영
④ Snapshot log / history
t1:S1 → t2:S2 → t3:S3 · is_current_ancestor
↓ manifest list → manifest
⑤ Data/Delete files
선택 root에 일관된 read path

Read 요청·응답·상태 변화

  1. Reader가 table만 조회하면 main/current snapshot을, VERSION AS OF 'baseline'이면 refs의 tag/branch snapshot ID를 선택한다.
  2. 선택 snapshot의 schema ID와 manifest-list를 읽고 manifest partition/file metrics로 pruning한다.
  3. 남은 data/delete file을 sequence rule에 따라 적용한다. COW/MOR와 v3 deletion vector 지원은 engine/connector별로 확인한다.
  4. Time travel/ref read는 current main pointer를 바꾸지 않는다. 같은 순간 main, audit, baseline reader가 서로 다른 일관된 view를 읽을 수 있다.

Write·publish 요청과 상태 변화

  1. Writer는 대상 branch head와 base metadata를 load한다. Main write와 audit branch write는 서로 다른 expected snapshot을 가질 수 있다.
  2. 새 data/delete file, manifest, manifest list, snapshot과 metadata JSON을 만든 뒤 operation별 conflict validation을 수행한다.
  3. Catalog pointer swap이 성공하면 metadata root가 바뀐다. 대상 branch ref가 새 snapshot으로 전진하고 main이 아니라면 main row는 바뀌지 않는다.
  4. 검증 후 fast-forward는 target branch가 source branch의 ancestor 조건을 만족할 때 ref를 전진시키는 metadata commit이다. File 복사가 아니다.
  5. Commit response 유실 시 새 refs/snapshot과 batch identity를 확인한 뒤 retry한다. Blind retry는 branch에 중복 commit을 만들 수 있다.

4. CS 관점의 내부 동작

개념Snapshot/history/ref에서의 의미
MVCCReader는 선택 snapshot을 고정하고 writer는 새 immutable version을 만든다. Reader와 writer가 in-place data lock을 공유하지 않아 isolation이 단순해진다.
Persistent DAGParent와 shared manifest/file로 version graph를 만든다. Branch는 root가 여러 개인 DAG를 만들지만 full data copy가 필요 없다.
Named pointerRef는 snapshot ID에 붙인 이름과 retention policy다. Main/branch는 전진할 수 있고 tag는 감사 기준으로 고정 운용한다.
Event log vs state setHistory는 main current 전이 event, snapshots는 retained node 집합이다. Rollback/branch 때문에 집합과 log의 모양이 다르다.
Reachability GCExpire snapshots는 main과 live refs, retention에서 도달 가능한 state를 보존해야 한다. Orphan cleanup은 별도 safety window가 필요하다.
LinearizationRef create/drop/fast-forward도 새 metadata JSON과 catalog swap으로 확정되는 metadata transaction이다.

Snapshots와 history가 다른 세 가지 경우

  • Rollback: 과거 snapshot이 다시 current가 되면 history에는 새로운 전이 event가 생기지만 snapshot node 자체를 복제하지 않는다.
  • Branch write: Named branch의 새 snapshot은 snapshots 집합에 있지만 main history의 current 전이에는 포함되지 않을 수 있다.
  • Expiration: Retention 정책으로 snapshot이 제거되면 time travel 가능 범위와 metadata/file reachability가 줄어든다. History는 영구 감사 원장이 아니다.

Schema, partition, sequence 연결

Table schema는 branches 전체에 대해 진화하지만 branch read와 snapshot-ID time travel의 schema 선택 동작은 engine 문서를 확인해야 한다. Field ID와 partition spec ID는 각 snapshot이 참조하는 old/new file을 안전하게 해석한다. Sequence number는 delete file/DV가 어느 data file에 적용되는지와 incremental ordering을 정한다.

5. 실무 설계 판단

판단Best practice와 이유
Ref 목적Audit tag, WAP branch, backfill branch를 이름·owner·TTL·publish 조건으로 구분한다. 영구 ref 남발은 snapshot/file GC를 막는다.
Retention 수치Rollback window, 최장 reader/job, 법적 audit, storage budget을 수치화해 max ref age·min snapshots·max snapshot age를 정한다.
Publish gateBranch row count·quality·schema/spec/manifest/file metrics와 source checkpoint를 검증하고 fast-forward 가능성을 확인한다.
MaintenanceExpire 전 refs·active reader/writer·branch TTL을 inventory하고 dry-run/영향 범위를 확인한다. Expire와 orphan cleanup을 같은 작업으로 취급하지 않는다.
Multi-engineSpark/Flink/Trino별 branch/tag DDL·read/write·schema selection·procedure와 format version 지원을 compatibility gate로 고정한다.

Anti-pattern: Branch를 cheap backup으로 무기한 남기고 snapshot expiration을 돌리지 않는 것. Data 복사는 없지만 ref가 오래된 snapshot과 file reachability를 붙잡아 storage/metadata가 계속 증가한다.

Edge case: Branch head read는 현재 table schema로 투영되고 snapshot-ID/tag read는 snapshot schema를 선택하는 등 schema semantics가 통합/엔진별로 다를 수 있다. Query 결과 column 계약을 compatibility test로 확인한다.

6. 장애 대응 표

상황: Snapshot expiration 뒤 감사용 과거 데이터 또는 branch 결과가 사라졌다고 보고됐다.

증상Ref/time travel 조회 실패, refs row 누락, snapshots/history 감소, manifest/data object 404, engine별 ref 결과 차이.
먼저 수집할 증거/지표Current metadata location/JSON, refs·snapshots·history·metadata-log, ref retention fields, expire procedure args/result, object delete/audit log, active reader/writer, branch publish/fast-forward log, engine/connector cache/version.
가능한 가설Ref 미생성/조기 drop/TTL 만료, 잘못된 catalog, stale cache, aggressive expiration, engine가 ref 미지원, concurrent maintenance, orphan cleanup의 짧은 age threshold, referenced object 손실.
안전한 첫 조치모든 maintenance/write를 중지하고 current/previous metadata JSON과 object audit를 보존한다. 새 session에서 exact catalog와 refs/snapshots를 read-only 확인하고 물리 삭제 여부를 분리한다.
Rollback/복구Snapshot과 file이 retained면 정상 API로 ref를 재생성하거나 known-good snapshot에 rollback한다. Object가 삭제됐으면 독립 backup에서 복원해 새 table/branch에서 검증 후 publish한다. Retention/alert를 보강한다.
하지 말아야 할 조치Metadata JSON/refs map을 수동 편집하지 않는다. Missing object를 빈 file로 만들지 않는다. 원인 확인 전 expire/orphan cleanup을 반복하지 않는다. Time travel을 독립 backup으로 간주하지 않는다.

자주 나는 오류와 해결

  • CREATE TAG/BRANCH 문법 오류: Runtime의 Spark/Iceberg DDL 문서를 확인한다. Connector 버전에 따라 retention clause 지원이 다를 수 있다.
  • Branch metadata table 이름 충돌: VERSION AS OF 'audit' 또는 branch_audit syntax 중 runtime 지원 방식을 사용한다.
  • Refs table column 차이: DESCRIBE local.day09.ref_lab.refs로 name/type/snapshot_id/retention column을 확인한다.
  • History와 snapshots row가 예상과 다름: Ref 생성은 snapshot이 아니며, 이전 실습 table을 PURGE했는지 확인한다.
  • File 수가 늘어남: Ref 생성 전후 exact file diff를 보아 metadata JSON만 늘었는지 확인한다. INSERT가 섞였으면 data file도 늘어난다.
  • Docker 연결 실패: Docker daemon을 시작하고 make smoke가 성공한 뒤 실습을 재개한다.

8. 놓치기 쉬운 함정

  1. Snapshot은 full table copy다. Metadata root이며 기존 manifest/data file을 공유한다.
  2. Snapshots와 history는 같은 목록이다. Node set과 main current 전이 log라서 rollback/branch/expiration에서 다르다.
  3. Branch는 warehouse directory 복사다. Snapshot ID를 가리키는 named metadata pointer다.
  4. Tag가 있으면 영원히 보존된다. Ref 자체와 snapshot retention 정책/TTL을 명시적으로 관리해야 한다.
  5. Ref read가 main을 바꾼다. Read selector일 뿐 current main commit은 아니다.
  6. Fast-forward는 file copy다. Ancestor 조건을 확인해 target ref를 source head로 전진시키는 metadata commit이다.
  7. Time travel은 backup이다. 같은 storage/catalog와 expiration에 의존해 독립 DR을 대체하지 않는다.
  8. 모든 engine이 ref를 동일하게 지원한다. DDL/read/write/schema/procedure 지원을 connector별로 확인한다.

9. 대기업 기술 면접 수준 질문

Q1. “Snapshots, history, refs의 차이를 rollback 예제로 설명하세요.”

좋은 답변 구조: 세 commit S1→S2→S3 수치 → snapshot node/parent/manifest → history main 전이 → tag/branch named root → rollback 시 S1 재current event → old nodes/file sharing → retention/expiration failure → backup 대안.

Q2. “Audit branch 기반 WAP를 설계하세요.”

좋은 답변 구조: Writer rate·SLO·validation 요구 → branch create/base snapshot → isolated write의 optimistic commit → row/schema/spec/metrics validation → fast-forward ancestor/conflict → response 유실/idempotency → TTL/cleanup → multi-engine 지원과 별도 staging table 대안.

Q3. “Snapshot retention을 비용과 복구 관점에서 설계하세요.”

좋은 답변 구조: RPO/RTO·audit 기간·최장 reader 수치 → refs inventory → min snapshots/max age/max ref age → manifest/data/delete/DV reachability → expiration과 orphan cleanup 순서 → concurrent writer/maintenance race → alert/dry-run/backup과 비용 모델.
