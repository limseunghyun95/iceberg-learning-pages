APACHE ICEBERG · WEEK 1 / DAY 01

raw Parquet/Hive partition의 한계

Lakehouse와 Table Format 정신 모델 · 예상 학습 25분 + 실습 30분

한 줄 요약
Parquet는 개별 파일을 효율적으로 저장하지만, 여러 파일의 현재 상태·원자적 변경·안전한 진화를 정의하지 않는다. Hive식 디렉터리 partition은 그 빈틈을 일부 메우지만 정확성과 확장성 책임을 writer와 사용자에게 떠넘긴다.

1. 선수 용어 사전

Data lake저렴하고 확장 가능한 파일 저장소에 분석 데이터를 보관하는 구조. S3 같은 object storage나 HDFS가 흔한 기반이다.
Parquet열 단위 저장 형식. 한 파일 안에서 필요한 column과 row group만 읽기 쉽게 만든다. 여러 파일 전체의 transaction은 정의하지 않는다.
Partition비슷한 값을 가진 row를 같은 파일·디렉터리에 모아 scan 범위를 줄이는 배치 규칙. 예: event_date=2026-07-29.
Table format여러 data file을 하나의 논리 table로 보이게 하는 metadata 구조와 commit 규칙. Iceberg가 여기에 해당한다.
Atomic변경이 전부 보이거나 전혀 보이지 않아야 한다는 성질. 중간 상태가 독자에게 노출되지 않는 것이 핵심이다.
Catalogtable 이름을 현재 metadata 위치에 연결하고 commit 시 current pointer 교체를 조정하는 control plane의 시작점이다.

2. 왜 중요한가

운영 table은 단순한 파일 묶음이 아니다. 다음 질문에 언제나 하나의 답이 있어야 한다.

  • 현재 table에 포함된 파일은 무엇인가?
  • 동시 writer 두 개 중 어떤 변경이 먼저 commit됐는가?
  • 실패한 job이 만든 일부 파일이 사용자에게 보이는가?
  • column rename과 partition 변경 뒤에도 old/new data를 정확히 읽는가?
  • 과거 시점의 동일한 결과를 다시 만들 수 있는가?

raw Parquet 디렉터리는 이 질문의 답을 protocol로 정의하지 않는다. 보통 application, scheduler, Hive Metastore, 디렉터리 이름 규칙을 조합해 답을 추측한다. 작은 pipeline에서는 작동할 수 있지만 writer·engine·파일 수가 늘면 암묵적 규칙이 correctness와 운영 비용의 병목이 된다.

핵심 구분: “파일을 읽을 수 있다”와 “일관된 table state를 읽는다”는 다른 보장이다.

3. 아키텍처 그림과 요청 흐름

아래는 reader가 현재 state를 찾는 경로다. 각 화살표는 단순 폴더 이동이 아니라 이전 계층이 다음 계층의 유효한 대상을 지목하는 indirection, 즉 간접 참조다.

① Catalog current pointer
table name → current metadata location
↓
② Metadata JSON
schema · partition specs · properties · snapshots
↓
③ Current snapshot
특정 시점의 committed table state
↓
④ Manifest list → ⑤ Manifest
manifest 통계 → file path · partition · column metrics
↓
⑥ Data file / Delete file
Parquet·ORC·Avro row data와 row 삭제 정보

Reader 요청·응답·상태 변화

  1. Query engine이 catalog에 table을 요청한다. 응답은 현재 metadata의 위치다.
  2. Engine은 metadata JSON에서 current snapshot을 고정한다. 이후 다른 writer가 commit해도 이 reader의 계획 기준은 바뀌지 않는다.
  3. Manifest list 통계로 불필요한 manifest를 제거하고, manifest의 partition·column metrics로 불필요한 data file을 제거한다.
  4. 선택한 data/delete file만 읽어 row 결과를 만든다. directory 전체 listing이 table membership의 진실이 아니다.

Writer 요청·응답·상태 변화

1Base metadata와 snapshot을 읽어 계획 기준을 기록한다.
2고유 경로에 immutable data file과 metadata file을 먼저 쓴다. 이때 새 파일은 아직 table에 보이지 않는다.
3Operation에 맞는 conflict validation을 한다. Append와 overwrite/delete의 안전 조건은 같지 않다.
4Catalog가 base pointer가 여전히 current인지 비교하며 새 metadata pointer로 원자 교체한다.
5교체 성공 순간이 commit의 성공 확정점, 즉 linearization point다. 실패 전에 만든 파일은 orphan 후보가 될 수 있다.

4. CS 관점의 내부 동작

상태의 소유자와 불변식

  • Parquet file: 한 파일의 encoding·compression·column statistics를 소유한다. table membership은 소유하지 않는다.
  • Hive partition directory/metastore: partition 위치를 나열하지만 partition 값과 source column의 의미 관계를 안전하게 강제하지 못할 수 있다.
  • Iceberg metadata tree: committed snapshot에 포함되는 file 집합과 schema/spec를 소유한다.
  • Catalog: 어느 metadata가 current인지와 pointer 전이의 원자성을 소유한다.

중요한 불변식은 “reader가 보게 되는 모든 file은 하나의 committed snapshot에서 도달 가능해야 한다”이다. Storage에 파일이 존재한다는 사실만으로 membership이 생기지 않는다.

왜 raw Parquet + directory listing이 약한가

  • 일관된 cut이 없다: writer가 100개 파일 중 60개를 쓴 순간 reader가 listing하면 partial batch를 볼 수 있다.
  • 동시성 protocol이 없다: 서로 다른 writer의 파일 추가·삭제·교체가 어떤 순서로 하나의 state가 되는지 정의되지 않는다.
  • 비용이 O(n)에 가까워진다: table state를 알기 위해 partition·file을 폭넓게 나열하면 규모가 커질수록 planning remote call과 metadata 부하가 증가한다.
  • 삭제와 overwrite가 위험하다: physical delete나 rename 도중 reader가 중간 상태를 볼 수 있고, rollback 기준도 없다.
  • 진화 정보가 분산된다: schema와 partition 의미가 file·directory·metastore·job code에 흩어져 old/new layout의 공존이 어렵다.

Hive partition의 정확성 함정

Hive식 partition은 흔히 event_date=2026-07-29/ 같은 directory와 별도 partition column을 사용한다. Writer가 event timestamp와 다른 timezone으로 partition 값을 만들거나 잘못된 날짜 문자열을 넣어도 파일은 정상 Parquet일 수 있다. Query가 logical column인 event_time만 filter하고 physical partition column을 빠뜨리면 전체 scan이 되거나, 잘못된 partition 값을 믿으면 조용히 틀린 결과가 생길 수 있다.

Iceberg hidden partitioning은 source column과 transform 관계를 table metadata로 관리한다. 그러나 이것이 모든 문제를 자동 해결한다는 뜻은 아니다. 잘못된 source data, engine별 지원 차이, 지나친 partition cardinality와 small file은 여전히 설계 대상이다.

5. 실무 설계 판단

판단권장 기준과 이유
Raw zone 유지원본 보존·단순 ingest 목적이면 가능하다. 다만 downstream이 이를 transactional table로 오해하지 않도록 immutability, batch completion marker, ownership을 명시한다.
Iceberg 도입동시 writer, schema/partition evolution, time travel, multi-engine read, row-level change, 대규모 planning 중 둘 이상이 중요하면 table format의 protocol 가치가 커진다.
Partition 전략Query predicate, 일별 data volume, target file size, skew를 근거로 선택한다. “날짜니까 무조건 day partition”은 피한다.
Migration기존 file을 metadata에 등록하는 순간부터 새 writer 경로, cleanup 소유권, rollback 경계를 함께 전환한다. Source와 Iceberg가 같은 file을 공유하면 한쪽 vacuum이 다른 쪽을 깨뜨릴 수 있다.
호환성 gateSpark·Flink·Trino가 동일 format version과 필요한 read/write/delete 기능을 지원하는지 자동 검증한다. Spec의 존재와 engine 구현 지원은 같지 않다.

Anti-pattern: small file이 늘어날 때 compaction만 추가하고 원인인 commit frequency·writer distribution을 고치지 않는 것. Compaction은 또 다른 write transaction이며 shuffle·storage·commit conflict 비용을 만든다.

Edge case: Catalog commit 응답이 timeout되면 실패로 단정할 수 없다. Pointer 교체는 성공했지만 응답만 유실됐을 수 있다. 같은 batch를 즉시 재실행하면 duplicate append가 생길 수 있으므로 current snapshot과 operation identity를 먼저 확인한다.

6. 장애 대응 표

상황: “어제 적재한 일부 row가 보이지 않거나 중복으로 보인다.”

증상Count 급변, 특정 시간대 누락, 같은 business key 중복, reader engine별 결과 불일치.
먼저 수집할 증거/지표Job run ID·입력 offset, catalog의 current metadata 위치, current snapshot ID와 timestamp, snapshot summary, manifest/file count, storage write 목록, commit retry·timeout log, engine·connector version.
가능한 가설Raw directory partial publish, 잘못된 Hive partition value, ambiguous commit 뒤 batch 재실행, stale catalog cache, concurrent overwrite/delete, 잘못된 table/catalog를 조회.
안전한 첫 조치Writer 재실행과 파일 삭제를 멈추고 현재 pointer→snapshot→manifest→file 경로를 고정해 증거를 보존한다. Known-good snapshot으로 read-only 비교 query를 실행한다.
Rollback/복구영향 범위가 확인되면 검증된 snapshot으로 rollback하거나, idempotent key와 정확한 predicate를 사용해 보정 commit을 만든다. Raw table이면 completion marker와 manifest를 재구성한 뒤 reader를 전환한다.
하지 말아야 할 조치Warehouse에서 “이상해 보이는” 파일을 수동 삭제하지 않는다. Commit timeout을 곧바로 실패로 간주해 동일 append를 blind retry하지 않는다. 증거 수집 전에 snapshot expire/orphan cleanup을 실행하지 않는다.

7. 30분 재현 실습

목표: Storage에 Parquet file을 임의로 추가해도 Iceberg table에는 보이지 않는다는 사실로 “directory 존재 ≠ table membership”을 증명한다.

사전 조건

  • 프로젝트 디렉터리에서 Docker가 실행 중이다.
  • conf/spark-defaults.conf의 local Hadoop catalog와 /workspace/warehouse 설정을 사용한다.
  • 먼저 결과를 예측한다: rogue Parquet copy를 넣은 뒤 COUNT(*)는 2일까, 4일까?

최소 명령

docker compose up -d

docker compose exec spark spark-sql -e "
CREATE NAMESPACE IF NOT EXISTS local.day01;
DROP TABLE IF EXISTS local.day01.raw_limit_lab;
CREATE TABLE local.day01.raw_limit_lab (
  id BIGINT,
  event_time TIMESTAMP,
  message STRING
) USING iceberg;
INSERT INTO local.day01.raw_limit_lab VALUES
  (1, TIMESTAMP '2026-07-29 09:00:00', 'alpha'),
  (2, TIMESTAMP '2026-07-29 09:01:00', 'beta');
SELECT COUNT(*) AS committed_rows FROM local.day01.raw_limit_lab;
SELECT * FROM local.day01.raw_limit_lab.files;
"

find warehouse -type f | sort

예상 관찰: Query count는 2다. Warehouse에는 Parquet data file뿐 아니라 metadata JSON, Avro manifest list와 manifest가 보인다. files metadata table의 file path가 committed data file을 가리킨다.

실패 주입

ORIGINAL_FILE=$(find warehouse -type f -name '*.parquet' | head -n 1)
ORIGINAL_DIR=$(dirname "$ORIGINAL_FILE")
cp "$ORIGINAL_FILE" "$ORIGINAL_DIR/rogue-copy.parquet"

find warehouse -type f -name '*.parquet' | sort

docker compose exec spark spark-sql -e "
SELECT COUNT(*) AS still_committed_rows
FROM local.day01.raw_limit_lab;
SELECT file_path FROM local.day01.raw_limit_lab.files;
"

예상 관찰: Physical Parquet file은 하나 늘지만 count는 여전히 2이고 metadata table에도 rogue copy가 나타나지 않는다. Iceberg reader는 directory listing으로 membership을 추측하지 않고 current snapshot의 manifest tree만 따른다.

자주 나는 오류와 해결

  • No such table: catalog prefix가 local인지 확인하고 SHOW CURRENT NAMESPACE를 실행한다.
  • ORIGINAL_FILE이 비어 있음: INSERT가 성공했는지 확인하고 find warehouse -type f로 실제 위치를 본다.
  • Docker package download 실패: 네트워크와 Maven cache를 확인한다. 같은 실행에서 warehouse 파일을 임의 변경하며 우회하지 않는다.
  • Count가 4로 보임: raw Parquet 경로를 직접 읽은 것인지, Iceberg table identifier를 조회한 것인지 구분한다.

Cleanup

find warehouse -type f -name 'rogue-copy.parquet' -delete

docker compose exec spark spark-sql -e "
DROP TABLE IF EXISTS local.day01.raw_limit_lab;
DROP NAMESPACE IF EXISTS local.day01;
"

Cleanup 명령은 이 실습에서 만든 이름만 대상으로 한다. 다른 table의 warehouse 경로를 넓게 삭제하지 않는다.

8. 놓치기 쉬운 함정

  1. “Parquet에 schema가 있으니 table schema도 해결됐다.” 파일별 schema는 있어도 table 전체의 current schema와 safe evolution 규칙은 별개다.
  2. “Metastore partition이 있으니 transaction도 있다.” Partition 등록과 여러 data file 변경의 원자적 publish는 다른 문제다.
  3. “Iceberg면 small file이 없다.” Iceberg는 file을 정확히 추적하지만 나쁜 writer 패턴을 자동 제거하지 않는다.
  4. “Time travel은 backup이다.” Snapshot은 같은 storage와 metadata에 의존한다. 계정·bucket 손상과 광역 장애를 대비한 DR을 대체하지 않는다.
  5. “공식 spec에 있으니 모든 engine이 지원한다.” Format v1/v2/v3 기능별 reader·writer·catalog 지원 matrix가 필요하다.

9. 대기업 기술 면접 수준 질문

Q1. “Parquet만으로 왜 충분하지 않습니까?”

좋은 답변 구조: 요구사항(동시 writer·과거 재현·진화) → Parquet의 책임 범위 → 현재 file 집합을 정하는 protocol 부재 → partial visibility와 listing 비용의 수치 가정(예: 100만 file, commit당 1천 file) → Iceberg metadata tree와 pointer swap → 추가 metadata·maintenance 비용이라는 trade-off → raw zone에서는 단순 Parquet가 합리적인 대안일 수 있음을 인정한다.

Q2. “Hive partition table을 Iceberg로 바꾸면 어떤 correctness 문제가 줄고, 무엇은 남습니까?”

좋은 답변 구조: Hive의 explicit partition column과 writer/user 책임 → timezone·format mismatch와 query filter 누락 → hidden transform과 partition evolution → old/new spec planning → 남는 문제인 source data 품질, small file, engine 호환성, migration 중 이중 writer → 검증 지표와 rollback 계획.

Q3. “Commit timeout이 났습니다. 재시도하면 됩니까?”

좋은 답변 구조: Timeout은 결과 불명확 상태라고 정의 → 성공 확정점은 catalog pointer swap → current metadata/snapshot과 operation identity 수집 → append·overwrite별 conflict 차이 → idempotency key 또는 checkpoint 기반 판정 → 중복/누락 위험 → 안전한 재시도·보정·rollback 절차를 제시한다.

10. 선수 지식 확인 3문제

  1. Columnar format은 row-oriented format보다 어떤 query에서 유리한가?
  2. Partition pruning의 목적은 CPU 계산을 줄이는 것인가, 읽을 file 범위를 줄이는 것인가?
  3. Atomic update에서 reader가 보면 안 되는 상태는 무엇인가?

짧은 정답/채점 기준

  1. 일부 column만 읽는 분석 query에서 I/O와 decoding을 줄인다고 답하면 통과.
  2. 우선 목적은 scan 대상 file/partition을 줄여 I/O와 planning·task 비용을 낮추는 것이라고 답하면 통과.
  3. 변경의 일부만 반영된 중간 상태라고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. Storage에 존재하지만 current manifest에서 참조하지 않는 Parquet file은 왜 table row로 보이지 않는가?
  2. Hive partition에서 logical time filter만으로 partition pruning이 실패할 수 있는 이유는 무엇인가?
  3. Iceberg commit의 성공이 확정되는 시점은 언제인가?

짧은 정답/채점 기준

  1. Table membership의 소유자는 directory가 아니라 committed snapshot의 manifest tree라고 설명하면 통과.
  2. Hive가 source column과 partition column의 변환 관계를 자동으로 알지 못해 별도 partition predicate가 필요할 수 있다고 설명하면 통과.
  3. Base pointer 검증과 함께 catalog의 current metadata pointer가 새 metadata로 원자 교체된 순간이라고 답하면 통과.
