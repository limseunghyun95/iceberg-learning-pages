Lakehouse와 Table Format 정신 모델 · 예상 학습 30분 + 실습 30분

한 줄 요약
Iceberg 운영의 첫 번째 기술은 구성요소 이름을 외우는 것이 아니라, “누가 어떤 상태를 소유하고 어느 계층에서 성공이 확정되는가”를 file format·table format·catalog·query engine·warehouse로 분리하는 것이다.

1. 선수 용어 사전

File format한 파일의 바이트 배치, 타입 인코딩, 압축과 통계를 정의한다. Parquet·ORC·Avro가 대표적이다.
Table format여러 파일을 하나의 일관된 table state로 관리하는 metadata 구조와 transaction 규칙이다. Iceberg는 open table format이다.
Catalogtable 이름을 현재 metadata 위치에 연결하고 create·load·rename·drop·commit을 조정하는 control plane의 진입점이다.
Query engineSQL이나 API를 계획하고 task를 실행하는 계산 계층이다. Spark·Flink·Trino 등이 같은 Iceberg table을 사용할 수 있다.
Warehousetable의 metadata·data file이 배치되는 기본 저장 경로다. 로컬 파일 시스템, HDFS, S3 같은 object storage가 될 수 있다.
Pointer실제 내용을 복사하는 대신 현재 유효한 객체의 위치를 가리키는 참조다. 주소표에서 최신 판의 위치를 찾는 것에 비유할 수 있다.
Control path / Data pathControl path는 이름·권한·현재 상태·commit 결정을 전달하고, data path는 실제 metadata와 row data의 바이트를 읽고 쓴다.
CASCompare-and-swap. “내가 읽은 이전 값이 아직 current일 때만 새 값으로 바꾼다”는 원자적 갱신 방식이다.

2. 왜 중요한가

장애 메시지 하나가 여러 계층에서 만들어질 수 있다. TABLE_OR_VIEW_NOT_FOUND가 났다고 해도 warehouse에서 file이 사라졌다는 뜻은 아니다. Catalog 이름이나 namespace가 틀렸을 수 있고, engine의 catalog cache가 오래됐을 수 있으며, catalog가 가리킨 metadata file에 접근할 권한이 없을 수도 있다.

반대로 S3나 local warehouse에서 Parquet file을 직접 열 수 있다고 table이 정상인 것도 아니다. Current snapshot에서 그 file이 참조되지 않거나, delete file을 함께 적용하지 않았거나, old schema를 field ID가 아닌 이름으로 잘못 읽을 수 있다.

운영 질문: “파일이 있습니까?”보다 먼저 “어느 catalog의 어느 metadata pointer에서 시작해 어떤 snapshot과 manifest를 따라 이 파일에 도달했습니까?”를 묻는다.

3. 아키텍처 그림과 요청 흐름

아래에서 위쪽은 control path, 아래쪽은 data path다. Query engine은 양쪽을 연결하지만 table state의 유일한 소유자는 아니다.

① Client SQL / API
SELECT · INSERT · MERGE · ALTER
↓
② Query engine
parse → optimize → plan → execute
↓ control path
③ Catalog
catalog.namespace.table → current metadata pointer · commit CAS
↓ data path
④ Iceberg table metadata
metadata JSON → snapshot → manifest list → manifest
↓ FileIO read / write
⑤ Warehouse / object storage
metadata files · Parquet/ORC/Avro data · delete files

Read 요청·응답·상태 변화

  1. Client가 local.sales.orders를 조회하면 engine은 local을 catalog 이름으로 해석한다.
  2. Engine이 catalog에 sales.orders load를 요청한다. Catalog는 현재 metadata 위치를 제공한다.
  3. Engine의 Iceberg connector는 metadata JSON에서 current snapshot을 선택한다. 이 시점부터 reader는 한 committed state를 기준으로 계획한다.
  4. Manifest list와 manifest의 partition·column metrics로 필요 없는 file을 pruning한다.
  5. FileIO가 warehouse에서 선택된 data/delete file만 읽는다. Engine은 delete 적용, projection, filter와 task 실행을 담당한다.

Write와 optimistic commit

  1. Engine이 base metadata·snapshot·schema·partition spec을 읽어 write plan을 만든다.
  2. Task가 warehouse의 고유 경로에 immutable data/delete file을 쓴다. 아직 current table state가 아니다.
  3. Driver가 새 manifest, manifest list와 metadata JSON을 만든다.
  4. Commit 전 현재 state가 바뀌었는지 operation별 conflict validation을 한다. Concurrent append와 predicate overwrite는 같은 조건으로 재시도할 수 없다.
  5. Catalog가 base pointer를 비교해 새 metadata pointer로 CAS한다. 이 교체 성공이 commit의 linearization point다.
  6. CAS 실패 시 compatible update는 새 base 위에서 재시도할 수 있지만, unsafe conflict는 사용자에게 실패로 반환해야 한다. 미참조 파일은 orphan 후보로 남을 수 있다.

4. CS 관점의 내부 동작

계층소유 상태와 불변식
File format한 파일 내부 row/column encoding과 통계를 소유한다. 파일 하나가 유효하다고 table 전체가 일관된 것은 아니다.
Table formatCommitted snapshot에서 도달 가능한 file 집합, schema·spec·sort order와 history를 소유한다. Reader가 partial state를 보지 않는 것이 핵심 불변식이다.
Catalog이름→current metadata 연결과 commit 원자성을 소유한다. Catalog 장애는 storage의 byte를 즉시 지우지 않지만 load·refresh·commit availability를 제한한다.
Engine계획, shuffle, task retry, row-level operation과 connector behavior를 소유한다. 같은 spec이라도 SQL 문법·지원 기능·cache가 다를 수 있다.
WarehouseByte durability와 path를 소유한다. “존재하는 file”과 “현재 table에 포함된 file”을 구분해야 한다.

Indirection과 immutable state

Iceberg는 기존 파일을 제자리에서 고치는 대신 새 파일과 새 metadata를 만들고 pointer를 바꾼다. 이 방식은 persistent data structure와 닮았다. Old snapshot은 이전 manifest tree를 계속 가리킬 수 있고, 새 snapshot은 변경된 일부 metadata와 file을 가리킨다. 장점은 reader isolation과 rollback 가능성이고, 비용은 metadata 증가·retention·cleanup 운영이다.

Failure window를 계층별로 보기

  • Data file write 전 실패: table state 변화 없음.
  • Data file write 후, metadata commit 전 실패: file은 있지만 table에 보이지 않는다. Orphan 후보지만 진행 중 writer와 구분해야 한다.
  • Catalog pointer swap 후 응답 timeout: commit 성공 여부가 불명확하다. Blind retry 전에 current snapshot과 operation identity를 확인한다.
  • Commit 후 engine cache 미갱신: 다른 engine과 결과가 일시적으로 다를 수 있다. Catalog·connector의 refresh semantics를 확인한다.
  • Storage에서 참조 file 삭제: catalog와 metadata가 정상이어도 read가 실패한다. Metadata만 rollback해도 byte가 없으면 복구되지 않는다.

5. 실무 설계 판단

판단Best practice와 이유
Catalog 선택동시 commit 보장, HA, 인증, multi-engine 지원과 latency를 기준으로 선택한다. 단순한 table 위치 저장소로만 평가하지 않는다.
권한 분리Catalog namespace/table 권한과 storage read/write/delete 권한을 별도로 설계한다. Catalog 접근과 byte 접근은 다른 공격면이다.
Engine 호환성Format version, data type, equality/position delete, deletion vector, branch/tag, maintenance procedure를 read/write별 matrix로 관리하고 배포 gate에서 검증한다.
관측성Query latency만 보지 말고 catalog request latency/error, commit retry/conflict, metadata/manifest/file count, 평균 file size, snapshot age를 함께 본다.
DRCatalog state와 warehouse byte를 함께 복구할 수 있어야 한다. Snapshot/time travel은 동일 storage가 손상되는 재해의 backup이 아니다.

Anti-pattern: 모든 engine에 warehouse 경로만 공유하고 “같은 Parquet를 보니 같은 table”이라고 가정하는 것. 서로 다른 catalog pointer·format support·cache를 사용하면 logical state와 결과가 갈라질 수 있다.

Edge case: 한 engine이 v3 기능을 써서 metadata를 commit했지만 다른 reader가 그 format version을 지원하지 않으면, storage와 catalog는 정상이어도 구형 reader는 table을 열지 못해야 안전하다. 모르는 metadata를 무시하고 읽는 것이 더 위험하다.

6. 장애 대응 표

상황: Spark에서는 table이 보이는데 Trino에서는 없거나, table 이름은 보이지만 file read가 실패한다.

증상Engine별 table 존재 여부·row count 불일치, metadata JSON 또는 Parquet 접근 거부, stale snapshot, commit timeout.
먼저 수집할 증거/지표각 engine의 catalog 이름·type·URI·warehouse, table identifier, current metadata location, snapshot ID, connector/Iceberg version, storage URI와 IAM 오류, catalog latency/error/cache TTL, writer commit ID.
가능한 가설서로 다른 catalog/namespace, stale cache, storage credential 차이, unsupported format feature, metadata pointer는 갱신됐지만 file upload 불완전, ambiguous commit.
안전한 첫 조치Write와 cleanup을 잠시 멈추고 두 engine이 반환한 metadata location과 snapshot ID를 비교한다. Known-good snapshot을 read-only로 조회하고 정확한 failing URI의 HEAD/read 권한을 확인한다.
Rollback/복구잘못된 pointer commit이면 검증된 snapshot으로 rollback하고, credential/catalog 설정 문제면 기존 metadata를 변경하지 않은 채 설정을 복구한다. Unsupported feature면 호환 reader 배포 또는 사전 합의한 format 정책으로 전환한다.
하지 말아야 할 조치Warehouse file을 수동 rename/delete하지 않는다. Catalog cache를 원인 확인 없이 반복 flush하지 않는다. Commit timeout 직후 동일 batch를 blind append하지 않는다. 구형 reader가 unknown metadata를 무시하도록 강제하지 않는다.

7. 30분 재현 실습

목표: 동일한 데이터라도 catalog를 통한 Iceberg table read와 warehouse의 raw Parquet read가 서로 다른 계약임을 확인한다.

사전 조건과 예측

  • 프로젝트 루트에서 Docker를 사용할 수 있고 local Hadoop catalog가 설정돼 있다.
  • 먼저 예측한다: catalog 이름을 일부러 틀리면 warehouse file은 삭제될까? Raw Parquet로 읽으면 Iceberg snapshot/delete semantics가 유지될까?

최소 명령

make smoke

docker compose exec spark spark-sql -e "
SHOW CURRENT NAMESPACE;
SHOW NAMESPACES IN local;
CREATE NAMESPACE IF NOT EXISTS local.day02;
DROP TABLE IF EXISTS local.day02.boundary_lab;
CREATE TABLE local.day02.boundary_lab (
  id BIGINT,
  category STRING,
  event_time TIMESTAMP
) USING iceberg;
INSERT INTO local.day02.boundary_lab VALUES
  (1, 'A', TIMESTAMP '2026-07-30 09:00:00'),
  (2, 'B', TIMESTAMP '2026-07-30 09:01:00');
DESCRIBE TABLE EXTENDED local.day02.boundary_lab;
SELECT * FROM local.day02.boundary_lab ORDER BY id;
SELECT snapshot_id, operation
FROM local.day02.boundary_lab.snapshots;
SELECT file_path, record_count
FROM local.day02.boundary_lab.files;
"

find warehouse -type f | sort

예상 관찰: local은 catalog 이름이고, day02는 namespace다. DESCRIBE의 Location은 warehouse 아래 table 위치를 보여준다. snapshots와 files metadata table은 raw Parquet file 자체가 제공하지 않는 table-level state를 보여준다.

실패 주입

docker compose exec spark spark-sql -e "
SELECT * FROM missing_catalog.day02.boundary_lab;
"

예상 관찰: Catalog resolution 단계에서 실패하지만 warehouse의 metadata/data file은 그대로 남는다. Control path 장애와 data durability가 같은 상태가 아님을 확인한다.

그다음 DESCRIBE 결과의 table Location 아래 data 경로를 확인하고, 실제 경로에 맞춰 raw Parquet read를 시도한다.

docker compose exec spark spark-sql -e "
SELECT * FROM parquet.\`/workspace/warehouse/day02/boundary_lab/data\`;
"

예상 관찰: 현재 실습에서는 row가 같아 보일 수 있지만 raw read는 catalog pointer, snapshot, delete file, schema/spec history를 우회한다. “지금 결과가 같다”는 것이 “계약이 같다”는 뜻은 아니다.

자주 나는 오류와 해결

  • Raw Parquet path not found: HadoopCatalog의 실제 namespace/table 위치는 설정에 따라 다를 수 있다. DESCRIBE의 Location과 find warehouse -type f로 경로를 확인해 바꾼다.
  • Unknown catalog: 실패 주입에서는 정상이다. 정상 query는 local.day02.boundary_lab을 사용한다.
  • Metadata table syntax 오류: Spark/Iceberg runtime이 프로젝트 기준 버전인지 make smoke와 설정 파일로 확인한다.
  • 두 read 결과가 같아서 차이가 안 보임: 이 실습의 증거는 row 차이가 아니라 raw read에 snapshot ID·manifest·delete 적용 계약이 없다는 점이다. Day 04 이후 time travel/delete 실험에서 결과 차이가 드러난다.

Cleanup

docker compose exec spark spark-sql -e "
DROP TABLE IF EXISTS local.day02.boundary_lab;
DROP NAMESPACE IF EXISTS local.day02;
"

Table이 정상 drop됐는지 확인한 뒤 종료한다. 다른 namespace나 warehouse 상위 경로를 수동 삭제하지 않는다.

8. 놓치기 쉬운 함정

  1. Warehouse가 catalog다. Warehouse는 byte 위치이고 catalog는 name/current pointer/commit을 관리한다.
  2. Engine이 table state를 소유한다. Engine은 state를 해석하고 cache할 수 있지만 committed state는 Iceberg metadata와 catalog pointer로 결정된다.
  3. 같은 S3 prefix면 같은 table이다. 서로 다른 catalog·metadata pointer를 쓰면 같은 byte를 보더라도 logical state는 다를 수 있다.
  4. Catalog 장애면 data가 사라졌다. Catalog availability와 storage durability는 분리해서 확인해야 한다.
  5. Raw Parquet read가 더 단순하고 안전하다. Delete·snapshot·field ID·partition evolution을 우회해 조용히 틀린 결과를 만들 수 있다.
  6. Format version만 맞으면 multi-engine 호환이다. Engine별 read/write/maintenance 기능과 SQL semantics까지 검증해야 한다.

9. 대기업 기술 면접 수준 질문

Q1. “Spark와 Trino가 같은 Iceberg table을 공유하는 architecture를 설계해 보세요.”

좋은 답변 구조: workload와 latency/SLA → 공통 catalog와 warehouse → engine별 connector/version matrix → catalog pointer부터 file까지 read path → Spark write의 commit linearization → Trino refresh/cache → IAM 경계 → catalog outage·ambiguous commit 시나리오 → HA·관측성·rollout gate → 한 engine만 writer로 제한하는 대안의 trade-off.

Q2. “Catalog와 object storage 중 어느 쪽이 source of truth입니까?”

좋은 답변 구조: 하나만 고르기보다 책임을 분리 → catalog는 current metadata pointer, storage는 immutable metadata/data byte → 둘이 함께 committed table state를 구성 → catalog pointer에서 도달 가능한 metadata tree라는 불변식 → 각각의 장애 시 영향 → backup/DR은 두 계층을 함께 복구 → raw directory listing을 source of truth로 삼는 대안의 한계.

Q3. “Commit timeout 이후 동일 batch 재처리를 어떻게 안전하게 결정합니까?”

좋은 답변 구조: 성공 확정점은 catalog CAS → timeout은 unknown outcome → operation/batch/checkpoint identity와 current snapshot summary 수집 → data file 존재만으로 판정하지 않음 → append·overwrite·delete별 conflict validation → 이미 commit됐으면 중복 방지, 미commit이면 idempotent 재계획 → orphan cleanup은 safety window 뒤 수행 → 비용과 latency trade-off.

10. 어제 내용 회상 3문제

  1. Storage에 Parquet file을 복사했는데 Iceberg table count가 늘지 않은 이유는?
  2. Hive partition에서 logical timestamp filter만 사용하면 느리거나 틀린 결과가 생길 수 있는 이유는?
  3. Raw Parquet directory가 multi-file atomic commit을 자체적으로 제공하지 못할 때 reader가 볼 수 있는 위험한 상태는?

짧은 정답/채점 기준

  1. Current snapshot의 manifest에서 참조해야 membership이 생긴다고 답하면 통과.
  2. Source column과 physical partition column의 변환 관계를 Hive가 자동 추론·검증하지 못할 수 있다고 답하면 통과.
  3. Writer가 일부 file만 쓴 partial batch 또는 서로 다른 writer 결과가 섞인 상태라고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. Catalog와 warehouse가 각각 소유하는 핵심 상태를 한 문장씩 설명하라.
  2. Query engine이 warehouse의 Parquet를 직접 읽으면 Iceberg table read와 어떤 계약이 달라지는가?
  3. Writer가 data file을 모두 썼지만 catalog CAS가 실패했다면 사용자에게 새 row가 보여야 하는가?

짧은 정답/채점 기준

  1. Catalog는 name→current metadata와 commit, warehouse는 metadata/data byte와 path/durability를 담당한다고 답하면 통과.
  2. Snapshot·manifest membership, delete 적용, field ID와 schema/spec history를 우회한다고 설명하면 통과.
  3. 아니다. Pointer 교체가 성공하지 않았으므로 file은 table state가 아니며 orphan 후보라고 답하면 통과.
