APACHE ICEBERG · WEEK 1 / DAY 05

metadata table과 warehouse file mapping

Lakehouse와 Table Format 정신 모델 · 예상 학습 30분 + 실습 30분

한 줄 요약
Metadata table은 Iceberg의 metadata graph를 SQL row로 투영한 관찰 창이며, warehouse directory의 파일이 아니라 catalog pointer에서 snapshot·manifest를 따라 도달 가능한 path가 table membership을 결정한다.

1. 선수 용어 사전

Metadata tableIceberg metadata를 SQL로 조회하도록 engine connector가 제공하는 read-only 가상 table이다. snapshots·manifests·files 등이 있다.
Metadata JSONSchema, partition spec, sort order, snapshot 목록, current snapshot과 이전 metadata log를 담는 table-level JSON file이다.
Manifest list한 snapshot이 참조하는 manifest들의 path, 길이, content, spec ID, file count와 partition summary를 기록한 Avro file이다.
ManifestData 또는 delete file의 path, partition tuple, column metrics, status와 sequence 정보를 담는 immutable Avro file이다.
Manifest entryManifest 안의 한 file record다. Status는 EXISTING(0), ADDED(1), DELETED(2)를 나타내고 nested data_file에 실제 path와 metrics가 있다.
File metricsRecord count, null/value count, lower/upper bounds처럼 file을 열기 전에 pruning과 품질 진단에 쓰는 통계다.
ReachabilityGraph의 root에서 pointer를 따라 어떤 객체에 도달할 수 있는 성질이다. Current snapshot에서 도달 가능해야 현재 table의 file이다.
Orphan fileStorage에는 있지만 유효한 table metadata에서 참조되지 않는 file 후보다. 진행 중 writer file과 구분할 safety window가 필요하다.

2. 왜 중요한가

운영 중 “row가 사라졌다”, “파일은 있는데 query에 안 나온다”, “planning이 갑자기 느려졌다”는 문제를 directory listing만으로 설명할 수 없다. 어느 metadata JSON이 current인지, 어떤 snapshot과 manifest를 거쳐 어느 data/delete file이 선택됐는지 증거 사슬을 만들어야 한다. Metadata table은 이 사슬의 핵심 부분을 SQL로 보여준다.

이 관찰법을 익히면 row count 하나 대신 snapshot operation, manifest 수, data/delete file 수, spec ID, record count, file size, bounds를 함께 비교할 수 있다. Commit 성공 여부, small-file 증가, partition evolution, COW/MOR delete read amplification, multi-engine 불일치와 maintenance race를 같은 graph 위에서 진단하게 된다.

핵심 불변식: Warehouse path의 존재는 필요조건일 수 있지만 table membership의 충분조건은 아니다. Current snapshot의 manifest entry에서 도달 가능한 path여야 현재 scan 대상이 된다.

3. 아키텍처 그림과 요청 흐름

왼쪽의 logical metadata table row를 오른쪽의 physical warehouse file로 한 단계씩 대응시킨다.

① Catalog pointer
namespace.table → current metadata JSON path
↓ load control path
② metadata_log_entries / metadata JSON
schema·spec·snapshots·current-snapshot-id
↓ current snapshot
③ snapshots row
snapshot_id → manifest_list path
↓ Avro manifest list
④ manifests row
path·content·spec ID·file counts·partition summaries
↓ Avro manifest entries
⑤ entries / files row
file_path·content·partition·metrics·sequence → Parquet/ORC/Avro byte

요청·응답·상태 변화

  1. Client가 local.day05.mapping_lab.files를 조회한다. Spark parser는 mapping_lab을 table, files를 metadata table 이름으로 해석한다.
  2. Connector가 catalog에서 current metadata location을 load한다. 이 control path가 어느 table state를 관찰할지 고정한다.
  3. snapshots는 metadata JSON의 snapshot 목록과 각 manifest-list path를 row로 투영한다. Metadata table 조회 자체는 새 snapshot을 만들지 않는다.
  4. manifests는 current snapshot의 manifest list를 읽어 manifest path, content, spec ID와 file count를 row로 만든다.
  5. entries는 manifest entry의 status·snapshot/sequence와 nested file metadata를 보여주고, files는 current snapshot의 live data/delete file 관찰에 편리한 view를 제공한다.
  6. Engine은 file_path가 가리키는 warehouse object를 scan할 수 있다. Directory에 별도 file을 복사해도 manifest entry가 생기지 않으므로 table query에는 포함되지 않는다.

현재 state와 전체 history view 구분

Metadata table관찰 범위와 용도
history / snapshots과거 current 이력과 유효 snapshot의 operation·summary·manifest-list root를 본다.
manifests / entries / files기본적으로 current snapshot의 manifest와 file membership을 진단한다.

metadata_log_entries현재 metadata JSON이 추적하는 이전 metadata file과 당시 최신 snapshot/schema/sequence를 본다.
refsMain branch, tag, branch가 붙잡는 snapshot과 retention 정보를 본다.

4. CS 관점의 내부 동작

개념Metadata mapping에서의 의미
Materialized indexManifest list와 manifest는 data file membership·partition·metrics를 미리 기록한 계층형 index다. Query마다 object storage 전체를 list하지 않는다.
IndirectionCatalog→JSON→snapshot→manifest-list→manifest→file의 간접 참조가 atomic state 전환, snapshot isolation과 metadata pruning을 가능하게 한다.
Reachability GC유효한 snapshot/ref graph에서 도달 가능한 file은 보존해야 한다. 미도달 file 후보를 지울 때 진행 중 writer와 path normalization을 고려한다.
Stable identitySchema field ID와 partition spec ID는 rename/evolution 뒤에도 old/new metadata를 해석하는 기준이다. Directory 이름만으로 schema/spec을 추정하지 않는다.
Partial orderSnapshot parent와 sequence number는 change/file/delete 적용 순서를 표현한다. Snapshot ID 숫자 크기나 object 생성 시각으로 순서를 추측하지 않는다.
Observability viewMetadata table은 source state 자체가 아니라 connector가 spec metadata를 SQL schema로 투영한 view다. Engine/version별 지원 column과 nested 표현이 다를 수 있다.

Read planning과 pruning

  1. Manifest list의 partition lower/upper summaries로 읽지 않을 manifest를 먼저 제거한다.
  2. 선택한 manifest 안에서 partition tuple과 field-ID 기반 value/null/NaN count, lower/upper bounds로 data file을 제거한다.
  3. 남은 file만 scan task가 연다. Data file이 많아도 planning metadata가 잘 구성되면 storage listing과 full file open을 피할 수 있다.
  4. Row-level delete table은 delete manifest를 먼저 계획하고 sequence number로 어느 data file에 delete를 적용할지 판정한다. V3 deletion vector는 referenced data file과 Puffin blob offset/length를 정확히 매핑해야 한다.

Writer commit과 관찰 가능 시점

Writer는 새 data/delete file → manifest → manifest list → metadata JSON 순으로 immutable object를 준비한다. 이들 path가 storage에 보여도 catalog pointer가 새 JSON으로 원자 교체되기 전에는 current metadata table에 보여서는 안 된다. Catalog swap이 성공한 뒤 새로 load한 metadata table query에서 새 snapshot/file이 보이는 것이 commit 확정 증거다.

Failure window와 비용

  • File upload 후 commit 전 실패: Warehouse listing에는 보이지만 files에는 없는 orphan 후보다.
  • Pointer swap 후 response timeout: 새 snapshot이 metadata table에 보일 수 있다. Blind retry 전에 snapshot summary와 batch identity를 확인한다.
  • Catalog cache stale: Engine별 metadata table 결과가 잠시 다를 수 있다. 같은 metadata location/snapshot ID인지 비교한다.
  • Manifest 폭증: Planning이 많은 Avro metadata를 읽어 latency와 driver memory가 증가한다. Rewrite manifests는 새 commit이며 concurrent writer와 race를 고려한다.
  • Metrics 풍부함: Pruning은 좋아지지만 writer CPU·metadata 크기와 민감한 값 bounds 노출 위험이 커질 수 있다.

5. 실무 설계 판단

판단Best practice와 이유
Commit 검증Job 종료 코드뿐 아니라 snapshot ID·operation·added records/files·batch identity와 source count를 함께 기록한다. Ambiguous commit을 file 존재만으로 판정하지 않는다.
Planning SLOSnapshot당 manifest 수·크기, data/delete file 수, planning latency와 driver memory를 dashboard로 묶어 임계치와 rewrite 기준을 정한다.
Path canonicalizationMetadata table path와 filesystem/object listing의 scheme·authority·encoding을 normalize한 뒤 비교한다. 문자열 prefix 차이를 orphan으로 오판하지 않는다.
Evolution 관찰Files/manifests의 spec ID, schema field ID, sort order ID를 기록해 old/new layout 공존을 정상 상태로 해석한다.
Delete 비용Data/delete manifest와 content별 file count, sequence, referenced data file, 평균 delete 적용량을 관찰해 COW/MOR·compaction 정책을 정한다.
Multi-engine gateSpark·Flink·Trino별 metadata table 이름·column·nested metrics·all_*·DV 표시와 refresh semantics를 호환성 test로 고정한다.

Anti-pattern: Storage inventory를 current table file 목록으로 간주해 metadata table과 diff한 뒤, 차집합을 즉시 삭제하는 것. 진행 중 writer, old snapshot/ref, path alias와 catalog cache 때문에 정상 file을 지울 수 있다.

Edge case: Partition evolution 뒤에는 manifest 하나가 하나의 partition spec만 저장하므로 old/new spec manifest가 함께 존재한다. 현재 partition directory 규칙 하나로 모든 file을 재해석하면 pruning과 orphan 판정이 틀린다.

6. 장애 대응 표

상황: Warehouse에는 Parquet가 있는데 query와 files metadata table에 나타나지 않는다.

증상Directory listing과 files path 집합 불일치, row count 미증가, orphan 후보 증가, engine별 snapshot/file count 차이.
먼저 수집할 증거/지표Catalog identifier와 current metadata location, current/history snapshot ID, snapshots/manifests/entries/files/all_files 결과, exact object URI·size·mtime, writer job/batch ID와 commit log, catalog/storage audit log, active writer 목록.
가능한 가설Commit 전 writer file, failed commit orphan, manual/raw copy, 다른 table/catalog의 file, expired snapshot의 잔여 file, stale cache, path scheme/authority mismatch.
안전한 첫 조치Write와 cleanup을 잠시 멈추고 exact path와 metadata chain을 보존한다. Current뿐 아니라 refs와 retained snapshot의 all_* view에서 참조 여부를 read-only로 확인하고 file age를 active writer 최대 시간과 비교한다.
Rollback/복구Commit 누락 data를 포함해야 한다면 검증된 Iceberg write/add-files 절차로 새 snapshot을 만들고, orphan이면 승인된 safety window 뒤 dry-run 결과를 검토해 정리한다. Missing referenced file이면 독립 backup에서 byte를 복원하고 새 table에서 검증한다.
하지 말아야 할 조치Parquet를 manifest/JSON에 수동 추가하지 않는다. Mtime만 보고 삭제하지 않는다. Metadata JSON과 current pointer를 직접 편집하지 않는다. Path mismatch 경고를 무시한 orphan cleanup을 실행하지 않는다.

예상 관찰: Metadata JSON, snap-*.avro manifest list, *-m*.avro manifest와 data/*.parquet가 계층별로 보인다. SQL row의 manifest-list/path/file-path를 실제 목록에서 찾을 수 있다. File 생성 시각이나 이름만으로 parent-child 관계를 결정하지 않는다.

실패 주입 · Valid Parquet를 수동 복사

KNOWN_FILE=$(find warehouse/day05/mapping_lab/data -type f -name '*.parquet' | head -n 1)
cp "$KNOWN_FILE" warehouse/day05/mapping_lab/data/rogue-copy.parquet

find warehouse/day05/mapping_lab/data -type f | sort

docker compose exec spark /opt/spark/bin/spark-sql -e "
SELECT count(*) AS current_rows FROM local.day05.mapping_lab;
SELECT file_path FROM local.day05.mapping_lab.files ORDER BY file_path;
"

예상 관찰: Directory에는 valid Parquet 복사본이 하나 늘지만 row count는 3이고 files에 rogue-copy.parquet가 없다. Warehouse listing은 membership source of truth가 아니다.

자주 나는 오류와 해결

  • KNOWN_FILE이 비어 있음: 정상 INSERT 성공과 files 결과를 확인하고 DESCRIBE TABLE EXTENDED의 실제 Location으로 경로를 수정한다.
  • Metadata table column 불일치: DESCRIBE local.day05.mapping_lab.files 등으로 runtime schema를 먼저 보고 engine/version 차이를 기록한다.
  • entries nested field 오류: Engine에 따라 struct 접근/표현이 다를 수 있다. 먼저 SELECT * ... entries LIMIT 1로 실제 schema를 확인한다.
  • 예상보다 manifest/file 수가 많음: Task 수, partition, write distribution과 manifest merge 설정에 따라 달라진다. 고정 개수가 아니라 path 연결과 record 총합을 검증한다.
  • 복사 뒤 raw Parquet query에는 row가 보임: 정상이다. Raw directory read는 Iceberg snapshot membership을 우회하므로 table query와 계약이 다르다.
  • Permission 또는 cache 공간 오류: make smoke, Docker disk와 프로젝트 Ivy cache path를 확인한다.

8. 놓치기 쉬운 함정

  1. Metadata table은 별도 database table이다. 실제로는 connector가 Iceberg metadata file을 SQL row로 투영한 read-only view다.
  2. files와 all_files는 같다. Current state와 retained snapshot 전체 history의 범위가 다르며 같은 file이 여러 snapshot에서 공유될 수 있다.
  3. Directory에 Parquet가 있으면 table row다. Manifest entry에 commit돼야 membership이 생긴다.
  4. Manifest의 DELETED status면 즉시 physical delete다. Entry status는 metadata tracking 정보이며 retained snapshot이 참조하면 file을 보존해야 한다.
  5. Snapshot ID와 file mtime으로 순서를 알 수 있다. Parent·committed_at·sequence number와 manifest entry를 사용한다.
  6. Partition path가 spec을 설명한다. Hidden partitioning과 evolution에서는 manifest의 spec ID와 typed partition tuple이 기준이다.
  7. Metrics는 항상 완전하고 동일하다. Write metrics mode, format/version/engine에 따라 bounds나 NaN 정보가 없을 수 있고 민감정보 정책도 고려해야 한다.
  8. Metadata diff의 차집합은 즉시 orphan이다. Active writer, refs, retention, path alias와 catalog refresh를 검증해야 한다.

9. 대기업 기술 면접 수준 질문

Q1. “Iceberg query가 10억 개 object 중 필요한 file을 찾는 경로를 설명하세요.”

좋은 답변 구조: Object listing 회피 요구 → catalog pointer→metadata JSON→snapshot→manifest list의 partition summary→manifest의 partition/column metrics→data/delete file → two-level pruning과 driver planning → field/spec ID와 sequence/delete 적용 → manifest 폭증·stale cache·missing object failure → rewrite manifest/partition/sort 대안과 write 비용 trade-off.

Q2. “Warehouse와 metadata table을 대조해 orphan cleanup을 설계하세요.”

좋은 답변 구조: Table 규모·writer 최대 시간·retention/refs 수치 가정 → canonical path inventory → current/all snapshot reachability → active/staged writer 제외 → dry-run과 age safety window → scheme/authority mismatch → catalog/object storage outage와 maintenance race → batch delete·audit·rollback 한계 → tag/backup과 비용.

Q3. “Spark와 Trino의 metadata table 결과가 다르면 어떻게 진단합니까?”

좋은 답변 구조: 같은 catalog·identifier·metadata location/snapshot ID인지 확인 → connector/runtime/format version과 refresh semantics → metadata table schema/nested metrics/all_* 지원 → exact manifest/file path 비교 → delete/COW/MOR/DV 및 partition evolution edge case → read-only refresh와 known-good snapshot → 단일 관측 engine 또는 compatibility gate 대안.

10. 어제 내용 회상 3문제

  1. Time travel과 rollback은 current table state를 각각 어떻게 다루는가?
  2. Timestamp time travel은 lineage와 snapshot-log 중 무엇을 기준으로 snapshot을 고르는가?
  3. Time travel이 backup/DR을 대체하지 못하는 이유는?

짧은 정답/채점 기준

  1. Time travel은 current를 바꾸지 않는 read, rollback은 current reference를 바꾸는 commit이라고 답하면 통과.
  2. 그 timestamp 이전의 마지막 current state를 기록한 snapshot-log라고 답하면 통과.
  3. 과거 snapshot도 같은 storage byte·IAM·catalog와 retention에 의존해 독립 장애 영역의 복구본이 아니라고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. snapshots·manifests·files의 path를 물리 file까지 순서대로 연결하라.
  2. Warehouse에 valid Parquet를 복사해도 Iceberg row가 늘지 않는 이유는?
  3. files와 all_files 차이를 cleanup 관점에서 설명하라.

짧은 정답/채점 기준

  1. Metadata JSON/current snapshot → snapshots.manifest_list → manifests.path → entries/files.file_path 순서를 말하면 통과.
  2. Current snapshot의 manifest entry에 commit되지 않아 metadata graph에서 도달할 수 없다고 답하면 통과.
  3. files는 current membership, all_files는 retained snapshots 전체의 tracked files이며 current에 없다고 즉시 삭제하면 안 된다고 답하면 통과.
