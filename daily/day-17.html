APACHE ICEBERG · WEEK 3 / DAY 17

hidden partitioning과 transform

Schema·Partition·Sort Evolution · 예상 학습 35분 + 실습 35분

한 줄 요약
Hidden partitioning은 사용자가 물리 partition column을 직접 만들거나 filter하지 않아도, Iceberg가 source value에 transform을 적용하고 query predicate를 안전한 partition predicate로 투영하는 protocol이다.

1. 선수 용어 사전

Partitioning비슷한 row를 같은 file group에 모아 query가 불필요한 file을 건너뛰게 하는 물리 배치 규칙이다.
Hidden partitioningPartition value 생성과 filter 사용을 table format이 책임져 사용자 schema에서 물리 partition column을 숨기는 방식이다.
Source column / IDTransform 입력이 되는 logical column과 그 stable field ID다. 예: event_time의 ID 3.
TransformSource value를 partition value로 바꾸는 결정적 함수다. 예: day(event_time), bucket[16](id).
Partition specSource ID, partition field ID, transform, partition name의 ordered list다. Metadata JSON이 versioned state로 소유한다.
Predicate projectionLogical filter를 partition value filter로 바꾸는 과정이다. 정답 row를 버리지 않는 보수적 변환이어야 한다.
Residual predicatePartition pruning 뒤 row/file level에서 다시 확인해야 하는 원래 조건의 남은 부분이다.
Pruning정답이 절대 없음을 metadata로 증명한 manifest·file을 읽기 대상에서 제거하는 일이다.

2. 왜 중요한가

Hive식 partition table에서는 writer가 event_date를 정확히 계산해 경로에 쓰고, reader도 event_time 조건과 별도로 event_date filter를 적어야 했다. 둘 중 하나라도 빠지거나 timezone 계산이 다르면 잘못된 경로에 쓰거나 전체 partition을 scan한다. Query가 물리 layout과 결합된다.

Iceberg는 day(event_time)이라는 관계를 metadata에 보관한다. 사용자는 business column인 event_time만 쓰고, writer가 partition tuple을 만들며 reader가 filter를 자동 투영한다. Physical layout을 바꿔도 logical SQL을 유지할 수 있는 이유다.

핵심 불변식: 한 data file 안의 모든 row는 그 file의 partition spec이 계산한 동일한 partition tuple을 가져야 한다. Pruning은 정답 row를 버리지 않는 보수적 증명이어야 한다.

3. 아키텍처 그림과 요청 흐름

Partition false positive는 허용, false negative는 금지

Read path: 요청·응답·상태

  1. Analyzer는 event_time name을 field ID에 bind하고 catalog pointer가 가리키는 metadata JSON과 snapshot을 pin한다.
  2. Planner는 snapshot의 manifest list를 읽고 각 manifest의 spec ID를 찾는다. 같은 logical filter라도 spec마다 다른 transform으로 투영해야 한다.
  3. event_time BETWEEN 10:10 AND 10:50을 hour(event_time)=H 후보로 만들 수 있다. Hour partition 전체에는 범위 밖 row도 있어 residual이 남는다.
  4. Manifest list의 partition summary로 manifest를 줄이고, manifest entry의 partition tuple과 field metrics로 data/delete file을 더 줄인다.
  5. Candidate data file을 열고 COW/MOR 정책에 맞춰 delete file을 적용한다. Equality delete field IDs와 data sequence, position delete/DV의 target relation을 보수적으로 결합한다.
  6. 마지막에 원래 logical predicate를 row에 평가한다. Projection이 낸 false positive는 여기서 제거되지만 false negative는 복구할 수 없으므로 금지된다.

Write path: transform에서 optimistic commit까지

  1. Writer가 base metadata, current schema, default partition spec ID를 읽는다. Source column은 name이 아니라 field ID로 선택한다.
  2. 각 row에 동일 spec의 transform을 적용한다. Null input은 모든 transform에서 null partition value를 만들어야 한다.
  3. Partition tuple별로 row를 모아 data file을 쓴다. 한 file에 다른 tuple이 섞이면 manifest가 거짓 index가 되어 correctness가 깨진다.
  4. Manifest entry에 spec에 맞는 partition tuple, file path, count·bounds와 sequence 관련 상태를 기록하고 manifest list/snapshot을 만든다.
  5. 새 metadata JSON을 object storage에 쓴 뒤 base catalog pointer와 conflict validation한다. CAS 성공이 commit의 linearization point다.
  6. CAS 전 timeout이면 current pointer를 다시 읽어 성공 여부를 판정한다. Data file 존재만으로 성공을 추정하거나 같은 batch를 blind retry하지 않는다.

4. CS 관점의 내부 동작

Transform 관계도

Transform입력 → 결과Pruning 성질·용도
identity원래 값 → 같은 type정확한 값·range pruning, low-cardinality column에 적합. Cardinality가 높으면 작은 file 위험.
bucket[N]Murmur3 32-bit hash → 0..N-1Equality/join key 분산에 유용. Hash collision 때문에 residual이 필요하고 range order는 보존하지 않는다.
truncate[W]숫자·decimal·string·binary → 같은 typePrefix/range locality를 줄인 cardinality로 보존. 음수 remainder와 UTF-8 경계를 spec대로 처리한다.
year/month/day/hourDate/time 계열 → 시간 단위 offset/dateTime-range pruning. Query granularity·data volume·late arrival에 맞춰 선택한다.
void모든 입력 → nullV1 partition field를 사실상 제거할 때 사용. Pruning 정보는 주지 않는다.
unknownReader가 모르는 transform안전하게 해당 field pruning을 포기한다. Writer는 unknown transform을 포함한 spec으로 data를 commit하면 안 된다.

Inclusive projection과 strict projection

Inclusive projection은 “이 partition에 정답 row가 있을 가능성이 있는가?”를 묻는다. 후보를 넓게 잡아 false positive를 허용하지만 정답 partition을 제외하지 않는다. 일반 scan planning의 안전한 기본이다.

Strict projection은 “이 partition의 모든 row가 원래 조건을 만족하는가?”를 묻는다. Metadata-only count나 delete planning 같은 최적화에 쓸 수 있지만 증명이 안 되면 원래 predicate를 유지해야 한다. 두 projection을 뒤집으면 data loss형 오답이 난다.

Bucket과 truncate의 작은 수학

bucket_N(x) = (murmur3_x86_32(x) & Integer.MAX_VALUE) % N이다. 동일 typed value는 engine이 달라도 같은 bucket이어야 한다. 단순 언어별 hashCode나 음수 modulo를 쓰면 multi-engine file 배치가 달라진다.

정수 truncate[10]은 1→0, -1→-10이어야 한다. 언어별 음수 remainder 차이를 방치하면 같은 row가 writer에 따라 다른 partition tuple을 갖는다. String truncate는 잘린 UTF-8이 유효해야 하며 byte 중간 절단이 아니다.

Data path와 control path

Control path: catalog pointer → metadata JSON의 schema/spec → snapshot → manifest list/manifest에서 어떤 file을 읽을지 결정한다. Data path: 결정된 data/delete file bytes를 읽고 residual을 평가한다. Hidden partitioning은 partition directory listing이 아니라 control path metadata를 index로 사용한다.

5. 실무 설계 판단

판단 기준Best practice와 이유
Transform 선택Query predicate 빈도, cardinality, 하루 ingest bytes, target file size를 수치화한다. Time range에는 day/hour, equality key에는 bucket, prefix/range에는 truncate를 후보로 검증한다.
Bucket 수N을 worker 수와 동일시하지 말고 partition당 bytes/file count/skew로 정한다. 너무 크면 small files, 너무 작으면 hot partition과 낮은 pruning 효과가 난다.
Predicate shapeBusiness column에 sargable range/equality를 쓴다. UDF·복잡한 cast는 transform projection을 막을 수 있으므로 explain plan과 scanned file count로 검증한다.
Null·timezoneNull partition 비율과 timestamp/timestamptz 의미, session timezone별 경계값을 canary한다. 모든 transform의 null→null 불변식을 지킨다.
Multi-engine gateSpark/Flink/Trino별 transform DDL·hash/truncate·predicate projection·unknown transform 지원을 동일 table/snapshot으로 비교한다.
MaintenanceRewrite가 spec·sort·sequence/delete 적용을 보존하는지 확인하고 concurrent writer와 conflict window를 관측한다. Partition directory를 직접 이동하지 않는다.

Version/engine 차이: V1/V2 reader는 unknown transform field를 pruning에서 무시해야 하며 V3 reader에는 이 동작이 필수다. Writer는 어떤 format version에서도 unknown transform spec으로 data commit을 해서는 안 된다. Timestamp_ns와 geospatial/variant 같은 V3 type은 전체 engine support matrix를 확인한다.

Anti-pattern: Partition path를 source of truth로 listing하거나, 사용자가 event_date를 중복 column으로 만들어 write/query 양쪽에서 수동 동기화하는 것이다.

Edge case: id=42는 bucket 하나로 투영되지만 같은 bucket의 다른 ID도 candidate다. 반대로 id BETWEEN 1 AND 1000은 bucket hash가 순서를 보존하지 않아 의미 있는 range pruning을 거의 제공하지 못한다.

6. 장애 대응 표

상황: Time-range query가 갑자기 전체 scan하거나 engine별 결과가 다르다.

증상Scanned manifest/file·bytes 급증, 특정 날짜 누락/중복, engine별 bucket/partition tuple 차이, null partition 급증, delete 적용 차이, commit conflict·orphan file 증가.
먼저 수집할 증거/지표Catalog metadata location·snapshot ID, metadata JSON의 default/spec 목록, manifest list spec ID·partition summary, manifest entry tuple·sequence, query/residual plan, scanned files/bytes, engine/connector/session timezone, old/new writer file sample과 delete files.
가능한 가설UDF/cast로 projection 불가, stale spec cache, Murmur3/negative truncate 구현 차이, null/timezone 경계 오류, unknown transform 오처리, 한 file에 tuple 혼합, raw path reader, old/new spec 공존 누락, MOR delete pruning bug.
안전한 첫 조치Affected write/maintenance를 중지하고 snapshot을 pin한다. Spec별 file·partition sample과 explain plan을 보존한다. 가능하면 문제 reader의 partition pruning만 보수적으로 비활성화해 full scan correctness를 비교하고 known-good connector로 교차 확인한다.
Rollback/복구Known-good writer/reader로 rollback하고 catalog-supported snapshot/metadata 복구를 사용한다. 잘못 쓴 file은 검증된 rewrite로 새 snapshot에 교체하고, orphan은 retention 후 supported cleanup으로 제거한다.
하지 말아야 할 조치Partition directory를 rename/move/delete하지 않는다. Metadata JSON·manifest tuple을 수동 편집하지 않는다. Listing 결과로 table membership을 재구성하거나 증거 없이 snapshot expire/orphan cleanup을 실행하지 않는다.

FROM local.day17.hidden_lab

FROM local.day17.hidden_lab

실패 주입 · Iceberg를 우회한 raw path read

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
DELETE FROM local.day17.hidden_lab WHERE id = 2;

SELECT id, event_time, message
FROM local.day17.hidden_lab ORDER BY id;

CREATE OR REPLACE TEMP VIEW raw_path_view
USING parquet
OPTIONS (
  path 'warehouse/day17/hidden_lab/data',
  recursiveFileLookup 'true',
  mergeSchema 'true'
);

SELECT id, event_time, message
FROM raw_path_view ORDER BY id;
"

예상 관찰: Iceberg read는 id 2를 제외한다. Raw path read는 manifest membership·snapshot·delete file/DV를 모르므로 old COW file까지 읽어 중복·삭제 row를 노출하거나, MOR delete를 적용하지 못한다. 정확한 mismatch 형태는 write mode와 engine에 따라 달라도 raw 결과를 정답으로 삼으면 안 된다.

자주 나는 오류와 해결

  • days/bucket DDL 문법 실패: 사용 중인 Spark/Iceberg 버전의 transform DDL을 확인한다. 일반 Spark partition column DDL로 바꾸지 않는다.
  • Warehouse path가 다름: files.file_path와 metadata log의 URI로 container-side path를 확인한다.
  • Metadata filename 정렬이 틀림: metadata_log_entries의 마지막 committed file URI를 사용한다.
  • Plan에 transform이 명시되지 않음: Engine별 explain 형식이 다르므로 실제 scanned files/bytes와 metadata table을 함께 비교한다.
  • Raw view가 schema conflict: 이것도 table protocol 우회의 실패 증거다. 강제 cast로 정답처럼 만들지 않는다.
  • DELETE mode 차이: COW/MOR와 format version, connector 설정을 기록하고 Iceberg logical 결과를 기준으로 비교한다.

8. 놓치기 쉬운 함정

  1. Hidden은 partition이 없다는 뜻이다. Partition tuple은 manifest에 존재하고 사용자 schema에서만 숨겨진다.
  2. Directory name이 partition state다. Catalog와 metadata tree가 source of truth다.
  3. Bucket은 range를 보존한다. Hash transform이므로 equality 분산에는 유용하지만 range order는 잃는다.
  4. Bucket 하나는 값 하나다. Collision이 있으므로 residual equality filter가 필요하다.
  5. Partition pruning이 row filter를 대체한다. Coarse transform의 false positive는 data read에서 제거해야 한다.
  6. Null은 별도 임의 bucket에 넣어도 된다. 모든 spec transform은 null input에 null을 반환해야 한다.
  7. Unknown transform이면 table을 못 읽는다. 안전하게 그 field pruning을 포기해야 하며 V3 reader에는 필수다.
  8. Raw Parquet read도 같은 table이다. Snapshot membership, delete semantics, evolution과 isolation을 잃는다.

9. 대기업 기술 면접 질문 3개

  1. 일 20TB event table의 partition transform을 설계하라.
    좋은 답변 구조: Query/SLO·ingest cardinality 수치 → day/hour/bucket/truncate 후보 → target file size·skew 비용 → read/write flow → late data·null·timezone → multi-engine canary → evolution/rollback 대안.
  2. Predicate projection이 false negative를 만들지 않는 이유를 설명하라.
    좋은 답변 구조: Logical predicate와 transform 정의 → inclusive/strict 차이 → hour·bucket 예제 → manifest/file pruning → residual → unknown transform·engine bug의 safe fallback과 observability.
  3. Raw Parquet query가 Iceberg query보다 빠르다는 팀을 설득하라.
    좋은 답변 구조: 측정 조건과 snapshot 고정 → catalog/manifest control path → COW/MOR/delete/DV·sequence → raw listing의 stale/orphan file 위험 → 비용 수치 → 안전한 최적화와 대안.

10. 어제 내용 회상 3문제

  1. Add/drop/rename/reorder 중 fresh field ID를 만드는 연산은 무엇인가?
  2. V1/V2에서 허용되는 primitive type promotion 세 가지는?
  3. Schema-only commit의 성공이 확정되는 순간은 언제인가?
짧은 정답/채점 기준
1) Add만 새 ID를 만든다. 2) int→long, float→double, 같은 scale의 decimal precision 확대. 3) Base pointer validation 뒤 catalog current metadata pointer의 atomic swap이 성공한 순간. Identity·조건·linearization point를 말하면 각 1점.

11. 오늘 내용 확인 문제 3개

  1. day(event_time) table에서 사용자가 query에 physical day column을 추가하지 않아도 되는 이유는?
  2. bucket[16](id)가 id=42를 한 bucket으로 투영해도 residual이 필요한 이유는?
  3. Reader가 모르는 partition transform을 만났을 때 correctness를 지키는 fallback은?
정답/채점 기준
1) Metadata spec이 source ID와 transform을 소유하고 planner가 logical predicate를 자동 projection한다. 2) Murmur3 hash collision으로 같은 bucket에 다른 ID가 들어갈 수 있다. 3) 해당 partition field를 pruning에 쓰지 않고 보수적으로 candidate를 포함한 뒤 data/residual을 평가한다. 책임·collision·safe fallback을 말하면 각 1점.
