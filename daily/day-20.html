랩: old/new spec query planning

Schema·Partition·Sort Evolution · 예상 학습 30분 + 실습 40분

한 줄 요약
Mixed-spec scan은 하나의 logical predicate를 manifest의 spec ID마다 안전한 partition predicate로 따로 투영하고, 후보 file을 합친 뒤 metrics·residual·delete applicability를 적용한다. Current spec 하나로 old file을 해석하면 빠른 오답이 된다.

1. 선수 용어 사전

Logical predicate사용자가 원본 column에 작성한 조건이다. 예: event_time >= 12:00 AND event_time < 13:00.
Predicate projection원본 조건을 partition transform의 값 조건으로 바꾸는 과정이다. Day spec과 hour spec은 서로 다른 결과를 만든다.
Inclusive projection정답일 가능성이 있는 partition을 모두 포함하는 보수적 투영이다. False positive는 허용하지만 false negative는 금지한다.
Split planningSpec별로 manifest와 file 후보를 고른 뒤 실제 scan task로 묶는 control-path 작업이다.
Manifest summaryManifest list에 있는 partition field의 lower/upper bound와 null 정보다. Manifest를 열기 전에 건너뛸 근거다.
ResidualPartition pruning만으로 확정하지 못한 원본 조건이다. Data path에서 row 또는 file-format index에 다시 적용한다.
Pinned snapshotReader가 scan 시작 때 고정한 immutable table state다. Concurrent commit은 refresh하기 전 이 scan에 섞이지 않는다.
Unified partition structMetadata table이 모든 spec의 partition field를 ID 순으로 합친 관찰용 struct다. 특정 spec에 없는 field는 null일 수 있다.

2. 왜 중요한가

Day partition에서 hour partition으로 바꾸면 old data는 day layout, new data는 hour layout으로 남는다. 사용자는 계속 event_time만 filter한다. 이 추상화가 안전하려면 planner가 물리 partition column을 current layout 하나로 단정하지 않아야 한다.

12시 한 시간을 찾는 조건은 old day spec에서는 “그 날짜 전체”라는 넓은 후보를, new hour spec에서는 “정확히 12시”라는 좁은 후보를 만든다. Old spec은 더 많이 읽을 수 있지만 row를 놓치지 않는다. 반대로 current hour field가 null인 old file을 제외하면 빠르지만 id 1 같은 정답 row를 영원히 잃는다.

Planner의 correctness 불변식: 후보 집합은 실제 정답 file 집합의 superset이어야 한다. Partition·manifest·file pruning 단계 어느 곳에서도 false negative를 만들면 안 되며, 불확실하거나 transform을 모르면 그 단계의 pruning을 포기한다.

3. 아키텍처 그림과 요청 흐름

① Catalog pointer → metadata JSON
snapshot 102 pin · specs [0=day, 1=hour] · default=1
↓ snapshot 102의 manifest list
② Manifest A · spec 0
12:00–13:00 → day=2026-08-21 · coarse candidate
↘ summary → manifest entries → file metrics
③ Manifest B · spec 1
12:00–13:00 → hour=2026-08-21 12 · precise candidate
↗ summary → manifest entries → file metrics
④ Spec별 candidate union
sort-order bounds · sequence · COW/MOR delete/DV applicability
↓ data/delete file read + residual
⑤ Logical result
old hit + new hit · snapshot 102 기준 일관된 결과

요청·응답·상태 변화

  1. Reader가 catalog에서 metadata location을 받아 immutable metadata JSON을 읽고 current snapshot 102를 pin한다. 이 순간 scan의 table membership root가 정해진다.
  2. Metadata의 partition-specs 전체와 snapshot의 manifest list를 읽는다. 각 manifest entry의 partition_spec_id는 반드시 그 목록의 spec을 가리킨다.
  3. Logical time predicate를 spec 0의 day(event_time), spec 1의 hour(event_time)에 각각 inclusive projection한다. Current default-spec-id를 old manifest 해석에 재사용하지 않는다.
  4. 각 spec의 transform type으로 manifest partition summary를 decode해 manifest를 줄이고, surviving manifest만 열어 partition tuple과 field metrics로 file을 줄인다.
  5. Day projection은 12시 밖의 old row가 든 file을 포함할 수 있다. 이것은 안전한 false positive이며 원본 event_time residual이 data read에서 제거한다.
  6. Spec별 candidate를 union하고 data/delete file의 partition, path, sequence를 비교해 equality/position delete 또는 지원되는 DV를 연결한다.
  7. Query 중 writer가 snapshot 103을 commit해도 pinned snapshot 102 scan에는 섞이지 않는다. 다음 refresh부터 새 pointer와 manifest list를 읽는다.

Writer와 maintenance가 동시에 움직일 때

  1. Writer는 base metadata를 읽고 current default spec으로 data file과 새 manifest를 준비한다.
  2. Rewrite는 old spec file을 new spec layout으로 다시 쓸 수 있지만, 새 snapshot CAS 전 old file은 여전히 current membership이다.
  3. Commit conflict가 나면 최신 metadata에서 file/partition conflict를 validation한 뒤 새 manifest list로 재시도한다. Prepared object의 존재는 성공 증거가 아니다.
  4. CAS 성공이 새 state의 linearization point다. Old snapshot reader가 끝나기 전에 expiration/orphan cleanup으로 old file을 지우면 isolation을 storage layer에서 깨므로 retention safety window가 필요하다.

4. CS 관점의 내부 동작

계층소유 상태 · 불변식 · 실패 경계
CatalogCurrent metadata pointer와 atomic replace를 소유한다. Read 시작 뒤 outage가 나도 이미 pin한 object가 있으면 진행할 수 있지만 refresh/commit은 막힐 수 있다.
Metadata JSONSchema/spec/sort history와 snapshot refs를 소유한다. Default spec은 새 write의 기본이지 모든 file의 physical schema가 아니다.
Manifest listSnapshot의 manifest membership, spec ID, counts, partition summaries와 sequence를 소유한다. Summary가 불충분하면 manifest를 읽어야 한다.
Manifest한 spec의 data 또는 delete file entry만 저장한다. Tuple schema가 spec에서 유도되므로 서로 다른 spec file을 섞을 수 없다.
File metricsField ID별 bounds/count를 소유한다. Sort order가 좋으면 bounds overlap이 줄지만 missing/truncated metrics에서는 보수적으로 포함한다.
Data/delete pathResidual과 delete applicability가 최종 row correctness를 만든다. Data sequence·file path·spec/partition 관계를 current default로 덮어쓰지 않는다.

왜 coarse projection이 안전한가

Hour 범위를 day transform에 투영하면 날짜 하나가 선택된다. 그 날짜의 old file에는 11시·13시 row도 섞일 수 있으므로 더 읽지만 12시 정답은 모두 포함한다. Partition pruning은 증명 가능한 “없음”만 제거하고, 원본 predicate residual이 마지막 정확성을 담당한다. 이 두 단계 분리는 approximate index와 exact verification을 결합하는 전형적인 CS 패턴이다.

Unknown transform과 version 경계

Reader가 partition transform을 모르면 그 field를 file filtering에 사용하지 않는 것이 안전하다. Table Spec은 v1/v2에서 이를 권고하고 v3에서는 요구한다. Writer는 모르는 transform이 든 spec으로 data를 commit해서는 안 된다. 즉 multi-engine 호환성의 최소값은 “table을 열 수 있음”이 아니라 “모든 active spec을 안전하게 project하고 residual을 유지함”이다.

Planning 비용

Metadata-only evolution은 즉시 rewrite 비용을 피하지만 active spec과 manifest 수가 늘어 projection·summary decode·manifest open 비용이 커질 수 있다. Planning latency는 대략 “spec별 projection + 읽은 manifest 수 + candidate file 수”에 비례한다. Manifest rewrite와 data rewrite는 correctness가 아니라 이 fan-out을 줄이는 후속 최적화다.

5. 실무 설계 판단

판단 기준Best practice와 이유
Reader gateEvolution 전 production engine별 old/new spec fixture와 expected row set을 실행한다. DDL 지원보다 spec-aware read correctness를 먼저 검증한다.
Planner 관측Snapshot/spec별 manifest 수, skipped/read manifests, candidate/scanned files, planning latency p95, residual과 scan bytes를 남긴다.
Evolution rolloutCompatibility canary → metadata-only default 전환 → writer spec ID 분포 → mixed scan comparison → 필요한 범위만 rewrite 순서로 진행한다.
Rewrite 기준Old-spec scan bytes·manifest fan-out이 SLO를 넘을 때만 targeted rewrite한다. “Spec이 두 개”라는 이유만으로 full rewrite하지 않는다.
CacheMetadata location/snapshot ID를 cache key에 포함하고 refresh 경계를 명시한다. Current spec만 갱신하고 manifest cache를 재사용하는 partial refresh를 피한다.
Storage/catalogPointer와 object read failure를 구분한다. Retry는 immutable object GET에 한정하고, pointer가 바뀌었다고 pinned scan 중간에 snapshot을 섞지 않는다.
Maintenance raceLong reader·streaming writer 최대 수명보다 긴 retention을 두고 snapshot expiration과 orphan cleanup을 분리한다.

Engine/version 차이: Apache Iceberg 1.11.0 Spark 문서는 files, manifests, all_manifests 등 metadata table을 제공한다. Column 노출과 EXPLAIN 표현은 Spark/connector 버전에 따라 달라질 수 있다. V1의 historical partition field-ID 할당은 multi-spec unified struct에서 type 충돌 위험이 있어 v2/v3보다 보수적으로 검증한다.

Anti-pattern: Warehouse directory를 listing해 path 이름으로 day/hour를 추측하거나, metadata table의 current hour field가 null인 row를 “old garbage”로 제거하는 custom planner다.

Edge case: Rewrite가 old spec file을 new spec file로 교체하는 동안 pinned reader는 old manifest를 계속 읽는다. 새 file이 보인다는 이유로 old object를 조기 삭제하면 metadata isolation은 맞아도 실제 read가 실패한다.

6. 장애 대응 표

상황: Partition evolution 후 특정 시간대 row가 누락되거나 planning latency가 급증했다.

증상Old 구간만 누락, engine별 count 불일치, 특정 predicate에서 0건, manifest/file read 수·planning p95 증가, object 404, rewrite 중 intermittent failure, delete 후 old row 재출현.
먼저 수집할 증거/지표Catalog metadata location, pinned/current snapshot ID, partition-specs/default ID, manifest list의 spec ID·summaries·counts·sequence, manifest tuple/entry status, files spec_id·partition·bounds·sort_order_id, residual/physical plan, engine version/cache age, object GET error, rewrite/expire/orphan commit 전후.
가능한 가설Default spec만 적용, unified struct null을 제외, transform/bound decode 오류, stale partial cache, overly strict projection, unknown transform 오처리, deleted manifest entry 포함, delete sequence/spec 적용 오류, manifest fan-out, object 조기 삭제, catalog/object storage 일시 장애.
안전한 첫 조치Affected rewrite/cleanup과 spec 변경을 멈추고 snapshot을 pin한다. Spec별 manifest/file sample과 plan을 보존한다. 문제 pruning을 보수적으로 끈 full scan 결과를 known-good reader와 비교하고 immutable object GET만 제한 재시도한다.
Rollback/복구Known-good connector와 이전 default spec으로 future writes를 복구한다. Missing object는 versioned backup/replica에서 같은 URI로 복원하고, 잘못된 membership은 catalog-supported retained snapshot rollback 또는 compensating commit으로 고친다. 검증된 group만 rewrite한다.
하지 말아야 할 조치Metadata JSON의 spec ID·manifest path·bounds를 수동 편집하지 않는다. Raw file 이동/삭제, pointer 강제 교체, snapshot expiration/orphan cleanup, 증거 없는 전체 rewrite나 blind commit retry를 실행하지 않는다.

WHERE event_time >= TIMESTAMP '2026-08-21 12:00:00'

실패 주입 · Current hour field만 보는 naive planner

# 실제 Iceberg scan을 망가뜨리지 않고 metadata table에서 잘못된 후보 선정을 모사한다.
docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SELECT spec_id, partition, file_path
FROM local.day20.plan_lab.files
WHERE partition.event_time_hour IS NOT NULL
ORDER BY spec_id, file_path;

SELECT spec_id, partition, file_path
FROM local.day20.plan_lab.files
ORDER BY spec_id, file_path;
"

예상 관찰: 첫 query는 current hour field가 없는 spec 0 file을 제외한다. 이를 actual scan candidate로 쓰면 id 1이 누락된다. 두 번째 query처럼 먼저 spec별로 group하고 각 transform에 맞는 predicate를 적용해야 한다. Field name이 다르면 DESCRIBE local.day20.plan_lab.files에서 unified struct field를 확인한다.

자주 나는 오류와 해결

  • REPLACE field 이름 오류: DESCRIBE TABLE EXTENDED와 metadata JSON의 exact partition field name을 사용한다.
  • all_manifests column 차이: Connector version의 metadata table schema를 DESCRIBE하고 동일 의미 field로 바꾼다.
  • Unified struct field가 없음: Query engine이 old/new field union을 어떻게 노출하는지 확인한다. Raw tuple position을 직접 비교하지 않는다.
  • EXPLAIN에 두 branch가 안 보임: Planner 내부 projection이 항상 text plan에 모두 노출되지는 않는다. Manifest spec ID, file set, 결과 row를 함께 증거로 쓴다.
  • id 1 또는 4 누락: Snapshot/spec ID, manifest summary, candidate files와 residual을 보존하고 pruning을 끈 known-good reader와 비교한다.
  • Metadata URI 404: Catalog pointer와 object URI를 먼저 기록하고 retry budget 안에서 immutable GET만 재시도한다. 다른 JSON을 임의로 current로 선택하지 않는다.

8. 놓치기 쉬운 함정

  1. Default spec은 read schema다. 새 writer의 기본이며 manifest는 자기 spec ID로 읽는다.
  2. Projection은 exact filter여야 한다. Coarse transform에서는 safe superset과 residual 조합이 정답이다.
  3. Unified partition struct의 null은 file 무효다. 해당 spec에 그 field가 없다는 뜻일 수 있다.
  4. Manifest summary만 읽으면 항상 충분하다. Summary가 match 가능하면 manifest entry까지 내려가야 한다.
  5. Sort order가 query correctness를 보장한다. Bounds pruning을 돕지만 residual·delete path를 대체하지 않는다.
  6. Unknown transform은 오류로 file을 버린다. 안전한 read는 그 field의 pruning을 무시한다.
  7. Concurrent commit을 scan 중간에 refresh한다. Pinned snapshot을 끝까지 사용해야 isolation이 유지된다.
  8. Rewrite commit 후 old object를 즉시 지운다. Old snapshot reader와 retention race를 먼저 해소해야 한다.

9. 대기업 기술 면접 질문 3개

  1. Day→hour evolution 중 12시 query planner를 설계하라.
    좋은 답변 구조: Query/SLO 수치 → catalog·snapshot pin → manifest spec ID → spec별 inclusive projection → summary/file metrics → candidate union·residual → delete sequence → failure window·rollback.
  2. Current spec field가 null인 old file을 제외해도 되는가?
    좋은 답변 구조: Unified struct의 의미 → old spec tuple schema → concrete false-negative row → default/write vs read 책임 → conservative fallback → multi-engine test gate.
  3. Evolution 뒤 planning p95가 4배가 됐다. 무엇을 측정하고 바꿀까?
    좋은 답변 구조: Spec/manifest/file 수와 selectivity → summary/bounds overlap → cache/object GET → small manifest·mixed layout → targeted manifest/data rewrite → concurrent reader safety → 비용·rollback 대안.

10. 어제 내용 회상 3문제

  1. Sort order와 write distribution은 각각 어떤 상태를 소유하는가?
  2. write.target-file-size-bytes를 올려도 file이 커지지 않는 이유 두 가지는?
  3. none distribution의 안전한 전제와 대표 failure mode는?
짧은 정답/채점 기준
  1. Sort order는 metadata/file layout 의도와 order ID, distribution은 engine의 row→task exchange plan이다. Data/control path 분리를 말하면 정답.
  2. Task input이 target보다 작고 AQE memory bytes가 압축 후 더 작아진다. Partition 경계·skew도 인정. File≤task와 compression이 핵심.
  3. Upstream clustering이 증명되거나 fanout 한계를 검증해야 한다. 위반 시 writer rejection, small files, OOM/FD 고갈이 가능하다. 전제+실패를 말하면 정답.

11. 오늘 내용 확인 문제 3개

  1. 12시 한 시간 predicate가 day spec과 hour spec에서 각각 어떤 후보를 만드는가?
  2. Manifest 하나가 여러 partition spec의 file을 섞을 수 없는 이유는?
  3. Planning 중 unknown transform을 만났을 때 안전한 reader 동작은?
짧은 정답/채점 기준
  1. Day spec은 그 날짜 전체라는 coarse superset, hour spec은 12시 hour라는 precise candidate를 만든다. Spec별 projection+residual을 말하면 정답.
  2. Manifest partition tuple struct와 summary schema가 한 spec에서 유도되기 때문이다. Spec ID와 tuple schema가 핵심.
  3. 그 field를 pruning에 사용하지 않고 file을 보수적으로 포함해 residual에서 검증한다. False negative 금지를 말하면 정답.
