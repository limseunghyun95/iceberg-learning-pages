APACHE ICEBERG · WEEK 4 / DAY 26

sequence number와 delete applicability

Commit·Isolation·Concurrency · 예상 학습 45분 + 실습 35분

한 줄 요약
Iceberg는 성공한 commit의 순서를 sequence number로 기록하고, data file의 논리적 나이와 delete의 나이·경로·partition을 비교해 어떤 행을 지울지 결정한다. Equality delete는 dataSeq < deleteSeq, position delete와 deletion vector는 dataSeq ≤ deleteSeq가 핵심이다.

1. 선수 용어 사전

Sequence number성공한 table commit에 부여되는 단조 증가 순서다. 벽시계 시간이 아니라 table history의 논리 시계이며, retry가 다른 순서에 성공하면 다시 배정된다.
Data sequenceFile 안 content의 논리적 나이다. Rewrite로 새 물리 file을 만들어도 같은 논리 content라면 과거 값을 보존할 수 있다.
File sequence그 물리 file이 현재 table membership에 처음 추가된 commit 순서다. “언제 이 file object가 붙었는가”를 나타낸다.
Equality delete지정 field 값이 같은 row를 지우라는 delete record다. 예: id=42. 적용 여부는 strict한 sequence 비교와 partition 범위로 판단한다.
Position deleteData file path와 row position으로 대상을 정확히 가리키는 delete record다. V2의 row-level delete 표현이다.
Deletion vector (DV)한 data file의 삭제 position 집합을 bitmap 계열 blob으로 저장하는 V3 표현이다. 같은 snapshot에서 data file당 최대 하나이며, 새 position delete file 대신 사용한다.
Applicability특정 delete가 특정 data file에 적용되는지 판정하는 규칙이다. Sequence 하나가 아니라 delete 종류, partition, path가 함께 필요하다.
Manifest inheritance새 entry의 null sequence를 manifest list에 기록된 sequence로 채우는 규칙이다. Writer가 commit retry 때 manifest를 재사용할 수 있게 한다.

2. 왜 중요한가

Append와 delete가 동시에 일어나고 compaction이 file을 바꾸는 table에서 “delete가 먼저인가, 새 row가 먼저인가”를 filename이나 timestamp로 결정하면 오삭제 또는 삭제 누락이 생긴다. Object storage의 수정 시간은 commit 순서가 아니며 snapshot ID도 시간 순서를 보장하는 카운터가 아니다. Iceberg는 table 단위 논리 시계인 sequence number로 이 문제를 푼다.

특히 physical rewrite와 logical age를 분리해야 한다. Sequence 1의 data를 compaction이 sequence 5에 새 file로 옮겨도 content는 sequence 1의 delete 대상이어야 한다. 그래서 data sequence는 논리 나이, file sequence는 물리 membership 나이라는 두 시계를 둔다.

불변식: Maintenance가 bytes와 file path를 바꿔도 이미 유효했던 delete의 논리적 효과를 잃거나, 원래 적용되지 않던 delete를 새 row에 소급 적용해서는 안 된다.

번호별 요청·응답·상태 변화

  1. Catalog load: Reader는 catalog에서 current metadata location을 받는다. Table state의 linearization point는 writer가 이 pointer의 compare-and-swap(CAS)에 성공한 순간이다.
  2. Snapshot 선택: Metadata JSON의 current snapshot 또는 time travel snapshot을 고정한다. Snapshot에는 성공 commit에서 확정된 sequence가 있다.
  3. Manifest pruning: Manifest list의 content, partition summary, sequence와 min sequence로 불필요한 manifest를 건너뛴다. 이는 correctness 규칙을 바꾸지 않는 비용 최적화다.
  4. Entry 해석: Reader는 data sequence와 file sequence를 분리해 읽는다. Rewrite된 F_rewrite는 새 fileSeq=3이지만 content의 dataSeq=1을 보존할 수 있다.
  5. Delete pair: Partition/spec 범위와 file metrics로 후보를 줄인 뒤 delete 종류별 sequence·path 규칙을 적용한다. File sequence를 delete pruning에 쓰면 rewrite 뒤 오답이 된다.
  6. Row scan: 적용 가능한 equality key, position set 또는 DV를 data row와 결합해 visible row만 반환한다.

4. CS 관점의 내부 동작

세 가지 시계와 state owner

상태소유자·의미변경 규칙
Snapshot sequenceMetadata/snapshot · 성공 commit 순서CAS 성공한 commit만 순서를 점유하며 retry 시 재배정

왜 Equality만 strict인가

Delete 종류Sequence 규칙추가 조건·이유
EqualitydataSeq < deleteSeq같은 partition(spec+tuple), 또는 delete가 unpartitioned. 같은 commit에서 insert한 동일 key까지 지우지 않도록 strict.
PositiondataSeq ≤ deleteSeq같은 partition, non-null referenced path가 data path와 일치. 이미 관찰한 정확한 row position을 가리키므로 같은 commit도 가능.
DV (V3)dataSeq ≤ deleteSeqReferenced data file과 partition 일치. 적용 가능한 DV가 있으면 그 file의 position delete는 무시.

예를 들어 sequence 7 commit이 equality delete id=42와 새 id=42 row를 함께 추가한다면 새 row의 dataSeq도 7이다. 7<7은 false이므로 새 row는 산다. 이를 ≤로 구현하면 같은 commit의 새 row까지 지워 의도와 다른 state transition이 된다.

Manifest inheritance와 retry

Writer는 새 entry의 sequence를 null로 둔 manifest를 만들 수 있다. Commit이 sequence 8에 성공하면 manifest list의 sequence 8을 상속한다. CAS conflict로 retry해 sequence 9에 성공해도 data manifest bytes를 다시 만들 필요 없이 manifest list만 새 순서로 작성할 수 있다. 반면 기존·삭제 entry는 원래 sequence를 명시적으로 보존해야 한다. 이 구분이 immutable artifact reuse와 correctness를 동시에 만든다.

Control path와 data path

Control path는 catalog pointer → metadata JSON → snapshot → manifest list → manifest entry로 이어지며 어떤 file이 table state인지와 sequence를 정한다. Data path는 선택된 data/delete object를 읽고 row를 병합한다. Object storage에 file을 PUT한 순간은 logical 성공이 아니다. Catalog CAS가 성공해야 sequence와 membership이 외부에 확정된다.

5. 실무 설계 판단

Best practice 1 · 두 시계를 함께 관찰: Metadata query와 장애 dashboard에 snapshot, data sequence, file sequence, spec ID, content type을 함께 남긴다. “새 file이라 delete보다 최신” 같은 filename 기반 추론을 금지한다.

Best practice 2 · planner 순서를 보존: Manifest/partition/metrics로 후보를 줄인 뒤 정확한 sequence·path 규칙을 적용한다. Pruning은 비용 최적화이며 applicability 규칙을 대체하지 않는다.

Best practice 3 · rewrite 검증: Compaction 전후 visible row checksum, delete file count, data/file sequence 분포를 비교한다. RewriteFiles 계열 action이 logical data sequence를 어떻게 보존하는지 engine/version 조합마다 회귀 테스트한다.

Best practice 4 · capability gate: Writer보다 reader가 느리게 업그레이드되는 조직에서는 V3/DV를 켜기 전에 모든 reader가 format과 delete 표현을 지원하는지 확인한다. Table spec 지원과 SQL surface 지원은 별개다.

V1/V2/V3 경계: V1은 row-level delete file을 지원하지 않는다. V2는 equality·position delete와 sequence semantics를 사용한다. V3는 DV를 추가하고 새 position delete file 생성을 deprecated 처리한다. V2에서 만든 position delete는 V3 upgrade 뒤에도 rewrite로 합쳐질 때까지 유효할 수 있다.

Maintenance race: Rewrite가 old data/delete file을 교체하는 동안 concurrent writer가 같은 범위를 commit할 수 있다. Validation failure는 안전 장치다. Retry 때 current snapshot을 refresh하고 새 delete를 빠뜨리지 않았는지 다시 검증한다.

Edge case: Partition evolution 뒤에는 spec ID와 partition tuple을 함께 비교해야 한다. 같은 화면 표시 값만으로 “같은 partition”이라 판단하지 않는다. Unpartitioned equality delete는 table 전역 후보가 될 수 있어 비용이 크다.

Anti-pattern: File sequence로 delete manifest를 prune하거나, equality에 ≤를 쓰거나, DV와 position delete를 동시에 중복 적용하거나, maintenance 성공을 row count만으로 판정하는 것이다.

6. 장애 대응 표

상황: DELETE 뒤 row가 되살아나거나, compaction 뒤 과거 delete가 사라지거나, 같은 commit의 새 row가 잘못 삭제된다.

증상DELETE 후 key 재등장, rewrite 전후 visible count/checksum 변화, same-commit insert 소실, DV/position 중복 적용, engine별 query 결과 불일치, scan task·delete pair 급증.
먼저 수집할 증거/지표Engine/connector/catalog와 format version, current·parent snapshot ID/sequence, manifest list와 entry의 content/status/data/file sequence, spec ID·partition tuple, equality IDs, referenced data path, DV offset/length, rewrite commit summary, affected key·row position.
가능한 가설Equality 비교를 ≤로 구현, file sequence로 prune, rewrite가 data sequence를 올림, spec ID 무시, stale reader가 새 delete 표현 미지원, DV와 position 중복 적용, commit unknown state 뒤 중복 write, manifest inheritance 오해.
안전한 첫 조치Affected writer·maintenance 범위를 일시 중지하고 current metadata를 새로 load한다. Snapshot/manifest/delete artifact를 보존한 채 한 key와 한 data file의 applicability matrix를 수동 계산하고, known-good engine에서 time travel 결과를 비교한다.
rollback/복구안전한 snapshot으로 rollback하거나 forward correction commit을 만든다. 잘못된 rewrite는 source snapshot에서 최신 delete까지 재계획하고, unsupported V3 reader는 upgrade 또는 compatible branch/table로 격리한다. Catalog unknown state는 pointer 확인 후 한 번만 재시도한다.
하지 말아야 할 조치Metadata/manifest 수동 편집, evidence 전 snapshot expiration·orphan cleanup, filename·mtime으로 순서 단정, 모든 delete를 강제 적용, CAS timeout 직후 무조건 재실행, format version 즉시 하향을 하지 않는다.

7. 35분 재현 실습

목표: V2 MOR delete 뒤 같은 key를 다시 insert해 position delete가 과거 data에만 적용되는지 관찰하고, metadata entry에서 data/file sequence를 추적한다.

사전 조건과 실행 전 예측

  • Docker daemon과 프로젝트 Spark/Iceberg 환경이 준비되어 있고 make smoke가 성공해야 한다.
  • 첫 INSERT의 dataSeq를 D1, DELETE의 sequence를 X2, 두 번째 INSERT를 D3라 쓰면 D1≤X2는 true, D3≤X2는 false라고 먼저 적는다.
  • 최종 결과에는 새 id=2 한 건이 보여야 한다. 과거 id=2만 delete 대상이다.
  • 학습 환경의 engine이 MOR row-level DELETE와 metadata table을 지원하는지 version을 기록한다.

2단계 · Entry의 두 sequence 확인

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
SELECT status, snapshot_id, sequence_number AS data_seq,
       file_sequence_number AS file_seq,
       data_file.content, data_file.file_path,
       data_file.record_count, data_file.referenced_data_file
FROM local.day26.seq_lab.entries
ORDER BY sequence_number, file_sequence_number, data_file.content;
"

예상 관찰: Content 0은 data file, content 1은 position delete다. Data/delete entry의 sequence가 snapshot 순서와 연결되고 delete의 referenced path가 old data file을 가리키는지 확인한다. Metadata table column shape는 connector version에 따라 다를 수 있으므로 오류 시 DESCRIBE local.day26.seq_lab.entries로 schema를 먼저 본다.

3단계 · 실패 주입: Equality에 잘못된 비교 적용

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
WITH cases AS (
  SELECT * FROM VALUES
    ('equality-old', 6, 7),
    ('equality-same-commit', 7, 7),
    ('position-same-commit', 7, 7)
  AS t(case_name, data_seq, delete_seq)
)
SELECT case_name, data_seq, delete_seq,
  CASE WHEN case_name LIKE 'equality%'
       THEN data_seq < delete_seq
       ELSE data_seq <= delete_seq END AS correct_applicable,
  data_seq <= delete_seq AS buggy_all_inclusive
FROM cases ORDER BY case_name;
"

관찰: equality-same-commit만 correct=false, buggy=true로 갈린다. 이 한 글자 차이가 same-commit insert를 살릴지 지울지 결정한다. 실행 전 결과를 종이에 예측한 뒤 비교한다.

자주 나는 오류와 해결

  • Delete file이 없음: MOR property 또는 SQL extension이 적용되지 않았거나 engine이 COW로 실행했을 수 있다. SHOW TBLPROPERTIES와 snapshot summary를 확인한다.
  • referenced_data_file column 오류: Connector metadata schema가 다를 수 있다. DESCRIBE ...entries 후 nested field 이름을 맞춘다.
  • 모든 id=2가 사라짐: Query cache를 refresh하고 snapshot/entry sequence를 확인한다. 새 INSERT가 실제로 commit됐는지 lineage부터 본다.
  • Row-level DELETE 미지원: Runtime의 Iceberg format/engine 지원 matrix를 확인하고 V2 MOR를 지원하는 Spark extension 환경에서 재현한다.
  • Production과 다름: Hadoop catalog 실습 결과를 REST/Glue/Hive catalog의 CAS·retry wrapping과 동일시하지 않는다.

8. 놓치기 쉬운 함정

  1. Snapshot ID가 commit 순서다. 순서 비교에는 sequence number를 쓴다.
  2. 새 file은 새 content다. Rewrite file은 file sequence만 새롭고 data sequence는 과거일 수 있다.
  3. 모든 delete 비교는 ≤다. Equality delete는 strict <다.
  4. Sequence만 맞으면 적용된다. Partition/spec과 position/DV의 referenced path 조건도 필요하다.
  5. File sequence로 오래된 data를 prune할 수 있다. Rewrite 때문에 logical age를 잃으므로 불가능하다.
  6. V3에서는 position delete가 즉시 사라진다. 기존 V2 artifact는 merge될 때까지 읽어야 한다.
  7. DV와 position delete를 모두 적용하면 안전하다. Applicable DV가 있으면 해당 data file의 position delete를 무시해야 중복 적용을 피한다.
  8. PUT 성공이면 sequence가 확정된다. Catalog pointer CAS 성공 전 artifact는 table state가 아니다.

9. 대기업 기술 면접 질문

  1. 왜 data sequence와 file sequence를 분리해야 합니까?
    좋은 답변 구조: ① rewrite/compaction 요구 ② logical age와 physical membership 정의 ③ delete applicability 불변식 ④ file sequence 사용 시 오삭제 예시 ⑤ metadata·validation 비용 ⑥ 대안과 trade-off.
  2. Equality delete는 왜 strict하고 position/DV는 inclusive입니까?
    좋은 답변 구조: ① delete 표현 정의 ② same-commit insert/delete 수치 예시(D=7, X=7) ③ key intent와 exact position intent ④ partition/path 조건 ⑤ 잘못 구현한 장애와 테스트.
  3. V2 table을 V3 DV로 전환하는 계획을 설계하세요.
    좋은 답변 구조: ① reader/writer inventory와 SLA ② support matrix·canary ③ existing position delete 공존 ④ one-DV-per-file 및 merge ⑤ maintenance race·rollback ⑥ row checksum·scan cost·delete density 지표.

10. 복습과 정답

어제 내용 회상 3문제

  1. Serializable과 snapshot isolation이 다르게 다루는 대표 conflict는 무엇인가?
  2. Catalog CAS timeout을 즉시 retry하면 위험한 이유는?
  3. MOR delete에서 sequence semantics가 특히 중요한 이유는?

짧은 정답: ① Predicate와 겹칠 수 있는 concurrent data add. Serializable은 실패시키고 snapshot은 허용할 수 있다. ② Commit 성공 여부가 불명이라 중복 state transition이 될 수 있다. ③ Data와 delete를 read time에 합치므로 어떤 세대의 data에 delete가 적용되는지 결정해야 한다. 각 답에서 보장·실패 창·복구를 말하면 만점.

오늘 내용 확인 3문제

  1. DataSeq=5, equality deleteSeq=5라면 적용되는가? Position delete라면?
  2. Sequence 2 content를 sequence 8에서 rewrite한 file의 data/file sequence는 어떻게 될 수 있는가?
  3. Applicable DV가 있는 data file에 과거 position delete도 발견되면 reader는 어떻게 해야 하는가?

정답/채점: ① Equality는 5<5가 false, position은 path·partition이 맞으면 5≤5가 true. ② Data sequence 2를 보존하고 file sequence 8을 받을 수 있다. ③ Applicable DV를 사용하고 그 data file의 position delete는 무시한다. Sequence 식뿐 아니라 partition/path 조건까지 언급하면 각 2점, rewrite 불변식과 중복 적용 방지 이유를 말하면 보너스 1점.
