APACHE ICEBERG · WEEK 2 / DAY 11

file metrics, bounds, counts

Metadata Tree와 Scan Planning · 예상 학습 30분 + 실습 35분

한 줄 요약
File metric은 “이 file에 답이 절대 없다”는 것을 data byte를 읽기 전에 안전하게 증명하는 보수적 요약이다. Bounds와 counts는 정답을 확정하는 통계가 아니라 false negative를 만들지 않는 pruning guard다.

1. 선수 용어 사전

MetricFile 전체를 짧게 요약한 metadata다. Row 수, column별 값·null·NaN 수, 최소·최대 범위 등이 있다.
Lower / upper bound모든 non-null·non-NaN 값보다 작거나 같은 하한과 크거나 같은 상한이다. 반드시 실제 min/max와 같을 필요는 없다.
Value count해당 column의 값 개수다. Iceberg spec에서 null과 NaN도 포함한다.
Null / NaN countNULL과 floating-point의 NaN(Not a Number)을 별도로 센 값이다. Bounds는 이 값을 포함하지 않는다.
Field IDColumn 이름과 별개인 영구 숫자 ID다. Metric map의 key라서 rename 뒤에도 통계가 같은 logical field에 연결된다.
False positive답이 없는데 후보 file을 읽는 것. 성능은 손해지만 결과는 맞다.
False negative답이 있는 file을 잘못 제외하는 것. Query 결과를 틀리게 하므로 허용되지 않는다.

2. 왜 중요한가

Partition만으로는 같은 날짜 안의 수천 file 중 어떤 file에 customer_id = 42가 있는지 알 수 없다. Iceberg는 manifest entry에 file-level column 요약을 넣어 data file을 열기 전에 후보를 줄인다. 이 단계가 잘 작동하면 object GET, network byte, task 수와 query latency가 함께 감소한다.

그러나 metric은 작은 index이므로 완전한 진실을 모두 담지 않는다. Truncated string bound, 빠진 map key, null/NaN, delete file과 schema evolution을 잘못 해석하면 pruning이 느려지거나 더 심각하게는 결과가 틀릴 수 있다. 그래서 writer가 보수적 bound 불변식을 지키고 reader는 “정보 없음”을 “값 없음”으로 오해하지 않아야 한다.

핵심 불변식: Lower bound ≤ file의 모든 non-null·non-NaN 값 ≤ upper bound여야 한다. Metric이 없거나 모호하면 file을 유지해 false positive를 허용하고, 근거 없이 제외해 false negative를 만들지 않는다.

3. 아키텍처 그림과 요청 흐름

① Catalog → metadata JSON
Current snapshot root 선택
↓ snapshot → manifest list
② Manifest-level pruning
Partition summaries로 읽을 manifest 선택
↓ manifest entry
③ File metrics
record/file size · value/null/NaN counts · lower/upper bounds
↓ predicate와 안전하게 비교
④ Candidate data/delete files
COW/MOR · sequence와 delete overlap 확인
↓ 실제 byte read
⑤ Parquet row-group/page pruning
남은 file 내부 index로 한 번 더 축소

Read 요청·응답·상태 변화

  1. Planner가 query predicate를 field ID와 현재 schema 기준 expression으로 bind한다.
  2. Partition spec ID별로 predicate를 projection해 manifest를 줄인 뒤, 남은 entry의 metric map을 field ID로 조회한다.
  3. id = 42인데 file bound가 [100, 200]이면 그 file은 제외한다. Bound가 없으면 후보로 남긴다.
  4. note IS NULL인데 null count가 0이면 제외할 수 있다. Count가 missing이면 “0”으로 간주하지 않는다.
  5. MOR에서는 data와 delete file metric 범위, partition과 sequence를 함께 보아 적용 가능한 delete 후보를 정한다. V3 DV는 referenced data file과 offset/length를 사용한다.
  6. 선택 file의 Parquet row-group/footer를 읽고 더 세밀한 filtering을 한 뒤 row predicate를 실제로 평가한다.

Write·commit 요청과 상태 변화

  1. Writer task가 data/delete file을 만들며 file format 통계에서 metric을 수집한다. 수집 mode는 none/counts/truncate/full 같은 정책에 영향을 받는다.
  2. Metric은 column 이름이 아니라 field ID key와 typed binary bound로 manifest entry에 기록된다. Delete file metric은 모든 deleted row를 반영하거나 생략해야 한다.
  3. 새 manifest와 manifest list, snapshot, metadata JSON을 쓴 뒤 base 이후 변경에 대해 optimistic conflict validation한다.
  4. Catalog pointer swap이 성공해야 metric이 current state의 control path에 들어온다. Response 유실 시 snapshot/file path로 성공 여부를 먼저 확인한다.
  5. Commit 실패 전에 생성된 object는 current graph에 없을 수 있다. Object listing만 보고 metric/file을 table에 수동 연결하지 않는다.

4. CS 관점의 내부 동작

Metric정확한 의미와 pruning 예
record_countData file의 물리 record 수, DV라면 cardinality다. MOR delete 적용 후 live row 수와 같지 않을 수 있다.
file_size / column_sizesScan cost와 split planning에 유용하다. Column size는 해당 column region byte이며 footer 등 공통 byte를 포함하지 않는다.
value_countsNull과 NaN을 포함한 값 개수다. Nested field에서는 record_count와 단순히 같다고 가정하지 않는다.
null countsIS NULL/IS NOT NULL 후보를 줄인다. Missing count는 0이 아니라 unknown이다.
NaN countsFloat/double의 NaN 존재를 별도로 나타낸다. NaN은 lower/upper bound에 넣지 않는다.
lower / upperInclusive conservative interval이다. Predicate interval과 겹치지 않을 때만 제외한다. 문자열 truncate는 interval이 넓어 false positive가 늘 수 있다.

왜 “요약”이 정답이 아닌가

Bound [10, 100]은 42가 존재한다는 뜻이 아니라 존재할 가능성을 배제하지 못한다는 뜻이다. Bloom filter처럼 membership을 더 좁히는 별도 index가 있어도 최종 row predicate는 data를 읽고 평가한다. 이 구조는 approximate synopsis를 exact result의 대체물이 아니라 I/O guard로 사용한다.

Schema, partition, delete와 연결

V3 이하 metric map은 field ID가 key이므로 rename/reorder에도 안전하다. Partition evolution에서는 spec ID별 partition projection 뒤 file metric을 적용한다. COW는 새 data file metric을 쓰고, MOR은 data와 equality/position delete metric overlap 및 sequence를 함께 본다. V3 DV는 한 data file을 직접 참조하지만 engine/connector 지원을 확인해야 한다.

Format version 경계

공식 spec에서 V3 이하 metric은 field-ID map이며, 더 새로운 spec text에는 typed content_stats 표현이 기술되어 있다. 실제 table format adoption과 Spark/Flink/Trino reader 지원은 별도다. Runtime이 쓰지 못하는 spec 기능을 단순히 문서에 있다는 이유로 활성화하지 않는다.

5. 실무 설계 판단

판단Best practice와 이유
수집 modeJoin/filter 핵심 column은 full 또는 충분한 truncate, 민감하거나 넓은 payload는 counts/none을 검토한다. Planning 이득과 manifest 크기·privacy 비용을 수치로 비교한다.
정확성 gate새 writer/engine 도입 시 sample file의 실제 min/max/null/NaN과 readable_metrics를 대조한다. 잘못 좁은 bound는 성능 문제가 아니라 correctness 사고다.
Pruning SLOPredicate별 candidate/total files, planning p95, scanned bytes와 manifest bytes를 함께 본다. File size만 최적화하면 metric selectivity를 놓친다.
민감정보Name, email, token 같은 column의 bounds는 manifest를 읽을 권한에 값을 노출할 수 있다. Metadata IAM·encryption과 metrics mode를 함께 설계한다.
Multi-engineField ID binding, NaN/decimal/timestamp ordering, truncated string과 delete metric 처리 결과를 Spark/Flink/Trino compatibility test로 고정한다.

Anti-pattern: 모든 column에 무조건 full bounds를 저장하는 것. Manifest가 커지고 write CPU·metadata I/O·민감정보 노출이 늘어도 query에서 사용되지 않을 수 있다.

Edge case: Data file record_count는 equality/position delete나 DV 적용 전 물리 row 수다. SUM(record_count)를 현재 table의 COUNT(*)로 사용하면 MOR table에서 틀릴 수 있다.

6. 장애 대응 표

상황: 특정 predicate query가 갑자기 거의 모든 file을 읽거나 engine별 결과가 다르다.

증상Candidate file 비율 급증, scanned bytes/p95 상승, readable_metrics null, engine별 file count/결과 차이, null·NaN·timestamp filter에서 재현.
먼저 수집할 증거/지표Current metadata/snapshot ID, files/entries readable_metrics, field/schema/spec ID, table metrics properties, writer/reader version, query plan·scan report, 실제 Parquet footer sample, delete files/DV와 sequence.
가능한 가설Metrics mode none/counts, truncate 폭이 짧음, 새 column metric 누락, field ID binding 오류, NaN/null 해석 차이, bad writer bound, stale metadata cache, delete overlap 증가.
안전한 첫 조치문제 snapshot을 고정하고 read-only로 metadata metric과 실제 file sample을 비교한다. 성능 문제면 정확성을 유지한 채 수집 mode를 새 file부터 canary 적용한다. 결과 불일치면 영향 engine/write를 중지한다.
Rollback/복구Bad writer가 만든 snapshot이면 retained known-good snapshot으로 rollback하고 file을 정상 writer로 rewrite한다. Metric 누락만 있으면 data rewrite/compaction으로 새 metric을 만들고 canary 검증 후 publish한다.
하지 말아야 할 조치Manifest binary bound를 수동 편집하지 않는다. Missing metric을 0/empty로 간주하지 않는다. Correctness 불일치를 cache 문제로 단정하지 않는다. 검증 전 snapshot expiration/orphan cleanup을 실행하지 않는다.

7. 35분 재현 실습

목표: 의도적으로 range와 null/NaN 분포가 다른 file을 만들고 readable_metrics로 query 후보를 예측한다. 이어 한 column의 metric 수집을 끄면 정답은 유지되지만 pruning 근거가 사라짐을 관찰한다.

사전 조건과 실행 전 예측

  • Docker daemon이 실행 중이고 프로젝트 루트에서 make smoke가 성공해야 한다.
  • 예측한다: id = 101, note IS NULL, score = 20은 각각 어느 file이 후보인가?
  • payload metric을 none으로 바꾼 뒤 payload = 'needle' 결과와 후보 수 중 무엇이 변하는가?

1단계 · 분포가 분리된 file 만들기

make smoke

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
CREATE NAMESPACE IF NOT EXISTS local.day11;
DROP TABLE IF EXISTS local.day11.metrics_lab PURGE;
CREATE TABLE local.day11.metrics_lab (
  id BIGINT, score DOUBLE, note STRING, payload STRING
) USING iceberg
TBLPROPERTIES (
  'write.metadata.metrics.column.id'='full',
  'write.metadata.metrics.column.score'='full',
  'write.metadata.metrics.column.note'='full',
  'write.metadata.metrics.column.payload'='full'
);
INSERT INTO local.day11.metrics_lab VALUES
  (1, 10.0, NULL, 'alpha'),
  (2, 20.0, 'x', 'beta'),
  (3, 30.0, NULL, 'gamma');
INSERT INTO local.day11.metrics_lab VALUES
  (100, 70.0, 'y', 'omega'),
  (101, CAST('NaN' AS DOUBLE), 'z', 'needle'),
  (102, NULL, 'w', 'zulu');
"

예상 관찰: 두 insert가 서로 다른 range의 data file을 만든다. File merge 설정에 따라 물리 file 수는 달라질 수 있으므로 metadata 결과를 기준으로 판단한다.

2단계 · Human-readable metric 읽기

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SELECT file_path, record_count, file_size_in_bytes,
       readable_metrics['id'] AS id_metric,
       readable_metrics['score'] AS score_metric,
       readable_metrics['note'] AS note_metric,
       readable_metrics['payload'] AS payload_metric
FROM local.day11.metrics_lab.files ORDER BY file_path;

EXPLAIN EXTENDED SELECT * FROM local.day11.metrics_lab WHERE id = 101;
SELECT * FROM local.day11.metrics_lab WHERE id = 101;
SELECT count(*) FROM local.day11.metrics_lab WHERE note IS NULL;
"

예상 관찰: ID range가 겹치지 않는 file은 id = 101 후보에서 제외할 수 있다. Note의 null count가 0인 file은 IS NULL 후보가 아니다. Score의 NaN/null count는 bounds와 별도로 보인다.

3단계 · Field ID key 확인

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SELECT file_path, value_counts, null_value_counts,
       nan_value_counts, lower_bounds, upper_bounds
FROM local.day11.metrics_lab.files ORDER BY file_path;
ALTER TABLE local.day11.metrics_lab RENAME COLUMN note TO memo;
SELECT file_path, readable_metrics['memo'] AS memo_metric
FROM local.day11.metrics_lab.files ORDER BY file_path;
"

예상 관찰: Raw map은 숫자 field ID가 key다. Rename 뒤 old file을 rewrite하지 않아도 같은 field ID metric이 새 이름 memo로 해석된다.

실패 주입 · payload metric 수집 중단

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
ALTER TABLE local.day11.metrics_lab SET TBLPROPERTIES
  ('write.metadata.metrics.column.payload'='none');
INSERT INTO local.day11.metrics_lab VALUES
  (1000, 99.0, 'metric-off', 'needle');

SELECT file_path, readable_metrics['payload'] AS payload_metric
FROM local.day11.metrics_lab.files ORDER BY file_path;
EXPLAIN EXTENDED SELECT * FROM local.day11.metrics_lab
WHERE payload = 'needle';
SELECT count(*) AS exact_rows FROM local.day11.metrics_lab
WHERE payload = 'needle';
"

예상 관찰: 새 file의 payload metric은 없고 query는 여전히 정확한 2 rows를 반환한다. Planner는 새 file을 metric으로 제외할 수 없어 false positive I/O를 허용한다. Missing은 “needle 없음”이 아니다.

자주 나는 오류와 해결

  • readable_metrics column 없음: DESCRIBE local.day11.metrics_lab.files로 runtime metadata-table schema를 확인한다.
  • Map key 오류: Raw maps는 column 이름이 아닌 field ID가 key다. Human-readable projection을 우선 사용한다.
  • NaN cast 오류: Runtime에 맞춰 CAST('NaN' AS DOUBLE) 또는 지원되는 literal syntax를 확인한다.
  • File이 예상보다 많음: Writer task/partition 수와 append별 file을 metadata path로 대조한다. 실습 목적은 정확한 file 개수가 아니라 range 차이다.
  • Explain에 file 수가 안 보임: Engine의 scan report/metrics를 사용하고, files table의 interval로 후보를 직접 계산한다.
  • Docker 연결 실패: Docker daemon을 시작하고 make smoke가 성공한 뒤 재개한다.

8. 놓치기 쉬운 함정

  1. Bounds 안에 값이 있으면 row가 존재한다. 존재 가능성만 남을 뿐 exact membership은 아니다.
  2. Missing metric은 0이다. Unknown이므로 안전하게 file을 유지해야 한다.
  3. Value count는 non-null count다. Null과 NaN도 포함한다.
  4. NaN은 min/max에 들어간다. Spec상 bounds에서 제외되고 별도 count로 추적한다.
  5. Record count는 현재 live row 수다. MOR delete/DV 적용 전 file record 수일 수 있다.
  6. Metric map key는 column 이름이다. V3 이하에서는 field ID다.
  7. Full metric이 항상 최선이다. Write/metadata/privacy 비용과 query 가치의 trade-off다.
  8. Spec 지원은 engine 지원이다. Format version과 Spark/Flink/Trino connector 구현을 분리한다.

9. 대기업 기술 면접 수준 질문

Q1. “File metrics로 pruning해도 query correctness가 유지되는 이유를 증명하세요.”

좋은 답변 구조: 10억 file·predicate 가정 → conservative interval 불변식 → partition/manifest/file/row-group 순서 → missing metric 처리 → false positive 허용/false negative 금지 → null/NaN/truncate edge → bad writer 검증과 rollback.

Q2. “Metrics mode를 column별로 설계하세요.”

좋은 답변 구조: Query log와 filter selectivity 수치 → key/time/category/payload 분류 → full/truncate/counts/none → manifest/write CPU/storage/privacy 비용 → canary와 candidate-file SLO → schema evolution·multi-engine compatibility → external index 대안.

Q3. “Data file record_count 합이 COUNT(*)와 다른 장애를 분석하세요.”

좋은 답변 구조: Snapshot 고정 → data/delete files와 sequence → COW/MOR/DV 구분 → position/equality delete 적용 → partition/spec/field ID → metadata table 증거 → 안전한 read 검증 → compaction/rollback과 하지 말아야 할 수동 수정.

10. 어제 내용 회상 3문제

  1. Manifest list와 manifest entry는 각각 무엇을 색인하는가?
  2. ADDED/EXISTING/DELETED는 물리 file 상태인가, snapshot 기준 membership delta인가?
  3. Added entry의 null sequence를 어떻게 해석해야 하는가?
짧은 정답/채점 기준
① Manifest list=manifest index, manifest entry=data/delete file record와 metric이라고 구분하면 2점.
② Snapshot에서 manifest가 추가될 때의 logical delta이며 DELETED가 즉시 object 삭제를 뜻하지 않는다고 답하면 2점.
③ Manifest-list context의 snapshot/data/file sequence를 상속하며 raw null=unknown이 아니라고 답하면 3점.

11. 오늘 내용 확인 문제 3개

  1. Bound [100, 200]인 file을 id = 42에서 제외해도 되는 이유는?
  2. Null count가 missing일 때 IS NULL query에서 어떻게 해야 하는가?
  3. Data file record_count 합과 현재 COUNT(*)가 달라질 수 있는 이유는?
짧은 정답/채점 기준
① 42가 conservative lower bound보다 작아 어떤 non-null 값도 match할 수 없다고 설명하면 2점.
② Missing=unknown이므로 file을 후보로 유지하고 row predicate를 평가한다고 답하면 2점.
③ MOR equality/position delete 또는 DV가 물리 data row를 logical view에서 제외할 수 있다고 답하면 3점.
