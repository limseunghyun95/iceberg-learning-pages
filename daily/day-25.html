snapshot/serializable isolation

Commit·Isolation·Concurrency · 예상 학습 40분 + 실습 35분

한 줄 요약
두 isolation 모두 committed snapshot을 일관되게 읽지만, serializable은 UPDATE·DELETE·MERGE 조건에 들어올 수 있는 concurrent data file 추가를 conflict로 막고 snapshot isolation은 이를 허용해 동시성을 높이는 대신 조건에 맞는 신규 row가 이번 operation에서 빠질 수 있다.

1. 선수 용어 사전

Isolation동시에 실행되는 transaction이 서로의 중간·완료 변화를 어느 범위까지 보거나 충돌로 판단할지 정한 규칙이다.
Snapshot특정 시점의 table file membership을 가리키는 immutable state node다. 물리 data를 복사한 백업이 아니라 manifest tree의 root다.
Snapshot isolationOperation은 시작 snapshot의 일관된 view를 읽고, 자신이 의존한 file을 concurrent delete/rewrite가 건드리면 실패한다. Concurrent matching add는 허용할 수 있다.
Serializable isolation성공한 operation들을 어떤 하나의 직렬 실행 순서로 설명할 수 있게 더 강하게 검증한다. 조건에 들어올 수 있는 concurrent add도 conflict다.
Phantom처음 scan에는 없었지만 concurrent insert로 predicate에 새로 들어온 row다. 예: 삭제 중인 날짜 범위에 늦게 들어온 event.
Write skew각 transaction이 서로 다른 row/file을 갱신해 직접 충돌은 없지만, 함께 commit되면 cross-row business invariant가 깨지는 anomaly다.
Predicate conflictConcurrent file의 partition/metric 범위가 UPDATE·DELETE·MERGE filter와 겹칠 가능성이 있어 해당 operation의 “모든 matching row 처리” 가정을 깨는 상태다.
Linearization pointCatalog가 expected metadata pointer를 새 metadata로 atomic하게 바꾼 순간이다. Validation 통과나 file PUT만으로는 commit 성공이 아니다.

2. 왜 중요한가

Isolation은 “정합성 on/off” 설정이 아니다. 더 강한 serializable은 phantom을 막아 조건 기반 operation의 의미를 지키지만, late ingestion과 UPDATE/DELETE/MERGE가 같은 범위를 자주 건드리면 validation 실패와 재계획 비용이 늘어난다. Snapshot isolation은 concurrent writer가 많은 환경에서 성공률을 높일 수 있지만, 신규 matching row가 이번 operation에서 빠져도 업무상 허용되는지 따져야 한다.

예를 들어 event_date='2026-08-26' 범위를 GDPR DELETE하는 동안 같은 날짜의 late event가 들어왔다고 하자. Serializable은 새 file이 delete predicate와 겹칠 수 있으므로 delete를 실패시켜 latest snapshot에서 다시 계획하게 한다. Snapshot isolation은 기존 source file이 concurrent delete되지 않았다면 delete를 commit할 수 있고, late row는 남을 수 있다. 후자가 허용되는지는 재처리 SLA와 삭제 보장에 달려 있다.

이름에 속지 말자: “Snapshot”은 약한 read consistency가 아니다. 두 수준 모두 reader에게 committed snapshot의 일관된 view만 보여준다. 차이는 주로 row-level writer가 commit 때 concurrent matching data를 얼마나 엄격히 검증하는가에 있다.

번호별 요청·응답·상태 변화

  1. Plan at S0: W1은 P를 partition transform과 file metric에 투영해 read set을 고정한다. COW는 matching data file을 읽어 replacement를 만들고, MOR는 delete file을 준비한다.
  2. Concurrent add: W2는 F1을 manifest에 추가하고 catalog CAS로 S1을 publish한다. F1의 bounds나 partition tuple이 P와 겹칠 수 있다.
  3. Serializable validation: W1은 base snapshot 이후 added data file이 P와 충돌할 수 있는지 보수적으로 검사한다. 가능성이 있으면 실제 row를 전부 읽지 않아도 실패한다.
  4. Snapshot validation: W1이 의존하거나 제거하는 file을 concurrent delete/rewrite가 건드렸는지는 검사하지만, P와 겹치는 add만으로 반드시 실패하지 않는다. 따라서 F1 row는 W1의 효과를 받지 않을 수 있다.
  5. Commit: 어느 분기든 validation 통과 뒤 새 manifest list·snapshot·metadata JSON을 만들고 expected pointer CAS를 성공해야 한다. 그 전까지 output은 unreachable artifact다.
  6. Read: Reader는 load한 committed snapshot을 끝까지 사용한다. Refresh 전에는 S0, refresh 후에는 S1/S2를 보며 중간 상태를 섞어 보지 않는다.

Predicate validation은 왜 보수적인가

Iceberg는 F1 전체를 다시 읽지 않고 manifest의 partition tuple과 lower/upper bounds로 “P와 절대 겹치지 않는다”를 증명한다. 증명하지 못하면 serializable은 conflict로 판단할 수 있다. False positive conflict는 성능 손실이지만, false negative는 serializability 손실이다. 따라서 넓은 bounds, null/NaN, 낮은 clustering, 오래된 partition spec은 validation 충돌 범위를 키울 수 있다.

Per-operation isolation, general database transaction과의 차이

Iceberg의 설정은 주로 한 table의 UPDATE/DELETE/MERGE 또는 overwrite operation이 commit할 때 적용된다. 여러 SQL 문장과 여러 table의 cross-row business constraint를 자동으로 하나의 serializable database transaction으로 묶는다는 뜻이 아니다. “A와 B 중 최소 한 명은 on-call” 같은 invariant는 application coordination, branch, catalog의 multi-table capability 또는 별도 transaction layer가 필요하다.

COW·MOR·sequence 연결

COW는 base data file을 replacement로 바꾸므로 source file existence가 핵심이다. MOR는 delete file을 더하고 reader가 data와 delete를 합치므로 concurrent data file이 해당 delete의 적용 대상인지 sequence semantics가 중요하다. Snapshot isolation에서 허용된 F1이 delete보다 뒤 sequence를 받으면 이번 delete가 F1에 적용되지 않을 수 있다. 정확한 적용 규칙은 Day 26에서 이어간다. V3 deletion vector도 물리 표현은 달라도 data file identity와 applicability 불변식을 지켜야 한다.

5. 실무 설계 판단

Best practice 1 · invariant부터 선택: “이번 DELETE 종료 시 P row가 0이어야 한다”면 serializable을 우선한다. “시작 시점 S0의 row만 처리하고 late row는 다음 checkpoint가 처리해도 된다”면 snapshot이 가능하다.

Best practice 2 · 수치화: Conflict rate, replan 시간, late-arrival rate, predicate 폭, 삭제 완료 SLA, batch cadence를 기록한다. Isolation을 낮추기 전에 허용되는 phantom 수와 reconciliation 시간 상한을 명시한다.

Best practice 3 · 범위 축소: Partition transform과 sort order를 query pattern에 맞추고, broad full-table predicate보다 event-time watermark·business key 범위를 사용해 validation scan과 false-positive conflict를 줄인다.

Best practice 4 · reconciliation: Snapshot isolation을 쓴다면 batch ID/watermark와 post-condition query를 저장하고, late row를 잡는 second pass를 자동화한다. “다음번에 언젠가”는 정책이 아니다.

Apache Iceberg 1.11.0 기준: write.delete.isolation-level, write.update.isolation-level, write.merge.isolation-level의 문서 기본값은 serializable이며 값은 serializable 또는 snapshot이다. Spark DataFrame overwrite의 write option isolation-level은 별도 surface이고, validate-from-snapshot-id와 함께 base를 명시할 수 있다.

Multi-engine 차이: Table Spec은 optimistic commit의 기반을 정하지만, Spark·Flink·Trino·각 catalog가 row-level SQL, COW/MOR, isolation property와 exception을 같은 범위로 지원한다고 가정하지 않는다. Writer engine/version 조합별 concurrent test를 release gate로 둔다.

Maintenance race: Compaction은 source file replacement validation으로 실패할 수 있고, serializable predicate conflict와 별개 원인이다. Ingestion, delete, rewrite가 같은 hot partition을 동시에 건드리지 않게 scope·시간·branch를 조정한다.

Anti-pattern: Conflict가 귀찮다는 이유로 전체 table을 snapshot으로 낮추고 post-condition을 두지 않거나, serializable이면 cross-table business invariant까지 자동 보호된다고 믿는 것이다.

Edge case: Catalog timeout은 isolation conflict가 아니라 unknown commit state일 수 있다. Object storage PUT 성공도 logical commit 성공이 아니다. 먼저 current metadata와 operation identity로 status를 확인한다.

7. 35분 재현 실습

목표: 같은 stale base 뒤 matching file을 추가하고 DataFrame overwrite를 serializable/snapshot으로 각각 commit해 predicate conflict 차이를 의도적으로 만든다.

사전 조건과 실행 전 예측

  • Docker daemon과 프로젝트 Spark/Iceberg 환경이 준비되어 있고 make smoke가 성공해야 한다.
  • Serializable table은 concurrent matching add 뒤 overwrite가 실패하고, snapshot table은 commit될 가능성이 높다고 예측한다.
  • Snapshot table에서 late row가 남을지 replacement에 의해 사라질지 먼저 적고 실제 row·snapshot lineage로 판정한다.
  • DataFrame write option 지원은 Spark/Iceberg connector 버전에 의존한다. 학습 환경은 Iceberg 1.11.0 기준이다.

1단계 · Spark shell에서 stale-base 시나리오 실행

make smoke
docker compose up -d spark

docker compose exec -T spark /opt/spark/bin/spark-shell <<'SCALA'
import org.apache.spark.sql.functions.expr
import spark.implicits._

spark.sql("CREATE NAMESPACE IF NOT EXISTS local.day25")

def setup(name: String): Long = {
  spark.sql(s"DROP TABLE IF EXISTS $name PURGE")
  spark.sql(s"""
    CREATE TABLE $name (
      id BIGINT, region STRING, payload STRING
    ) USING iceberg
    PARTITIONED BY (region)
    TBLPROPERTIES ('format-version'='2')
  """)
  spark.sql(s"INSERT INTO $name VALUES (1, 'A', 'base')")
  spark.sql(s"""
    SELECT snapshot_id FROM $name.snapshots
    ORDER BY committed_at DESC LIMIT 1
  """).head.getLong(0)
}

def staleOverwrite(name: String, level: String): Unit = {
  val base = setup(name)
  spark.sql(s"INSERT INTO $name VALUES (2, 'A', 'late-after-base')")
  val replacement = Seq((100L, "A", s"replacement-$level"))
    .toDF("id", "region", "payload")
  try {
    replacement.writeTo(name)
      .option("isolation-level", level)
      .option("validate-from-snapshot-id", base.toString)
      .overwrite(expr("region = 'A'"))
    println(s"RESULT $level: COMMIT SUCCEEDED")
  } catch {
    case e: Throwable =>
      println(s"RESULT $level: ${e.getClass.getSimpleName}: ${e.getMessage}")
  }
  spark.sql(s"SELECT * FROM $name ORDER BY id").show(false)
  spark.sql(s"""
    SELECT committed_at, snapshot_id, parent_id, operation
    FROM $name.snapshots ORDER BY committed_at
  """).show(false)
}

staleOverwrite("local.day25.serializable_lab", "serializable")
staleOverwrite("local.day25.snapshot_lab", "snapshot")
System.exit(0)
SCALA

예상 관찰: Serializable은 base 이후 region A에 추가된 file이 overwrite predicate와 겹쳐 validation failure를 내야 한다. Snapshot은 concurrent add만으로는 같은 검사를 강제하지 않아 commit될 수 있다. 실제 row 결과는 connector 구현과 overwrite plan을 함께 기록하고, 성공/실패 문구만 보지 않는다.

채점 기준: Serializable 실패는 corruption이 아니라 business predicate 보존을 위한 safe abort다. Snapshot 성공은 더 “정확하다”는 뜻이 아니라 concurrent add를 허용한 계약이다. 두 table 모두 reader는 partial snapshot을 보지 않는다.

실패 주입과 대안

  • 의도적 stale base: Initial snapshot ID를 저장한 뒤 matching append를 먼저 commit하고 그 오래된 ID로 overwrite validation을 시작한다.
  • Serializable도 성공: Connector가 해당 DataFrame option을 지원하지 않거나 predicate/file metric이 겹치지 않은 것일 수 있다. SHOW TBLPROPERTIES, runtime version, log를 보존하고 row-level DELETE table property 실습으로 교차 검증한다.
  • Snapshot도 실패: Concurrent add가 아니라 source delete/CAS 또는 overwrite plan validation이 원인일 수 있다. Exception의 validator 이름과 snapshot diff를 확인한다.

자주 나는 오류와 해결

  • Unknown option: Iceberg runtime이 1.11.0인지 확인하고 Spark DataSource V2 경로를 사용한다.
  • AnalysisException: Catalog와 SQL extensions 설정을 make smoke 및 프로젝트 compose config로 확인한다.
  • getLong type 오류: DESCRIBE local.day25.serializable_lab.snapshots로 snapshot_id type을 확인한다.
  • Both results identical: Message와 lineage, final rows를 모두 비교한다. Isolation 차이는 항상 row count 하나로만 드러나지 않는다.
  • Production과 다름: Hadoop catalog 학습 결과를 REST/Glue/Hive catalog의 conflict wrapping·retry와 동일시하지 않는다.

8. 놓치기 쉬운 함정

  1. Snapshot isolation reader는 dirty data를 본다. 두 수준 모두 committed snapshot만 본다.
  2. Serializable이면 lock을 오래 잡는다. Iceberg는 optimistic validation과 atomic metadata swap으로 구현한다.
  3. Snapshot은 source delete도 무시한다. 자신이 의존한 file의 conflicting delete/rewrite는 여전히 안전하지 않다.
  4. Serializable이면 multi-table ACID다. 보장은 operation·table·connector surface를 벗어나 자동 확장되지 않는다.
  5. Conflict가 많으면 isolation을 낮추면 된다. 업무 invariant와 reconciliation SLA가 먼저다.
  6. File metric overlap은 실제 row conflict 확정이다. 보수적 가능성 판정이라 false positive가 있을 수 있다.
  7. COW와 MOR 결과는 같다. Artifact와 sequence/delete applicability가 달라진다.
  8. CAS timeout은 isolation failure다. Commit 성공 여부가 불명인 unknown state이므로 status check가 먼저다.

9. 대기업 기술 면접 질문 3개

  1. Snapshot isolation과 serializable isolation의 차이를 Iceberg file validation으로 설명하라.
    좋은 답변 구조: Committed S0 read → predicate/read set → concurrent matching add와 source delete → 두 분기 → CAS linearization → phantom·throughput trade-off.
  2. GDPR DELETE와 late ingestion이 경쟁한다. 어떤 isolation과 운영 정책을 선택할 것인가?
    좋은 답변 구조: 삭제 SLA·late rate 수치 → predicate 범위 → serializable safe abort → snapshot+watermark/second pass 대안 → COW/MOR 비용 → post-condition·감사 증거.
  3. Serializable conflict가 20%다. Isolation을 낮추지 않고 개선하라.
    좋은 답변 구조: λ·stale window·bounds 측정 → partition/sort/predicate scope → maintenance 분리 → batch coalescing/backoff → false-positive 분석 → canary와 correctness gate.

10. 어제 내용 회상 3문제

  1. Append CAS conflict와 overwrite semantic conflict는 어떻게 다른가?
  2. Specific file delete와 expression delete의 retry validation 차이는?
  3. Validation 통과 뒤에도 commit 성공이 아닌 이유는?
짧은 정답/채점 기준
  1. Append는 add-only라 새 current에 합칠 수 있지만 overwrite는 source/predicate 변화가 lost update를 만들 수 있다. Read/write set 교집합이 핵심.
  2. Specific file delete는 대상 file이 live인지 검사하고, expression delete는 current에 재적용 가능하되 row-level isolation은 matching add를 추가 검사한다. Spec/engine 층을 구분하면 정답.
  3. 새 metadata pointer의 conditional catalog swap이 아직 남아 있다. CAS=linearization point가 핵심.

  3. Snapshot isolation을 선택할 때 반드시 함께 설계할 운영 장치는?
짧은 정답/채점 기준
  1. Operation이 load한 committed snapshot의 일관된 view이며 partial/uncommitted file set은 보지 않는다. Committed snapshot을 말하면 정답.
  2. UPDATE/DELETE/MERGE predicate에 match할 수 있는 concurrent data file 추가다. Phantom add가 핵심.
  3. Watermark/batch ID, post-condition query, late row second pass와 완료 SLA다. Reconciliation을 구체화하면 정답.
