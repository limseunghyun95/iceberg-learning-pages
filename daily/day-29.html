APACHE ICEBERG · WEEK 5 / DAY 29

copy-on-write vs merge-on-read

Row-level Update/Delete와 Format Version · 예상 학습 40분 + 실습 35분

한 줄 요약
Copy-on-write(COW)는 변경이 닿은 data file을 즉시 다시 써 read path를 단순하게 만들고, merge-on-read(MOR)는 기존 data file을 유지한 채 delete file과 새 row를 commit해 write latency를 낮추는 대신 reader와 compaction에 병합 비용을 넘긴다.

1. 선수 용어 사전

Row-level mutationTable의 일부 row만 UPDATE·DELETE·MERGE하는 변경이다. Iceberg data file은 immutable이므로 같은 bytes를 제자리 수정하지 않는다.
Copy-on-write (COW)변경 row가 들어 있는 data file을 읽고, 살아남은 row와 수정 row를 새 data file로 복사한 뒤 old file을 metadata에서 제거하는 방식이다.
Merge-on-read (MOR)기존 data file을 유지하고 삭제 표식을 delete file에 기록한다. UPDATE는 old row 삭제 표식과 new row data를 함께 commit하며 reader가 scan 중 합친다.
Delete fileV2에서 도입된 row 삭제 정보다. Position delete는 file path+row position, equality delete는 field ID로 식별한 key 값을 저장한다.
Write amplification논리적으로 바꾼 bytes보다 물리적으로 읽고 다시 쓴 bytes가 더 큰 현상이다. 큰 file의 row 1개 COW 수정이 대표적이다.
Read amplification질의 결과에 필요한 data 외에 delete file을 열고 매칭·필터링하는 추가 I/O·CPU·memory 비용이다.
CompactionSmall data/delete file을 더 큰 data file로 다시 써 scan 비용을 회수하는 maintenance다. MOR 비용이 사라지는 것이 아니라 뒤로 이동한 것이다.
Mode propertywrite.delete.mode, write.update.mode, write.merge.mode가 SQL operation별 전략을 선언한다. 실제 지원은 engine·connector·format version을 함께 확인한다.

2. 왜 중요한가

“COW가 빠른가, MOR가 빠른가”라는 질문에는 workload가 빠져 있다. 하루 한 번 읽는 CDC table이라면 MOR의 낮은 write latency가 유리할 수 있지만, 수천 개 dashboard query가 같은 file을 반복 읽는다면 delete merge 비용이 쓰기 절감액을 넘어선다. 반대로 512MB file의 row 1개를 자주 고치는 table에서 COW를 고집하면 매 mutation마다 수백 MB를 읽고 쓰게 된다.

이 선택은 단순 성능 knob가 아니다. Snapshot이 참조하는 file 종류, reader가 지켜야 할 불변식, conflict validation 범위, maintenance 주기, multi-engine 호환성과 장애 복구 절차가 바뀐다. 그래서 “writer가 빨랐다”가 아니라 end-to-end read/write/maintenance 비용과 freshness SLO를 함께 측정해야 한다.

핵심 판단: COW는 변경 비용을 commit 전에 지불해 current snapshot을 self-contained한 data file 집합으로 만들고, MOR는 변경 의도를 별도 artifact로 commit해 reader가 snapshot 일관성 아래 data+delete를 결합하도록 한다.

번호별 요청·응답·상태 변화

  1. Plan: Engine은 current snapshot을 고정하고 predicate·partition·metrics로 candidate data file을 찾는다. Mode property는 control path의 전략 선택이고, row bytes는 아직 바뀌지 않는다.
  2. COW prepare: Candidate file 전체를 읽어 변경되지 않은 row도 복사한다. 바꾼 row가 적을수록 logical change 대비 physical I/O 비율이 커진다.
  3. MOR prepare: Existing data file은 유지한다. DELETE는 delete artifact를, UPDATE는 old row delete와 new row data를 만든다. Writer는 빠르지만 file fan-out이 늘 수 있다.
  4. Commit: 두 방식 모두 immutable artifact와 새 metadata graph를 준비한 뒤 catalog CAS로 공개한다. COW/MOR도 atomicity와 optimistic conflict validation을 우회하지 않는다.
  5. Read: COW reader는 current data file만 읽는다. MOR reader는 manifest pruning 후 data file별 적용 가능한 delete를 sequence·partition·file scope로 붙이고 row를 제거한다.
  6. Compact: MOR delta가 누적되면 maintenance writer가 data+delete를 읽어 새 base data file을 쓴다. 이 동안 concurrent commit validation과 snapshot retention race를 관리해야 한다.

간단한 비용 모델

영향 data file 크기를 F, 변경 bytes를 Δ, delete artifact를 X, 해당 snapshot을 읽는 query 수를 Q라 하자. 대략 COW mutation 비용은 read(F)+write(F), MOR mutation 비용은 write(X+new rows)다. 반대로 query당 COW 추가 merge는 거의 0이고 MOR는 read(X)+match(data,X)를 지불한다. 총비용은 storage 단가뿐 아니라 p95 latency, CPU, shuffle, compaction, cache hit와 재시도까지 포함한다.

예: 512MB file의 row 10개를 바꾸고 그 snapshot을 10,000번 읽는다면 COW는 한 번 큰 rewrite, MOR는 10,000번 delete 적용이 된다. 같은 table을 한 번만 읽고 계속 변경한다면 반대 결론이 날 수 있다. 따라서 “MOR=빠름”과 “COW=안전함” 같은 단일 라벨은 부족하다.

Data path와 control path

Data path: COW는 old data read → filter/update → new data write, MOR는 delete/new data write → read-time merge다. Control path: 두 모드 모두 base snapshot load → validation → manifests/metadata 생성 → catalog CAS다. 실패 window도 artifact PUT 전, PUT 후 CAS 전, CAS 응답 유실로 동일하나, MOR는 orphan 후보에 delete file이 추가된다.

5. 실무 설계 판단

판단 축COW 쪽 근거MOR 쪽 근거
Read:write 비율Read-heavy, p95 query SLO 엄격Write-heavy, mutation freshness 우선
변경 밀도File의 큰 비율을 바꿔 rewrite 낭비가 작음큰 file의 극소수 row만 변경
Engine 집합Delete 지원이 제각각인 multi-engine모든 reader가 같은 delete feature를 검증
Maintenance별도 compaction 운영 여력이 낮음Delete/file SLO와 compaction budget 보유
Conflict scopeHot file rewrite가 낮은 빈도Fine-grained delta가 유리하되 semantics 검증 필요

Best practice 1 · 모드를 operation별로 분리: DELETE, UPDATE, MERGE의 빈도와 행위를 따로 계측한다. 한 table에 세 property를 기계적으로 같은 값으로 맞출 필요는 없다.

Best practice 2 · file-level 지표: 변경 row 수뿐 아니라 scanned/replaced data bytes, added delete files, delete/data file ratio, query당 delete files opened, compaction lag, p95를 수집한다.

Best practice 3 · MOR 예산: Partition/file별 delete file 수나 deleted-row ratio가 threshold를 넘으면 compaction을 예약한다. Fixed cron만 쓰면 hotspot과 한산한 partition을 동일하게 취급한다.

Best practice 4 · 호환성 gate: Spark·Flink·Trino 등 모든 reader/writer의 format version과 delete/DV 지원을 staging에서 교차 검증한다. Spec이 허용한다는 사실과 배포 engine이 구현했다는 사실을 분리한다.

Apache Iceberg 1.11.0 기준: write.delete.mode, write.update.mode, write.merge.mode 기본은 copy-on-write이며 merge-on-read 선택은 v2 이상으로 문서화되어 있다. Spark의 row-level SQL은 Iceberg SQL extensions가 필요하다.

Format 경계: V1은 row-level delete file을 지원하지 않는다. V2는 position/equality delete를, V3는 deletion vector를 추가하며 새 position delete 추가를 금지한다. 오늘의 COW/MOR 논리는 공통이지만 실제 delta artifact와 reader 알고리즘은 version별로 다르다.

Anti-pattern: Write latency 하나만 보고 MOR 전환, delete file 개수 무제한 방치, COW를 row 1개 CDC에 사용, raw Parquet reader 병행, property만 바꾸고 기존 delta를 즉시 사라졌다고 가정하는 것이다.

Edge case: Predicate가 partition 전체를 정확히 제거하면 engine은 metadata-only delete로 file reference만 제거할 수 있다. 이때 row-level COW/MOR 비교 자체가 적용되지 않으므로 snapshot summary와 file diff를 먼저 본다.

6. 장애 대응 표

상황: MOR 전환 뒤 query가 느려지거나 engine별 row count가 달라졌다.

증상Read p95·planning time 급증, delete file open/bytes 증가, OOM·spill, Spark와 다른 engine의 row count 불일치, deleted row 재등장, compaction conflict, referenced delete file 404.
먼저 수집할 증거/지표Snapshot ID·sequence·operation/summary, table format/property history, data/delete manifests와 content type, file별 record_count/size/partition, query plan·delete planning mode·opened files·spill, engine/connector version, compaction job base/current metadata, object HEAD/404.
가능한 가설Delete file 누적, equality key의 낮은 선택도, position path mismatch, sequence 적용 오류/미지원 reader, V2/V3 feature 불일치, compaction 지연·충돌, premature cleanup, stale catalog cache, raw Parquet 우회.
안전한 첫 조치영향 snapshot과 engine을 pin하고 mutation/cleanup을 일시 중지한다. Known-good Iceberg reader로 row count와 metadata files를 교차 확인하고, dry-run 성격으로 compaction 후보·비용을 산정한다.
rollback/복구호환 reader로 우회하거나 검증된 rewrite로 data+delete를 새 base file에 materialize한다. 잘못된 snapshot은 reference 보존 후 rollback/forward fix하고, 404 artifact는 동일 URI 복원 또는 안전 snapshot으로 되돌린다. 이후 COW 기본값과 threshold를 조정한다.
하지 말아야 할 조치Raw data file만 읽어 delete를 무시하지 않는다. Manifest/sequence를 수동 편집하거나 delete file을 직접 지우지 않는다. Blind VACUUM·orphan cleanup, 전체 table 무계획 rewrite, validation 비활성화, 지원 미확인 engine 재투입을 하지 않는다.

7. 35분 재현 실습

목표: 같은 1,000-row dataset을 COW/MOR table에 넣고 row 1개를 삭제한다. 두 query 결과는 같지만 current file graph가 COW의 data rewrite와 MOR의 data+delete로 달라지는지 확인한다.

사전 조건과 실행 전 예측

  • Docker Desktop이 정상이고 프로젝트 make smoke가 성공해야 한다. Lab은 Spark SQL extensions와 Iceberg 1.11.0 runtime을 사용한다.
  • 두 table의 final count는 999다. COW에는 current delete file이 0개, MOR에는 1개 이상이 생길 것이라고 먼저 적는다.
  • COW data file의 record count는 999로 바뀌고, MOR base data file은 1,000 row를 유지한 채 delete artifact가 1 row를 가리킬 것으로 예상한다. Task/file 수에 따라 물리 file 개수는 달라질 수 있다.

make smoke

TBLPROPERTIES (

  'write.update.mode'='merge-on-read',
  'write.merge.mode'='merge-on-read'
);

INSERT INTO local.day29.cow
SELECT /*+ REPARTITION(1) */ id, concat('v-', cast(id AS STRING)) FROM range(0, 1000);
INSERT INTO local.day29.mor
SELECT /*+ REPARTITION(1) */ id, concat('v-', cast(id AS STRING)) FROM range(0, 1000);
"

3단계 · Current file graph 비교

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
SELECT 'cow' AS mode, content, count(*) AS files,
       sum(record_count) AS records, sum(file_size_in_bytes) AS bytes
FROM local.day29.cow.files GROUP BY content
UNION ALL
SELECT 'mor' AS mode, content, count(*) AS files,
       sum(record_count) AS records, sum(file_size_in_bytes) AS bytes
FROM local.day29.mor.files GROUP BY content
ORDER BY mode, content;

SELECT committed_at, operation, summary
FROM local.day29.cow.snapshots ORDER BY committed_at;
SELECT committed_at, operation, summary
FROM local.day29.mor.snapshots ORDER BY committed_at;
"

예상 관찰: content=0은 data, V2의 content=1은 position delete, content=2는 equality delete다. COW는 current data만, MOR는 base data와 delete가 함께 보인다. Snapshot summary의 added/removed data/delete file 수가 전략의 증거다.

4단계 · Failure injection: MOR delta 누적

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
DELETE FROM local.day29.mor WHERE id = 43;
DELETE FROM local.day29.mor WHERE id = 44;
DELETE FROM local.day29.mor WHERE id = 45;

SELECT content, count(*) AS files, sum(record_count) AS records,
       sum(file_size_in_bytes) AS bytes
FROM local.day29.mor.files GROUP BY content ORDER BY content;

EXPLAIN FORMATTED
SELECT * FROM local.day29.mor WHERE id BETWEEN 40 AND 50;
"

관찰: 작은 logical deletes가 여러 snapshot/delete artifact로 누적될 수 있다. Query 결과는 맞아도 planning·file open·merge 비용은 증가한다. Exact file 수는 engine batching과 distribution에 따라 달라지므로 “몇 개”보다 data/delete 비율과 추세를 본다.

자주 나는 오류와 해결

  • DELETE syntax/extension 오류: spark.sql.extensions와 catalog 설정을 확인하고 make smoke를 다시 실행한다.
  • MOR에도 delete file이 없음: Property 오타, format-version, metadata-only delete 여부, engine connector 버전을 확인한다. Unpartitioned row 1개 조건은 metadata-only가 아니어야 한다.
  • Data file이 여러 개: Spark task/AQE가 hint를 조정할 수 있다. File 수 자체가 아니라 current content와 record 합계를 비교한다.
  • 두 count가 다름: 동일 snapshot을 읽는지, catalog cache와 reader의 delete 지원을 확인한다. Raw Parquet path로 검증하지 않는다.
  • EXPLAIN에 delete가 명시되지 않음: Plan 표시는 engine 버전별로 다르다. Metadata table과 scan metrics를 함께 사용한다.

8. 놓치기 쉬운 함정

  1. COW는 in-place update다. 아니다. Immutable old file을 새 file로 교체한다.
  2. MOR는 read할 때 SQL update를 다시 계산한다. 아니다. Committed delete/new-data artifact를 deterministic하게 적용한다.
  3. MOR는 항상 더 싸다. Write 비용을 read와 compaction으로 옮긴다.
  4. Property를 MOR로 바꾸면 기존 file이 변환된다. 이후 operation 전략만 바뀌며 기존 snapshot/file은 그대로다.
  5. Reader가 Parquet를 읽으면 충분하다. Delete manifest·scope·sequence를 해석하지 못하면 deleted row가 보인다.
  6. Delete file 수만 작으면 건강하다. Size, deleted-row ratio, key selectivity, data file fan-out과 query 횟수도 봐야 한다.
  7. Compaction은 metadata-only다. Data+delete를 읽고 새 data를 쓰는 큰 write이며 conflict·orphan window가 있다.
  8. V3는 MOR 비용을 없앤다. DV가 position representation을 효율화하지만 reader merge와 synchronous maintenance 책임은 남는다.

9. 대기업 기술 면접 질문

  1. 하루 10억 건 append, 1천만 건 CDC, dashboard QPS 500인 table의 COW/MOR를 선택하라.
    좋은 답변 구조: Freshness·p95·cost SLO → file size/변경 밀도/Q 수치 → operation별 mode → data/delete read path → compaction threshold → multi-engine gate → failure/rollback과 대안.
  2. MOR 전환 뒤 p95가 3배가 됐다. Root cause와 안전한 복구를 설명하라.
    좋은 답변 구조: Snapshot pin → delete file/bytes/selectivity/plan evidence → sequence·engine 호환 가설 → staged compaction → COW fallback → concurrent writer validation → SLO 재검증.
  3. COW와 MOR의 linearization point와 conflict 차이를 설계 리뷰하라.
    좋은 답변 구조: 공통 catalog CAS → prepared artifact 차이 → read/write set과 isolation → explicit/unknown failure → orphan 종류 → retry/replan → correctness와 throughput trade-off.

10. 복습과 정답

어제 내용 회상 3문제

  1. Object storage에 data file이 있지만 current catalog pointer에서 도달할 수 없다면 table row인가?
  2. CAS 요청 뒤 timeout이 났을 때 같은 batch를 즉시 다시 append하면 안 되는 이유는?
  3. Orphan cleanup 전에 확인할 두 축은?

짧은 정답: ① 아니다. Reachable metadata graph가 membership의 권위자다. ② CAS 성공 후 응답만 유실됐을 수 있어 중복 commit 위험이 있다. Operation identity로 status check한다. ③ 모든 valid refs에서의 reachability와 active writer·retry를 덮는 safety window다.

정답/채점: ① COW는 affected data file을 새 data file로 rewrite하고 old reference를 제거한다. MOR는 old data를 유지하고 delete file을, UPDATE라면 new row data도 쓴다. ② Snapshot에 적용 가능한 모든 delete를 반영한 logical row set을 반환해야 한다는 불변식이다. ③ Read:write 비율, 변경 밀도/affected bytes, delete file·bytes/ratio, query p95, compaction lag, engine 호환 중 세 가지 이상과 이유를 말하면 만점.
