랩: SQL 한 번마다 생기는 파일 추적

Lakehouse와 Table Format 정신 모델 · 예상 학습 25분 + 실습 35분

한 줄 요약
SQL의 효과는 “파일이 생겼다”가 아니라 catalog pointer가 가리키는 immutable metadata graph의 전후 차이로 판정한다. CREATE는 최초 metadata를, INSERT는 data file과 snapshot chain을 만들고, SELECT와 분석 단계에서 실패한 INSERT는 table state를 바꾸지 않는다.

1. 선수 용어 사전

Checkpoint실험의 한 시점에서 SQL 결과, current snapshot, metadata row와 warehouse file 목록을 함께 저장한 관찰 지점이다.
State diff두 checkpoint 사이에 추가·제거·변경된 상태의 차이다. File 수만이 아니라 pointer, snapshot, manifest와 row를 비교한다.
Control path무엇이 table의 현재 상태인지 결정하는 경로다. Catalog pointer → metadata JSON → snapshot → manifest list → manifest 순서다.
Data path실제 row byte를 읽고 쓰는 data/delete file 경로다. Control path가 선택한 file만 table scan에 참여한다.
Linearization point동시 작업 사이에서 commit이 한순간에 성공한 것으로 간주되는 지점이다. Iceberg에서는 catalog의 current metadata pointer가 원자적으로 교체되는 순간이다.
Invariant모든 정상 상태에서 반드시 지켜져야 하는 조건이다. 예: current snapshot의 manifest에서 도달 가능한 data file만 현재 table row를 구성한다.
Orphan candidateStorage에는 있지만 유효한 metadata graph에서 보이지 않는 file 후보다. 진행 중 writer와 retained snapshot을 확인하기 전에는 삭제 대상이 아니다.

2. 왜 중요한가

데이터 엔지니어는 “INSERT가 성공했다”는 console 문구보다 강한 증거가 필요하다. Data file upload 뒤 catalog commit이 실패할 수 있고, 반대로 catalog commit 뒤 client response가 끊기면 실패처럼 보여도 새 snapshot은 이미 current일 수 있다. SQL 전후의 metadata graph를 저장하면 성공이 확정된 시점과 실패 window를 분리할 수 있다.

이 랩은 Week 1의 다섯 개 개념을 하나의 증거 사슬로 묶는다. Raw Parquet와 table state의 차이, file/table/catalog/engine/warehouse의 책임 경계, CREATE·INSERT·SELECT의 state transition, snapshot/time travel, metadata table과 실제 path mapping을 직접 검증한다.

판정 원칙: SQL 종료 코드 + current snapshot ID + metadata table diff + warehouse file diff를 함께 기록한다. 어느 하나만으로 commit 결과를 단정하지 않는다.

3. 아키텍처 그림과 요청 흐름

⓪ T0 · Baseline

번호별 요청·응답·상태 변화

  1. T0: Table path와 catalog entry가 없는 기준 상태를 저장한다. 이 기준이 없으면 기존 file을 이번 SQL의 산출물로 오판한다.
  2. CREATE: Engine이 schema의 stable field ID, partition transform/spec ID와 table property를 metadata JSON에 기록하고 catalog에 table identifier를 등록한다. 빈 table은 current snapshot이 없을 수 있다.
  3. INSERT #1: Writer task가 partition별 data file을 쓴다. Driver가 manifest와 manifest list, 새 metadata JSON을 준비한 뒤 base metadata location이 여전히 current인지 검증하고 pointer를 교체한다.
  4. INSERT #2: 새 snapshot은 parent S1을 가리킨다. 새 manifest와 기존 manifest를 함께 참조하거나 manifest merge를 할 수 있어 물리 file의 정확한 개수는 engine 설정과 task 수에 따라 달라진다.
  5. SELECT: Reader는 catalog → metadata JSON → current snapshot → manifest list → manifest → data/delete file 순서로 계획하고 metrics로 pruning한다. 정상 table SELECT는 새 snapshot을 만들지 않는다.
  6. Invalid INSERT: Column 수가 맞지 않아 Spark 분석 단계에서 거절되면 data write와 commit이 시작되지 않는다. 실패 시점이 더 늦다면 uncommitted file이 남을 수 있으므로 동일 결론을 일반화하지 않는다.

4. CS 관점의 내부 동작

SQL소유자·불변식·성공 확정
CREATECatalog가 identifier와 current metadata location을 소유한다. Metadata JSON이 schema/spec를 소유한다. Catalog create가 성공해 새 table을 load할 수 있을 때 확정된다.
INSERTStorage가 immutable object byte를, metadata graph가 membership을 소유한다. Base state conflict validation 후 pointer swap이 성공해야 row가 current가 된다.
SELECTReader는 선택한 snapshot의 일관된 view를 소유한다. 결과 전달은 query 성공이지만 table state 전환은 없다. Engine 임시 shuffle/cache file은 table metadata 밖의 상태다.
실패 write분석 전 실패, data write 후 실패, pointer swap 후 응답 유실을 구분한다. “Client가 오류를 봄”은 commit 실패와 동치가 아니다.

Persistent data structure와 optimistic transaction

Iceberg metadata tree는 기존 object를 덮어쓰지 않고 새 root를 만드는 persistent data structure와 닮았다. Writer는 base metadata를 읽고 새 data/delete file과 metadata를 만든다. Commit 시 catalog의 pointer가 여전히 base를 가리키는지 비교한 뒤 교체한다. Append는 재계획·재시도할 수 있는 경우가 있지만 overwrite/delete는 겹치는 file·partition·predicate에 대한 conflict validation 의미가 더 강하므로 blind retry하면 안 된다.

Catalog pointer → metadata JSON → snapshot → manifest list → manifest → data/delete file이 read path다. Manifest list와 manifest의 partition summary·field-ID 기반 lower/upper bounds는 두 단계 pruning을 돕는다. Partition evolution은 spec ID별 해석, schema evolution은 field ID별 해석이 필요하다. Sequence number는 이후 COW/MOR delete 및 v3 deletion vector의 적용 순서를 판단하는 핵심이다.

Failure window와 비용 trade-off

  • Data upload 전: Table state와 storage 모두 대체로 불변이다. Parser·analyzer 오류가 여기에 해당한다.
  • Data upload 후 pointer swap 전: Storage 비용은 생겼지만 table에는 보이지 않는 orphan 후보가 남을 수 있다.
  • Pointer swap 후 응답 전: Commit은 성공했지만 client는 timeout을 볼 수 있다. Operation identity와 새 snapshot을 먼저 조회한다.
  • 많은 작은 INSERT: Snapshot·manifest·data file이 빠르게 늘어 read planning과 storage 요청 비용이 증가한다. 큰 batch는 효율적이지만 latency와 retry 비용이 커진다.
  • Multi-engine: 같은 spec table이라도 metadata table schema, write distribution, manifest merge, refresh와 v2/v3 feature 지원은 connector/version별로 다르다.

5. 실무 설계 판단

판단Best practice와 이유
증거 단위Job/batch ID, 시작 base snapshot, 종료 current snapshot, operation summary, record/file count와 exact metadata location을 한 묶음으로 남긴다. Ambiguous commit을 재현할 수 있다.
Checkpoint 간격교육/incident 재현은 SQL 한 문장마다, production은 commit마다 snapshot metrics를 수집한다. Object 전체 listing은 비싸므로 sampling과 metadata table을 우선한다.
재시도 정책Append/overwrite/delete를 구분하고 source batch identity와 conflict scope를 검증한다. Timeout 직후 동일 INSERT를 실행하는 anti-pattern은 중복 append를 만든다.
운영 metricCommit latency/conflict, snapshot·manifest·data/delete file 증가량, 평균 file size, planning latency와 catalog/object-storage 오류율을 함께 본다.
호환성 gateSpark·Flink·Trino의 runtime/connector, format version, supported write/delete/DV, metadata table column과 refresh 동작을 표와 자동 test로 고정한다.

Anti-pattern: Warehouse file의 mtime 정렬을 commit 순서로 간주하고, 가장 최근 file을 수동 삭제하거나 metadata JSON을 편집하는 것. Object clock·retry·병렬 upload는 순서를 보장하지 않는다.

Edge case: SELECT 자체는 table state를 바꾸지 않지만 engine의 result cache, shuffle, spill, query history는 별도 시스템 상태를 만들 수 있다. “아무 file도 생기지 않는다”가 아니라 “Iceberg table graph가 바뀌지 않는다”가 정확하다.

6. 장애 대응 표

상황: INSERT client가 timeout됐고 warehouse에는 새 Parquet가 보이지만 row 반영 여부가 불명확하다.

증상Client timeout/connection reset, 새 storage file, source checkpoint 미진행, row 수 또는 engine별 결과 불일치.
먼저 수집할 증거/지표시작/현재 metadata location과 snapshot ID, snapshots/history/manifests/files 결과, snapshot summary의 operation·added files/records, exact object URI·mtime·size, job/batch ID, catalog audit/compare-and-swap 응답, writer log.
가능한 가설분석/계획 단계 실패, data upload 후 commit 실패, concurrent writer conflict, pointer swap 성공 후 응답 유실, stale catalog cache, 다른 catalog/namespace 관찰.
안전한 첫 조치동일 batch 재실행과 cleanup을 멈춘다. 새 session에서 catalog를 refresh/load하고 base 이후 snapshot의 summary와 source batch identity를 read-only로 대조한다.
Rollback/복구Commit 성공이면 source checkpoint를 idempotently 전진시키고 검증한다. 실패면 operation semantics에 맞게 재계획한다. 잘못된 중복 commit은 검증된 snapshot rollback 또는 조건부 overwrite/delete로 새 commit을 만들고, orphan은 safety window 뒤 정리한다.
하지 말아야 할 조치Timeout만 보고 즉시 INSERT를 반복하지 않는다. Warehouse file을 수동 table member로 만들거나 삭제하지 않는다. Current metadata pointer/JSON을 직접 수정하지 않는다. Active writer 중 orphan cleanup을 실행하지 않는다.

예상 관찰: Column 수 불일치로 분석 단계에서 실패하고 row는 3, snapshot은 2개, file diff는 비어 있다. 실패를 예측한 뒤 실행하고, 실제 error class와 어느 단계까지 진행했는지 기록한다.

자주 나는 오류와 해결

  • warehouse/day06가 없음: T0의 find 오류를 무시하는 것은 정상이다. CREATE 뒤 DESCRIBE TABLE EXTENDED의 Location을 확인한다.
  • Namespace path가 다름: Catalog warehouse 설정과 identifier mapping을 확인하고 실제 Location을 checkpoint 명령에 반영한다.
  • Metadata table column 오류: DESCRIBE local.day06.sql_trace.snapshots로 runtime schema를 확인한다. Connector/version별 column 차이를 기록한다.
  • Manifest/file 수가 예측과 다름: Partition, task 수, distribution mode, target file size와 manifest merge를 확인한다. 고정 개수보다 parent/path/reachability를 채점한다.
  • SELECT 뒤 diff가 있음: Table path가 아닌 engine temp/cache path를 섞지 않았는지 확인한다. Current snapshot ID가 바뀌었는지를 우선 본다.
  • Invalid INSERT가 다른 단계까지 진행: Runtime/SQL coercion 차이일 수 있다. Error log, snapshot/file diff를 보존하고 더 확실한 schema mismatch로 바꾸되 같은 실패를 반복하지 않는다.

8. 놓치기 쉬운 함정

  1. SQL 한 번이면 file 하나다. Partition과 task 수, manifest merge에 따라 여러 file이 생기거나 기존 manifest가 공유된다.
  2. CREATE는 아무 state도 만들지 않는다. Data snapshot은 없어도 catalog entry와 최초 metadata JSON은 생긴다.
  3. SELECT는 아무 file도 만들지 않는다. Iceberg table graph는 불변이지만 engine temp/cache/log는 별도다.
  4. 모든 실패 INSERT는 file을 만들지 않는다. 분석 전 실패와 data upload/commit 단계 실패는 failure window가 다르다.
  5. Client 성공/실패가 commit 결과다. Pointer swap과 response 사이 네트워크 오류 때문에 결과가 불명확할 수 있다.
  6. Warehouse 최신 file이 current다. Mtime이 아니라 catalog에서 metadata graph를 따라 reachability를 판정한다.
  7. 두 engine의 file count가 다르면 corruption이다. 같은 catalog pointer인지, cache/refresh와 metadata table 지원을 먼저 비교한다.
  8. 실패 뒤 보이는 file은 즉시 삭제한다. Active writer, retained snapshot/ref와 safety window 없이 삭제하면 정상 data를 잃는다.

9. 대기업 기술 면접 수준 질문

Q1. “하나의 INSERT가 성공하기까지 내부 경로와 확정 시점을 설명하세요.”

좋은 답변 구조: Batch 크기·partition/task 수 가정 → base metadata load → data file → manifest → manifest list → metadata JSON → optimistic conflict validation → catalog pointer swap이라는 linearization point → response 유실 failure window → snapshot summary와 batch identity 검증 → retry/rollback·small-file trade-off.

Q2. “Timeout 난 append를 안전하게 재처리하는 runbook을 설계하세요.”

좋은 답변 구조: Idempotency key/source checkpoint 요구 → 시작/현재 snapshot과 operation summary 수집 → catalog/object audit와 exact file path → 성공·실패·불명확 세 상태 → 성공이면 checkpoint 전진, 실패면 재계획 → 중복이면 새 corrective commit → orphan safety window → blind retry 대안과 RPO/RTO.

Q3. “하루 10만 commit 때문에 planning이 느려졌다면 무엇을 바꾸겠습니까?”

좋은 답변 구조: Commit rate, 평균 file/manifest size, latency SLO 수치 → snapshot/manifest/file growth 측정 → streaming trigger·batching·distribution/target size → manifest/data rewrite 순서와 concurrent maintenance race → latency·recovery granularity·write amplification trade-off → multi-engine compatibility와 rollback window.

10. 어제 내용 회상 3문제

  1. Warehouse file 존재가 current table membership의 충분조건이 아닌 이유는?
  2. files와 all_files metadata table은 관찰 범위가 어떻게 다른가?
  3. Partition evolution 뒤 old/new file을 directory 이름 하나로 해석하면 왜 위험한가?

짧은 정답/채점 기준

  1. Current snapshot의 manifest entry에서 도달 가능해야 membership이 생긴다고 답하면 통과.
  2. files는 current, all_files는 retained snapshots 전체의 tracked files라고 답하면 통과.
  3. Manifest마다 spec ID와 typed partition tuple로 해석해야 old/new transform을 함께 처리할 수 있다고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. CREATE, INSERT, SELECT 중 catalog pointer와 snapshot을 각각 어떻게 바꾸는가?
  2. INSERT client timeout 뒤 가장 먼저 반복하면 안 되는 행동과 먼저 수집할 증거는?
  3. 분석 단계 invalid INSERT의 T4→T5 diff가 비어 있어야 하는 이유는?

짧은 정답/채점 기준

  1. CREATE는 최초 metadata/catalog entry, INSERT는 새 snapshot과 pointer swap, SELECT는 table state 불변이라고 답하면 통과.
  2. Blind retry를 멈추고 base/current metadata location·snapshot, operation summary와 batch identity를 먼저 본다고 답하면 통과.
  3. Schema/arity 검증에서 data write·commit 전에 거절되어 current pointer와 warehouse table file이 변하지 않는다고 답하면 통과.
