APACHE ICEBERG · WEEK 4 / DAY 23

optimistic concurrency와 retry

Commit·Isolation·Concurrency · 예상 학습 35분 + 실습 35분

한 줄 요약
Iceberg의 optimistic retry는 CAS 실패 뒤 SQL을 무작정 다시 실행하는 일이 아니라, 비싼 immutable data file은 재사용하고 operation의 가정이 새 current state에서도 성립하는지 검증한 뒤 metadata tree만 다시 만들어 commit하는 transaction protocol이다.

1. 선수 용어 사전

Optimistic concurrencyLock을 오래 잡지 않고 충돌이 드물다고 가정해 작업을 먼저 준비한 뒤 commit 때 base가 여전히 유효한지 검사하는 방식이다.
Contention여러 writer가 같은 table pointer를 동시에 갱신하려 경쟁하는 상태다. Commit rate와 작업 시간이 길수록 충돌 확률이 커진다.
CAS conflictCompare-and-swap 시 expected base metadata가 더 이상 current가 아니어서 pointer 교체가 거절된 명시적 충돌이다.
AssumptionOperation이 안전하려면 참이어야 하는 조건이다. 예: rewrite 대상 source file이 아직 table에 포함되어 있다.
Action검증된 가정 위에서 적용할 metadata 변화다. 예: 새 data file 추가, source file 제거, schema/spec 교체.
Rebase / re-apply최신 metadata를 다시 읽고 이미 준비한 action을 새 base에 적용해 새 manifest list·snapshot·metadata JSON을 만드는 일이다.
Exponential backoffRetry 간 대기 시간을 점차 늘리고 jitter를 섞어 모든 writer가 동시에 재충돌하는 thundering herd를 줄이는 방식이다.
Retry budget횟수뿐 아니라 최소/최대 대기, 총 timeout, job SLA로 제한한 재시도 자원이다. 무한 retry는 장애를 지연시킬 뿐이다.

2. 왜 중요한가

큰 table write에서 가장 비싼 단계는 shuffle과 data/delete file 생성이다. 모든 commit conflict마다 이 작업을 처음부터 반복하면 비용과 지연이 폭증한다. 반대로 충돌을 무시하고 old base에서 만든 metadata를 강제로 publish하면 concurrent writer의 변화를 잃거나 이미 제거된 file을 부활시킬 수 있다.

Iceberg는 immutable output을 재사용 가능한 action으로 만들고, 최신 table state에서 operation별 assumption만 다시 검사한다. Append처럼 기존 file을 제거하지 않는 작업은 대체로 새 current에 추가하기 쉽지만, rewrite·overwrite·delete·schema/spec 변경은 겹치는 state를 더 엄격히 검증해야 한다. 그래서 retry 가능성은 error code가 아니라 transaction 의미가 결정한다.

핵심 구분: CAS conflict는 “다른 writer가 먼저 성공했다”는 확정 상태라 revalidation으로 간다. Network timeout은 내 CAS가 성공했을 수도 있는 unknown state라 status check가 먼저다.

3. 아키텍처 그림과 요청 흐름

① W1·W2가 같은 base M0/S0 load
schema/spec/snapshot + operation assumptions 고정
↓ 각자 unique immutable output 준비
② Data/delete file + manifest 준비
비싼 data plane work · 아직 logical visibility 없음
↓ W1 CAS(M0→M1) 성공
③ Current=M1/S1
W1 linearized · reader refresh 시 S1
↓ W2 CAS(M0→M2) conflict
④ Refresh + assumption validation
M1에서 action 재적용 가능한가?
↓ valid: metadata만 rebuild · invalid: abort
⑤ Backoff 후 CAS(M1→M2′)
성공 또는 retry budget 소진

번호별 요청·응답·상태 변화

  1. Base: 두 writer는 catalog pointer M0와 snapshot S0를 읽고 각 operation의 read set·write set·validation 범위를 계획한다.
  2. Prepare: Executor는 unique path에 immutable data/delete file을 쓰고 driver는 manifest를 만든다. 이 stage는 CAS retry에서 재사용할 수 있어야 비용 이점이 생긴다.
  3. First winner: W1의 catalog CAS만 M0를 M1으로 바꾸며 성공한다. W2의 prepared file은 아직 table에 보이지 않는다.
  4. Refresh/validate: W2는 M1을 읽고 M0→M1 사이의 concurrent changes를 검사한다. Append action은 보통 새 manifest를 S1에 더할 수 있다. Source file을 교체하는 rewrite라면 그 source들이 여전히 존재하는지 확인한다.
  5. Rebuild/retry: Valid하면 이미 쓴 data file과 manifest를 최대한 재사용해 새 manifest list·snapshot·M2′를 만들고 backoff 뒤 CAS한다. Invalid하면 SQL 전체를 blind replay하지 않고 conflict를 상위 workflow에 반환한다.
  6. Read path: Reader는 catalog pointer → metadata JSON → snapshot → manifest list → manifest → data/delete file을 따라 committed graph만 본다. Retry 중인 W2 artifact는 current pointer에서 unreachable하다.

Cost model

Writer 수를 W, base load부터 CAS까지의 평균 시간을 T, table commit rate를 λ라 하면 충돌 가능성은 대략 λ×T가 커질수록 증가한다. 큰 shuffle은 T를 늘리고, 작은 streaming commit은 λ를 늘린다. 그래서 retry 횟수만 올리기 전에 commit frequency·manifest size·catalog latency·write scope를 함께 줄여야 한다.

5. 실무 설계 판단

Best practice 1 · error taxonomy: CAS conflict, validation failure, unknown commit state, object storage transient error, non-retryable schema/IAM 오류를 별도 code와 metric으로 분류한다. 같은 retry loop에 넣지 않는다.

Best practice 2 · retry budget: Apache Iceberg 1.11.0 문서의 기본 table property는 commit retry 4회, min wait 100ms, max wait 60초, total timeout 30분이다. 이를 그대로 SLA로 간주하지 말고 batch/streaming latency와 catalog rate limit에 맞춰 조정한다. Unknown state status-check는 별도 기본 3회다.

Best practice 3 · reuse evidence: Retry 전후 data file path, file size, manifest path, base/current snapshot, attempt count, validation latency를 기록한다. Data file이 매번 새로 생기면 engine이 work reuse를 못 하거나 상위 workflow가 SQL을 blind replay하는 신호다.

Best practice 4 · contention 감소: Streaming checkpoint를 너무 자주 commit하지 않고, maintenance가 같은 hot partition/file을 건드리지 않게 시간·scope를 분리하며, 필요하면 branch/WAP와 작은 batch coalescing을 검토한다.

Engine/catalog 차이: Table Spec은 atomic swap 메커니즘을 catalog에 위임한다. Metastore/REST/Glue/JDBC 계열은 구현별 conditional update·throttling·status-check 특성이 다르고, 학습 환경의 Hadoop file scheme은 deprecated이며 object/local file system에 production 안전성을 대표하지 않는다. Spark·Flink·Trino가 같은 retry property와 exception을 같은 방식으로 노출한다고 단정하지 말고 connector별 failure test를 둔다.

Anti-pattern: Conflict rate가 높을 때 retry 횟수만 100으로 올리거나, job scheduler가 engine 내부 retry를 모르고 같은 batch를 중첩 실행하거나, compaction이 source file conflict를 무시하고 stale remove를 강제하는 것이다.

Edge case: COW/MOR rewrite나 v3 deletion vector maintenance는 data/delete file과 sequence semantics를 함께 보존해야 한다. Prepared output을 재사용할 수 있어도 concurrent delete가 source applicability를 바꿨다면 retry 대신 replan이 필요하다.

6. 장애 대응 표

상황: Commit conflict와 retry가 급증해 pipeline latency·비용·중복 위험이 커졌다.

증상CommitFailed/ValidationException 증가, p95 commit latency·attempt 수 상승, catalog conditional update throttling, 동일 batch 중복, prepared orphan 증가, streaming checkpoint 지연, compaction 반복 실패.
먼저 수집할 증거/지표Writer/engine/catalog/version, base·current metadata location과 snapshot lineage, operation type·read/write scope, attempt별 CAS 결과·validation 이유·backoff, commit rate λ·prepare time T, checkpoint/batch ID, data/manifest path 재사용 여부, object PUT·catalog latency/error, maintenance timeline.
가능한 가설Hot partition/file contention, excessive streaming commit frequency, long shuffle로 stale window 확대, maintenance overlap, retry without jitter, scheduler duplicate run, connector retry bug, catalog throttling/outage, unknown state를 conflict로 오분류, schema/spec concurrent update.
안전한 첫 조치Blind replay와 중첩 scheduler run을 멈추고 operation identity로 성공 여부를 확정한다. Writer scope와 maintenance를 분리하고 current snapshot을 refresh해 validation failure 이유를 보존한다. Known-good retry budget/backoff로 canary 한 건만 실행한다.
Rollback/복구성공한 snapshot은 유지하고 failed prepared file은 safety window 후 orphan cleanup한다. Duplicate는 compensating delete/overwrite로 정정한다. Invalid rewrite는 latest state에서 source set을 재계획하고, checkpoint/offset은 committed operation identity에 맞춘다.
하지 말아야 할 조치모든 예외의 무한 retry, validation 비활성화, catalog pointer/metadata JSON 수동 편집, stale source file 강제 remove, timeout 뒤 동일 append 즉시 재실행, 증거 전 orphan cleanup·snapshot expiration은 금지한다.

목표: 여러 독립 Spark writer를 동시에 실행해 CAS contention을 만들고, retry 0과 retry 4에서 성공 snapshot·실패 log·physical file과 committed membership 차이를 비교한다.

사전 조건과 실행 전 예측

  • Docker daemon과 프로젝트 Spark/Iceberg 환경이 준비되어 있고 make smoke가 성공해야 한다.
  • 동시에 8개 append를 시작하면 retry 0에서 몇 개가 성공할지, retry 4에서 왜 더 많이 성공할지 먼저 적는다.

  • 학습용 local은 Hadoop catalog다. Production metastore/REST catalog의 수치나 오류 이름을 그대로 추정하지 않는다.

예상 관찰: 시작 시각이 완전히 같지 않아 여러 writer가 차례로 성공할 수 있지만, 충분히 겹친 writer 중 일부는 CAS conflict로 실패한다. Physical Parquet 수가 committed files 수보다 많을 수도 있고 engine cleanup으로 같을 수도 있다. Membership 판단은 metadata table이 기준이다. 충돌이 없으면 이 단계만 한 번 더 실행하되 writer ID는 새 범위를 쓴다.

예상 관찰: Retry 4 group은 conflict 후 latest metadata에 append를 re-apply할 기회가 있어 성공률이 높다. 그래도 retry budget·catalog 특성·동시성에 따라 실패할 수 있으며 “4회면 반드시 성공”은 아니다.

실패 주입의 채점 기준

  • CAS conflict를 data file corruption으로 설명하면 오답이다. 다른 writer가 base를 먼저 바꾼 control-plane 경쟁이다.
  • Retry를 SQL 전체 blind replay로 설명하면 오답이다. Engine 내부 retry는 prepared work 재사용과 assumption validation이 핵심이다.
  • 모든 8 writer가 성공하면 conflict가 없었다는 증거는 아니다. Log와 attempt/latency metric을 보고 내부 retry 여부를 확인해야 한다.

자주 나는 오류와 해결

  • Container not running: docker compose up -d spark 후 docker compose ps로 확인한다.
  • 모든 writer 성공: 시작 겹침이 부족할 수 있다. Writer 수를 12로 늘리거나 같은 단계를 새 ID로 반복한다.
  • Host resource 부족: Writer를 4개로 줄이고 두 번 실행한다. 실습 목표는 경쟁이지 노트북 과부하가 아니다.
  • Log grep 결과 없음: 각 /tmp/day23-*.log의 종료부와 table row/snapshot 수를 직접 비교한다.
  • Unexpected duplicate ID: 이전 단계 ID 범위를 재사용했는지 확인한다. Table에 PK uniqueness는 자동 강제되지 않는다.
  • Production과 오류가 다름: Hadoop catalog 학습 결과를 metastore/REST catalog와 동일시하지 말고 해당 catalog에서 별도 canary한다.

8. 놓치기 쉬운 함정

  1. Optimistic concurrency는 conflict를 막는다. 충돌을 허용하고 commit 때 발견·검증한다.
  2. CAS conflict와 unknown state는 같다. 전자는 명시적 실패, 후자는 성공 가능성이 남아 있다.
  3. Retry는 항상 안전하다. Operation assumptions가 최신 state에서 유효할 때만 안전하다.
  4. Data file을 다시 안 쓰면 모든 비용이 작다. Manifest list·metadata rebuild, catalog round-trip, validation은 반복된다.
  5. Append는 business-level idempotent다. Metadata rebase 가능성과 동일 batch 중복 방지는 다른 문제다.
  6. Retry 수를 늘리면 contention이 해결된다. λ와 T, hot scope, maintenance overlap을 줄여야 한다.
  7. 같은 engine이면 catalog 차이가 없다. Atomic update·throttling·status-check는 catalog 구현에 달려 있다.
  8. Failed attempt file은 즉시 삭제한다. Active retry가 재사용할 수 있어 safety window가 필요하다.

9. 대기업 기술 면접 질문 3개

  1. Iceberg optimistic concurrency를 lock-free라고만 말하지 말고 end-to-end로 설명하라.
    좋은 답변 구조: Base M0/S0 → immutable prepare → CAS → conflict → refresh/assumption validation → work reuse/rebuild → backoff/retry budget → reader visibility와 linearization point.
  2. Streaming commit p99이 2초에서 40초로 증가했다. 진단과 개선을 설계하라.
    좋은 답변 구조: λ·T·writer 수치 → error taxonomy → catalog/attempt/validation metrics → hot partition/maintenance 가설 → checkpoint coalescing·scope 분리·backoff → correctness·latency trade-off.
  3. Compaction commit이 append보다 retry하기 어려운 이유를 방어하라.
    좋은 답변 구조: Read/write set → source file existence assumption → concurrent delete/rewrite/sequence 영향 → valid/invalid retry 분기 → replan 비용 → branch/WAP·maintenance window 대안.

10. 어제 내용 회상 3문제

  1. Data file이나 metadata JSON 생성이 아니라 catalog pointer CAS가 commit 성공 시점인 이유는?
  2. CAS 응답 전에 network가 끊기면 왜 blind append를 하면 안 되는가?
  3. Object storage와 catalog는 각각 어떤 상태를 소유하는가?
짧은 정답/채점 기준
  1. CAS 전 artifact는 current graph에서 unreachable하고 CAS 후 전체 graph가 한꺼번에 reachable하기 때문이다. Reachability+linearization을 말하면 정답.
  2. CAS는 성공했지만 응답만 유실됐을 수 있어 같은 batch를 재실행하면 중복된다. Unknown state→status check가 핵심.
  3. Object storage는 immutable bytes/durability, catalog는 table name의 current metadata pointer와 conditional update를 소유한다. Data/control plane을 구분하면 정답.

11. 오늘 내용 확인 문제 3개

  1. Optimistic retry가 expensive data file을 재사용해도 반드시 다시 만들어야 하는 metadata는?
  2. CAS conflict 뒤 rewrite를 retry하기 전에 확인할 핵심 assumption은?
  3. Retry 횟수를 늘리기 전에 줄여야 할 contention 변수 두 가지는?
짧은 정답/채점 기준
  1. 새 current state를 반영한 manifest list, snapshot, metadata JSON과 catalog CAS attempt다. Metadata rebase를 말하면 정답.
  2. 교체·제거할 source file이 여전히 table에 있고 concurrent change가 operation 의미를 침범하지 않았는지다. Source/read set validity가 핵심.
  3. Commit rate λ와 prepare-to-CAS 시간 T, 또는 writer/hot scope·maintenance overlap이다. 경쟁 빈도와 stale window 두 축을 말하면 정답.
