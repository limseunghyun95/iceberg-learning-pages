APACHE ICEBERG · WEEK 3 / DAY 21 · 회상·복습

회상: rewrite 없이 evolution 가능한 범위

Schema·Partition·Sort Evolution · 예상 학습 30분 + 실습 35분

한 줄 요약
Iceberg의 schema·partition·sort evolution은 새 metadata state를 atomic하게 공개해 기존 data file rewrite를 피하지만, “물리 파일을 안 바꿔도 됨”은 downstream 의미·모든 engine 지원·성능까지 자동으로 안전하다는 뜻이 아니다.

1. 선수 용어 사전

Metadata-only기존 data file byte를 다시 쓰지 않고 새 metadata JSON과 catalog pointer 교체로 table 계약을 바꾸는 방식이다.
Physical compatibilityOld file을 그대로 두어도 field ID, spec ID, sort order ID로 새 reader가 안전하게 해석할 수 있는 성질이다.
Semantic compatibility업무 의미, null 처리, 집계·join·SLA와 downstream 계약이 변화 후에도 기대와 맞는지 여부다.
IdentitySchema field ID, partition spec/field ID, sort order ID처럼 이름·순서와 분리된 객체의 정체성이다.
Default state새 writer가 사용할 current schema/default spec/default sort order다. Old file의 실제 ID를 덮어쓰는 read schema가 아니다.
Rewrite기존 row를 새 schema/layout/order의 data file로 다시 materialize하고 새 snapshot으로 교체하는 별도 작업이다.
Compatibility matrix변경별 file rewrite 필요성, reader/writer 지원, downstream 영향, rollback과 검증 증거를 표로 고정한 운영 계약이다.
Backfill새 column 값이나 새 layout을 과거 row에도 실제로 채우기 위해 data를 다시 쓰는 작업이다. Metadata evolution과 목적이 다르다.

2. 왜 중요한가

“Iceberg는 rewrite 없이 schema를 바꾼다”는 문장은 절반만 맞다. Column rename은 Iceberg-aware reader가 field ID로 old file을 읽게 해주지만, raw Parquet reader나 name 기반 ETL은 깨질 수 있다. Optional column 추가는 old row를 null/default로 보이게 할 수 있지만 실제 historical business value를 채워 주지는 않는다.

Partition evolution도 old/new layout을 함께 읽어 correctness를 지키지만, old day file을 hour query가 더 넓게 읽는 scan 비용은 남는다. Sort order 변경은 future file의 layout 의도만 바꾸며 old file과 streaming unsorted file은 그대로다. 따라서 rewrite 여부는 correctness, semantic migration, performance remediation을 나누어 결정해야 한다.

핵심 판단: “Spec이 metadata-only를 허용하는가?”와 “우리 조직의 모든 reader·writer·downstream이 안전한가?”는 서로 다른 질문이다. 첫 질문은 Table Spec, 둘째는 compatibility matrix와 canary가 답한다.

3. 아키텍처 그림과 요청 흐름

① 변경 요청 + 호환성 matrix
schema/spec/order · engines · downstream · SLO
↓ base metadata와 current IDs 고정
② 새 metadata JSON 준비
new schema/spec/order ID · old history 보존 · data file 불변
↓ catalog compare-and-swap
③ 성공 확정: pointer → new metadata
future writer는 new default · pinned reader는 old snapshot 계속 사용
↓ old/new state를 ID로 reconcile
④ Read path
field ID projection · spec별 pruning · file sort ID · delete sequence
↓ metrics·semantic canary·cost 관측
⑤ 유지 또는 별도 migration
metadata-only 유지 · targeted backfill/rewrite · compensating rollback

State transition과 성공 시점

  1. Planner가 catalog pointer의 base metadata를 읽고 current schema/spec/order ID와 current snapshot을 기록한다.
  2. Schema update는 기존 field ID를 유지하고 새 field에 fresh ID를 준 새 schema를 만든다. Partition/sort update도 unique ID를 가진 정의를 history에 추가한다.
  3. 새 metadata JSON을 object storage에 쓰는 것은 준비 단계다. Catalog가 expected old pointer에서 new pointer로 atomic하게 바뀐 순간에만 evolution이 성공한다.
  4. Old snapshot을 pin한 reader는 old metadata graph를 끝까지 읽고, refresh한 reader와 future writer는 new default를 본다. 두 state가 한 query에 반쯤 섞이면 안 된다.
  5. New writer는 새 schema/spec/order로 file을 만들지만, manifest entry는 실제 file의 schema/spec/sort ID와 sequence를 보존한다. Default ID만 보고 old file을 재해석하지 않는다.
  6. Canary가 semantic mismatch나 scan 회귀를 찾으면 future default를 compensating metadata commit으로 되돌릴 수 있다. 이미 쓴 new file은 그 ID로 계속 해석 가능해야 한다.
  7. Historical 값을 채우거나 old layout 비용을 줄여야 할 때만 backfill/rewrite를 별도 snapshot으로 수행한다. 그 commit 역시 optimistic validation과 CAS를 통과해야 한다.

Read path: evolution을 숨기는 ID 연결

Reader는 catalog pointer → metadata JSON → snapshot → manifest list → manifest → data/delete file 순서로 간다. Schema rename/reorder는 field ID projection으로, partition evolution은 manifest의 spec ID별 predicate projection으로, sort evolution은 file의 sort order ID와 bounds로 해석한다. 그 뒤 sequence number로 COW/MOR delete file 또는 지원되는 DV의 적용 대상을 정하고 residual을 평가한다.

4. CS 관점의 내부 동작

EvolutionMetadata-only 불변식 · 남는 비용/위험
SchemaField ID가 identity이므로 add/drop/rename/reorder와 허용된 promotion에서 old bytes를 유지한다. Name/position 기반 consumer, defaults, business meaning과 metric bound decode는 별도 검증한다.
PartitionOld/new spec과 manifest가 공존하고 reader가 spec별 split planning한다. Planning fan-out, coarse old pruning, overwrite 단위 변화와 v1 field-ID history가 남는다.
SortDefault order를 새 ID로 바꾸어도 old file ID/unsorted state는 그대로다. Bounds overlap·compression·query scan은 즉시 개선되지 않으며 result ordering도 보장하지 않는다.
Rewrite새 immutable file과 snapshot으로 membership을 교체한다. Shuffle/I/O/commit conflict·delete sequence·concurrent writer race와 old reader retention 비용을 지불한다.

Schema evolution 허용선

Add/drop/rename/reorder는 field ID identity를 보존하면 metadata-only다. Primitive promotion은 v1/v2에서 int→long, float→double, 같은 scale을 유지한 decimal precision 확장이 대표 안전선이다. V3+에는 unknown→구체 type, date→timestamp/timestamp_ns가 추가되지만 timezone timestamp로의 promotion은 허용되지 않고 range failure와 partition transform 제약을 함께 확인해야 한다.

Nullable column을 required로 강화하는 것은 old null 존재를 metadata만으로 증명할 수 없어 Spark DDL에서 허용되지 않는다. Struct 계층 자체를 접거나 펴는 변화, primitive↔struct, equality를 바꾸는 map key field add/drop도 단순 evolution이 아니다.

Control path와 data path 분리

Evolution commit은 schema/spec/order 정의와 default pointer를 바꾸는 control-path 전이다. Data path의 Parquet/ORC/Avro bytes는 그대로다. 이 indirection이 O(data) migration을 O(metadata) transition으로 바꾸지만, old/new encoding을 연결하는 reader correctness와 version-aware metric decode가 전제다.

5. 실무 설계 판단

Evolution compatibility matrix

변경RewriteGuardrail
Add optional대개 불필요Old row의 null/initial default 의미와 downstream null 처리 검증. Historical value가 필요하면 backfill.
Drop/rename/reorderIceberg read에는 불필요Field ID 유지·재사용 금지. Raw/name/position consumer와 HMS positional validation canary.
Safe widen불필요Format version별 허용선, old bounds decode, partition transform 결과 불변과 downstream type mapping 검증.
Nullable→requiredMetadata-only 금지Null 전수 검증·정제 후 engine 지원 경로를 설계. Spark는 SET NOT NULL을 허용하지 않는다.
Partition changeCorrectness에는 불필요Spec-aware readers, split planning, dynamic overwrite semantics와 planning/scan SLO. 비용 때문에 targeted rewrite 가능.
Sort changeCorrectness에는 불필요Per-file order ID, writer/distribution 지원, bounds overlap. Query output order와 혼동 금지.
Meaning change대개 backfill 필요Unit·timezone·enum·PII policy를 column rename으로 숨기지 말고 새 field+dual write+validation으로 migration.

Best practice: Producer/consumer inventory → version별 read/write/DDL matrix → sample old/new file canary → metadata-only commit → field/spec/order ID와 result diff 관측 → 필요 시 작은 targeted rewrite 순서로 진행한다.

Engine/version 차이: Apache Iceberg 1.11.0 Spark 문서는 Spark 3 ALTER TABLE로 add/drop/rename/reorder/widen/required→optional을 지원한다. Hive Catalog는 position이 이동하는 schema 변경을 HMS가 거절할 수 있고, validation을 끄면 Hive engine의 직접 read가 틀릴 수 있다. V3의 date promotion과 defaults 같은 기능은 모든 engine이 같은 시점에 지원한다고 단정하지 말고 capability test를 둔다.

Anti-pattern: “DDL 성공=조직 전체 호환”으로 간주하거나, unit가 bytes에서 KiB로 바뀌는데 comment/rename만 고쳐 old/new value를 섞는 것이다.

Edge case: Partition source field를 type promotion할 때 transform 결과가 달라지면 promotion할 수 없다. Date→timestamp처럼 spec 자체는 허용해도 active partition transform과 multi-engine hash/transform 구현을 함께 검사해야 한다.

6. 장애 대응 표

상황: Metadata-only evolution 후 old row가 null/누락되거나 engine별 결과와 비용이 갈라졌다.

증상Raw reader에서 renamed column null/없음, old 구간 누락, engine별 schema/count 차이, dynamic overwrite 범위 변화, file scan·planning p95 증가, writer가 old spec/order로 계속 commit, catalog success 후 object 404.
먼저 수집할 증거/지표Catalog metadata location·snapshot ID, schemas/current schema와 field IDs/defaults, partition-specs/default/field IDs, sort-orders/default와 per-file sort_order_id, manifest spec/sequence, file physical schema·bounds, query plan/residual, engine/connector/catalog version, downstream query, commit/rewrite/cleanup timeline.
가능한 가설Name/position 기반 reader, field ID 재사용/mapping 오류, unsupported promotion/default, current spec만 적용, stale writer/cache, sort declaration만 믿은 pruning, HMS positional schema, semantic unit/timezone mismatch, rewrite conflict, old object 조기 삭제, catalog/object storage partial failure.
안전한 첫 조치Affected DDL/writer/rewrite/cleanup을 멈추고 snapshot을 pin한다. Metadata·manifest·old/new file schema와 query result sample을 보존한다. Known-good Iceberg reader로 spec/ID-aware full scan을 비교하고 raw reader를 production path에서 격리한다.
Rollback/복구Compensating schema/spec/order metadata commit으로 future default를 되돌리고 known-good engine을 사용한다. Missing historical value는 validated backfill, layout 비용은 targeted rewrite로 새 snapshot에 교체한다. Missing object는 versioned backup/replica에서 같은 URI로 복원한다.
하지 말아야 할 조치Metadata JSON/field·spec·order ID를 수동 편집하거나 ID를 재사용하지 않는다. Raw file rename/delete, pointer 강제 교체, snapshot expiration/orphan cleanup, 증거 없는 full rewrite와 blind retry를 실행하지 않는다.

7. 35분 재현 실습

목표: Schema·partition·sort metadata를 연속 변경해 old data file path가 그대로임을 증명하고, Iceberg field-ID read는 성공하지만 raw Parquet name-based read가 rename을 따라오지 못하는 실패를 관찰한다.

실패 주입 · Raw Parquet name-based read

# files metadata table에서 old file_path를 복사해 OLD_FILE에 넣는다.
OLD_FILE='warehouse/day21/evolution_lab/data/old-file.parquet'

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SELECT payload
FROM parquet.\`$OLD_FILE\`;
"

예상 관찰: Raw Parquet schema에는 old physical name data가 있으므로 payload를 resolve하지 못하거나 null/분리된 column처럼 보일 수 있다. 같은 file을 Iceberg table로 읽으면 field ID 덕분에 payload='old-a/old-b'가 나온다. 이 실패는 file을 고치는 신호가 아니라 raw bypass를 격리하고 consumer를 Iceberg-aware path로 옮길 증거다.

자주 나는 오류와 해결

  • Partition field 이름 오류: DESCRIBE TABLE EXTENDED와 metadata JSON의 exact name을 쓴다.
  • ALTER COLUMN FIRST 실패: Hive Catalog positional validation 또는 connector 지원을 확인하고 canary catalog에서 검증한다.
  • INSERT column list 미지원: DESCRIBE의 current logical order에 맞춘 explicit SELECT를 사용하고 결과를 재확인한다.
  • Raw path 불일치: Warehouse를 추측하지 말고 files.file_path의 정확한 URI를 사용한다.
  • Old row source가 null: Optional add의 정상 결과다. Historical business value가 필요하면 검증된 backfill을 별도 설계한다.
  • File path가 ALTER 중 바뀜: 자동 maintenance나 외부 writer가 동시에 동작했는지 snapshot/commit timeline을 확인한다.

8. 놓치기 쉬운 함정

  1. Metadata-only면 downstream도 무중단이다. Raw/name/position consumer와 business semantics는 별도다.
  2. Rename은 새 column을 만든다. Field ID를 유지하는 같은 identity이며 old physical name과 연결된다.
  3. Drop 후 같은 이름을 재사용해도 된다. 새 field는 fresh ID여야 하며 old value를 부활시키면 안 된다.
  4. 모든 type widen은 안전하다. Spec/version의 promotion 목록과 partition transform 불변을 확인한다.
  5. Partition evolution은 old file을 새 layout으로 옮긴다. Old/new spec은 공존하고 split planning이 필요하다.
  6. Sort evolution은 table 전체를 정렬한다. New default일 뿐 old/streaming file은 다른 order ID일 수 있다.
  7. DDL 성공은 모든 engine 지원 증거다. Read/write/DDL/metadata table capability를 따로 검증한다.
  8. Rewrite가 끝나면 old object를 즉시 지운다. Pinned reader와 retained snapshot 안전 창을 먼저 보장한다.

9. 대기업 기술 면접 질문 3개

  1. Petabyte table의 schema·partition·sort를 무중단으로 바꾸는 rollout을 설계하라.
    좋은 답변 구조: Workload/SLO와 engine inventory → ID/state transition → catalog CAS → old/new read path → semantic canary → metrics → targeted rewrite 기준 → rollback·retention.
  2. “Rename은 metadata-only인데 장애가 났다”를 설명하라.
    좋은 답변 구조: Field ID vs physical name → Iceberg-aware/raw reader 경로 → old/new file schema → concrete failure → safe first action → consumer migration·name mapping 대안 → file rewrite trade-off.
  3. 어떤 evolution에서 rewrite가 필요한가?
    좋은 답변 구조: Correctness/semantic/performance 목적 분리 → 허용 promotion·required/null 경계 → partition/sort coexistence 비용 → 수치 threshold → maintenance race·sequence → backfill/rewrite/새 column 대안.

10. 어제 내용 회상 3문제

  1. 12시 predicate가 day spec과 hour spec에서 각각 어떤 후보 partition을 만드는가?
  2. Unified partition struct에서 current hour field가 null인 old file을 제외하면 왜 틀리는가?
  3. Mixed-spec scan 중 concurrent commit이 발생해도 결과가 섞이지 않는 이유는?
짧은 정답/채점 기준
  1. Day는 날짜 전체의 coarse superset, hour는 12시의 precise candidate다. Spec별 projection+residual을 말하면 정답.
  2. Null은 old spec에 그 field가 없다는 뜻이며 old file에도 정답 row가 있을 수 있다. Default spec으로 old tuple을 해석하면 false negative가 핵심.
  3. Reader가 시작 때 immutable snapshot/manifest graph를 pin하고 refresh 전까지 같은 root를 쓰기 때문이다. Snapshot isolation을 말하면 정답.

11. 오늘 내용 확인 문제 3개

  1. Metadata-only evolution과 semantic migration의 차이는?
  2. Schema rename이 Iceberg read에는 안전하지만 raw Parquet read에는 위험한 이유는?
  3. Partition/sort evolution 뒤 rewrite를 선택할 수치 기준 두 가지는?
짧은 정답/채점 기준
  1. 전자는 ID와 metadata로 old bytes를 새 logical state에 연결하고, 후자는 historical value/meaning을 실제로 바꾼다. Physical vs business meaning이 핵심.
  2. Iceberg는 field ID로 projection하지만 raw reader는 physical name/position을 사용한다. Identity source 차이를 말하면 정답.
  3. 예: planning p95·manifest fan-out, scanned bytes/file 수, bounds overlap, compression, query SLO. 측정 가능한 비용 두 개와 targeted rewrite를 말하면 정답.
