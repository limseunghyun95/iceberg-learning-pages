APACHE ICEBERG · WEEK 6 / DAY 40

Trino interoperability·type/feature matrix

Catalog·Multi-engine·Streaming · 개념 45분 + 실습 35분

한 줄 요약
같은 Iceberg table을 연다는 사실은 호환성의 시작일 뿐이다. Catalog pointer와 snapshot을 동일하게 보고, format version·type·delete artifact·DML·procedure의 교집합을 round-trip test로 증명해야 multi-engine 계약이 성립한다.

1. 선수 용어 사전

Interoperability서로 다른 engine이 같은 table state를 의미 손실 없이 읽고, 허용된 쓰기를 이어 가는 능력이다. 단순 file open보다 넓다.
Capability matrixEngine·connector·catalog 조합별 read/write/type/delete/procedure 지원을 표로 고정한 배포 계약이다.
Format versionMetadata JSON의 format-version이다. V1은 analytic table, V2는 row-level delete, V3는 nanosecond timestamp·variant·deletion vector·row lineage 등을 추가한다.
ArtifactData file, equality/position delete file, deletion vector, manifest처럼 table semantics를 구성하는 물리 객체다.
Round tripSpark write→Trino read→Trino write→Spark read처럼 양방향으로 값·schema·snapshot을 검증하는 test다.
Semantic driftQuery는 성공하지만 timestamp precision, timezone, decimal, nested field 의미가 달라지는 조용한 불일치다.
Reader ceiling모든 production reader 중 가장 낮은 지원 수준이다. Writer가 이 경계를 넘으면 table 전체가 읽히지 않을 수 있다.

2. 왜 중요한가

Iceberg는 engine 독립 table format이지만 각 engine은 독립 release cadence와 connector 구현을 가진다. Spark가 V3 type이나 deletion vector를 쓰기 시작해도 Trino가 그 조합을 안정적으로 읽는다는 보장은 없다. “Spec에 있다”와 “이 connector version이 production-grade로 읽고 쓴다”를 분리해야 한다.

호환성 실패는 즉시 exception만 만들지 않는다. TIME(6)·TIMESTAMP(6) precision 축소, timezone 해석, FIXED→VARBINARY mapping처럼 query는 성공해도 round trip에서 정보가 달라질 수 있다. 행 수만 비교하는 test는 부족하다.

핵심 불변식: 어느 writer도 production reader ceiling보다 높은 format/type/artifact를 publish하지 않는다. 한 engine이 만든 snapshot은 다른 승인 engine이 동일 row set·schema identity·delete semantics로 해석해야 한다.

3. 아키텍처 그림과 요청 흐름

① Trino coordinator
SQL parse · connector capability · query planning
↓ table name / reference
② Catalog
name → current metadata JSON pointer · atomic commit primitive
↓ metadata location + storage credential
③ Metadata JSON → snapshot → manifest list → manifest
format version · field ID · partition spec · data/delete artifact
↓ prune / split planning
④ Trino workers
Parquet/ORC/Avro read · delete merge · type conversion
↓ DML이면 new files + manifests
⑤ Optimistic catalog commit
validate base pointer → atomic swap → Spark/Flink reader에 공개

번호별 요청·응답·상태 변화

  1. Resolve: Coordinator는 connector와 catalog를 통해 table name을 current metadata location으로 해석한다.
  2. Load: Metadata JSON의 format version, schemas, partition specs, sort orders, snapshots, refs를 읽는다. 지원하지 않는 높은 version이면 반드시 실패해야 한다.
  3. Plan: Manifest list와 manifest metrics로 file을 prune한다. Delete file/DV를 인식하지 못하면 삭제 row가 되살아나는 correctness bug가 된다.
  4. Read: Worker가 data file과 적용 가능한 delete artifact를 합성하고 Iceberg type을 Trino type으로 바꾼다.
  5. Write: INSERT/UPDATE/MERGE/DELETE는 immutable candidate file과 새 metadata를 만든다. 지원 범위는 Trino·catalog·file format·table format의 교집합이다.
  6. Commit: Catalog pointer swap이 성공 확정점이다. Object storage에 file만 생긴 것은 commit이 아니다.
  7. Re-open: Spark/Flink가 새 pointer부터 graph를 다시 읽어 같은 값·delete semantics를 확인해야 round trip이 끝난다.

4. CS 관점의 내부 동작

호환성은 집합의 교집합

배포 가능한 table 기능 집합은 Spec ∩ Writer ∩ Reader ∩ Catalog ∩ FileIO ∩ Policy다. Spec은 가능한 표현을 정의하지만 실제 release가 모두 구현했다는 뜻은 아니다. Catalog는 atomic commit과 credential 범위를 제공해야 하고 FileIO는 object storage scheme·encryption을 처리해야 한다.

축호환 조건깨질 때 결과
Format모든 reader가 version과 artifact를 지원.Load 거부 또는 delete 무시.
Type양방향 mapping과 precision 보존.Query 실패 또는 silent coercion.
OperationDML·DDL·procedure validation 일치.충돌 누락, 예상 밖 rewrite.
ReferenceBranch/tag/snapshot syntax·retention 일치.다른 state 조회 또는 rollback 상실.
Control plane같은 catalog pointer와 auth scope 사용.Split-brain table 또는 commit 실패.

Type mapping에서 정보량 보기

현재 공식 Trino 문서는 Iceberg TIME을 TIME(6), TIMESTAMP를 TIMESTAMP(6)으로 mapping하고 V3 nanosecond timestamp는 TIMESTAMP(9)으로 mapping한다. FIXED(L)는 VARBINARY로 보이므로 길이 제약을 query type만으로 보존하지 않는다. Nested struct/list/map은 field ID와 nullability까지 비교한다.

V3는 deletion vector, row lineage, variant, nanosecond timestamp를 더한다. 현재 Trino 문서는 V1·V2 지원과 V3 experimental 지원을 구분한다. “Trino 최신은 V3를 읽는다”가 아니라 exact version과 필요한 V3 feature 각각을 test해야 한다.

성공 확정점과 cache

Write 성공은 task가 file을 썼을 때가 아니라 catalog pointer가 새 metadata로 교체됐을 때다. Reader는 query planning 시 선택한 snapshot에 고정된다. Metadata/file-system cache가 켜져 있으면 새 query freshness와 cache TTL도 관찰하되, running query가 새 snapshot으로 이동한다고 기대하지 않는다.

5. 실무 설계 판단

Best practice 1 · Exact BOM: Spark/Flink/Trino version, Iceberg connector/runtime, JVM/Scala, catalog, FileIO, file format을 한 Bill of Materials로 version-control한다.

Best practice 2 · Read/write gate 분리: Trino read 허용과 Trino MERGE/DELETE 허용은 별도 승인한다. Reader-only consumer가 많을수록 writer 수를 줄여 protocol surface를 작게 만든다.

Best practice 3 · Golden table: Null, NaN, decimal 경계, pre/post epoch timestamp, timezone, UUID, binary, nested rename, old/new partition spec, equality/position delete를 가진 작은 table을 모든 release에서 round trip한다.

Best practice 4 · Reader ceiling: V2→V3 upgrade 전 모든 reader와 fallback version이 V3 table load, 필요한 type, DV read, maintenance procedure를 통과해야 한다. Metadata-only upgrade라도 호환성 위험은 metadata-only가 아니다.

Best practice 5 · Ownership: Table property·schema·partition·sort·format upgrade의 단일 owner와 change approval을 둔다. Engine session property가 durable table contract를 몰래 바꾸지 못하게 한다.

Anti-pattern: 한 engine의 smoke SELECT만으로 호환 선언, latest 문서를 구버전 cluster에 적용, 행 수만 비교, timestamp를 문자열로 우회, production에서 바로 format upgrade, connector default 의존, 같은 warehouse를 서로 다른 catalog에 등록하는 것이다.

Edge case: Engine A가 모르는 partition transform은 pruning만 못 할 수도 있고 table load가 실패할 수도 있다. V3 reader는 unknown transform을 무시하고 읽어야 하지만 older implementation은 깨질 수 있으므로 rollout test가 필요하다.

Version/engine 차이: 현재 확인한 Trino 문서는 V1·V2를 지원하고 V3는 experimental로 명시한다. Iceberg 1.11.0과 Spark 3.5.8을 쓰는 이 프로젝트에서도 Trino connector는 별도 구현이므로 Java runtime version만 맞춘다고 feature parity가 생기지 않는다.

6. 장애 대응 표

상황: Spark에서는 정상인데 Trino에서 table load 실패, stale row, type 오류, MERGE 후 값 불일치가 발생한다.

증상Unsupported format/type, snapshot 불일치, 삭제 row 재등장, timestamp·decimal 차이, branch/tag 조회 실패, DML commit conflict, 한 engine만 stale metadata를 읽음.
먼저 수집할 증거/지표Exact engine/connector/catalog/FileIO version, query ID, catalog config, current metadata location·format-version·snapshot ID·schema/spec ID, manifest content, delete artifact, table properties, plan, source/target value hash, cache TTL, commit exception/request ID.
가능한 가설Reader ceiling 초과, V3 experimental feature, unsupported type/transform, timezone·precision coercion, delete artifact 미지원, 다른 catalog pointer, stale cache, storage 권한, concurrent conflict, procedure 차이.
안전한 첫 조치Write와 maintenance를 일시 중지하고 두 engine의 current metadata location·snapshot ID를 read-only로 비교한다. 실패 snapshot 이전 참조와 artifacts를 보존하고 golden query로 mismatch 축을 format/type/delete/catalog/cache 중 하나로 좁힌다.
rollback/복구Compatible connector로 rollback하거나 검증된 snapshot/branch를 reader endpoint로 고정한다. 잘못 쓴 row는 evidence로 범위를 정해 forward correction한다. Format version은 숫자만 downgrade하지 말고 higher-version artifact/type 제거 가능성을 검증한다.
하지 말아야 할 조치Metadata JSON 수동 편집, delete/Puffin file 삭제, format-version 숫자 강등, cache 전체 삭제로 덮기, 같은 warehouse를 새 catalog에 재등록, evidence 전 expire/orphan cleanup, mismatch table에 추가 MERGE를 하지 않는다.

7. 35분 재현 실습

목표: 현재 저장소에는 Trino runtime이 없으므로 Node.js로 capability gate와 lossy type mapping을 재현한다. 결과를 먼저 예측한 뒤 실행하고, production 전에는 같은 case를 실제 Spark·Trino sandbox로 교체한다.

사전 조건과 실행 전 예측

  • Node.js 18 이상. Repository file은 변경하지 않는다.
  • V2 + position delete + microsecond timestamp는 승인되고, V3 + DV는 experimental policy로 차단될 것이다.
  • FIXED(16)을 Trino VARBINARY로 round trip하면 길이 제약 metadata가 사라질 것이다.
  • 두 engine이 다른 metadata pointer를 보면 row hash 비교 전에 split-brain으로 중단해야 한다.

1단계 · Capability matrix gate

node <<'NODE'
const engines = {
  spark:{formats:[1,2,3],types:['timestamp_us','timestamp_ns','fixed'],artifacts:['data','position_delete','equality_delete','dv'],v3:'approved'},
  trino:{formats:[1,2,3],types:['timestamp_us','timestamp_ns','fixed'],artifacts:['data','position_delete','equality_delete','dv'],v3:'experimental'}
};
const policy={allowExperimental:false};
const tables=[
  {name:'orders_v2',format:2,types:['timestamp_us'],artifacts:['data','position_delete']},
  {name:'orders_v3',format:3,types:['timestamp_ns'],artifacts:['data','dv']}
];
for(const t of tables){
  const failures=[];
  for(const [name,e] of Object.entries(engines)){
    if(!e.formats.includes(t.format)) failures.push(`${name}:format`);
    if(t.types.some(x=>!e.types.includes(x))) failures.push(`${name}:type`);
    if(t.artifacts.some(x=>!e.artifacts.includes(x))) failures.push(`${name}:artifact`);
    if(t.format===3 && e.v3==='experimental' && !policy.allowExperimental) failures.push(`${name}:v3-experimental`);
  }
  console.log(t.name, failures.length?`BLOCK ${failures.join(',')}`:'APPROVE');
}
NODE

예상 관찰: orders_v2 APPROVE, orders_v3 BLOCK trino:v3-experimental. “읽을 수 있음”과 “조직이 production 승인함”은 다르다.

2단계 · Failure injection: type 정보 손실

node <<'NODE'
const iceberg={type:'FIXED',length:16,value:Buffer.alloc(16,7)};
const trino={type:'VARBINARY',value:iceberg.value};
const writtenBack={type:'BINARY',value:trino.value};
console.log('value-equal=',iceberg.value.equals(writtenBack.value));
console.log('constraint-equal=',iceberg.type===writtenBack.type && iceberg.length===writtenBack.length);
console.log({icebergType:iceberg.type,trinoType:trino.type,roundTripType:writtenBack.type});
NODE

예상 관찰: Byte 값은 같아도 constraint는 false다. Golden test는 값뿐 아니라 Iceberg schema type·field ID·nullability를 비교해야 한다.

3단계 · Failure injection: 다른 catalog pointer

node <<'NODE'
const observations={
  spark:{catalog:'rest-prod',metadata:'s3://warehouse/orders/metadata/v105.metadata.json',snapshot:9005},
  trino:{catalog:'hms-prod',metadata:'s3://warehouse/orders/metadata/v102.metadata.json',snapshot:9002}
};
const same=observations.spark.metadata===observations.trino.metadata;
console.log(observations);
console.log('same-current-pointer=',same);
console.log('decision=',same?'continue row checksum':'STOP split-brain investigation');
NODE

예상 관찰: Row checksum 전에 중단한다. 같은 warehouse path라도 catalog current pointer가 다르면 같은 table state가 아니다.

4단계 · Golden row checksum

node <<'NODE'
const crypto=require('crypto');
function canonical(rows){return rows.slice().sort((a,b)=>a.id-b.id).map(r=>JSON.stringify(r)).join('\n');}
function digest(rows){return crypto.createHash('sha256').update(canonical(rows)).digest('hex');}
const spark=[{id:1,amount:'10.20',ts:'2026-10-28T00:00:00.123456Z'},{id:2,amount:null,ts:null}];
const trino=[{id:1,amount:'10.20',ts:'2026-10-28T00:00:00.123456Z'},{id:2,amount:null,ts:null}];
console.log('spark=',digest(spark));
console.log('trino=',digest(trino));
console.log('same=',digest(spark)===digest(trino));
NODE

판정: Canonicalization은 type/precision을 숨기지 않게 설계한다. 실제 gate는 row hash와 함께 snapshot ID, schema JSON, data/delete file counts, plan을 저장한다.

자주 나는 오류와 해결

  • 실제 Trino에서 table not found: Catalog name·namespace·REST/HMS endpoint와 current metadata location을 비교한다.
  • Unsupported type: 문자열 cast로 production을 통과시키지 말고 schema contract와 reader upgrade 순서를 결정한다.
  • Delete row 재등장: Snapshot의 delete manifest content와 reader의 artifact 지원을 확인한다.
  • DML 충돌: Base snapshot, isolation/validation, concurrent Spark/Flink job을 수집하고 blind retry하지 않는다.
  • Node가 없음: 이론 결과를 기록하고 production과 분리된 sandbox에서 exact connector test를 수행한다.

Cleanup

실습은 in-memory process만 사용해 cleanup이 없다. 실제 sandbox에서는 writer를 중지하고 마지막 snapshot과 golden 결과를 보존한 뒤 test namespace를 catalog API로 제거한다. Object path를 먼저 직접 삭제하지 않는다.

8. 놓치기 쉬운 함정

  • Spec 지원 = connector 지원이 아니다. Exact release와 feature를 확인한다.
  • SELECT 성공 = write 호환이 아니다. DML과 procedure는 별도 gate다.
  • 값 동일 = schema 동일이 아니다. FIXED/BINARY, precision, nullability, field ID를 본다.
  • Format V3 support = 모든 V3 기능 안정이 아니다. Type·DV·maintenance를 각각 test한다.
  • 같은 storage path = 같은 table이 아니다. Catalog current pointer가 identity 기준이다.
  • Time travel = cache refresh가 아니다. Reference와 metadata cache를 구분한다.
  • Format upgrade = 쉽게 downgrade 가능이 아니다. Higher-version artifact가 생기면 숫자만 되돌릴 수 없다.

9. 대기업 기술 면접 질문

  1. Spark writer와 Trino reader의 호환 gate를 설계하라.
    좋은 답변 구조: Workload/SLO → exact BOM → catalog pointer → format/type/artifact matrix → golden dataset → 양방향 snapshot/schema/value 검증 → failure injection → canary → rollback과 owner.
  2. V2→V3 upgrade 승인 조건은?
    좋은 답변 구조: 필요한 V3 feature → reader ceiling → Trino experimental 경계 → DV/type/row-lineage test → maintenance support → branch/canary → irreversible artifact → fallback 불가 조건.
  3. Spark와 Trino의 COUNT가 다르다. 어떻게 조사할 것인가?
    좋은 답변 구조: Query time/reference 고정 → catalog/metadata/snapshot ID → schema/spec → manifest data/delete counts → delete capability → filter/plan/cache → row hash → writer freeze → compatible recovery.

10. 복습과 정답

어제 내용 회상 3문제

  1. Flink checkpoint green이 Iceberg commit success를 뜻하지 않는 이유는?
  2. Commit 성공 뒤 ack 유실 시 복구가 중복을 어떻게 막는가?
  3. Checkpoint interval을 정할 때 file size 외 어떤 비용을 보는가?

짧은 정답/채점: ① Commit은 completion callback 뒤 별도로 실패할 수 있다. ② Restored state와 snapshot summary의 job/checkpoint marker를 대조한다. ③ Freshness/RPO, writer당 bytes, backpressure, catalog QPS·latency, snapshot/small-file 수를 본다. 두 state machine과 확정점을 말하면 만점.

  1. Multi-engine 호환성의 여섯 교집합은 무엇인가?
  2. Trino query가 성공해도 type round trip이 깨지는 예는?
  3. 두 engine의 COUNT가 다를 때 가장 먼저 비교할 pointer는?

짧은 정답/채점: ① Spec·Writer·Reader·Catalog·FileIO·Policy. ② FIXED→VARBINARY→BINARY 제약 손실, timestamp precision/timezone drift 등. ③ Catalog가 반환한 current metadata location과 snapshot ID. File listing보다 pointer를 먼저 말하면 만점.
