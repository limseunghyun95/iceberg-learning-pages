APACHE ICEBERG · WEEK 4 / DAY 22

immutable write와 atomic metadata swap

Commit·Isolation·Concurrency · 예상 학습 35분 + 실습 35분

한 줄 요약
Iceberg writer는 data·delete·manifest·metadata file을 먼저 immutable하게 준비하고, catalog가 가리키는 metadata pointer를 old에서 new로 원자적으로 교체하는 한 순간에만 table state 전체를 공개한다.

1. 선수 용어 사전

Immutable file한번 완성한 뒤 제자리 수정하지 않는 file이다. 변경은 새 unique path의 file을 쓰고 metadata가 참조 대상을 바꾸는 방식으로 표현한다.
Catalog pointerTable 이름을 현재 metadata JSON 위치에 연결하는 작은 권위 상태다. Object storage의 최신 파일 목록이 table state를 결정하지 않는다.
Atomic관찰자가 old state 전체 또는 new state 전체만 보고 중간 상태는 볼 수 없다는 성질이다. 여러 물리 file을 한꺼번에 rename한다는 뜻이 아니다.
CAS / check-and-putCompare-and-swap. Pointer가 내가 읽은 expected old value일 때만 new value로 바꾸는 조건부 원자 연산이다.
Linearization point분산된 여러 단계의 작업이 논리적으로 한 순간에 성공했다고 볼 수 있는 지점이다. Iceberg metastore table에서는 pointer CAS 성공 순간이다.
Base metadataWriter가 계획을 시작할 때 고정한 metadata version과 snapshot이다. Commit은 이 base가 여전히 유효한지 검증한다.
Orphan file물리 저장소에는 존재하지만 어떤 유효 snapshot metadata에서도 참조되지 않는 file이다. 실패한 시도의 정상 부산물일 수 있다.
Unknown commit stateCatalog가 CAS를 처리했는지 알기 전에 client 연결이 끊겨 성공·실패를 확정할 수 없는 상태다. 실패로 단정하고 batch를 다시 쓰면 중복될 수 있다.

2. 왜 중요한가

한 번의 INSERT도 실제로는 executor가 여러 data file을 쓰고, driver가 manifest와 manifest list를 만들고, 새 snapshot을 포함한 metadata JSON을 쓰는 분산 작업이다. 이 file들이 생성되는 순서는 제각각이고 일부 task는 재시도될 수 있다. 물리 file 존재만으로 table membership을 정하면 독자는 반쪽 결과, 중복, partial upload를 보게 된다.

Iceberg는 data plane의 큰 immutable object와 control plane의 작은 pointer를 분리한다. 새 object는 미리 준비하되 catalog pointer가 바뀌기 전에는 독자에게 보이지 않는다. Pointer swap 한 번으로 수천 개 file의 logical membership을 원자적으로 바꾸므로 object store에서 directory rename이나 consistent listing에 의존하지 않는다.

핵심 질문: “새 Parquet가 저장소에 있는가?”가 아니라 “현재 catalog pointer에서 시작한 metadata graph가 그 file을 참조하는가?”를 묻는다.

3. 아키텍처 그림과 요청 흐름

① Base load
catalog pointer P0 → metadata M0 → snapshot S0 고정
↓ plan · unique output identity
② Immutable file write
data/delete file 완전 close · 아직 table에는 안 보임
↓ collect path · metrics · partition · sequence intent
③ Metadata tree 준비
manifest → manifest list → snapshot S1 → metadata M1
↓ operation별 conflict validation
④ Catalog CAS: P0 → M1
expected=M0 일 때만 swap · linearization point
↓ success / conflict / response lost
⑤ 결과 확정
success: S1 공개 · conflict: 재검증 · unknown: status check

번호별 요청·응답·상태 변화

  1. Base load: Writer는 table 이름을 catalog에서 resolve하고 M0와 S0를 읽는다. Schema/spec/sort와 쓰기 operation의 가정을 함께 고정한다.
  2. File write: Task마다 충돌하지 않는 path에 Parquet/ORC/Avro data file 또는 v2/v3 delete file·DV를 쓴다. 성공한 task의 file만 driver가 수집한다. 이때 object storage가 file을 durable하게 저장해도 table membership은 아직 0이다.
  3. Metadata prepare: Driver는 file path·partition tuple·bounds·counts를 manifest에 쓰고, manifest list와 snapshot을 만든 뒤 self-contained M1을 새 path에 쓴다. 기존 M0와 S0는 수정하지 않는다.
  4. Validation: Append, overwrite, delete, rewrite마다 필요한 가정을 현재 state에서 다시 검사한다. 오늘은 swap 구조에 집중하고 상세 conflict 규칙은 Day 24에서 다룬다.
  5. CAS: Catalog가 현재 pointer가 M0인지 비교하고 M1로 바꾼다. 성공 전 reader는 S0 전체, 성공 후 refresh한 reader는 S1 전체를 본다. Metadata tree 내부 file 생성 시각은 공개 순서를 결정하지 않는다.
  6. Result: 명시적 conflict면 새 current state에 재적용 가능한지 검증한다. Network timeout이면 CAS가 이미 성공했을 수 있으므로 M1/snapshot/operation identity가 current history에 있는지 status check한다.

Reader의 data path

Reader는 catalog pointer → metadata JSON → 선택한 snapshot → manifest list → manifest → data/delete file 순서로만 membership을 찾는다. Field ID로 column을 projection하고 spec ID별 partition pruning, file metric pruning을 수행한 뒤 sequence number로 equality/position delete 또는 지원되는 deletion vector 적용 범위를 정한다. Warehouse listing은 이 authoritative path에 포함되지 않는다.

4. CS 관점의 내부 동작

개념Iceberg에서의 의미
Persistent data structure새 snapshot은 변한 manifest만 추가하고 불변인 old manifest를 재사용한다. Full table copy 없이 새 logical version을 만든다.
MVCCMulti-Version Concurrency Control. Reader는 시작 시 고른 committed snapshot version을 계속 읽고 writer는 별도 version을 준비한다.
LinearizabilityCatalog pointer update가 한 순서로 관찰돼 concurrent commit 중 하나만 같은 base에서 성공한다. Table Spec은 이 atomic operation의 구체 구현을 catalog에 위임한다.
Failure atomicityCAS 전 실패는 old state를 유지하고 prepared file을 orphan으로 남긴다. CAS 후 성공은 new graph 전체를 공개한다.
Idempotency boundaryCatalog status check와 batch identity로 이미 성공한 operation을 구분한다. 단순 SQL 재실행 자체가 자동으로 idempotent하다고 가정하면 안 된다.

상태의 소유자와 불변식

  • Object storage: Byte durability와 object identity를 소유한다. Table membership이나 current version은 소유하지 않는다.
  • Manifest: Data/delete file의 membership, partition, metric, sequence 정보를 소유한다. Warehouse directory name은 이 계약을 대체하지 못한다.
  • Snapshot/metadata JSON: Manifest graph와 schema/spec/order, snapshot history를 묶은 immutable table version이다.
  • Catalog: Table name의 current metadata pointer와 conditional update를 소유한다. Commit 성공을 확정하는 authoritative control plane이다.

5. 실무 설계 판단

Best practice 1 · publish-last: Data/delete file을 완전히 close하고 checksum·size·metrics를 얻은 뒤 manifest, manifest list, metadata JSON을 쓰고 마지막에만 pointer를 교체한다. Catalog에 먼저 빈 snapshot을 공개하고 file을 나중에 채우지 않는다.

Best practice 2 · unique path와 operation identity: Task attempt가 같은 object를 덮어쓰지 않도록 unique path를 쓰고, streaming checkpoint/batch ID·application ID·snapshot summary 같은 재현 가능한 증거로 unknown success를 판별한다. 어떤 key가 자동 제공되는지는 engine/version별로 확인한다.

Best practice 3 · 두 종류의 retry 분리: 명시적 CAS conflict의 rebase/revalidation retry와 network 단절 뒤 status-check retry를 구분한다. Apache Iceberg 1.11.0 문서의 기본 table property는 commit retry 4회, unknown state status check 3회지만 workload·catalog SLA에 맞춰 total timeout과 backoff를 설계한다.

Catalog/버전 차이: Metastore/DB catalog는 expected metadata location을 검사하는 check-and-put으로 pointer를 바꾼다. HadoopTableOperations의 file-system version/rename 방식은 Table Spec에서 deprecated이며 object store와 local file system에 안전하지 않고 v4에서 제거 예정이라고 명시돼 있다. REST catalog도 protocol과 구현이 실제 atomicity·status-check 동작을 제공해야 하므로 capability와 failure test가 필요하다.

Anti-pattern: Object 생성 시각이 최신인 metadata JSON을 current로 추측하거나, catalog timeout을 곧바로 실패로 기록해 같은 append를 다시 실행하거나, job 실패 직후 warehouse의 최근 file을 일괄 삭제하는 것이다.

Edge case: COW rewrite는 새 data file, MOR는 data와 equality/position delete file, v3 지원 경로는 deletion vector를 준비할 수 있지만 어느 경우든 current snapshot이 참조하기 전에는 logical effect가 없다. Commit 후에는 sequence number와 file membership을 보존한 채 읽어야 한다.

6. 장애 대응 표

상황: Writer가 timeout됐고 warehouse에는 새 file이 있지만 table 반영 여부가 불명확하다.

증상Driver에 timeout/unknown commit state, 새 data·manifest·metadata object 존재, row가 보이거나 안 보임, duplicate batch 가능성, catalog pointer와 job 로그 불일치, committed snapshot에서 object 404.
먼저 수집할 증거/지표Catalog current metadata location과 ETag/version, M0/M1 table UUID·current snapshot·metadata log, snapshots/summary/parent, manifest list와 manifest file paths, added data/delete file paths·sizes, batch/checkpoint/application ID, CAS request/response·retry/status-check 로그, object PUT/GET audit와 cleanup timeline.
가능한 가설CAS 성공 뒤 응답 유실, CAS conflict 후 prepared orphan, stale catalog/client cache, duplicate blind retry, partial upload, task retry duplicate output, wrong table/branch/catalog, cleanup race, object storage durability·IAM·KMS 문제.
안전한 첫 조치동일 batch 재실행과 orphan cleanup을 멈춘다. Catalog를 강제 refresh해 current pointer에서 metadata graph를 추적하고 operation identity·added file이 committed snapshot에 있는지 확인한다. Reader는 known-good snapshot을 pin한다.
Rollback/복구성공 확인 시 batch를 완료 처리하고 downstream offset을 맞춘다. 실패 확인 시 가정을 재검증해 재시도한다. Duplicate는 새 compensating delete/overwrite transaction으로 정정하고, missing committed object는 versioned backup/replica에서 같은 URI로 복원한 뒤 snapshot rollback 여부를 판단한다.
하지 말아야 할 조치Timeout을 실패로 단정한 blind append, metadata JSON·version hint·catalog pointer 수동 편집, warehouse 최신 file 일괄 삭제, committed file rename, 증거 전 snapshot expiration/orphan cleanup, raw listing으로 current state 추정은 금지한다.

실패 주입의 채점 기준

  • “File copy가 INSERT와 같은 효과”라고 답하면 오답이다. Manifest/snapshot/metadata와 catalog publish가 없다.
  • “Metadata JSON 생성이 commit 성공”도 오답이다. Catalog가 그 metadata를 current로 원자 교체해야 한다.
  • “Manual orphan을 즉시 production에서 지운다”도 오답이다. 실제 환경에서는 active writer·retry·branch와 age threshold 증거가 필요하다.

자주 나는 오류와 해결

  • Find 결과가 없음: 먼저 INSERT 성공과 warehouse/day22/commit_lab/data 경로를 확인한다.
  • Permission denied: Host workspace 소유권을 확인하고 container 내부 root 권한으로 임의 변경하지 않는다.
  • Raw Parquet path 오류: Container에서 보이는 절대 경로는 /workspace/warehouse/...다.
  • Metadata table column 차이: Connector/version에 따라 column projection이 다를 수 있으므로 DESCRIBE local.day22.commit_lab.files로 확인한다.
  • Manual orphan이 table에 보임: Raw Parquet 결과와 Iceberg table 결과를 혼동했는지, 잘못된 table/catalog를 조회했는지 확인한다.

8. 놓치기 쉬운 함정

  1. Parquet upload 성공이 commit 성공이다. CAS 전에는 table effect가 없다.
  2. Metadata JSON이 가장 최신 timestamp면 current다. Catalog pointer만 current를 정한다.
  3. Atomic commit은 모든 file의 atomic rename이다. 큰 file은 미리 쓰고 작은 pointer 하나를 atomic swap한다.
  4. Timeout은 실패다. CAS 후 응답만 유실됐을 수 있어 status check가 먼저다.
  5. 모든 retry는 같은 SQL을 다시 실행하면 된다. Revalidation과 idempotency 없이 append하면 중복될 수 있다.
  6. Orphan은 발견 즉시 삭제한다. Active writer와 장기 retry가 아직 쓸 file일 수 있다.
  7. Object store listing consistency가 table correctness를 결정한다. Reader는 catalog에서 시작한 explicit graph를 따른다.
  8. 모든 catalog의 atomic 구현이 같다. Spec은 메커니즘을 위임하며 Hadoop file scheme과 metastore CAS의 경계가 다르다.

9. 대기업 기술 면접 질문 3개

  1. Object store 위 Iceberg INSERT의 성공 시점을 설계 수준으로 설명하라.
    좋은 답변 구조: State owners → immutable data/metadata prepare → base validation → catalog CAS linearization point → reader old/new visibility → failure windows → object store listing을 쓰지 않는 이유.
  2. Commit API가 timeout됐는데 file은 생성됐다. 중복 없이 복구하라.
    좋은 답변 구조: Unknown state 선언 → 증거와 operation identity → current metadata/snapshot/manifest 추적 → success/failure 분기 → status-check/backoff → duplicate compensating transaction → 금지 조치.
  3. 초당 50개 streaming commit과 batch compaction이 같은 table을 쓴다. Control plane을 설계하라.
    좋은 답변 구조: Commit rate·catalog SLA 수치 → CAS contention → checkpoint/idempotency → retry/status-check budget → maintenance scope → metrics/alerts → branch/WAP·commit coalescing 대안과 비용.

10. 어제 내용 회상 3문제

  1. Metadata-only evolution과 semantic migration은 무엇이 다른가?
  2. Column rename 후 Iceberg read는 되지만 raw Parquet read가 깨질 수 있는 이유는?
  3. Partition/sort evolution 후 correctness에는 rewrite가 불필요해도 targeted rewrite를 선택할 수 있는 기준은?
짧은 정답/채점 기준
  1. 전자는 ID와 metadata로 old bytes를 새 logical state에 연결하고, 후자는 historical business value/meaning을 실제 변경한다. Physical vs semantic을 말하면 정답.
  2. Iceberg는 field ID, raw reader는 physical name/position을 identity로 쓰기 때문이다. Identity source 차이가 핵심.
  3. Planning p95, scanned bytes/file 수, manifest fan-out, bounds overlap, compression·query SLO 같은 측정치다. 수치 threshold와 비용을 말하면 정답.

11. 오늘 내용 확인 문제 3개

  1. Data file·metadata JSON 생성이 아니라 catalog pointer CAS가 commit 성공 시점인 이유는?
  2. CAS 응답을 받기 전에 network가 끊기면 왜 blind retry하면 안 되는가?
  3. Object storage와 catalog가 각각 소유하는 상태는 무엇인가?
짧은 정답/채점 기준
  1. Pointer 교체 전 artifact는 current graph에서 도달할 수 없고 교체 후 전체 graph가 한꺼번에 reachable해지기 때문이다. Reachability+linearization이 핵심.
  2. CAS는 성공했지만 응답만 유실됐을 수 있어 같은 append를 다시 하면 중복된다. Unknown state→status check를 말하면 정답.
  3. Object storage는 immutable bytes/durability, catalog는 table name의 current metadata pointer와 conditional update를 소유한다. Data plane/control plane을 구분하면 정답.
