APACHE ICEBERG · WEEK 2 / DAY 10

manifest list와 manifest entry

Metadata Tree와 Scan Planning · 예상 학습 30분 + 실습 35분

한 줄 요약
Manifest list는 snapshot이 사용할 manifest들의 작은 색인이고, manifest entry는 각 data/delete file의 table membership과 통계를 기록한다. 이 두 층 덕분에 Iceberg는 object storage 전체를 나열하지 않고 필요한 파일만 찾는다.

1. 선수 용어 사전

AvroSchema와 record를 함께 다루는 직렬화 file format이다. Iceberg의 manifest list와 manifest는 Avro로 저장된다.
Manifest list한 snapshot에 속한 manifest file 목록과 요약을 담는 snapshot별 Avro index다.
Manifest같은 partition spec과 같은 content 종류의 file entry 묶음이다. Data manifest와 delete manifest가 분리된다.
Manifest entryFile 하나에 대한 status, snapshot/sequence와 data_file 구조를 담는 record다.
PruningPredicate와 절대 겹치지 않는 metadata/file을 읽기 전에 제외하는 과정이다.
Sequence numberFile content의 상대적 나이를 나타내는 commit 순서 값이다. Delete 적용과 incremental ordering에 사용된다.
COW / MOR / DVCopy-on-write는 data file을 다시 쓰고, merge-on-read는 delete 정보를 읽을 때 합친다. DV(deletion vector)는 v3의 delete 표현이며 engine 지원은 별도 확인한다.

2. 왜 중요한가

Object storage directory를 전부 list해 현재 file을 찾으면 table 크기와 무관하게 path 수에 비례한 O(n) metadata I/O가 필요하다. Iceberg는 catalog에서 시작하는 명시적 graph를 따라가므로 “존재하는 object”와 “현재 snapshot에 속한 object”를 분리한다.

Manifest list와 manifest는 단순 파일 목록이 아니다. Partition 범위, file 수, row 수, column bounds를 여러 층에 둔 index다. Query planner는 작은 상위 index에서 후보를 줄인 뒤 더 자세한 하위 index를 읽는다. 동시에 writer는 기존 manifest를 재사용해 매 commit마다 table 전체 파일 목록을 다시 쓰지 않는다.

핵심 불변식: Snapshot의 manifest list에서 도달해 live로 해석되는 entry만 table state에 속한다. Warehouse에 object가 존재하거나 entry의 status가 DELETED라는 사실만으로 즉시 물리 삭제 여부를 판단하지 않는다.

3. 아키텍처 그림과 요청 흐름

① Catalog pointer
Current metadata JSON location
↓ current-snapshot-id
② Snapshot
manifest-list path · schema/spec/sequence context
↓ partition summary로 manifest pruning
③ Manifest list
manifest path/length · spec ID · content · sequence · file/row counts
↓ 필요한 manifest만 read
④ Manifest entries
status · snapshot/sequence · path · partition · record/file/column metrics
↓ entry/file metrics로 file pruning
⑤ Data / Delete files
Parquet row-group pruning · COW 또는 MOR/DV merge

Read 요청·응답·상태 변화

  1. Reader는 catalog가 가리키는 metadata JSON과 선택 snapshot을 고정한다. 이것이 control path의 root다.
  2. Manifest list의 partition summaries를 query predicate와 비교해 겹치지 않는 manifest를 제외한다.
  3. 남은 manifest만 읽고 각 entry의 partition과 column metrics로 data/delete file 후보를 줄인다.
  4. Data path는 선택된 file byte를 읽는다. MOR에서는 sequence rule로 적용 가능한 equality/position delete 또는 DV를 병합한다.
  5. Reader가 고정한 snapshot graph는 concurrent commit이 current pointer를 바꿔도 변하지 않는다.

Write·commit 요청과 상태 변화

  1. Writer는 base snapshot과 expected catalog pointer를 읽고 immutable data/delete file과 새 manifest를 쓴다.
  2. 작은 manifest merge 정책에 따라 기존 manifest를 그대로 재사용하거나 entries를 새 manifest로 rewrite한다.
  3. Commit attempt마다 새 manifest list와 snapshot, metadata JSON을 만든다. 새 manifest의 optimistic sequence 값은 commit에서 확정된다.
  4. Engine은 append/overwrite/delete 범위와 base 이후 변경을 validation한다. Conflict면 새 current를 load해 안전한 operation만 재계획한다.
  5. Catalog의 atomic pointer swap이 성공하는 순간 commit이 확정된다. 그 전 object는 생성됐어도 current table state가 아니다.

4. CS 관점의 내부 동작

개념Manifest tree에서의 의미
Two-level indexManifest list는 manifest 범위 index, manifest는 file-level index다. 필요한 하위 block만 읽어 planning I/O를 줄인다.
Persistent structure새 snapshot은 바뀐 manifest를 추가하면서 unchanged manifest를 공유한다. Version 생성 비용이 전체 table 크기보다 변경량에 가까워진다.
Tri-state deltaEXISTING(0), ADDED(1), DELETED(2)는 manifest가 추가된 snapshot을 기준으로 membership 변화를 표현한다. DELETED entry는 scan에 쓰지 않는 정보다.
Context inheritanceAdded entry의 nullable snapshot/sequence는 manifest-list metadata에서 상속될 수 있다. Raw null을 “값 없음”으로 해석하면 안 된다.
Logical clockData sequence는 content age와 delete applicability, file sequence는 file이 table에 들어온 순서를 표현한다. 둘은 목적이 다르다.
Linearization pointManifest byte 생성이 아니라 catalog pointer CAS/atomic swap 성공이 commit의 단일 확정 시점이다.

Manifest list가 저장하는 것

  • 주소와 크기: manifest_path, manifest_length.
  • 해석 context: partition_spec_id, data/delete content, sequence_number, min_sequence_number, added_snapshot_id.
  • 요약: ADDED/EXISTING/DELETED file·row count와 partition field lower/upper/null summaries.
  • Version 경계: v1은 content와 sequence가 없어서 reader가 data/0으로 해석한다. v3에는 row lineage 관련 field가 추가될 수 있다.

Manifest entry가 저장하는 것

status, snapshot_id, sequence_number, file_sequence_number와 중첩된 data_file 구조다. Data_file에는 content, path, format, partition tuple, record_count, file_size와 field ID별 value/null/NaN count, lower/upper bounds 등이 있다. Field ID가 column rename/reorder 뒤에도 metric 의미를 연결하고 partition spec ID가 old/new partition tuple을 해석한다.

5. 실무 설계 판단

판단Best practice와 이유
Manifest 크기Planning latency, manifest count/bytes, entries per manifest와 commit rate를 같이 본다. 너무 작으면 open/I/O가 늘고 너무 크면 selective query도 큰 index를 읽는다.
Partition clustering자주 쓰는 predicate의 partition range가 manifest마다 겹치지 않게 쓰기 분배와 manifest clustering을 관찰한다. 같은 file 수라도 pruning 효과가 달라진다.
Rewrite manifestsBefore/after manifest count, planning p95와 predicate별 scanned manifests를 비교한다. Rewrite도 새 optimistic commit이므로 writer race와 retry를 runbook에 넣는다.
Format versionV1/V2/V3 manifest field와 delete/DV 지원을 engine별 compatibility matrix로 검증한다. Spec 가능과 connector 구현을 동일시하지 않는다.
관찰 API운영 진단은 Spark manifests, all_manifests, entries, files metadata table을 우선 사용한다. Column 이름은 runtime의 DESCRIBE로 확인한다.

Anti-pattern: Manifest 수가 많다는 이유만으로 writer와 동시에 무조건 rewrite를 반복하는 것. Planning 개선보다 maintenance commit, object I/O와 conflict 비용이 더 커질 수 있다.

Edge case: Partition evolution 뒤에는 서로 다른 spec ID의 manifest가 공존한다. 같은 position의 partition value를 같은 의미로 비교하지 말고 spec ID와 field ID 기반으로 predicate를 projection해야 한다.

6. 장애 대응 표

상황: Commit rate가 오른 뒤 query planning p95가 급증하고 driver가 manifest I/O에 오래 머문다.

증상Planning p95 상승, manifest GET/bytes 증가, driver CPU/heap 상승, 실행 task가 시작되기 전 지연, selective query도 많은 manifest scan.
먼저 수집할 증거/지표Current snapshot/metadata location, manifests/all_manifests row와 size/count, entries/file count, partition summaries 겹침, commit rate, planning/scan report, object GET latency/404, recent rewrite와 writer conflict log.
가능한 가설작은 append가 만든 manifest 폭증, range가 겹치는 poor clustering, stale cache, object storage throttling, partition evolution 혼재, connector regression, maintenance와 writer race.
안전한 첫 조치Read-only로 current snapshot의 manifest 분포와 query predicate가 건너뛴 비율을 확인한다. 작은 비핵심 table/branch에서 rewrite 효과와 conflict를 재현하고 write rate를 임시 완화한다.
Rollback/복구Rewrite commit이 성능/호환 문제를 만들었으면 retained known-good snapshot으로 rollback한다. Writer policy와 rewrite threshold를 조정하고 canary·planning SLO를 둔다.
하지 말아야 할 조치Manifest Avro를 직접 삭제·편집하지 않는다. Current graph 확인 없이 metadata directory를 정리하지 않는다. Active writer와 무제한 rewrite를 경쟁시키지 않는다. 단일 query latency만으로 원인을 확정하지 않는다.

2단계 · Logical metadata graph 조회

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SELECT committed_at, snapshot_id, parent_id, operation, manifest_list
FROM local.day10.manifest_lab.snapshots ORDER BY committed_at;

SELECT content, path, length, partition_spec_id, added_snapshot_id,
       added_data_files_count, existing_data_files_count,
       deleted_data_files_count, partition_summaries
FROM local.day10.manifest_lab.manifests ORDER BY path;

SELECT status, snapshot_id, sequence_number, file_sequence_number,
       data_file.content, data_file.file_path,
       data_file.partition, data_file.record_count
FROM local.day10.manifest_lab.entries ORDER BY data_file.file_path;

SELECT content, file_path, partition, record_count, file_size_in_bytes
FROM local.day10.manifest_lab.files ORDER BY file_path;
"

예상 관찰: Snapshot의 manifest_list path가 manifest rows를 가리키고, live entry의 data_file.file_path가 files row와 연결된다. Entry status는 0/1/2이며 current scan은 live 상태만 사용한다.

예상 관찰: Rogue Avro object는 directory에는 있지만 어떤 current manifest list도 가리키지 않는다. Manifest/entry/table row count는 복사 전과 동일해야 한다.

자주 나는 오류와 해결

  • entries column 오류: DESCRIBE local.day10.manifest_lab.entries로 runtime schema를 보고 nested field 이름을 조정한다.
  • manifest pattern이 비어 있음: find .../metadata -type f로 실제 writer naming을 확인하고 manifest row의 path와 대조한다.
  • Current manifest 수가 예상과 다름: Writer manifest merge가 동작할 수 있다. Snapshots의 manifest_list와 all_manifests를 함께 본다.
  • Sequence가 null: Added entry는 manifest-list context에서 상속될 수 있다. Metadata table projection과 spec version을 확인한다.
  • Warehouse 경로가 다름: Metadata table의 absolute path를 기준으로 catalog warehouse 설정을 확인한다.
  • Docker 연결 실패: Docker daemon을 시작하고 make smoke가 성공한 뒤 실습을 재개한다.

8. 놓치기 쉬운 함정

  1. Manifest list와 manifest는 같은 파일이다. 전자는 snapshot별 manifest index, 후자는 file entry 묶음이다.
  2. Manifest 하나는 한 commit이다. Manifest는 snapshot 사이에서 재사용·merge될 수 있어 1:1이 아니다.
  3. DELETED entry면 object가 즉시 사라진다. Scan에서 제외된 logical delta이며 물리 삭제는 snapshot expiration/GC 뒤다.
  4. Null sequence는 unknown이다. Added entry는 manifest-list context에서 값을 상속할 수 있다.
  5. File path가 warehouse에 있으면 live다. Current graph reachability와 entry status가 membership을 결정한다.
  6. Partition value position만 보면 된다. Evolution 후에는 partition spec ID와 field ID를 함께 해석한다.
  7. Manifest rewrite는 무상이다. Object I/O와 새 commit, writer conflict, cache invalidation 비용이 있다.
  8. 모든 engine이 V3/DV와 metadata table을 동일 지원한다. Spec과 connector version의 차이를 compatibility test로 고정한다.

9. 대기업 기술 면접 수준 질문

Q1. “10PB table에서 predicate에 맞는 file을 어떻게 찾습니까?”

좋은 답변 구조: File/partition/manifest 수 가정 → catalog root → snapshot → manifest list partition summary → manifest entry partition/column metric → Parquet row group → single-node planning I/O 수치 → poor clustering/false positive → distributed listing 대안과 trade-off.

Q2. “ADDED/EXISTING/DELETED와 sequence inheritance를 설명하세요.”

좋은 답변 구조: Manifest가 추가된 snapshot 기준 delta → 각 status의 scan 의미 → snapshot/data/file sequence 구분 → added null 상속 → delete applicability → COW/MOR/DV → v1/v2/v3와 engine 지원 경계 → raw Avro 진단 함정.

Q3. “Manifest 폭증으로 planning latency가 느릴 때 운영 설계를 제시하세요.”

좋은 답변 구조: Planning p95·manifest count/bytes·commit rate 수치 → partition summary 겹침 → write/merge 정책 → canary rewrite → optimistic conflict/maintenance race → rollback snapshot → engine cache/compatibility → data file compaction과 구분.

10. 어제 내용 회상 3문제

  1. Snapshot, history, refs는 각각 어떤 질문에 답하는가?
  2. Branch/tag를 만들어도 full table copy가 필요 없는 이유는?
  3. Snapshot expiration 전에 refs를 inventory해야 하는 이유는?
짧은 정답/채점 기준
① Snapshot=immutable state node, history=main current 전이 log, ref=named snapshot pointer를 모두 구분하면 3점.
② Ref가 기존 snapshot/manifest/file graph root를 공유하며 file을 복제하지 않는다고 설명하면 2점.
③ Live ref와 retention이 old snapshot/file reachability를 보호하므로 잘못 expire하면 감사·branch read가 깨진다고 설명하면 2점.

11. 오늘 내용 확인 문제 3개

  1. Manifest list와 manifest가 각각 어느 수준에서 pruning하는가?
  2. Manifest entry의 DELETED는 무엇을 의미하며 물리 file 삭제와 왜 다른가?
  3. Added entry의 null sequence를 raw null로 해석하면 안 되는 이유는?
짧은 정답/채점 기준
① Manifest list는 partition summary로 manifest를, manifest는 partition/column metric으로 file을 pruning한다고 답하면 2점.
② Snapshot 기준 logical membership delta이며 scan에서 제외되지만 object GC는 retained snapshot 만료 뒤라고 답하면 2점.
③ Snapshot/data/file sequence가 manifest-list context에서 상속될 수 있고 delete applicability에 필요하다고 답하면 3점.
