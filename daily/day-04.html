APACHE ICEBERG · WEEK 1 / DAY 04

snapshot·time travel 첫 관찰

Lakehouse와 Table Format 정신 모델 · 예상 학습 30분 + 실습 30분

한 줄 요약
Snapshot은 table 전체를 복사한 백업이 아니라 특정 시점의 metadata tree root이며, time travel은 current pointer를 바꾸지 않고 과거 snapshot에서 read path를 시작하는 읽기 연산이다.

1. 선수 용어 사전

Snapshot한 commit이 만든 immutable table state다. Snapshot ID, 생성 시각, parent snapshot, operation summary와 manifest list 위치를 가진다.
Current snapshot기본 branch인 main이 현재 가리키는 snapshot이다. 일반 SELECT는 이 state를 읽는다.
Snapshot log과거에 current였던 snapshot ID와 시각의 기록이다. 특정 timestamp의 time travel state를 고르는 기준이다.
LineageParent snapshot ID로 이어지는 계보이다. Git commit의 parent 관계와 비슷하지만 Iceberg snapshot은 table data/metadata state를 가리킨다.
Time travelSnapshot ID, timestamp, tag 같은 selector로 과거의 유효한 state를 read-only 조회하는 기능이다.
Rollback과거 snapshot을 다시 current로 만드는 상태 변경이다. Time travel 조회와 달리 catalog pointer와 table history를 바꾸는 commit이다.
Branch / TagBranch는 새 commit으로 head가 움직일 수 있는 named reference이고, tag는 특정 snapshot을 붙잡는 named reference다. 각각 retention 정책을 가질 수 있다.
RetentionSnapshot과 참조 file을 얼마나 오래 보존할지 정하는 수명 정책이다. Time travel 가능 기간과 storage 비용을 함께 결정한다.

2. 왜 중요한가

데이터 파이프라인의 현재 결과가 잘못됐을 때 가장 먼저 필요한 것은 “수정”이 아니라 언제부터 무엇이 달라졌는지 재현하는 일이다. Snapshot을 알면 배포 전후 row count, file membership, schema와 operation summary를 같은 table에서 비교할 수 있다. Backfill 검증, 감사, 장애 원인 분석과 재현 가능한 분석의 공통 기반이다.

하지만 time travel을 backup으로 오해하면 위험하다. 과거 snapshot도 같은 object storage의 data file을 참조한다. Snapshot expiration이나 잘못된 file 삭제, bucket 손상, 계정/IAM 사고가 생기면 과거 state도 읽지 못할 수 있다. Time travel은 logical history이고, backup/DR은 독립 장애 영역의 복구 수단이다.

핵심 불변식: Time travel reader는 선택한 snapshot에서 도달 가능한 manifest와 data/delete file만 읽으며, 조회 자체는 current snapshot을 바꾸지 않는다.

3. 아키텍처 그림과 요청 흐름

같은 catalog와 metadata JSON에서 시작하되 selector가 current인지 과거인지에 따라 snapshot root만 달라진다.

① SQL selector
SELECT current · VERSION AS OF snapshot/tag · TIMESTAMP AS OF time
↓ resolve table
② Catalog pointer
table name → current metadata JSON
↓ choose root
③ Snapshot selector
current-snapshot-id OR explicit snapshot/tag OR snapshot-log timestamp lookup
↓ immutable read path
④ Snapshot → manifest list → manifest
partition/file metrics로 pruning
↓ selected content
⑤ Data file + 적용 가능한 delete file
과거 snapshot의 schema·sequence 규칙으로 row 구성

A. Current SELECT

  1. Engine이 catalog에서 현재 metadata location을 load한다.
  2. Metadata JSON의 current-snapshot-id 또는 main reference를 선택한다.
  3. 선택한 snapshot의 manifest tree에서 file을 pruning하고 scan task를 만든다.
  4. Query 도중 새 writer가 commit해도 이미 선택한 snapshot은 immutable이므로 partial state로 바뀌지 않는다.

B. VERSION AS OF

  1. Client가 snapshot ID 또는 tag 이름을 selector로 제공한다.
  2. Engine은 current metadata가 보존하는 snapshot/reference에서 selector를 검증한다.
  3. 해당 snapshot의 manifest list로 read root를 바꾼다. Catalog의 current pointer는 그대로다.
  4. Snapshot ID나 tag로 조회할 때 schema 선택 규칙은 engine/selector에 따라 다를 수 있다. Spark 공식 문서는 snapshot ID와 tag 조회에는 snapshot schema, branch head 조회에는 table schema를 사용하는 경우를 구분한다.

C. TIMESTAMP AS OF

  1. Engine이 사용자가 준 timestamp를 명확한 timezone 기준으로 해석한다.
  2. Table spec에 따라 snapshot-log에서 그 시각보다 같거나 앞선 마지막 current snapshot을 찾는다.
  3. 선택된 snapshot에서 동일한 manifest/data read path를 수행한다. 정확히 그 시각에 새 파일을 재구성하는 연산이 아니다.
  4. 해당 시각보다 앞선 snapshot이 없거나 snapshot-log가 보존되지 않았다면 informative error로 실패해야 한다.

4. CS 관점의 내부 동작

개념Snapshot/time travel에서의 의미
Persistent data structure새 snapshot은 변하지 않은 manifest/data file을 과거 snapshot과 공유할 수 있다. 전체 table 복사 없이 여러 logical version을 유지한다.
MVCC 정신 모델Multi-Version Concurrency Control처럼 reader가 한 committed version을 고정한다. 구현은 database page version이 아니라 immutable files와 metadata pointer다.
State ownerMetadata JSON이 snapshots·snapshot-log·refs를 소유하고, snapshot이 manifest-list root를, storage가 실제 byte를 소유한다. Engine은 selector와 scan을 해석한다.
OrderingSnapshot ID는 시간순 번호가 아니다. V2/V3 sequence number는 table change 순서를 나타내며 delete 적용 판단에도 쓰인다. Timestamp lookup은 snapshot-log를 사용한다.
IsolationReader가 잡은 snapshot root는 query 중 변하지 않는다. Writer의 catalog pointer swap은 새 reader의 root를 바꾸지만 기존 reader의 root를 mutate하지 않는다.
Garbage collectionSnapshot expiration은 더 이상 보존할 history에서 snapshot을 제거하고, 어떤 retained snapshot/ref에서도 참조하지 않는 file만 삭제 가능하게 한다.

Time travel과 rollback의 state transition 차이

연산읽는 rootTable state 변화
현재 조회current snapshot없음
Time travel명시한 과거 snapshot없음
Rollback검증 후 과거 snapshotCurrent reference를 바꾸는 commit

Failure window와 비용

  • Catalog outage: 이미 load한 snapshot으로 진행 중인 read는 계속될 수 있지만, 새 load/refresh와 rollback commit은 실패할 수 있다.
  • Storage object missing: Snapshot metadata가 살아 있어도 참조 data/delete file이 없으면 과거 read가 실패한다.
  • Expire와 장기 reader race: Reader가 사용하는 snapshot/file의 수명보다 공격적인 expiration/cleanup 정책은 query 실패나 corruption 위험을 만든다.
  • Retention 증가: 감사·rollback 기간은 길어지지만 metadata와 더 이상 current가 아닌 data/delete file의 storage 비용도 늘어난다.
  • Retention 축소: 비용과 metadata 크기는 줄지만 incident investigation, late reprocessing과 reproducibility window도 줄어든다.

5. 실무 설계 판단

판단Best practice와 이유
Retention SLO감사 기간, 최대 backfill 지연, incident 탐지 시간, reader 최대 실행 시간을 수치화한 뒤 snapshot/ref 보존 기간을 정한다. 관성적으로 기본값만 쓰지 않는다.
재현 identityDashboard·모델·batch 결과에 table identifier, snapshot ID, query/app version과 timestamp timezone을 함께 기록한다.
중요 state 고정감사·월말 마감처럼 만료되면 안 되는 snapshot은 명시적 tag와 retention으로 보호하고 정기적으로 refs를 감사한다.
Maintenance 분리Expire snapshots와 remove orphan files를 다른 책임과 runbook으로 운영한다. Dry-run/후보 목록, safety window, 진행 중 writer와 branch/tag를 확인한다.
복구 전 검증먼저 과거 snapshot을 read-only time travel로 검증하고, row/file/schema 차이를 승인한 뒤 rollback이나 compensating write를 선택한다.
Multi-engineSpark·Flink·Trino의 snapshot/tag/branch syntax, schema selection, timestamp precision/timezone, format version과 delete/DV 지원을 compatibility matrix로 시험한다.

Anti-pattern: “최근 7일 time travel 가능”을 SLA로 약속하면서 expiration job, tag retention, backup 또는 모니터링을 코드와 운영 정책으로 고정하지 않는 것.

Edge case: Partition evolution 뒤 과거 snapshot은 old partition spec의 file을 가리킬 수 있다. Reader는 snapshot→manifest의 spec ID를 따라야 하며, 현재 directory layout만 보고 과거 partition을 추측하면 안 된다. Row-level delete가 있는 table은 snapshot과 sequence number에 맞는 position/equality delete 또는 v3 deletion vector를 적용해야 한다.

6. 장애 대응 표

상황: 어제 snapshot을 time travel하자 “snapshot not found” 또는 file read 오류가 발생한다.

증상Snapshot ID 없음, timestamp 이전 snapshot 없음, metadata는 열리지만 data/delete file 404, engine별 과거 row/schema 불일치.
먼저 수집할 증거/지표Current metadata location, snapshots/history/refs, 요청 snapshot ID와 UTC timestamp, 최근 expire/remove-orphan 실행 시각·인자·결과, failing file URI, catalog/storage audit log, engine/connector/format version.
가능한 가설Snapshot expiration, tag/ref 미생성 또는 만료, timezone 오해, 잘못된 table/catalog, storage lifecycle/manual delete, engine cache 또는 unsupported selector/schema/delete feature.
안전한 첫 조치Write와 maintenance를 일시 중지하고 현재 table을 변경하지 않은 채 snapshots/history/refs와 정확한 failing URI를 보존한다. Known-good snapshot을 read-only로 확인한다.
Rollback/복구Snapshot과 file이 유효하면 time travel 결과를 검증한 뒤 승인된 rollback/cherry-pick/compensating write를 수행한다. File이 삭제됐다면 독립 backup/replica에서 byte와 catalog/metadata 일관성을 함께 복원하고 새 table에서 먼저 검증한다.
하지 말아야 할 조치Metadata JSON이나 current pointer를 직접 편집하지 않는다. Missing file을 빈 파일로 대체하지 않는다. 증거 수집 전에 expiration/orphan cleanup을 재실행하지 않는다. Timezone을 바꿔가며 무작위 rollback하지 않는다.

자주 나는 오류와 해결

  • FIRST_SNAPSHOT_ID parse 오류: 문자열 그대로 두지 말고 첫 snapshot의 숫자 ID로 치환한다. Snapshot ID를 timestamp처럼 해석하지 않는다.
  • Snapshot ID 순서 오판: 숫자 크기로 과거/현재를 정하지 말고 committed_at과 parent_id를 함께 본다.
  • Timestamp 조회 결과가 예상과 다름: Session timezone과 literal timezone을 기록하고 snapshot-log 시각과 비교한다.
  • Warehouse path 불일치: DESCRIBE TABLE EXTENDED의 Location을 확인한다. Catalog/namespace 설정에 따라 경로가 달라질 수 있다.
  • Metadata table column 차이: Engine/Iceberg runtime별 schema를 DESCRIBE local.day04.snapshot_lab.snapshots로 확인하고 지원 matrix에 기록한다.
  • Iceberg runtime cache/공간 오류: make smoke와 docker compose ps를 먼저 확인하고 Docker disk 및 프로젝트의 Ivy cache 경로를 점검한다.

8. 놓치기 쉬운 함정

  1. Snapshot은 table 전체 복사다. 기존 immutable file을 공유하는 metadata root이므로 copy 비용 없이 version을 만들 수 있다.
  2. Time travel은 rollback이다. Time travel은 read-only selector이고 rollback은 current reference를 변경하는 commit이다.
  3. Snapshot ID가 클수록 최신이다. Snapshot ID는 충돌 가능성을 낮춘 고유값이며 시간순 sequence가 아니다.
  4. Timestamp는 snapshot 생성 계보만 보면 된다. Table spec은 과거 current state를 나타내는 snapshot-log를 point-in-time lookup에 사용한다.
  5. History가 있으면 file도 영원히 있다. Expiration, lifecycle, 수동 삭제와 storage 장애는 time travel 가능성을 없앨 수 있다.
  6. Time travel은 backup/DR이다. 같은 storage 장애 영역과 credentials에 의존하므로 독립 복구본을 대체하지 않는다.
  7. 과거 snapshot은 현재 schema로만 읽힌다. Snapshot ID/tag/branch selector별 schema semantics와 engine 차이를 검증해야 한다.
  8. Expire와 orphan cleanup은 같은 일이다. 전자는 snapshot retention graph를 처리하고 후자는 metadata에서 참조되지 않는 file 후보를 찾는다. Safety window와 race가 다르다.

9. 대기업 기술 면접 수준 질문

Q1. “Iceberg time travel을 구현 관점에서 설명하고 backup과 비교하세요.”

좋은 답변 구조: 재현/감사 요구사항 → catalog pointer→metadata JSON→snapshot-log/selector→manifest list→manifest→data/delete file read path → immutable file 공유와 snapshot isolation → current pointer 불변 → expiration/storage failure window → 30일 retention의 metadata/storage 비용 → 독립 bucket/account backup·replication 대안과 RPO/RTO.

Q2. “하루 10만 commit table에서 90일 time travel SLO를 어떻게 설계합니까?”

좋은 답변 구조: Commit rate·snapshot/manifest/file 증가량 수치 가정 → 감사/late data/reader 최대 시간 → branch/tag와 retention 정책 → metadata rewrite·snapshot expiration schedule → object lifecycle 금지/정렬 → planning latency·storage 비용 모델 → dry-run·지표·alert → snapshot granularity를 줄이는 commit batching 대안과 latency trade-off.

Q3. “잘못된 MERGE 뒤 rollback 여부를 어떻게 결정합니까?”

좋은 답변 구조: 영향 범위와 downstream consumption 중지 → current/parent snapshot, summary, schema/spec, data/delete/DV 증거 → 과거 snapshot read-only 검증 → rollback이 concurrent valid write를 되돌릴 위험 → compensating MERGE/cherry-pick/branch 검증 대안 → catalog CAS conflict와 ambiguous outcome → 승인·audit·재발 방지.

10. 어제 내용 회상 3문제

  1. INSERT의 성공이 확정되는 linearization point는 어디인가?
  2. SELECT가 file을 고르는 경로를 catalog부터 순서대로 말하라.
  3. Data file은 써졌지만 commit 전에 실패한 file과 row의 상태는?

짧은 정답/채점 기준

  1. Catalog의 current metadata pointer 원자 교체가 성공하는 순간이라고 답하면 통과.
  2. Catalog pointer → metadata JSON → snapshot → manifest list → manifest → data/delete file 순서를 말하면 통과.
  3. Storage에는 존재할 수 있지만 current snapshot에서 도달하지 않는 orphan 후보이며 row는 공개되지 않았다고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. Time travel과 rollback의 table state 변화 차이를 설명하라.
  2. Timestamp time travel은 어떤 history를 기준으로 snapshot을 고르는가?
  3. Snapshot retention을 짧게 잡을 때 비용 외에 잃는 운영 능력 세 가지는?

짧은 정답/채점 기준

  1. Time travel은 current를 바꾸지 않는 read, rollback은 current reference를 바꾸는 commit이라고 답하면 통과.
  2. 그 시각 이전의 마지막 current state를 나타내는 snapshot-log라고 답하면 통과.
  3. Incident 조사·감사/재현·late backfill 또는 rollback window 중 세 가지를 비용과 연결해 답하면 통과.
