APACHE ICEBERG · WEEK 2 / DAY 12

partition/manifest/file pruning

Metadata Tree와 Scan Planning · 예상 학습 30분 + 실습 35분

한 줄 요약
Iceberg scan planning은 query predicate를 partition transform에 투영해 manifest를 줄이고, manifest entry의 partition·column metric으로 file을 줄인 뒤, file format index로 row group을 줄이는 계층형 증명 과정이다.

1. 선수 용어 사전

PredicateWHERE 절처럼 row가 조건을 만족하는지 판정하는 식이다.
ProjectionSource-column predicate를 partition transform의 값에 적용 가능한 보수적 predicate로 바꾸는 과정이다.
Partition specSource field ID, transform, partition field ID와 이름의 집합이다. Evolution 뒤 여러 spec이 공존할 수 있다.
Partition summaryManifest list가 manifest 안 partition 값의 null/NaN 여부와 lower/upper 범위를 요약한 index다.
File metricManifest entry의 field-ID별 value/null/NaN count와 lower/upper bound다.
SargableIndex가 검색 범위를 계산할 수 있는 predicate 형태를 뜻한다. 임의 함수로 감싸면 pushdown이 약해질 수 있다.
Candidate fileMetadata만으로 match 가능성을 배제하지 못해 실제로 읽어야 하는 file이다.

2. 왜 중요한가

1PB table에서 query가 하루치 1GB만 필요해도 planner가 모든 object를 list하고 모든 footer를 열면 scan 시작 전부터 비용이 폭발한다. Iceberg는 catalog가 가리키는 metadata graph와 작은 synopsis를 위에서 아래로 읽어 후보 집합을 단계별로 축소한다.

Pruning은 단순한 “partition skip”이 아니다. Query predicate → spec별 partition predicate → manifest summary → entry partition/metric → Parquet row group으로 이어지는 pipeline이다. 어느 단계가 selectivity를 잃었는지 알아야 partition spec, sort order, metric mode, file size와 manifest maintenance를 올바르게 조정할 수 있다.

핵심 불변식: 각 단계는 match가 불가능하다고 증명된 후보만 제거한다. 정보가 없거나 transform을 이해하지 못하면 유지한다. False positive I/O는 허용하지만 답이 있는 file을 제거하는 false negative는 허용하지 않는다.

3. 아키텍처 그림과 요청 흐름

① Catalog pointer → metadata JSON
Current snapshot과 schema/spec 선택
↓ query predicate를 field ID에 bind
② Snapshot → manifest list
Spec별 partition summary로 manifest pruning
↓ 남은 manifest만 GET
③ Manifest entries
Partition tuple + file counts/bounds로 file pruning
↓ data/delete candidate pairing
④ Data/Delete files
Sequence · COW/MOR · DV applicability
↓ selected byte range read
⑤ Parquet row-group/page
File-internal statistics와 최종 row predicate

Read 요청·응답·상태 변화

  1. Reader가 catalog에서 current metadata JSON을 얻고 snapshot, schema ID와 모든 partition spec을 고정한다. 이것이 control path의 일관된 root다.
  2. event_time BETWEEN t1 AND t2를 각 manifest의 spec에 맞게 day(event_time), hour(event_time) 같은 partition predicate로 투영한다.
  3. Manifest list의 partition summary와 file count로 절대 match하지 않는 manifest를 건너뛴다.
  4. 남은 manifest entry에서 해당 spec의 partition tuple을 먼저, 그 다음 field-ID별 bounds/counts를 검사해 data/delete file을 줄인다.
  5. MOR에서는 partition·sequence·metric overlap으로 equality/position delete를 data file과 짝짓는다. V3 DV는 referenced data file을 직접 가리키지만 engine 지원을 확인한다.
  6. 실행기는 선택 file의 Parquet row-group/page 통계로 더 줄이고 최종 row predicate를 평가한다. Concurrent commit은 고정 snapshot을 바꾸지 않는다.

Write·commit과 다음 scan의 상태 변화

  1. Writer가 current spec으로 partition 값을 만들고 immutable data/delete file과 field metric을 쓴다.
  2. Manifest entry와 manifest summary를 만들고 기존 manifest를 재사용하거나 merge한다. Partition evolution 전 manifest는 old spec ID를 유지한다.
  3. 새 manifest list, snapshot, metadata JSON을 쓰고 base 이후 변경과 operation 범위를 optimistic validation한다.
  4. Catalog pointer swap이 성공해야 새 file과 summary가 다음 scan의 control path에 들어온다. 실패 object는 table membership이 아니다.
  5. Rewrite manifests/data files도 새 commit이다. Active writer와 race하면 conflict·retry가 발생할 수 있으므로 planning SLO와 commit 실패율을 함께 본다.

4. CS 관점의 내부 동작

단계입력 → 판정 → 비용
Partition projectionLogical predicate → spec transform → partition interval. Hidden partitioning이라 user가 물리 column을 쓸 필요가 없다.
Manifest pruningPartition interval → manifest-list summary → manifest GET 여부. 작은 상위 index가 object request를 크게 줄인다.
File pruningEntry partition/metric → candidate files. Bound가 넓거나 missing이면 false positive가 남는다.
Delete planningData/delete partition·sequence·bounds → applicable delete set. Read amplification과 correctness가 만나는 단계다.
File-format pruningCandidate file → Parquet footer/row groups → byte ranges. Iceberg metric과 Parquet 통계는 서로 다른 granularity다.
Final evaluationDecoded rows → exact predicate → result. 앞 단계의 synopsis는 정답 자체가 아니다.

Spec evolution을 안전하게 읽는 법

Manifest를 쓴 partition spec ID가 기준이다. Current spec 하나로 old manifest를 해석하면 안 된다. Reader는 source field ID와 각 spec의 transform으로 predicate를 따로 투영하고 결과 후보를 합친다. Unknown transform이면 filtering에서 그 field를 무시해 file을 유지해야 한다.

Selectivity와 비용 모델

전체 manifest M, entry F, 선택 file K라고 하면 이상적인 planner는 manifest list O(M)의 작은 summary를 보고 일부 manifest의 entry만 읽어 K를 찾는다. 그러나 manifest range가 심하게 겹치거나 file metric이 없으면 M과 F 대부분을 읽는다. Partition 수만 늘리는 것이 아니라 summary 겹침, files/manifest, candidate ratio와 object GET latency를 같이 측정해야 한다.

5. 실무 설계 판단

판단Best practice와 이유
Partition transformQuery 시간 범위·cardinality·file size를 수치화해 day/hour/bucket/truncate를 고른다. 지나치게 미세하면 small file과 metadata가 늘어난다.
Metric / sortPartition 내부 핵심 predicate column에 metric을 유지하고 sort/clustering으로 file bounds 겹침을 낮춘다.
관측성Total→manifest→file→row-group candidate 수, planning p95, metadata/data bytes와 GET count를 단계별로 기록한다.
MaintenanceRewrite manifests는 summary locality, rewrite data files는 size·clustering을 개선한다. 효과와 optimistic conflict 비용을 canary에서 비교한다.
Multi-engineSpark/Flink/Trino별 predicate pushdown, transform/timezone, null·NaN, delete/DV와 scan metric 노출 차이를 compatibility gate로 고정한다.

Anti-pattern: 느린 query에 partition을 무조건 더 세분화하는 것. File 수와 manifest 수, commit/maintenance 비용이 커져 planning이 오히려 느려질 수 있다.

Edge case: Timestamp with/without time zone의 day/hour projection이 engine session timezone과 충돌하면 경계 file 후보가 달라질 수 있다. 결과 correctness는 보수적으로 유지하되 scan 비용이 달라질 수 있으므로 engine별 경계 테스트가 필요하다.

6. 장애 대응 표

상황: 하루치 selective query가 table의 대부분 file을 읽기 시작했다.

증상Planning p95·object GET·candidate file·scanned bytes 급증, explain에서 pushdown filter 누락, engine별 scan량 차이.
먼저 수집할 증거/지표Current snapshot/metadata, query text/plan, spec IDs와 transforms, manifests partition_summaries, files readable_metrics, candidate ratio, writer/reader version, delete file/DV, object-store latency/404.
가능한 가설Non-sargable predicate, partition evolution 처리 차이, range-overlapping manifests/files, metric none, small-file 폭증, stale cache, timezone cast, maintenance/writer race, connector regression.
안전한 첫 조치Snapshot을 고정하고 read-only metadata tables와 explain으로 어느 단계부터 후보가 줄지 않는지 확인한다. Exact source predicate로 canary query를 비교하고 write/maintenance 변경을 일시 중지한다.
Rollback/복구Connector regression이면 known-good version/engine으로 되돌린다. Bad rewrite/commit이면 retained snapshot으로 rollback한다. Metric·clustering 문제는 canary rewrite 후 새 snapshot을 publish한다.
하지 말아야 할 조치Manifest/partition path를 수동 삭제하지 않는다. 근거 없이 spec을 다시 만들지 않는다. Active writer와 대규모 rewrite를 동시에 시작하지 않는다. Missing metric을 empty로 간주하지 않는다.

예상 관찰: Day transform은 8월 1일·3일 file을, ID bound는 같은 8월 2일의 [1000,1001] file을 제외할 수 있다. 최종 결과는 id 101 한 row다.

실패 주입 · 새 file의 ID metric 제거

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
ALTER TABLE local.day12.pruning_lab SET TBLPROPERTIES
  ('write.metadata.metrics.column.id'='none');
INSERT INTO local.day12.pruning_lab VALUES
  (9999, TIMESTAMP '2026-08-02 05:00:00', 'metric-off');

SELECT file_path, partition, readable_metrics['id'] AS id_metric
FROM local.day12.pruning_lab.files ORDER BY file_path;
SELECT count(*) AS exact_rows FROM local.day12.pruning_lab
WHERE event_time >= TIMESTAMP '2026-08-02 00:00:00'
  AND event_time < TIMESTAMP '2026-08-03 00:00:00'
  AND id = 101;
"

예상 관찰: 새 file은 day partition 때문에 8월 2일 후보지만 ID metric이 없어 id=101에서 제외할 근거가 없다. Extra I/O는 생겨도 최종 결과는 여전히 1 row다.

자주 나는 오류와 해결

  • days transform 문법: Runtime에 따라 days(event_time) DDL 지원을 확인한다.
  • readable_metrics 없음: DESCRIBE local.day12.pruning_lab.files로 metadata-table schema를 확인한다.
  • Manifest 수가 예상과 다름: Writer manifest merge/reuse 설정 때문이다. Partition summary와 file path 연결을 기준으로 본다.
  • Explain에 candidate 수가 없음: Engine scan report/metrics를 사용하고 metadata bounds로 수동 예측한다.
  • Timezone 경계 차이: Session timezone과 timestamp type을 고정한 뒤 다시 비교한다.
  • Docker 연결 실패: Docker daemon을 시작하고 make smoke가 성공한 뒤 재개한다.

8. 놓치기 쉬운 함정

  1. Partition pruning은 directory listing이다. Iceberg는 manifest metadata와 spec transform을 사용한다.
  2. Current spec만 보면 된다. Manifest를 쓴 spec ID로 predicate를 각각 투영해야 한다.
  3. Bound가 겹치면 row가 있다. Candidate일 뿐 최종 predicate가 필요하다.
  4. Missing metric은 empty다. Unknown이므로 file을 유지한다.
  5. More partitions는 항상 빠르다. Small file·manifest·commit 비용이 늘 수 있다.
  6. Data file만 prune하면 된다. MOR은 delete file/DV applicability도 함께 계획해야 한다.
  7. Manifest rewrite는 data clustering을 고친다. Metadata locality만 바꾸며 data rewrite와 책임이 다르다.
  8. 모든 engine의 pushdown이 같다. Transform, timezone, function, format version 지원을 engine별로 검증한다.

9. 대기업 기술 면접 수준 질문

Q1. “10PB table의 1시간 query scan planning을 설계하세요.”

좋은 답변 구조: File/manifest/commit rate 수치 → catalog root/snapshot → spec별 hour/day projection → manifest/file/row-group candidate 비율 → object GET·metadata bytes → delete planning → SLO/observability → partition·sort·metric 대안과 trade-off.

Q2. “Partition evolution 뒤에도 old/new data를 정확히 prune하는 이유는?”

좋은 답변 구조: Source field ID와 spec ID → manifest별 transform → predicate projection → unknown transform 보수 처리 → candidate union → no rewrite evolution → engine compatibility와 timezone edge → false-positive 비용.

Q3. “Planning p95가 10배 느려진 장애를 분석하세요.”

좋은 답변 구조: Snapshot 고정 → 단계별 candidate/GET/bytes → query shape/spec/summary/metric/delete 확인 → connector/object-store/maintenance 가설 → safe canary → rewrite manifests vs data files → optimistic race/rollback → 하지 말아야 할 수동 삭제.

10. 어제 내용 회상 3문제

  1. Lower/upper bound가 실제 min/max와 반드시 같지 않아도 안전한 이유는?
  2. Missing null count를 0으로 해석하면 왜 위험한가?
  3. Data file record_count 합이 현재 COUNT(*)와 다를 수 있는 이유는?
짧은 정답/채점 기준
① 모든 실제 값을 포함하는 conservative interval이면 겹치지 않을 때만 제외해 안전하다고 답하면 2점.
② Missing=unknown인데 0으로 보면 NULL row가 있는 file을 false-negative로 제거할 수 있다고 답하면 2점.
③ MOR equality/position delete 또는 DV가 물리 row를 logical view에서 제외한다고 답하면 3점.

11. 오늘 내용 확인 문제 3개

  1. Manifest list와 manifest는 각각 어느 후보를 제거하는가?
  2. Partition evolution 뒤 predicate를 current spec 하나로만 해석하면 안 되는 이유는?
  3. Manifest rewrite와 data-file rewrite의 pruning 개선 범위는 어떻게 다른가?
짧은 정답/채점 기준
① Manifest list summary는 manifest를, entry partition/metric은 data/delete file을 제거한다고 답하면 2점.
② Old manifest는 old spec transform/ID로 작성돼 spec별 projection이 필요하다고 답하면 2점.
③ Manifest rewrite는 metadata grouping/summary locality, data rewrite는 file size·sort/clustering·bounds를 바꾼다고 답하면 3점.
