APACHE ICEBERG · WEEK 1 / DAY 03

Iceberg table 생성·insert·select

Lakehouse와 Table Format 정신 모델 · 예상 학습 30분 + 실습 30분

한 줄 요약
CREATE TABLE은 이름과 최초 metadata state를 만들고, INSERT는 새 immutable file을 쓴 뒤 catalog pointer를 원자적으로 바꾸며, SELECT는 그 pointer에서 시작한 한 snapshot만 읽는다.

1. 선수 용어 사전

DDLData Definition Language. Table의 구조를 정의하는 SQL이다. CREATE·ALTER·DROP이 여기에 속한다.
DMLData Manipulation Language. Row를 넣고 읽고 바꾸는 SQL이다. 오늘은 INSERT와 SELECT를 다룬다.
SchemaColumn 이름·타입·필수 여부를 정의한 계약이다. Iceberg는 이름뿐 아니라 영속적인 field ID로 column identity를 관리한다.
Partition transform원본 값을 물리 partition 값으로 바꾸는 함수다. days(event_time)은 timestamp에서 날짜 값을 계산한다. 사용자가 별도 partition column을 관리하지 않아 hidden partitioning이라 부른다.
Snapshot특정 시점의 table state를 가리키는 immutable 버전이다. 파일 복사본이 아니라 manifest tree의 root에 가깝다.
ManifestData/delete file의 path, partition 값, column 통계와 상태를 기록한 metadata file이다. Manifest list는 snapshot이 사용하는 manifest들을 가리킨다.
Optimistic commit긴 lock을 잡지 않고 base state를 읽어 새 state를 준비한 뒤, 마지막에 base가 그대로인지 검증해 pointer를 교체하는 방식이다.
Linearization point동시 실행을 한순간에 일어난 것처럼 정렬할 때 작업의 성공이 확정되는 논리적 시점이다. Iceberg commit에서는 catalog의 current metadata 교체가 그 지점이다.

2. 왜 중요한가

SQL 세 문장은 짧지만 내부 책임은 전혀 다르다. CREATE TABLE이 성공했다면 catalog 이름과 최초 metadata가 함께 유효해야 한다. INSERT task가 Parquet를 모두 썼어도 pointer 교체 전이면 새 row는 table에 포함되지 않는다. SELECT는 warehouse를 directory listing해서 “보이는 파일 전부”를 읽는 대신, catalog가 가리킨 snapshot의 manifest에 포함된 file만 읽는다.

이 경계를 이해하면 “파일은 있는데 row가 없다”, “INSERT가 timeout 났는데 재실행해도 되는가”, “두 engine의 count가 왜 다른가” 같은 운영 질문을 table state 관점에서 풀 수 있다. SQL 성공 여부를 driver log 한 줄로만 판단하지 않고, current snapshot과 metadata tree라는 증거로 확인하게 된다.

오늘의 불변식: Committed table state는 catalog의 current metadata pointer에서 도달 가능한 snapshot·manifest·file 집합이다. Warehouse에 존재하지만 이 graph에서 도달할 수 없는 file은 현재 table의 row가 아니다.

A. CREATE TABLE의 state transition

  1. Spark가 identifier, schema, partition transform과 table property를 분석한다. USING iceberg은 Iceberg catalog/provider 경로를 선택한다.
  2. Catalog가 같은 이름이 없는지 확인하고 새 table location을 정한다. 이 프로젝트에서는 Hadoop catalog의 warehouse 아래에 놓인다.
  3. Iceberg가 schema field ID, partition spec ID, format version 등 최초 table metadata를 새 JSON에 기록한다.
  4. Catalog가 table 이름을 최초 metadata에 원자적으로 연결한다. 이 연결이 성공해야 CREATE 성공이다. Data row가 없다면 current snapshot은 아직 없을 수 있다.

B. INSERT INTO의 optimistic commit

  1. Driver가 base metadata, current snapshot, schema와 partition spec을 읽는다.
  2. Write task가 row를 schema에 맞게 변환하고 partition transform을 계산한 뒤 고유한 immutable data file을 쓴다. 이 단계는 table에 공개되지 않은 준비 단계다.
  3. Driver가 새 file을 기록한 manifest, manifest list, 새 snapshot과 새 metadata JSON을 만든다. Append snapshot에는 새 data file이 추가된다.
  4. Commit 직전에 base pointer가 아직 current인지 확인한다. 다른 writer가 먼저 commit했다면 append가 안전한지 새 base에서 재검증·재계획한다.
  5. Catalog가 pointer를 새 metadata로 원자 교체한다. 교체 성공이 INSERT의 성공 확정점이다. 이후 새로 load한 reader가 새 snapshot을 본다.
  6. Pointer 교체 전에 실패한 data file은 current state에서 도달하지 않는 orphan 후보다. 진행 중 writer와 retention을 고려하지 않고 즉시 삭제하면 안 된다.

C. SELECT의 consistent read

  1. Reader는 catalog에서 metadata pointer를 한 번 load하고 current snapshot을 선택한다. Query가 시작한 뒤 새 commit이 생겨도 이미 잡은 snapshot은 변하지 않는다.
  2. Snapshot의 manifest list에서 partition 요약으로 manifest를 pruning하고, manifest의 partition/column bounds로 data file을 pruning한다.
  3. 선택된 data file과 적용 가능한 delete file만 scan task로 만든다. 오늘 INSERT-only table에는 보통 delete file이 없다.
  4. Spark task가 Parquet column projection과 filter를 수행해 row를 반환한다. Field ID가 schema evolution 중 column identity를 지키고, sequence number는 이후 delete 적용 순서를 판정하는 데 쓰인다.

4. CS 관점의 내부 동작

개념Iceberg에서의 의미
State ownerCatalog는 current pointer를, metadata JSON은 schema/spec/snapshot 목록을, snapshot·manifest는 file membership을, storage는 byte durability를 소유한다. Spark는 이 state를 해석하고 실행한다.
Immutability기존 data/metadata file을 제자리에서 바꾸지 않고 새 객체를 쓴다. Reader가 붙잡은 old snapshot은 안정적으로 유지되지만 metadata와 orphan 관리 비용이 생긴다.
Atomicity수백 개 file write가 하나의 pointer swap으로 공개된다. Reader는 “일부 task file만 보이는 중간 상태”가 아니라 commit 전 또는 후의 snapshot을 본다.
Optimistic concurrencyWriter가 lock 없이 준비하고 마지막에 conflict를 검증한다. Append는 종종 새 base에 재적용할 수 있지만 overwrite/delete는 대상 file이나 predicate가 바뀌면 실패해야 안전하다.
IsolationReader는 선택한 snapshot의 일관된 view를 본다. Writer isolation은 operation별 validation 범위에 의해 정해진다. 모든 engine이 database lock을 공유해서 얻는 성질이 아니다.
Persistent tree새 snapshot은 기존 manifest/file을 재사용하면서 변경분을 연결할 수 있다. Time travel이 전체 table 복사 없이 가능한 대신 retention 정책이 필요하다.

성공이 확정되는 시점과 failure window

  • CREATE metadata write 후 catalog 등록 전: 저장소에 metadata가 남아도 이름으로 load할 수 없다. CREATE는 아직 성공이 아니다.
  • INSERT data file write 후 commit 전: byte는 존재하지만 current snapshot의 member가 아니다. SELECT 결과에 포함되면 안 된다.
  • Pointer swap 후 client timeout: 서버에서는 commit됐지만 client가 성공 응답을 못 받았을 수 있다. 즉시 같은 append를 반복하면 중복 row 위험이 있다.
  • SELECT planning 중 새 commit: 기존 query는 old snapshot을 계속 읽고 다음 refresh/query가 새 snapshot을 본다. 이는 stale bug가 아니라 snapshot isolation의 결과일 수 있다.
  • Object storage read 실패: pointer와 metadata가 정상이어도 참조된 byte가 없거나 권한이 막히면 query가 실패한다. Metadata rollback만으로 삭제된 data를 복구할 수 없다.

비용 trade-off

Commit마다 metadata JSON과 snapshot/manifest가 늘고, 작은 INSERT를 자주 실행하면 작은 data file과 planning overhead가 증가한다. 반대로 commit을 너무 크게 묶으면 end-to-end latency, 재시도 비용과 conflict window가 커진다. 목표 file size, commit 주기, writer 병렬도는 ingestion latency와 scan 비용을 함께 놓고 정한다.

5. 실무 설계 판단

판단Best practice와 이유
Identifier 고정Job 설정에 catalog.namespace.table을 명시하고 시작 시 catalog type·warehouse·format version을 기록한다. Default catalog 의존은 환경별 오발행을 만든다.
Schema 계약Source→target column mapping과 null/type 정책을 배포 전에 검증한다. 자동 schema merge는 명시적 승인과 호환성 test가 있을 때만 켠다.
IdempotencyBatch ID·checkpoint·source offset을 snapshot summary나 별도 ledger와 연결한다. Ambiguous timeout을 “실패”로 단정해 blind append하지 않는다.
File 크기입력 크기, partition cardinality, task 수와 target file size를 함께 조정한다. File은 task와 Iceberg partition 경계를 넘지 못하므로 property 하나만 바꿔 큰 file을 보장할 수 없다.
검증 queryRow count만 보지 말고 snapshot ID·operation·added records/files, files metadata와 source batch count를 함께 확인한다.
Multi-engine gateSpark·Flink·Trino별 format version, type, partition transform, field ID, delete/deletion vector, COW/MOR 지원을 read/write로 나눠 test한다. Spec 지원과 engine 구현 지원은 다르다.

Anti-pattern: 매 micro-batch마다 tiny INSERT를 발생시키고 “나중에 compaction하면 된다”고 가정하는 것. Compaction 자체도 새 commit이며 streaming writer·snapshot expiration·orphan cleanup과 race가 날 수 있다.

Edge case: Spark 문법과 atomicity는 catalog 구현에 따라 다를 수 있다. 공식 문서에서 CTAS는 SparkCatalog에서는 atomic이지만 SparkSessionCatalog에서는 atomic이 아니라고 구분한다. 오늘 프로젝트는 Iceberg 1.11.0의 Hadoop-backed SparkCatalog 설정이며, 다른 engine/catalog에 그대로 일반화하지 않는다.

6. 장애 대응 표

상황: INSERT가 timeout 또는 conflict로 끝났고, 재실행하면 중복될지 알 수 없다.

증상Driver timeout, commit state unknown, commit conflict/retry exhausted, row count가 예상보다 많거나 적음, storage에는 새 data file이 보임.
먼저 수집할 증거/지표Table identifier와 current metadata location, 작업 전후 snapshot ID·timestamp·operation·summary, batch/checkpoint ID, source offset 범위, commit retry/conflict log, 새 file path와 생성 시각, catalog latency/error.
가능한 가설Pointer swap은 성공했지만 응답만 유실, concurrent writer가 먼저 commit, data write 후 metadata commit 전 실패, schema/partition validation 실패, catalog 또는 storage의 일시 장애.
안전한 첫 조치동일 batch 재실행과 cleanup을 멈춘다. Current snapshot과 직전 history를 read-only로 조회하고 batch identity·source offset·added records/files가 이미 반영됐는지 확인한다.
Rollback/복구이미 commit됐으면 완료로 기록해 중복 실행을 막는다. 미commit이 증명되면 동일 input을 idempotent하게 재계획한다. 잘못 중복 commit됐다면 영향 snapshot과 downstream read를 확인한 뒤 검증된 overwrite/delete 또는 snapshot 복구 절차를 사용한다.
하지 말아야 할 조치Timeout만 보고 blind append하지 않는다. Warehouse file 존재만으로 commit 성공을 판정하지 않는다. 최근 file을 수동 삭제하지 않는다. 확인 없이 pointer나 metadata JSON을 직접 편집하지 않는다.

7. 30분 재현 실습

목표: CREATE → INSERT → SELECT마다 table state가 어떻게 바뀌는지 metadata table과 warehouse file로 확인하고, 분석 단계 실패는 새 snapshot을 만들지 않음을 검증한다.

사전 조건과 실행 전 예측

  • 프로젝트 루트에서 Docker를 사용할 수 있고 make smoke가 성공해야 한다.
  • 예측 1: CREATE 직후 snapshots에는 몇 행이 있을까?
  • 예측 2: INSERT 한 번은 data file과 snapshot을 최소 몇 개 만들까?
  • 예측 3: Column 수가 맞지 않는 INSERT는 data file 또는 snapshot을 만들까?

최소 명령

make smoke

docker compose exec spark /opt/spark/bin/spark-sql -e "
CREATE NAMESPACE IF NOT EXISTS local.day03;
DROP TABLE IF EXISTS local.day03.sql_path_lab;

CREATE TABLE local.day03.sql_path_lab (
  id BIGINT NOT NULL,
  event_time TIMESTAMP,
  category STRING,
  amount DECIMAL(12,2)
) USING iceberg
PARTITIONED BY (days(event_time));

SELECT count(*) AS snapshots_after_create
FROM local.day03.sql_path_lab.snapshots;

INSERT INTO local.day03.sql_path_lab VALUES
  (1, TIMESTAMP '2026-07-31 09:00:00', 'book', 12000.00),
  (2, TIMESTAMP '2026-07-31 10:00:00', 'food', 8500.50),
  (3, TIMESTAMP '2026-08-01 09:00:00', 'book', 22000.00);

SELECT id, event_time, category, amount
FROM local.day03.sql_path_lab
WHERE event_time >= TIMESTAMP '2026-07-31 00:00:00'
ORDER BY id;

SELECT committed_at, snapshot_id, operation, summary
FROM local.day03.sql_path_lab.snapshots
ORDER BY committed_at;

SELECT file_path, partition, record_count, file_size_in_bytes
FROM local.day03.sql_path_lab.files
ORDER BY file_path;
"

find warehouse/day03/sql_path_lab -type f | sort

예상 관찰: CREATE 직후에는 row change snapshot이 없으므로 snapshot 수가 0일 수 있다. INSERT가 성공하면 append snapshot 1개와 하나 이상의 data file이 보인다. 서로 다른 날짜 값은 서로 다른 Iceberg partition에 기록되므로 task/분배에 따라 data file 수는 2개 이상일 수 있다. 정확한 file 수를 상수로 가정하지 말고 files metadata와 실제 경로를 매핑한다.

실패 주입: 잘못된 column 수

먼저 현재 snapshot ID를 기록한 뒤, target은 4개 column인데 3개 값만 제공한다.

docker compose exec spark /opt/spark/bin/spark-sql -e "
SELECT snapshot_id, operation
FROM local.day03.sql_path_lab.snapshots
ORDER BY committed_at DESC LIMIT 1;
SELECT count(*) AS rows_after_failed_insert
FROM local.day03.sql_path_lab;
"

자주 나는 오류와 해결

  • Docker daemon 연결 실패: Docker Desktop을 시작하고 docker compose ps로 확인한다.
  • Dependency download 실패: 최초 실행은 Iceberg runtime을 받아야 한다. Network와 Ivy cache를 확인한 뒤 make smoke부터 재검증한다.
  • days transform 문법 오류: 공식 문서는 day(ts)와 호환 목적의 기존 days(ts) 문법을 구분한다. 프로젝트 runtime에서 문제가 나면 day(event_time)로 바꾸고 engine/version을 기록한다.
  • Warehouse 경로 불일치: DESCRIBE TABLE EXTENDED local.day03.sql_path_lab의 Location을 확인한다. Namespace/table 경로를 추측해 상위 directory를 삭제하지 않는다.
  • 예상보다 data file이 많음: Partition 수, shuffle task와 distribution이 file 수를 좌우한다. Row count가 맞는지 확인하고 file 수 자체를 correctness 조건으로 삼지 않는다.
  • 실패 SQL 때문에 shell exit가 non-zero: 의도한 결과다. 실패 전후 검증 query는 다음 명령으로 따로 실행한다.

Cleanup

docker compose exec spark /opt/spark/bin/spark-sql -e "
DROP TABLE IF EXISTS local.day03.sql_path_lab PURGE;
DROP NAMESPACE IF EXISTS local.day03;
"

실습 전용 table만 PURGE한다. 실행 중인 writer가 있거나 다른 table이 섞인 warehouse 상위 경로는 수동 삭제하지 않는다.

8. 놓치기 쉬운 함정

  1. Data file write 완료가 INSERT 성공이다. Catalog pointer 교체가 성공해야 table에 공개된다.
  2. SELECT는 warehouse의 최신 파일을 모두 읽는다. 선택한 snapshot에서 manifest를 따라 도달한 file만 읽는다.
  3. CREATE TABLE은 directory 하나를 만드는 일이다. 이름, schema/spec ID, metadata와 catalog 연결을 생성하는 logical state transition이다.
  4. Partition column을 직접 넣어야 한다. Hidden partitioning에서는 source column에 transform을 적용하므로 query와 write가 물리 partition column을 직접 관리하지 않는다.
  5. Field 이름이 같으면 schema가 같다. Iceberg의 identity는 field ID다. Rename/evolution과 raw Parquet name-based read를 혼동하지 않는다.
  6. Commit conflict는 항상 retry하면 된다. Append는 재적용 가능할 수 있지만 overwrite/delete는 conflict validation을 통과해야 한다.
  7. COW/MOR와 deletion vector가 오늘 INSERT에 이미 필요하다. 이들은 row-level update/delete의 write/read 비용을 바꾸는 후속 주제다. Engine과 format version 지원을 확인한 뒤 선택한다.
  8. Snapshot retention이나 orphan cleanup은 안전한 housekeeping이다. 장기 reader/writer, branch/tag, maintenance commit과 race를 검토하지 않으면 복구 가능성을 잃거나 진행 중 file을 지울 수 있다.

9. 대기업 기술 면접 수준 질문

Q1. “하루 5TB append table의 INSERT 경로를 설계하고 성공을 어떻게 판정하겠습니까?”

좋은 답변 구조: Latency/SLA·partition cardinality·목표 file size 수치 가정 → catalog/schema/spec load → task data write → manifest/snapshot 생성 → optimistic validation → pointer swap이라는 성공 확정점 → batch ID와 snapshot summary 검증 → timeout/중복/orphan failure window → commit 빈도와 small-file/재시도 비용 trade-off → streaming이나 staged publish 대안.

Q2. “INSERT와 동시에 SELECT가 실행되면 partial data가 보이지 않는 이유를 설명하세요.”

좋은 답변 구조: Reader가 query 시작 시 metadata pointer와 snapshot을 고정 → writer는 immutable file을 비공개로 준비 → catalog CAS가 linearization point → old reader는 old snapshot, new reader는 new snapshot → manifest membership 불변식 → catalog/storage 장애와 cache edge case → database row lock과 다른 구현 방식 → 비용은 metadata/retention.

Q3. “Spark와 Trino가 같은 table을 읽을 때 CREATE/INSERT 계약을 어떻게 검증합니까?”

좋은 답변 구조: 공통 catalog와 identifier/warehouse 확인 → format version·type·partition transform·field ID 지원 matrix → Spark write 후 snapshot/manifest/file 경로 추적 → Trino read count·predicate pruning·refresh 검증 → delete/COW/MOR/deletion vector는 별도 gate → catalog outage와 unsupported feature 실패 방식 → 단일 writer 정책 또는 feature downgrade 대안과 trade-off.

10. 어제 내용 회상 3문제

  1. Catalog와 warehouse가 각각 소유하는 핵심 상태는 무엇인가?
  2. Raw Parquet path read가 Iceberg table read와 다른 이유를 metadata tree 관점에서 설명하라.
  3. Catalog pointer swap 후 응답 timeout이 났을 때 blind retry가 위험한 이유는?

짧은 정답/채점 기준

  1. Catalog는 이름→current metadata와 commit 원자성, warehouse는 metadata/data byte와 durability를 소유한다고 답하면 통과.
  2. Raw read는 snapshot→manifest membership, delete 적용, field ID와 partition evolution 계약을 우회한다고 답하면 통과.
  3. Commit은 이미 성공했지만 응답만 유실됐을 수 있어 같은 append가 중복될 수 있다고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. CREATE, INSERT, SELECT 각각에서 current table state와 관련된 핵심 동작 한 가지를 말하라.
  2. INSERT task가 data file을 모두 쓴 뒤 pointer swap 전에 실패했다. 그 file과 row의 상태는?
  3. SELECT가 file을 고르는 순서를 catalog pointer부터 data file까지 말하라.

짧은 정답/채점 기준

  1. CREATE는 최초 metadata를 이름에 연결, INSERT는 새 snapshot commit, SELECT는 한 snapshot을 고정한다고 답하면 통과.
  2. File은 storage에 존재할 수 있지만 current snapshot에서 도달하지 않는 orphan 후보이며 row는 table에 공개되지 않았다고 답하면 통과.
  3. Catalog pointer → metadata JSON → current snapshot → manifest list → manifest → 선택된 data/delete file 순서를 말하면 통과.
