APACHE ICEBERG · WEEK 2 / DAY 14 · 회상·복습

회상: O(n) listing 회피의 의미

Metadata Tree와 Scan Planning · 예상 학습 25분 + 실습 35분

한 줄 요약
Iceberg는 warehouse의 n개 object를 매번 전수 listing하지 않고, catalog가 고정한 snapshot의 계층형 metadata index를 predicate로 pruning해 필요한 manifest와 data/delete file만 찾는다.

1. 선수 용어 사전

Big-O / O(n)입력 크기 n이 커질 때 작업량의 증가 형태를 표현한다. O(n)은 object가 두 배면 검사할 항목도 대략 두 배가 되는 선형 비용이다.
ListingObject storage prefix 아래 key들을 페이지 단위로 열거하는 control-plane 요청이다. “어떤 file이 table에 속하는가”를 보장하지 않는다.
Index전체 대상을 직접 검사하지 않고 후보를 좁히는 요약 구조다. Manifest list는 manifest의 index, manifest는 content file의 index처럼 동작한다.
n, M, F, Kn은 warehouse object 수, M은 snapshot의 manifest 수, F는 live content file 수, K는 predicate가 남긴 candidate file 수로 두자.
Pruning요약 정보로 “답이 절대 없음”을 증명해 후보를 읽기 전에 제외하는 과정이다. 정보가 없으면 안전하게 유지한다.
Persistent graphImmutable node를 새 version이 재사용하는 자료구조다. Snapshot은 기존 manifest를 공유하면서 새 table state를 만든다.
Fan-out상위 node 하나가 가리키는 하위 node 수다. 너무 많은 작은 manifest/file은 fan-out과 GET 비용을 키운다.
Control / data pathMetadata를 따라 scan task를 만드는 경로가 control path, 선택된 data/delete bytes를 읽는 경로가 data path다.

2. 왜 중요한가

1PB table에 1천만 개 file이 있을 때 query마다 prefix를 모두 list하고 각 footer를 읽으면, 실제 결과가 한 시간치 10개 file뿐이어도 planning이 n에 묶인다. Object-store listing은 페이지 요청, network latency, rate limit, 비용과 일관성·권한 오류까지 control path에 끌어온다.

Iceberg의 장점은 “metadata가 있으니 O(1)”이 아니다. Catalog root를 O(1)에 찾은 뒤 manifest list와 일부 manifest를 읽는 계층형 탐색으로 n과 scan planning 비용의 직접 결합을 끊는 것이다. Predicate selectivity, manifest layout, metric 품질이 나쁘면 M과 F에 가까운 작업이 남을 수 있다.

회상 문장: Iceberg는 object listing을 더 빠르게 하는 기술이 아니라, authoritative snapshot graph와 보수적 index를 사용해 listing을 정상 read path에서 제거하는 table protocol이다.

3. 아키텍처 그림과 요청 흐름

비교: warehouse LIST prefix → n개 key 분류 → footer/partition 추론
Membership 불명확 · O(n) page scan · orphan/old snapshot 혼입

⑤ Manifest entries

Reader 요청·응답·상태 변화

  1. Reader가 catalog에서 current metadata location을 얻는다. 이 mutable pointer가 table state의 유일한 entry point다.
  2. Metadata JSON에서 current snapshot ID, schema field ID와 partition specs를 pin한다. Concurrent commit이 생겨도 이 scan의 root는 바뀌지 않는다.
  3. Snapshot의 manifest-list path를 읽고 query predicate를 각 manifest의 spec으로 투영한다. Partition summary와 file count가 불가능한 manifest를 제외한다.
  4. 남은 manifest에서 live data/delete entry를 읽고 partition tuple, null/count/lower/upper metric을 field ID로 평가한다.
  5. MOR이면 data/file sequence, partition, equality IDs 또는 referenced data file을 이용해 applicable delete/DV를 pairing한다. COW이면 rewritten data file이 후보다.
  6. 실행기는 K개 candidate의 Parquet row group/page를 추가 pruning하고 최종 predicate와 delete를 적용한다. Warehouse full list는 없다.

Writer와 index 갱신

  1. Writer는 immutable data/delete file과 file metrics를 쓴다. 이때 object는 존재하지만 table membership은 아직 없다.
  2. Manifest entry, manifest와 새 manifest list를 만들고 snapshot을 metadata JSON에 추가한다. Fast append는 기존 manifest를 재사용하고 작은 새 manifest를 붙일 수 있다.
  3. Base pointer와 operation 범위를 optimistic conflict validation한 뒤 catalog pointer를 atomic swap한다. 성공 응답이 state transition의 linearization point다.
  4. 충돌 시 retry 가능한 append인지, overwrite/delete의 겹치는 file/partition인지 isolation 규칙으로 판정한다. 실패 upload는 orphan 후보이며 즉시 삭제하면 안 된다.
  5. Commit이 누적되어 작은 manifest가 많아지면 rewrite manifests가 metadata fan-out을 줄인다. 이 maintenance도 새 snapshot commit이며 active writer와 race할 수 있다.

4. CS 관점의 내부 동작

비용 모델을 정직하게 쓰기

접근대략적 control-path 비용과 함정
Raw listingO(n) key 열거 + file/partition 해석. Old snapshot, orphan, 임시 file을 현재 membership과 구분할 protocol이 별도로 필요하다.
Iceberg selective scanRoot O(1) + manifest-list O(M)의 작은 summary + matching manifest entries + K tasks. Summary로 많은 manifest를 건너뛰면 n과 무관해진다.
Iceberg full scanCurrent snapshot의 live F를 결국 읽으므로 O(F) task가 필요하다. 그래도 unrelated object와 expired/orphan file은 열거하지 않는다.
Degraded metadataM이 크고 summaries가 겹치거나 metrics가 없으면 많은 manifest/entry가 후보로 남는다. Listing 회피가 곧 항상 작은 상수 비용이라는 뜻은 아니다.

Indirection이 주는 세 가지 성질

  1. Consistency: Reader가 catalog pointer 하나를 pin하면 immutable graph 전체가 한 snapshot을 나타낸다. Directory listing의 페이지 사이에 concurrent write가 끼는 문제를 피한다.
  2. Indexability: Manifest list의 partition ranges가 manifest를, manifest의 partition/column metric이 content file을 필터링한다. False positive는 허용하고 false negative는 금지한다.
  3. Shareability: Snapshot이 slow-changing manifest를 재사용해 metadata rewrite 비용을 낮춘다. 대신 references와 retention을 고려한 reachability GC가 필요하다.

Evolution과 delete가 비용 모델에 끼치는 영향

Partition evolution 뒤 old/new spec이 공존하므로 reader는 manifest의 partition spec ID마다 predicate를 다르게 투영한다. Current spec만 적용하면 correctness를 해칠 수 있다. Rename 뒤 metric은 name이 아니라 field ID로 bind한다. V2 MOR에서는 equality/position delete, V3에서는 deletion vector가 candidate data와 함께 계획되므로 K는 단순 data file 수보다 클 수 있다. Engine이 기능을 모르면 “pruning이 덜 된다”가 아니라 잘못된 결과나 read failure가 될 수 있어 compatibility gate가 필요하다.

5. 실무 설계 판단

판단Best practice와 이유
SLO 분해Catalog latency, metadata GET, manifests considered/read, files considered/selected, planning p95와 data bytes를 분리한다. “Query가 느림”만으로는 병목 계층을 찾지 못한다.
Manifest 관리M, entries/manifest, partition-range overlap과 average size를 관찰해 rewrite threshold를 잡는다. 무조건 매 commit rewrite하면 write latency와 conflict가 커진다.
Metric / clustering핵심 predicate column의 metric mode와 sort/clustering을 함께 설계한다. Partition만 늘리면 small file과 metadata가 증가할 수 있다.
Listing 사용 경계정상 read는 metadata graph, orphan audit는 충분히 오래된 object listing + 모든 retained refs reachability를 사용한다. 두 경로를 섞지 않는다.
Multi-engineSpark/Flink/Trino별 metadata cache, pushdown, metadata tables, spec transform, delete/DV와 format version 지원을 동일 snapshot canary로 검증한다.
Failure budgetCatalog outage는 새 root 획득과 commit을 막고, object-store metadata 404는 pin한 scan을 깨뜨린다. Cache TTL과 retry는 성공 불명확성·staleness를 감춘다는 점을 반영한다.

Anti-pattern: “Listing이 없으니 maintenance도 필요 없다.” Snapshot/manifest/small file이 무제한 누적되면 metadata GET, planning CPU, commit retry와 GC 비용이 커진다.

Edge case: Full table scan은 current live file을 모두 읽어야 하므로 O(F)를 없앨 수 없다. Iceberg가 제거하는 것은 warehouse의 모든 unrelated object n을 찾는 비용과 current membership을 추론하는 불확실성이다.

6. 장애 대응 표

상황: Data file 수는 비슷한데 scan planning p95와 object-store metadata 요청이 급증했다.

증상Planning p95/GET/CPU 증가, manifests read 비율 상승, selective query candidate file 폭증, engine별 latency 차이, cleanup/rewrite 뒤 404 또는 commit conflict 증가.
먼저 수집할 증거/지표Catalog latency·metadata location·snapshot ID, M/manifest size/entries와 partition summaries, F/K와 readable metrics, explain/scan report, cache hit/TTL, connector version, object GET/LIST/403/404, streaming commit·rewrite·expire/orphan job 시간.
가능한 가설Fast append로 작은 manifest 폭증, range overlap, metric none, non-sargable predicate, partition evolution/field-ID 해석 차이, delete/DV amplification, stale cache, connector regression, maintenance/writer race, catalog/object throttling.
안전한 첫 조치문제 snapshot과 query를 pin하고 read-only metadata tables로 M→matching manifests→K를 계산한다. Maintenance와 write 설정 변경을 멈추고 known-good engine의 같은 snapshot과 비교한다.
Rollback/복구Connector 회귀는 known-good으로 rollback한다. Canary rewrite manifests/data files로 효과·conflict를 검증한 후 새 snapshot을 publish한다. Bad commit은 retained snapshot으로 catalog-supported rollback한다.
하지 말아야 할 조치Warehouse full listing을 query path에 붙이지 않는다. Manifest/metadata를 직접 삭제·편집하지 않는다. Active writer 중 대규모 rewrite/expire를 동시에 시작하지 않는다. 403을 missing object로 단정하지 않는다.

SELECT count(*) AS current_live_files

예상 관찰: Physical object 수에는 old metadata, old manifests와 data file이 섞여 current live file 수보다 많다. Listing count는 table membership이나 query task 수가 아니다.

자주 나는 오류와 해결

  • Property가 무시됨: Connector 버전의 table property와 SHOW TBLPROPERTIES를 확인한다. 정확한 M은 구현별 merge 동작에 따라 달라진다.
  • Procedure 이름/인자 오류: Catalog system procedure 지원과 Spark extensions 설정을 확인한다. 지원하지 않으면 before 상태만 보존하고 임의 file rewrite를 하지 않는다.
  • Manifest 수가 그대로: 이미 적절히 묶였거나 target size 정책 때문이다. Path, size, partition summaries와 procedure output을 비교한다.
  • Explain에 candidate 수 없음: Engine scan report와 metadata bounds로 K를 수동 계산한다.
  • Warehouse path가 다름: files.file_path의 absolute URI와 catalog config로 실제 root를 확인한다.
  • Commit conflict: Active writer를 멈추고 현재 snapshot과 procedure 결과를 확인한다. Blind retry로 같은 maintenance를 중복 실행하지 않는다.

8. 놓치기 쉬운 함정

  1. Iceberg scan planning은 O(1)이다. Root lookup 뒤 M, matching entries와 K에 비례하는 작업이 남는다.
  2. Listing을 안 하면 orphan을 찾을 수 없다. 정상 read와 별도의 안전한 orphan audit에서는 listing을 쓰되 retained refs와 age threshold를 대조한다.
  3. Manifest list는 file path 목록뿐이다. Partition summaries와 counts가 manifest-level pruning index 역할을 한다.
  4. Partition pruning만 있으면 충분하다. Field-ID metrics, sort/clustering, Parquet index와 delete applicability가 다음 계층을 담당한다.
  5. Current spec으로 old manifest도 해석한다. Manifest를 쓴 partition spec ID별 inclusive projection이 필요하다.
  6. Missing metric이면 file에 값이 없다. Unknown이므로 candidate를 유지해야 correctness가 보존된다.
  7. Rewrite manifests는 data file을 compact한다. Metadata layout만 바꾸며 rewrite data files와 비용·race가 다르다.
  8. 모든 engine이 같은 index를 사용한다. Pushdown, cache, metadata table, V2/V3 delete/DV 지원 차이를 실제 snapshot으로 검증한다.

9. 대기업 기술 면접 수준 질문

Q1. “Iceberg는 O(n) listing을 피한다”를 비용 모델과 정확성 관점에서 설명하라.

좋은 답변 구조: n/M/F/K 정의 → catalog root와 snapshot pin → manifest-list/manifest 2-level index → selective/full scan의 다른 복잡도 → listing membership 불명확성 → metadata degradation과 maintenance trade-off까지 방어한다.

Q2. Streaming append로 planning p95가 10배 늘었다. 설계와 복구안을 제시하라.

좋은 답변 구조: Commit rate·file size·M/entries/overlap·K 수치 가정 → fast append 경로 → catalog/object/engine 지표 분리 → canary rewrite manifests와 data compaction의 책임 구분 → active writer conflict, rollback, threshold와 SLO를 포함한다.

Q3. Object store outage와 catalog outage가 reader/writer에 미치는 차이는?

좋은 답변 구조: State owner와 control/data path 분리 → cached root의 staleness 한계 → catalog가 없으면 refresh/commit 불가, object가 없으면 metadata/data GET 실패 → commit 성공 불명확성·idempotency → cache/retry/DR의 correctness와 availability trade-off를 제시한다.

  3. Current snapshot의 authoritative F만 읽어 unrelated old/orphan object를 열거하지 않고 일관된 membership을 얻는다고 답하면 정답.
