APACHE ICEBERG · WEEK 5 / DAY 35 · RECALL & REVIEW

회상: v1/v2/v3 feature·호환 경계

Row-level Update/Delete와 Format Version · 개념 30분 + 실습 35분

한 줄 요약
Format version은 기능 목록표가 아니라 reader·writer가 반드시 이해해야 하는 metadata 계약의 하한선이다. Upgrade는 기존 file을 즉시 rewrite하지 않지만 새 계약을 모르는 engine을 배제할 수 있으므로, 모든 소비자의 read·write·maintenance capability가 증명된 뒤에만 catalog pointer를 새 metadata로 전진시켜야 한다.

1. 선수 용어 사전

Table Specification여러 engine이 같은 table state를 해석하기 위한 공개 wire/storage 계약이다. 특정 Spark·Flink·Trino 구현 자체가 아니다.
Format versionTable metadata JSON의 format-version 값이다. Reader가 이보다 높은 버전을 모르면 조용히 무시하지 말고 load를 거부해야 한다.
Backward compatibility새 reader가 과거 버전 artifact를 올바르게 읽는 능력이다. Upgrade 후에도 old manifest와 data file이 남으므로 필수다.
Forward compatibility옛 reader가 미래 버전 metadata를 올바르게 읽는 능력이다. 새 기능이 이를 깨뜨릴 때 format version이 올라간다.
CapabilityEngine이 table을 load하는 능력, data/delete를 scan하는 능력, 새 artifact를 쓰는 능력, maintenance하는 능력을 각각 뜻한다. 하나의 “지원” boolean으로 합치면 안 된다.
Metadata-only upgrade기존 data tree를 즉시 rewrite하지 않고 새 table metadata에서 version 계약을 올리는 state transition이다.
Mixed-version treeCurrent table version은 v2/v3지만 historical snapshot·manifest·data file에는 이전 버전 규칙으로 작성된 artifact가 함께 있는 정상 상태다.
DowngradeFormat version을 낮추는 일이다. 이미 새 artifact가 생겼을 수 있어 일반적으로 금지되며, property 숫자만 되돌리는 것은 안전한 rollback이 아니다.

2. 왜 중요한가

“V2를 읽는다”와 “V2 row-level delete를 쓴다”는 다른 문장이다. 어떤 connector는 v2 metadata를 load하고 position delete를 적용할 수 있지만 equality delete를 쓰거나 compaction procedure를 실행하지 못할 수 있다. V3도 table load, extended type, row lineage, deletion vector read/write가 같은 시점에 구현된다고 가정할 수 없다.

Upgrade의 위험은 data rewrite 시간이 아니라 호환 집합이 즉시 바뀐다는 점이다. Catalog pointer가 v3 metadata를 가리키는 순간 old reader는 아직 data file이 전부 v1 형식이어도 table 자체를 거부해야 한다. 반대로 지원하지 않는 feature를 무시하고 값을 반환한다면 hard failure보다 위험한 silent corruption이 된다.

Week 5 최종 불변식: Spec에 기능이 존재한다는 사실, library가 format version을 load한다는 사실, engine이 그 기능을 end-to-end로 읽고 쓰며 유지보수한다는 사실은 서로 다른 증거다.

3. 아키텍처 그림과 요청 흐름

① Consumer inventory
Spark · Flink · Trino · batch · stream · maintenance job
↓ 각 consumer의 load / read / write / maintain capability 증명
② Catalog current pointer → M1, format-version=1
Snapshot → manifest list → data manifest → immutable data files
↓ CAS로 새 metadata M2 publish
③ Current pointer → M2, format-version=2
기존 v1 files는 그대로 유효 · 새 commit은 sequence/delete metadata를 쓸 수 있음
↓ 별도 v3 capability gate 통과 뒤에만 upgrade
④ Current pointer → M3, format-version=3
V1/V2 historical artifacts + V3 type/default/row-lineage/DV artifact 공존 가능
↓ query마다 current root에서 mixed tree를 계획
⑤ Reader 결과는 logical equivalence를 보존
old data + applicable delete/DV + schema/default semantics를 함께 적용

번호별 요청·응답·상태 변화

  1. Inventory: Table owner는 interactive query만 보지 않고 streaming checkpoint, recovery tool, snapshot expiration, compaction, orphan cleanup까지 consumer graph에 넣는다.
  2. Evidence: 각 engine/version에 대해 golden table을 load하고 old snapshot, current snapshot, row-level delete, metadata table, write/rollback/maintenance를 구분해 시험한다.
  3. V1→V2: Writer가 latest metadata를 읽고 v2 metadata를 준비한 뒤 catalog CAS에 성공하면 upgrade가 확정된다. Existing v1 manifests는 rewrite되지 않아도 v2 reader가 default 규칙으로 읽는다.
  4. V2 feature activation: Version 숫자를 올린 것만으로 delete file이 생기지 않는다. 이후 MOR DELETE/MERGE 같은 commit이 delete manifest와 sequence를 추가할 때 실제 read path가 확장된다.
  5. V2→V3: V3 reader는 old v2 position/equality delete도 계속 적용하면서 새 DV·row lineage·extended type을 해석해야 한다. Upgrade와 새 feature 사용을 두 배포 단계로 나누면 rollback window가 커진다.
  6. Query: Reader는 current metadata version을 먼저 gate하고, snapshot의 manifest별 version/default 규칙을 적용한다. 모르는 상위 version을 “아는 field만 읽기”로 처리하면 안 된다.

4. CS 관점의 내부 동작

V1/V2/V3 계약 비교

Version핵심 계약Reader/Writer 관점
V1Immutable Parquet/Avro/ORC 기반 analytic table, snapshot·manifest·evolution.Data file 집합을 읽는다. V2의 sequence/delete file을 알지 못한다.
V2Row-level delete file, sequence number, 더 엄격한 writer requirement.Position/equality delete applicability를 data file에 적용한다. V1 artifact는 default sequence/content 규칙으로 계속 읽는다.
V3Nanosecond·variant·geometry/geography 등 확장 type, column default, multi-argument transform, row lineage, binary DV, encryption key metadata.새 semantics와 old V2 delete를 함께 처리한다. Spec 채택과 개별 engine feature 구현 시점은 다르다.

Reader는 관대하고 writer는 엄격해야 한다

Upgrade가 metadata tree 전체를 rewrite하지 않으므로 later-version reader는 prior manifest에서 빠진 field를 spec의 default로 채워야 한다. 예를 들어 V1 artifact를 V2에서 읽을 때 sequence 관련 값과 manifest content는 V1→V2 규칙에 따라 해석한다. 반면 writer는 현재 table version의 required field와 불변식을 모두 지켜 새 metadata를 만들어야 한다. “읽을 수 있음”을 근거로 incomplete metadata를 쓰면 다음 engine에서 깨진다.

Format version은 feature flag와 다르다

Format version은 table 전체의 최소 해석 계약이다. write.delete.mode=merge-on-read 같은 property는 그 계약 안에서 어떤 artifact를 만들지 선택하는 동작 flag다. V2로 올린 직후에는 delete file이 없을 수 있고, V3로 올려도 DV나 row lineage가 즉시 모든 file에 생긴다고 단정할 수 없다. 따라서 version upgrade commit과 new feature activation commit을 분리해 관찰해야 한다.

성공 확정 시점과 downgrade 불가능성

Upgrade 성공은 새 metadata JSON 생성이 아니라 catalog pointer CAS가 성공해 current root가 바뀐 순간 확정된다. 그 뒤 새 writer가 V2/V3-only artifact를 publish할 수 있으므로 단순히 property를 낮추는 downgrade는 안전하지 않다. 복구가 필요하면 consumer를 차단하고 pre-upgrade snapshot/backup에서 새 table을 만들거나, forward fix로 호환되지 않는 artifact를 rewrite하는 migration을 설계한다.

5. 실무 설계 판단

Best practice 1 · Capability matrix: Engine 이름 옆에 지원/미지원 한 칸을 두지 않는다. 최소한 load metadata, scan data, apply position delete, apply equality delete, apply DV, append, row-level write, schema evolution, snapshot/compaction/orphan maintenance를 별도 열로 둔다.

Best practice 2 · 두 단계 rollout: 먼저 모든 consumer를 새 version-capable connector로 올리고 old-format table을 계속 운용한다. Golden query와 recovery drill이 통과한 뒤 format version만 올린다. 마지막으로 new write feature를 canary table에서 활성화한다.

Best practice 3 · 최소 공통 분모: Multi-engine table의 format version은 가장 최신 writer가 아니라 가장 느린 critical reader/recovery tool이 결정한다. 새 기능의 가치가 compatibility 비용보다 클 때만 별도 table이나 serving copy로 분리한다.

Best practice 4 · Evidence 보존: Upgrade 전 current metadata location, snapshot ID, engine/container image digest, connector version, query checksum을 기록한다. Upgrade 뒤에도 old snapshot read와 row-count/key-hash를 비교한다.

Anti-pattern: Spec V3 채택을 “모든 Spark/Flink/Trino가 V3 지원”으로 번역하기, staging의 append 성공만 보고 production MERGE 허용하기, format-version 숫자를 rollback switch로 보기, maintenance job을 matrix에서 빼는 것이다.

Edge case: Table은 V3인데 아직 V3-only artifact가 없으면 old engine이 우연히 읽는 것처럼 보일 수 있다. 이는 지원 증거가 아니라 test coverage hole이다. 반대로 V2 table도 equality delete, position delete, Puffin statistics 등 실제 artifact 조합에 따라 필요한 capability가 달라진다.

Version/engine 차이: 현재 Table Specification은 V1·V2·V3를 adopted로, V4를 개발 중으로 명시한다. Apache 구현 상태 표도 language/library별 read·write·catalog 기능이 다름을 보여준다. 프로젝트 Spark 3.5.8 + Iceberg 1.11.0 lab 결과를 다른 engine이나 최신 connector에 그대로 일반화하지 않는다.

6. 장애 대응 표

상황: Format upgrade 뒤 일부 engine이 table load에 실패하거나 삭제된 row를 다시 보여 준다.

증상Unsupported format version, metadata parse error, old snapshot만 성공, engine별 row count/key hash 불일치, 삭제 row 재등장, DV/Puffin read error, maintenance job 실패, streaming checkpoint 재시작 실패.
먼저 수집할 증거/지표Current/previous metadata location과 format-version, upgrade snapshot·timestamp, engine/connector/runtime exact version, failing query와 snapshot ID, manifest content·sequence, data/delete/DV file 수, affected partition/key checksum, catalog logs, maintenance/stream checkpoint, canary 결과.
가능한 가설Reader가 상위 version 미지원, metadata load만 지원하고 delete/DV 적용 미지원, writer가 required field 누락, old reader cache, new type/default semantics mismatch, compaction이 old delete를 누락, catalog pointer와 engine cache 불일치, recovery tool이 feature matrix에서 빠짐.
안전한 첫 조치모든 writer·maintenance와 문제 engine의 serving traffic을 멈춘다. Current metadata와 artifact를 보존하고 known-good engine으로 current/previous snapshot checksum을 비교한다. 영향 없는 reader는 검증된 snapshot을 pin한다.
rollback/복구아직 new-version artifact가 없다면 catalog 구현이 제공하는 검증된 restore 절차를 사용한다. 이미 생성됐다면 property downgrade 대신 compatible connector로 forward fix/rewrite하거나 pre-upgrade snapshot에서 별도 table을 재구성해 atomic consumer cutover한다. Checkpoint와 checksum을 다시 맞춘다.
하지 말아야 할 조치Metadata JSON·catalog pointer 수동 편집, format-version 숫자 강제 하향, 모르는 field/delete/DV 무시, failing engine으로 compaction, delete file 임의 삭제, 증거 수집 전 snapshot expiration/orphan cleanup, 일부 query 성공만으로 traffic 재개를 하지 않는다.

7. 35분 재현 실습

목표: V1 table을 만든 뒤 metadata-only로 V2에 upgrade하고, old data file이 그대로 남는 상태에서 V2 row-level delete artifact를 추가한다. 마지막으로 downgrade 실패를 주입해 format version이 reversible toggle이 아님을 확인한다.

사전 조건과 실행 전 예측

  • Docker Desktop이 정상이고 프로젝트 make smoke가 성공해야 한다. Runtime은 Spark 3.5.8 + Iceberg 1.11.0, local Hadoop-backed SparkCatalog와 SQL extensions다.
  • V1→V2 upgrade 직후 row count와 data file path는 같고 metadata JSON만 새로 생길 것이라고 먼저 적는다.
  • V2에서 MOR DELETE를 실행하면 current logical row는 3→2가 되고, data file과 position delete file이 함께 계획될 것이라고 예측한다.
  • V2→V1 downgrade 시도는 non-zero로 실패해야 한다. 실패가 나면 실습 성공이며 억지로 metadata를 편집하지 않는다.

0단계 · 환경 확인

make smoke
rg -n "apache/spark|iceberg-spark-runtime" docker-compose.yml conf/spark-defaults.conf

1단계 · V1 baseline과 증거 만들기

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
CREATE NAMESPACE IF NOT EXISTS local.day35;
DROP TABLE IF EXISTS local.day35.compat PURGE;
CREATE TABLE local.day35.compat (
  id BIGINT, payload STRING
) USING iceberg
TBLPROPERTIES ('format-version'='1');
INSERT INTO local.day35.compat VALUES
  (1, 'alpha'), (2, 'beta'), (3, 'gamma');
SHOW TBLPROPERTIES local.day35.compat ('format-version');

"

예상 관찰: Property는 1, row는 3, files.content는 data를 뜻하는 0이다. V1에서는 sequence field가 없거나 V2 reader의 default 관점으로 0처럼 보일 수 있으므로 metadata table schema를 먼저 확인한다.

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
ALTER TABLE local.day35.compat

예상 관찰: Property는 2가 되고 metadata log에는 새 metadata JSON이 추가된다. Row count는 3이고 기존 data file path는 유지된다. Upgrade는 catalog root의 계약을 바꾸지만 historical tree를 즉시 rewrite하지 않는다.

3단계 · V2 feature activation과 read path 확장

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
ALTER TABLE local.day35.compat SET TBLPROPERTIES (
  'write.delete.mode'='merge-on-read',
  'write.delete.granularity'='file'
);
DELETE FROM local.day35.compat WHERE id = 2;
SELECT * FROM local.day35.compat ORDER BY id;
SELECT content, count(*) AS files, sum(record_count) AS records
FROM local.day35.compat.files GROUP BY content ORDER BY content;
SELECT status, content, sequence_number, file_sequence_number,
       data_file.file_path
FROM local.day35.compat.entries
ORDER BY sequence_number, data_file.file_path;
EXPLAIN FORMATTED SELECT * FROM local.day35.compat WHERE id >= 1;
"

예상 관찰: Logical result는 id 1과 3이다. Current files에는 data(content=0)와 position delete(content=1)가 공존하고, reader는 applicable delete를 merge한다. V2 upgrade와 V2-only artifact 생성은 서로 다른 state transition임이 보인다.

예상 관찰: Downgrade command는 실패하고 table은 V2, logical row는 2로 남는다. 이 hard failure가 old reader에게 V2 delete를 무시하게 허용하는 것보다 안전하다.

5단계 · Production capability gate 작성

# 실제 조직의 engine/version별로 PASS/FAIL/UNKNOWN을 채운다.
# UNKNOWN은 PASS가 아니라 upgrade blocker다.
printf '%s\n' \
  'consumer,load_v3,read_old_v2_delete,read_dv,write_dv,maintain' \
  'spark-batch,UNKNOWN,UNKNOWN,UNKNOWN,UNKNOWN,UNKNOWN' \
  'flink-stream,UNKNOWN,UNKNOWN,UNKNOWN,UNKNOWN,UNKNOWN' \
  'trino-serving,UNKNOWN,UNKNOWN,UNKNOWN,N/A,UNKNOWN' \
  'recovery-tool,UNKNOWN,UNKNOWN,UNKNOWN,N/A,UNKNOWN'

판정: 하나라도 critical path에 UNKNOWN/FAIL이 있으면 V3 upgrade를 중단한다. 본 lab의 V2 성공은 V3/DV 지원 증거가 아니다.

자주 나는 오류와 해결

  • metadata_log_entries column 오류: DESCRIBE local.day35.compat.metadata_log_entries로 runtime schema를 확인하고 존재하는 column만 선택한다.
  • DELETE extension 오류: conf/spark-defaults.conf의 Iceberg Spark extensions와 1.11.0 runtime package를 확인한다.
  • Position delete가 안 생김: Property가 MOR인지 확인하고 current files/entries를 본다. Planner가 COW를 택했다면 engine/version 차이를 기록한다.
  • Downgrade가 뜻밖에 성공: 즉시 writer를 멈추고 metadata log·artifact를 보존한다. 같은 환경을 production-safe로 간주하지 말고 connector bug/behavior를 별도 조사한다.
  • V3를 직접 시험하고 싶음: 공유 table이 아니라 폐기 가능한 canary에서만 load/read/write/maintenance matrix 전체를 수행한다. Property 숫자 변경만으로 인증하지 않는다.

8. 놓치기 쉬운 함정

  • 최신 spec = 최신 engine 지원이 아니다. Spec은 계약이고 connector는 구현이다.
  • Table load 성공 = feature 안전이 아니다. 실제 delete/DV/type/default artifact가 포함된 fixture로 결과를 검증해야 한다.
  • Upgrade = rewrite가 아니다. Old artifact가 남기 때문에 new reader의 backward compatibility가 중요하다.
  • Format version = write mode가 아니다. Version은 가능한 계약, write property는 실제 artifact 선택이다.
  • Snapshot rollback = format downgrade가 아니다. Current table metadata 계약과 historical snapshot 선택은 다른 축이다.
  • Query engine만 consumer가 아니다. Stream recovery, compaction, expiration, orphan cleanup, catalog migration tool도 포함한다.
  • V3 table이면 모든 delete가 DV가 아니다. Upgrade된 tree에는 old V2 delete file이 남을 수 있어 reader가 둘 다 처리해야 한다.

9. 대기업 기술 면접 질문

  1. 10PB V2 table을 V3로 올리는 rollout을 설계하라.
    좋은 답변 구조: Consumer/복구 경로 inventory → connector exact version → load/read/write/maintain capability matrix → golden fixture와 수치 SLA → connector 선배포 → metadata-only canary upgrade → DV/새 type activation 분리 → checksum/latency 관찰 → failure window와 forward-fix/별도 table cutover 대안.
  2. V3로 올렸지만 V3-only artifact는 아직 없다. Old reader traffic을 허용해도 되는가?
    좋은 답변 구조: Spec의 upper-version hard gate → 우연한 성공과 지원 구분 → cache/metadata parse/미래 commit race → silent corruption 위험 → version-aware admission control → old-format serving copy라는 대안.
  3. Upgrade 후 Trino와 Spark row count가 다르다. 어디서부터 조사할 것인가?
    좋은 답변 구조: Snapshot pin과 수치 차이 → metadata location/format version → engine/connector matrix → manifest content/sequence → position/equality/DV applicability → partition/key checksum → cache/compaction race → 안전한 traffic stop·known-good reader → forward rewrite 또는 pre-upgrade snapshot copy.

10. 복습과 정답

어제 내용 회상 3문제

  1. MOR DELETE 뒤 logical row count와 physical file count가 반대로 움직일 수 있는 이유는?
  2. Query plan만 보고 delete applicability를 완전히 증명할 수 없는 이유는?
  3. Position delete rewrite 전후 반드시 같아야 하는 logical invariant 두 가지는?

짧은 정답/채점: ① Data file을 즉시 rewrite하지 않고 delete file을 추가하므로 logical row는 줄고 physical planning artifact는 늘 수 있다. ② Plan label은 engine별 표현이며 path·position·partition·sequence 적용 증거를 모두 노출하지 않는다. ③ Row count와 key/hash 또는 ordered result가 같아야 한다. 각 문항에서 상태 소유자와 metadata 증거를 언급하면 만점.

오늘 내용 확인 3문제

  1. V1→V2 upgrade에 data file rewrite가 필수가 아닌 이유는?
  2. “V3 지원”을 최소 네 개 capability로 쪼개 보라.
  3. Format downgrade가 property rollback으로 안전하지 않은 이유는?

짧은 정답/채점: ① V1 artifact는 V2에서도 유효하고 missing field default 규칙으로 읽기 때문이다. ② 예: metadata load, old delete read, DV read, DV write, new type/default, maintenance 중 네 가지 이상. ③ Upgrade 후 새 version-only artifact와 semantics가 생길 수 있어 old reader가 이를 해석하지 못하며 downgrade 자체가 금지되기 때문이다. “version 숫자와 artifact activation 분리”까지 말하면 만점.

11. 공식 자료

  • Apache Iceberg Table Spec · Format Versioning — V1/V2/V3의 채택 상태, 기능 경계와 forward-compatibility 원칙.
  • Apache Iceberg Table Spec · Appendix E — prior-version metadata default와 version별 writer requirement.
  • Apache Iceberg · Implementation Status — language/library별 read·write·catalog·maintenance capability 차이.
  • Apache Iceberg 1.11.0 · Configuration — 프로젝트 runtime의 format-version reserved property.
