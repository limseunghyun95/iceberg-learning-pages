APACHE ICEBERG · WEEK 3 / DAY 18

partition spec ID와 spec coexistence

Schema·Partition·Sort Evolution · 예상 학습 35분 + 실습 35분

한 줄 요약
Partition evolution은 old file을 옮기지 않고 새 spec을 default로 추가하므로, reader는 current spec 하나가 아니라 manifest마다 기록된 spec ID로 predicate를 따로 투영한 뒤 결과를 합쳐야 한다.

1. 선수 용어 사전

Partition specSource field ID, partition field ID, transform, name의 ordered list로 이루어진 물리 배치 계약이다.
Spec IDPartition spec 전체 version을 식별하는 정수다. Layout 변경은 unique spec ID를 가진 새 spec을 만든다.
Partition field IDSpec 안 partition tuple field의 정체성이다. 같은 의미의 field는 evolution 뒤에도 ID를 재사용한다.
Default spec ID새 writer가 기본으로 선택할 spec이다. Reader가 old manifest를 해석할 때 강제로 적용하는 current layout이 아니다.
Manifest한 partition spec으로 쓴 data 또는 delete file만 모아 놓은 immutable Avro index다.
Split planning동일 logical predicate를 spec별 transform에 각각 투영해 후보 file을 만들고 union하는 계획 과정이다.
Coexistence한 snapshot에서 old/new spec의 manifest와 file이 동시에 table membership을 갖는 상태다.
Dynamic overwriteIncoming row가 만든 partition을 암시적으로 교체하는 write 방식이다. Spec 변경 시 교체 단위도 달라진다.

2. 왜 중요한가

일 단위 table이 커져 시간 단위로 바뀌어도 수 PB의 old file을 즉시 rewrite할 이유는 없다. Iceberg는 기존 day(event_time) spec과 file을 그대로 두고, 새 hour(event_time) spec을 writer default로 만든다. 전환 순간의 작업은 metadata change이며 old/new layout은 자연스럽게 공존한다.

이 유연성은 reader에게 의무를 만든다. New default spec으로 old manifest의 partition tuple을 해석하면 day 값과 hour 값을 같은 위치의 정수로 오인해 정답 file을 버릴 수 있다. 따라서 manifest list의 partition_spec_id가 어느 transform과 tuple schema를 써야 하는지 결정한다.

핵심 불변식: 각 manifest는 정확히 한 spec을 사용하며, read는 manifest의 spec ID로 partition tuple과 summary를 해석한다. default-spec-id는 주로 새 write의 기본값이지 old read의 schema가 아니다.

3. 아키텍처 그림과 요청 흐름

① Catalog pointer → metadata JSON
partition-specs [spec 0, spec 1] · default-spec-id=1
↓ snapshot 고정 → manifest list
② Manifest group A · spec 0
day(event_time) · old data/delete files · day summaries
↘ day 기준 predicate projection
③ Manifest group B · spec 1
hour(event_time) · new data/delete files · hour summaries
↗ hour 기준 predicate projection
④ Spec별 candidate union
manifest/file metrics · sequence · residual · COW/MOR/DV
↓ file read + logical predicate 재검사
⑤ 하나의 logical result
사용자는 layout 전환을 SQL에서 보지 않음

Read path: 요청·응답·상태

  1. Reader가 catalog pointer의 metadata JSON과 snapshot을 pin하고 partition-specs 전체를 load한다.
  2. Manifest list의 각 entry에서 partition_spec_id와 해당 spec field 순서에 맞춘 partition summary를 읽는다.
  3. Logical time-range predicate를 spec 0에는 day predicate, spec 1에는 hour predicate로 별도 projection한다.
  4. 각 spec의 manifest summary와 manifest entry tuple, field metrics로 후보를 줄인다. Tuple의 같은 position을 spec 사이에서 직접 비교하지 않는다.
  5. Spec별 candidate data/delete file을 union하고 sequence number, equality field ID, position target 또는 DV 관계를 보수적으로 적용한다.
  6. Data path에서 residual을 평가해 false positive를 제거한다. 어느 spec의 정답 file도 빠지지 않아야 snapshot isolation이 유지된다.

Evolution write path와 state transition

  1. S0: Metadata v10은 spec 0 day(ts)를 default로 두고 snapshot 100은 spec 0 manifest를 가리킨다.
  2. UpdateSpec이 base metadata를 읽고 hour(ts) field에 새 partition field ID를 할당해 unique spec 1을 만든다. Equivalent field가 유지되면 기존 field ID를 재사용한다.
  3. 새 metadata v11의 partition-specs에 spec 0·1을 모두 보존하고 default-spec-id만 1로 바꾼 뒤 catalog CAS한다. 이 metadata-only transition 자체는 data file이나 snapshot을 rewrite하지 않는다.
  4. S1: 새 writer는 spec 1로 partition tuple과 새 manifest를 만든다. Manifest 하나에는 spec 하나만 들어간다.
  5. Append가 snapshot 101과 manifest list를 만들며 old spec 0 manifest와 new spec 1 manifest를 함께 참조한다. CAS 성공이 새 row 공개 시점이다.
  6. Stale writer가 spec 0으로 준비한 append는 engine/operation validation에 따라 conflict·retry되거나 old spec manifest로 안전하게 공존할 수 있다. 운영은 commit 성공만 보지 말고 spec ID 분포를 관측한다.

4. CS 관점의 내부 동작

상태/ID소유자 · 불변식 · 역할
Spec IDMetadata JSON의 spec version key다. Manifest list와 manifest metadata가 참조하며 table의 partition-specs에 반드시 존재해야 한다.
Field IDPartition tuple field의 identity다. Equivalent source ID·transform·name field는 reuse해야 metadata table union과 evolution 의미가 유지된다.
Default spec IDWriter control path의 기본 선택이다. Deprecated current partition-spec도 read 기준이 아니며 reads는 manifest spec을 사용한다.
Last partition IDTable 전체에서 새 partition field ID가 과거 의미와 충돌하지 않게 하는 high-water mark다.
Manifest schemaPartition tuple struct type은 manifest가 쓴 spec에서 유도된다. 그래서 manifest는 여러 spec의 file을 섞을 수 없다.
Snapshot여러 spec manifest를 포함할 수 있는 immutable membership root다. Spec 변경과 snapshot 변경은 별도 state transition이다.

Spec equivalence와 ID reuse

두 spec은 field 수가 같고 각 위치의 source IDs, transform definition, partition name이 같으면 equivalent다. Writer는 이미 compatible spec이 있는데 duplicate spec을 만들면 안 된다. 기존 spec에 equivalent field가 있으면 partition field ID도 reuse해야 한다.

day(ts)를 그대로 두고 bucket[16](id)만 추가하면 day field ID는 유지되고 bucket에는 fresh ID가 필요하다. day(ts)를 hour(ts)로 바꾸면 transform 의미가 달라 fresh field ID를 가져야 한다.

V1과 V2/V3의 차이

V2는 partition field ID를 명시적으로 추적하고 table의 last-partition-id로 전체 spec에 걸쳐 새 ID를 할당한다. V1 reference implementation은 각 spec에서 1000부터 순차 할당한 이력이 있어, 서로 다른 type/의미가 같은 ID를 가질 수 있고 multi-spec metadata table 해석에 문제가 생길 수 있다. Upgraded table을 다룰 때 format version과 실제 spec history를 함께 본다.

비용 모델

Evolution 시점 비용은 O(metadata)이지만 이후 planning은 spec 수만큼 predicate projection과 manifest group 처리가 늘어난다. 즉시 full rewrite 비용을 피하는 대신 metadata fan-out과 mixed-layout 운영 복잡도를 지불한다. Rewrite는 성능 최적화이며 correctness를 위한 즉시 선행 조건이 아니다.

5. 실무 설계 판단

판단 기준Best practice와 이유
Evolution triggerPartition당 bytes/file count, query selectivity, late arrival, skew와 target file size를 수치화한다. Calendar가 바뀌었다는 이유만으로 spec을 늘리지 않는다.
RolloutWriter/reader compatibility canary → metadata-only default 변경 → spec ID 분포 관찰 → 필요 시 controlled rewrite 순서로 진행한다.
Overwrite semanticsDynamic overwrite는 spec 변경 후 교체 단위가 day에서 hour처럼 달라진다. 명시적 predicate가 있는 overwrite/MERGE 또는 DataFrameWriterV2로 의도를 고정한다.
Metadata queriesPartition field drop/rename은 files/partitions의 union struct를 바꿀 수 있다. Field name·position에 고정된 dashboard를 spec/ID aware하게 만든다.
MaintenanceRewrite 결과가 어떤 spec으로 이동하는지, concurrent append/delete와 sequence validation이 안전한지 확인한다. 모든 old file을 한 번에 바꾸지 않아도 된다.
ObservabilitySnapshot별 manifest count/spec ID, file/bytes/spec 분포, scanned files, planning latency, stale writer commit과 dynamic overwrite 범위를 지표화한다.

Engine/version 차이: Spark 3는 Iceberg SQL extensions로 ADD/DROP/REPLACE PARTITION FIELD를 제공한다. 최신 Flink DDL은 ALTER TABLE에서 table property 변경만 지원하므로 Java API나 지원되는 관리 경로가 필요할 수 있다. Spec-level read 호환과 DDL 노출을 같은 것으로 보지 않는다.

Anti-pattern: Evolution 직후 old partition directory를 새 layout으로 이동하거나, current default spec으로 모든 manifest tuple을 cast하는 custom reader를 운영하는 것이다.

Edge case: Spec 변경 직전에 시작한 streaming writer가 old spec manifest를 나중에 commit할 수 있다. Protocol상 old spec이 유효하면 coexistence는 correctness 문제는 아닐 수 있지만 rollout SLO와 file layout 기대에는 어긋나므로 writer refresh·spec telemetry가 필요하다.

6. 장애 대응 표

상황: Partition evolution 뒤 old 구간이 누락되거나 query planning 비용이 급증했다.

증상Evolution 이전 row만 누락, engine별 결과 차이, scanned manifest/file·planning latency 증가, metadata table schema 오류, new write가 old spec에 계속 쌓임, dynamic overwrite가 예상보다 좁거나 넓음.
먼저 수집할 증거/지표Catalog metadata location·snapshot ID, partition-specs/default/last-partition-id, manifest list의 partition_spec_id·summary, manifest key metadata와 tuple schema, files의 spec_id·partition·sequence, query/residual plan, engine/connector/cache version, overwrite/maintenance commit 전후.
가능한 가설Reader가 default spec만 적용, tuple position 비교, v1 field-ID collision, stale spec cache/writer, spec별 projection 누락, unknown transform 오처리, dynamic overwrite 단위 변경, partial rewrite 또는 MOR delete/spec·sequence 적용 bug.
안전한 첫 조치Affected overwrite/rewrite와 schema/spec 변경을 멈추고 snapshot을 pin한다. Spec별 manifest/file sample과 plan을 보존한다. 문제 reader에서 해당 spec pruning을 보수적으로 끄고 full scan 결과를 known-good Iceberg reader와 비교한다.
Rollback/복구Catalog-supported retained metadata/snapshot rollback 또는 compensating spec evolution을 사용한다. Wrong-layout file은 검증된 rewrite로 새 snapshot에 교체하고 writer를 known-good spec-aware version으로 되돌린다.
하지 말아야 할 조치Metadata JSON의 spec/field ID나 manifest tuple을 수동 편집하지 않는다. Old directories/files를 이동·삭제하지 않는다. 증거 없이 snapshot expire/orphan cleanup·전체 rewrite를 실행하지 않는다.

실패 주입 · Dynamic overwrite 의미 변화

docker compose run --rm spark /opt/spark/bin/spark-sql -e "
SET spark.sql.sources.partitionOverwriteMode=dynamic;

INSERT OVERWRITE local.day18.spec_lab
VALUES (40, TIMESTAMP '2026-08-18 12:45:00', 'overwrite-12');

SELECT id, event_time, message
FROM local.day18.spec_lab
WHERE event_time >= TIMESTAMP '2026-08-18 00:00:00'
  AND event_time < TIMESTAMP '2026-08-19 00:00:00'
ORDER BY event_time;
"

예상 관찰: New default의 12시 partition은 id 4 대신 id 40으로 교체되지만, old day-spec의 id 1·2와 new 13시 id 5는 남는다. “2026-08-18 하루 전체 overwrite”를 기대했다면 위험한 의미 차이다. 결과는 engine/config에 민감하므로 production 전 exact writer mode를 검증한다.

자주 나는 오류와 해결

  • REPLACE PARTITION FIELD 이름 오류: Metadata JSON의 exact partition field name을 사용한다. 추측한 directory name을 쓰지 않는다.
  • SQL extensions 미설정: Spark session에 Iceberg extensions/catalog 설정이 있는지 make smoke와 config로 확인한다.
  • all_manifests column 이름 차이: DESCRIBE로 connector version의 metadata table schema를 확인하고 동일 의미 field를 선택한다.
  • Metadata filename 정렬 오류: metadata_log_entries의 마지막 committed file URI를 사용한다.
  • Old row가 안 보임: Snapshot ID, manifest spec ID, plan을 보존하고 raw path가 아닌 Iceberg table read로 재현한다.
  • Overwrite 결과가 다름: Static/dynamic mode와 DataFrameWriter V1/V2, engine version을 기록한다. 예상에 맞추려 강제 file 삭제를 하지 않는다.

8. 놓치기 쉬운 함정

  1. Default spec은 모든 file의 spec이다. 새 writer 기본값일 뿐 old manifest는 자기 spec ID로 읽는다.
  2. Spec 변경은 old file을 재배치한다. Metadata-only이며 old layout은 그대로 공존한다.
  3. Partition tuple의 같은 위치는 같은 의미다. 반드시 spec과 field ID를 함께 해석해야 한다.
  4. Manifest 하나에 여러 spec file을 넣을 수 있다. Manifest partition struct schema는 한 spec에서 유도된다.
  5. 새 spec마다 모든 partition field ID를 새로 만든다. Equivalent field는 ID를 reuse해야 한다.
  6. Spec evolution 뒤 dynamic overwrite 의미는 같다. 암시적 교체 partition 단위가 달라질 수 있다.
  7. Rewrite가 끝나야 query가 정확하다. Spec-aware split planning이 correctness를 보장하고 rewrite는 비용 최적화다.
  8. Format version을 무시해도 된다. V1 field-ID history는 multi-spec metadata 해석에 특별한 주의가 필요하다.

9. 대기업 기술 면접 질문 3개

  1. Day partition 5PB table을 hour partition으로 무중단 전환하라.
    좋은 답변 구조: Query/ingest/SLO 수치 → metadata state transition → spec/field ID → split planning → writer rollout·stale writer → overwrite/maintenance race → 지표·rollback → full rewrite 대안 비용.
  2. Reader가 default spec만 사용하면 어떤 correctness bug가 나는가?
    좋은 답변 구조: Manifest list read path → day/hour tuple type·단위 → 잘못된 projection의 false negative → old row 누락 예제 → safe fallback(full scan/residual) → multi-engine canary.
  3. Partition evolution 직후 planning latency가 3배가 됐다. 어떻게 진단할까?
    좋은 답변 구조: Snapshot/spec별 manifest·file 수 수치 → query plan/projection → small files·summary 품질 → stale writer/partial rewrite → safe first action → rewrite/manifest compaction 대안·rollback.

10. 어제 내용 회상 3문제

  1. Hidden partitioning에서 사용자가 physical partition column을 query에 직접 넣지 않아도 되는 이유는?
  2. Bucket equality projection 뒤에도 residual이 필요한 이유는?
  3. Reader가 unknown transform을 만났을 때 안전한 fallback은?
짧은 정답/채점 기준
1) Metadata spec이 source ID와 transform을 소유하고 planner가 자동 projection한다. 2) Hash collision 때문에 같은 bucket에 다른 값이 존재한다. 3) 해당 field pruning을 포기하고 candidate를 포함한 뒤 residual을 평가한다. 책임·collision·보수성을 말하면 각 1점.

11. 오늘 내용 확인 문제 3개

  1. default-spec-id와 manifest의 partition_spec_id는 각각 언제 쓰는가?
  2. 왜 manifest 하나는 여러 partition spec의 file을 섞을 수 없는가?
  3. Day→hour 전환 뒤 같은 logical time filter를 reader는 어떻게 계획하는가?
정답/채점 기준
1) Default는 새 write 기본 선택, manifest spec ID는 그 manifest의 tuple/summary read 해석에 쓴다. 2) Manifest partition struct schema가 한 spec에서 유도되기 때문이다. 3) Day/hour spec별로 predicate를 각각 projection·prune하고 candidate를 union한 뒤 residual을 평가한다. write/read 책임·schema·split planning을 말하면 각 1점.
