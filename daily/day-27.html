랩: 두 writer concurrent commit

Commit·Isolation·Concurrency · 예상 학습 20분 + 실습 35분

한 줄 요약
같은 base snapshot에서 출발한 두 writer 중 하나만 첫 catalog CAS에 성공하지만, append처럼 compatible한 변화는 최신 state에 rebase해 다시 commit할 수 있고 같은 data file을 교체하는 overwrite는 validation으로 안전하게 거부해야 한다.

1. 선수 용어 사전

WriterTable에 새 snapshot을 만들려는 job 또는 process다. Spark driver, Flink checkpoint committer, maintenance action 모두 writer가 될 수 있다.
Base snapshotWriter가 계획을 세울 때 읽은 출발 state다. “이 file들이 현재 존재한다”는 validation 전제의 기준점이다.
CASCompare-and-swap. Catalog pointer가 내가 예상한 metadata M0일 때만 M1로 바꾸는 원자 연산이다. 동시 commit의 승자를 정하는 linearization point다.
Optimistic concurrency긴 lock을 잡지 않고 각 writer가 독립 준비한 뒤 commit 시점에 충돌을 검사하는 방식이다. 충돌이 드물면 throughput이 높다.
RebaseCAS에서 진 writer가 최신 metadata를 읽고 자신의 논리 변화를 그 위에 다시 얹는 과정이다. 기존 data file을 다시 쓸 필요가 없는 경우가 많다.
ValidationBase 이후 변화가 operation의 전제를 깨는지 검사한다. Source file 소실, predicate와 겹치는 신규 file, delete 충돌 등이 대상이다.
Orphan artifactObject storage에는 있지만 committed metadata graph에서 도달할 수 없는 data·manifest·metadata file이다. 실패 writer의 준비물이 대표적이다.
Unknown commit stateCAS 요청 뒤 응답을 잃어 성공과 실패를 확정할 수 없는 상태다. 명시적 CAS conflict와 달리 blind retry하면 중복 commit 위험이 있다.

2. 왜 중요한가

Production에서는 streaming append, batch overwrite, CDC MERGE, compaction이 같은 table을 동시에 쓴다. “동시에 쓰면 하나는 무조건 실패한다”도, “Iceberg가 알아서 모두 retry한다”도 틀리다. 결과는 operation의 read/write set과 최신 state가 전제를 깨는지에 달려 있다.

Blind append 두 건은 서로의 file을 읽거나 지우지 않으므로 보통 compatible하다. 첫 writer가 pointer를 바꿔 두 번째의 CAS가 실패해도, 두 번째는 최신 snapshot 위에 자신의 manifest를 다시 연결할 수 있다. 반대로 두 overwrite가 같은 source file을 제거하려 하면 첫 commit 뒤 두 번째의 전제가 사라진다. 이를 다시 얹으면 삭제된 data를 되살리거나 상대 writer의 결과를 덮을 수 있으므로 safe abort가 맞다.

오늘의 핵심 구분: CAS 실패는 “누가 먼저 commit했다”는 신호이고, validation 실패는 “내 계획의 의미가 더 이상 안전하지 않다”는 신호다. Timeout은 성공 여부조차 모르는 세 번째 상태다.

번호별 요청·응답·상태 변화

  1. Plan: 두 writer는 M0가 가리키는 metadata JSON, S0, manifest list와 manifest를 읽는다. Data path에는 각자 새 file을 쓰지만 control path는 아직 바뀌지 않는다.
  2. First commit: W-A가 새 metadata M1을 준비하고 catalog CAS에 성공한다. 성공 확정 시점은 file PUT이나 manifest 생성이 아니라 pointer swap이다.
  3. Refresh: W-B의 stale expected pointer는 CAS에서 거절된다. W-B는 S1을 읽어 S0 이후 added/removed data·delete file과 sequence를 비교한다.
  4. Compatible branch: Append는 기존 file을 제거하지 않아 W-A의 append와 합성 가능하다. W-B는 새 manifest list/metadata만 만들고 준비한 data/manifest를 재사용해 M1→M2를 시도한다.
  5. Conflict branch: Overwrite가 제거하려던 source file이 W-A에 의해 사라졌다면 plan 전제가 깨졌다. W-B는 prepared replacement를 publish하지 않고 validation exception으로 끝난다.
  6. Read: Reader는 load한 snapshot을 query 끝까지 사용한다. S1과 S2의 file set을 임의로 섞거나 failed writer의 orphan을 directory listing으로 읽지 않는다.

비용 모델

Optimistic concurrency는 lock 대기 대신 충돌 시 metadata refresh, manifest diff, predicate validation, 새 metadata 생성 비용을 낸다. Append retry는 이미 쓴 data/manifest를 재사용해 비교적 싸다. Overwrite·MERGE·maintenance는 source file과 predicate가 넓을수록 replan 비용과 safe failure 확률이 커진다. Commit rate가 catalog CAS 처리량을 넘으면 backoff만으로는 해결되지 않으며 micro-batch 합치기, hot partition 분리, maintenance window가 필요하다.

5. 실무 설계 판단

Best practice 1 · operation identity: Job run ID, source checkpoint, batch ID를 snapshot summary에 남긴다. Unknown state에서 current history를 검색해 성공 여부를 판정하고 중복 재실행을 막을 수 있다.

Best practice 2 · retry taxonomy: CommitFailed/CAS conflict, ValidationException, CommitStateUnknown을 같은 retry handler에 넣지 않는다. Exception class, base/current snapshot, attempt와 backoff를 구조화해 기록한다.

Best practice 3 · 수치 예산: Commit p95/p99, CAS conflict rate, validation failure rate, retry attempts, status-check latency, orphan bytes, catalog error rate를 본다. Retry 횟수보다 total timeout과 downstream SLA를 함께 제한한다.

Best practice 4 · scope 축소: Overwrite/MERGE predicate와 compaction file group을 작게 유지하고 streaming hot partition과 maintenance 범위를 시간·branch로 분리한다. 충돌 영역이 줄면 false-positive validation과 replan도 줄어든다.

Apache Iceberg 1.11.0 문서 기준: Table behavior property의 기본값은 commit retry 4회, 최소 wait 100ms, 최대 wait 60초, total timeout 30분이다. Unknown-state status check는 별도 기본 3회다. 이 값은 보장 자체가 아니라 retry budget이며 catalog SLA와 job deadline에 맞춰 조정한다.

Multi-engine 차이: Table Spec은 atomic replacement와 retry 원칙을 정의하지만 Spark·Flink·Trino와 REST/Hive/Glue/Hadoop catalog의 exception wrapping, automatic retry, isolation option, status-check surface는 같지 않다. Engine/version 조합별 concurrency contract test를 release gate로 둔다.

Maintenance race: Rewrite action이 새 file을 준비한 뒤 streaming delete가 source에 붙으면 rewrite validation이 실패할 수 있다. 실패를 강제로 무시하면 delete가 유실될 수 있으므로 latest delete까지 포함해 다시 계획한다.

Anti-pattern: 모든 conflict를 지수 backoff로만 덮거나, append가 재시도 가능하다는 사실을 overwrite에도 일반화하거나, timeout 직후 동일 batch를 새 ID로 다시 쓰는 것이다.

Edge case: Catalog CAS는 성공했지만 client가 응답 전에 끊길 수 있다. Object storage가 read-after-write consistent해도 이 control-plane ambiguity는 남는다. Data object 존재 여부만으로 성공을 판정하지 않는다.

6. 장애 대응 표

상황: 동시 writer에서 commit 실패·retry 폭증·중복 batch 또는 orphan file이 관찰된다.

증상CommitFailedException/ValidationException/CommitStateUnknown, retry storm, p99 commit 지연, 같은 batch row 중복, snapshot summary 누락, prepared data·manifest 증가, maintenance와 ingestion 동시 실패.
먼저 수집할 증거/지표Engine/connector/catalog/version, exact exception class와 cause, operation·isolation·COW/MOR, base/current snapshot ID·sequence·parent, added/removed data/delete paths와 predicate/spec ID, job/batch ID, attempt/backoff, object PUT·catalog request timeline, current metadata pointer.
가능한 가설Compatible append의 정상 CAS 경쟁, 같은 source file overwrite, concurrent matching add/delete, compaction race, stale cache, retry budget 과소/과대, catalog throttling, 응답 유실 뒤 unknown state, idempotency key 불일치.
안전한 첫 조치동일 batch blind retry와 orphan cleanup을 멈춘다. Catalog를 refresh해 current graph에서 operation identity와 prepared path를 조회한다. 명시적 CAS conflict만 canary 한 건으로 revalidate하고, validation failure는 충돌 범위를 격리한다.
rollback/복구성공 확인 시 checkpoint를 해당 snapshot에 맞춘다. 미성공 확인 시 latest snapshot에서 재계획한다. 중복은 compensating DELETE/MERGE로 forward fix하고, 잘못된 overwrite는 영향 검증 후 rollback한다. 고유 orphan은 safety window와 reachability 확인 뒤 정리한다.
하지 말아야 할 조치Validation 비활성화, stale plan 무한 retry, metadata JSON·pointer 수동 편집, timeout을 실패로 단정, warehouse 최신 file 일괄 삭제, 증거 전 snapshot expiration/remove-orphan, job ID를 바꾼 중복 append를 하지 않는다.

7. 35분 재현 실습

목표: 같은 base에서 미리 만든 두 append operation은 둘 다 성공하는 반면, 같은 source file을 지우는 두 overwrite 중 두 번째는 validation failure가 되는 것을 Iceberg API와 snapshot lineage로 확인한다.

사전 조건과 실행 전 예측

  • Docker Desktop이 정상 실행 중이고 프로젝트의 make smoke가 성공해야 한다. 학습 환경은 Spark 3.5.8 + Iceberg 1.11.0이다.
  • 두 append operation은 같은 base ID를 출력하고 최종 row/file 수가 base 포함 3이 될 것이라고 예측한다.
  • 두 overwrite operation은 같은 victim path와 base를 사용하며, A 성공 뒤 B는 ValidationException 계열로 실패할 것이라고 예측한다.
  • 실패 B가 준비한 replacement file은 table query에는 안 보이고 orphan 후보가 된다. 실습은 실패가 확정된 뒤 그 고유 file만 지운다.

1단계 · Deterministic concurrent-commit model 실행

make smoke
docker compose up -d

docker compose exec -T spark /opt/spark/bin/spark-shell <<'SCALA'
import org.apache.iceberg._
import org.apache.iceberg.spark.Spark3Util

spark.sql("CREATE NAMESPACE IF NOT EXISTS local.day27")
spark.sql("DROP TABLE IF EXISTS local.day27.concurrent_lab PURGE")
spark.sql("""
  CREATE TABLE local.day27.concurrent_lab (
    id BIGINT, writer STRING, note STRING
  ) USING iceberg
""")
spark.sql("INSERT INTO local.day27.concurrent_lab VALUES (0, 'base', 'seed')")

def firstDataFile(t: Table): DataFile = {
  val tasks = t.newScan().planFiles()
  try tasks.iterator().next().file()
  finally tasks.close()
}

// 동일 Parquet bytes를 unique path로 복제해 commit 전 prepared data file을 만든다.
def cloneDataFile(t: Table, src: DataFile, label: String): DataFile = {
  val token = java.util.UUID.randomUUID().toString
  val target = s"${t.location()}/data/day27-$label-$token.parquet"
  val in = t.io().newInputFile(src.path().toString).newStream()
  val out = t.io().newOutputFile(target).create()
  val buf = new Array[Byte](64 * 1024)
  try {
    var n = in.read(buf)
    while (n != -1) {
      if (n > 0) out.write(buf, 0, n)
      n = in.read(buf)
    }
  } finally {
    in.close()
    out.close()
  }
  DataFiles.builder(t.spec()).copy(src)
    .withPath(target)
    .withFileSizeInBytes(t.io().newInputFile(target).getLength())
    .build()
}

// A. Compatible append: 두 operation을 commit 전에 만들어 같은 base를 고정한다.
val seedTable = Spark3Util.loadIcebergTable(spark, "local.day27.concurrent_lab")
val seedFile = firstDataFile(seedTable)
val appendFileA = cloneDataFile(seedTable, seedFile, "append-A")
val appendFileB = cloneDataFile(seedTable, seedFile, "append-B")
val appendTableA = Spark3Util.loadIcebergTable(spark, "local.day27.concurrent_lab")
val appendTableB = Spark3Util.loadIcebergTable(spark, "local.day27.concurrent_lab")
val appendBaseA = appendTableA.currentSnapshot().snapshotId()
val appendBaseB = appendTableB.currentSnapshot().snapshotId()
val appendA = appendTableA.newAppend().appendFile(appendFileA)
  .set("lab.writer", "append-A")
val appendB = appendTableB.newAppend().appendFile(appendFileB)
  .set("lab.writer", "append-B")
appendA.commit()
appendB.commit() // stale base를 refresh/rebase한 뒤 내부 retry로 성공해야 한다.
println(s"APPEND_BASES=$appendBaseA,$appendBaseB")

// B. Failure injection: 같은 victim을 교체하는 overwrite 둘을 같은 base에 고정한다.
val overwriteTableA = Spark3Util.loadIcebergTable(spark, "local.day27.concurrent_lab")
val overwriteTableB = Spark3Util.loadIcebergTable(spark, "local.day27.concurrent_lab")
val overwriteBase = overwriteTableA.currentSnapshot().snapshotId()
val victim = firstDataFile(overwriteTableA)
val replacementA = cloneDataFile(overwriteTableA, victim, "overwrite-A")
val replacementB = cloneDataFile(overwriteTableB, victim, "overwrite-B")
val overwriteA = overwriteTableA.newOverwrite()
  .deleteFile(victim).addFile(replacementA)
  .validateFromSnapshot(overwriteBase)
  .validateNoConflictingData().validateNoConflictingDeletes()
  .set("lab.writer", "overwrite-A")
val overwriteB = overwriteTableB.newOverwrite()
  .deleteFile(victim).addFile(replacementB)
  .validateFromSnapshot(overwriteBase)
  .validateNoConflictingData().validateNoConflictingDeletes()
  .set("lab.writer", "overwrite-B")

overwriteA.commit()
var expectedFailure = false
try {
  overwriteB.commit()
  println("OVERWRITE_B=UNEXPECTED_SUCCESS")
} catch {
  case e: Throwable =>
    expectedFailure = true
    println(s"OVERWRITE_B=EXPECTED_FAILURE ${e.getClass.getSimpleName}: ${e.getMessage}")
}

// B가 publish되지 않았음이 확정된 경우에만 우리가 만든 고유 orphan을 지운다.
if (expectedFailure) {
  overwriteTableB.io().deleteFile(replacementB.path().toString)
  println(s"CLEANED_KNOWN_ORPHAN=${replacementB.path()}")
}

spark.sql("REFRESH TABLE local.day27.concurrent_lab")
spark.sql("""
  SELECT committed_at, snapshot_id, parent_id, operation,
         summary['lab.writer'] AS lab_writer,
         summary['added-data-files'] AS added,
         summary['deleted-data-files'] AS deleted
  FROM local.day27.concurrent_lab.snapshots
  ORDER BY committed_at
""").show(false)
spark.sql("SELECT count(*) AS visible_rows FROM local.day27.concurrent_lab").show(false)
spark.sql("SELECT content, file_path, record_count FROM local.day27.concurrent_lab.files ORDER BY file_path").show(false)
System.exit(0)
SCALA

예상 관찰: APPEND_BASES의 두 값은 같고 snapshot lineage에는 append-A, append-B가 연속 parent로 남는다. 두 번째 append는 library 내부 CAS retry 때문에 사용자 코드에는 성공으로 보일 수 있다. Overwrite A만 snapshot이 되고 B는 expected failure다. 최종 visible row 수는 3이며 failed replacement path는 metadata table에 없어야 한다.

2단계 · Commit graph와 current state 재확인

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
SELECT made_current_at, snapshot_id, parent_id, is_current_ancestor
FROM local.day27.concurrent_lab.history ORDER BY made_current_at;

SELECT status, snapshot_id, sequence_number, file_sequence_number,
       data_file.file_path
FROM local.day27.concurrent_lab.entries
ORDER BY sequence_number, file_sequence_number, data_file.file_path;
"

채점 기준: ① append B가 base snapshot을 parent로 직접 쓰지 않고 A 이후 current snapshot 위에 연결됐는가, ② overwrite B의 replacement가 current files에 없는가, ③ reader가 partial artifact가 아닌 committed graph만 보는가를 설명하면 통과다.

실패 주입 해설

  • 주입: 두 overwrite가 같은 base와 같은 victim file을 삭제하도록 operation object를 commit 전에 모두 준비했다.
  • 안전한 실패: A commit 뒤 victim은 current membership에서 사라진다. B의 validation은 stale source를 발견하고 publish를 거부한다.
  • 왜 blind retry가 아닌가: B가 latest state에서 다시 무엇을 교체해야 하는지는 업무 의미를 포함한 재계획 문제다. 기존 victim 삭제를 그냥 무시하고 B replacement를 추가하면 A 결과와 중복될 수 있다.
  • Unknown state는 미주입: Catalog 응답 유실은 임의로 만들면 상태 판정이 복잡해진다. 이 실습에서는 명시적 validation failure만 만들고 unknown state는 runbook으로 다룬다.

자주 나는 오류와 해결

  • Docker API 500/daemon 오류: Docker Desktop이 완전히 시작됐는지 확인하고 docker version, docker compose version을 먼저 점검한다.
  • Dependency download 실패: 네트워크와 /tmp/.ivy2 쓰기 권한을 확인한 뒤 make smoke로 runtime loading을 선행한다.
  • FileAlreadyExistsException: 이전 비정상 종료 artifact일 수 있다. Table을 drop/purge한 뒤 새 namespace로 재실행한다. Production path를 임의 삭제하지 않는다.
  • OVERWRITE_B unexpected success: validateFromSnapshot와 두 validation 호출이 빠졌는지, 두 operation의 victim path/base가 정말 같은지 출력한다.
  • Metadata column 오류: Connector version별 schema 차이는 DESCRIBE local.day27.concurrent_lab.entries로 확인해 projection을 맞춘다.
  • 다른 catalog에서 결과 차이: Hadoop/REST/Hive/Glue의 CAS와 exception wrapping은 다를 수 있다. Snapshot lineage와 current files라는 불변식으로 판정한다.

8. 놓치기 쉬운 함정

  1. 두 writer가 같은 base면 둘 중 하나는 최종 실패한다. Compatible append는 rebase 후 둘 다 성공할 수 있다.
  2. CAS conflict는 corruption이다. Optimistic concurrency에서 정상적인 경쟁 신호다.
  3. 모든 CAS conflict는 blind retry 가능하다. Latest diff가 operation 전제를 깨는지 먼저 검증해야 한다.
  4. Validation failure는 retry 횟수를 늘리면 해결된다. Stale plan을 반복하는 한 의미적 충돌은 사라지지 않는다.
  5. Timeout은 실패다. Catalog가 commit한 뒤 응답만 잃었을 수 있다.
  6. Data file PUT 성공은 table commit 성공이다. Catalog pointer가 새 metadata를 가리켜야 한다.
  7. Retry는 모든 bytes를 다시 쓴다. Immutable data/manifest를 재사용하고 작은 metadata tree만 다시 만들 수 있다.
  8. Orphan은 즉시 삭제해도 된다. Unknown state, 장기 writer, 다른 branch의 reachability를 확인한 뒤 safety window를 둔다.

9. 대기업 기술 면접 질문

  1. 초당 50개 micro-batch append와 시간당 compaction이 같은 table에 commit한다. Control plane을 설계하라.
    좋은 답변 구조: Commit rate·catalog p99·SLA 수치 → append/rewrite read-write set → CAS/rebase/validation 경로 → retry/status-check budget → hot scope 분리 → batch coalescing·branch 대안과 비용 → metrics/alert.
  2. Commit timeout 뒤 job을 재실행해도 되는지 어떻게 판단하는가?
    좋은 답변 구조: Unknown state 정의 → operation/batch identity → catalog current pointer와 snapshot history → summary/added paths 확인 → success/failure/계속 unknown 세 분기 → idempotent recovery와 하지 말아야 할 조치.
  3. 왜 concurrent append는 merge 가능하지만 같은-file overwrite는 그렇지 않은가?
    좋은 답변 구조: Base snapshot과 set 연산 모델 → append의 독립 add set → overwrite의 delete+add/read dependency → source file 소실 수치 예시 → serializable validation → replan·lock/queue 대안과 throughput trade-off.

10. 복습과 정답

어제 내용 회상 3문제

  1. Data sequence와 file sequence를 분리해야 하는 rewrite 사례는?
  2. Equality delete와 position delete의 same-sequence 비교는 어떻게 다른가?
  3. Applicable DV가 있는 data file에 position delete도 있으면 reader는 무엇을 선택하는가?

짧은 정답: ① Sequence 2 content를 sequence 8에 rewrite하면 dataSeq=2, fileSeq=8이 가능하다. ② Equality는 dataSeq<deleteSeq, position은 path·partition이 맞을 때 dataSeq≤deleteSeq다. ③ Applicable DV를 쓰고 그 data file의 position delete는 무시한다. 논리 나이·same-commit 의미·중복 적용 방지까지 말하면 만점.

오늘 내용 확인 3문제

  1. 두 append가 같은 M0를 예상했는데 모두 최종 성공할 수 있는 이유는?
  2. 같은 source file을 교체하는 overwrite B가 A 이후 실패해야 하는 불변식은?
  3. CAS conflict, validation failure, unknown state의 첫 조치를 각각 한 문장으로 말하라.

정답/채점: ① B의 첫 CAS는 실패하지만 A의 append와 compatible하므로 최신 M1에 rebase하고 CAS(M1→M2)할 수 있다. ② 이미 제거된 victim을 여전히 current라고 가정한 plan을 publish하지 않아 상대 결과를 잃거나 data를 되살리지 않아야 한다. ③ CAS conflict는 refresh/revalidate, validation failure는 latest에서 재계획, unknown은 status check가 먼저다. Linearization point와 orphan 처리까지 연결하면 각 2점+보너스 1점.
