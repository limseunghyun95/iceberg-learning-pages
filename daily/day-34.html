랩: delete file 생성과 query plan

Row-level Update/Delete와 Format Version · 개념 25분 + 실습 40분

한 줄 요약
오늘은 SQL DELETE 한 번을 catalog pointer→snapshot→delete manifest→position delete row→data-file scan task까지 추적하고, delete rewrite 전후에 live row 불변식과 file graph·query plan 비용이 어떻게 달라지는지 직접 증명한다.

1. 선수 용어 사전

Metadata tableIceberg metadata graph를 SQL row로 보여 주는 관찰 창이다. snapshots, files, entries, position_deletes가 대표적이다.
Content codefiles.content의 0은 data, 1은 position delete, 2는 equality delete다. V3 DV는 별도 manifest metadata로 추적된다.
Position delete삭제 대상 data file의 full path와 0-based row position을 기록하는 V2 delete file이다.
Manifest entryContent file의 status, snapshot ID, data/file sequence와 file metadata를 가진 immutable manifest row다.
Scan taskReader가 실행할 단위다. 선택된 data file, byte range, residual predicate와 적용할 delete files/DV를 묶는다.
EXPLAIN FORMATTEDSpark가 만든 logical/physical plan을 사람이 읽을 수 있게 출력한다. Plan label은 version별로 달라질 수 있다.
Minor compaction작은 position delete files를 더 큰 file로 합치고 dangling position rows를 거르는 maintenance다.
Logical equivalence물리 file graph가 바뀌어도 query가 보는 live row 집합은 동일해야 한다는 rewrite 불변식이다.
Golden evidenceCount만이 아니라 key set/hash, snapshot ID, file graph, plan, procedure output을 함께 저장한 검증 증거다.

2. 왜 중요한가

운영자는 “DELETE가 성공했다”는 SQL 결과만으로는 충분하지 않다. COW인지 MOR인지, 어떤 data file에 어떤 delete가 붙었는지, reader가 어느 snapshot에서 무엇을 적용하는지, compaction이 live rows를 보존했는지를 증명해야 한다. 장애 시 이 chain이 없으면 data loss와 단순 성능 저하를 구분하지 못한다.

Metadata table은 내부 file graph를 SQL로 관찰하게 해 주지만 그 자체가 current state의 owner는 아니다. Catalog pointer가 가리키는 metadata JSON과 snapshot이 authoritative state이며, metadata table은 그 snapshot의 manifests를 projection한 결과다. 따라서 모든 관찰에는 snapshot ID를 붙인다.

오늘의 완료 조건: DELETE 전후 live key set, snapshot/sequence, current data·delete files, position delete target path, query plan, rewrite procedure output을 모으고 rewrite 전후 live key hash가 같음을 확인한다.

3. 아키텍처 그림과 요청 흐름

① DELETE FROM … WHERE id IN (...)
Engine이 base snapshot과 matching rows를 읽음
↓ MOR writer: target path + row position 수집
② New position delete file
(data_file_path, pos) sorted rows + metrics
↓ delete manifest → manifest list → new snapshot/metadata JSON
③ Conflict validation + catalog CAS
Pointer swap 성공 순간 DELETE 공개
↓ next reader pins new snapshot
④ Delete manifests → data manifests
path + partition + data sequence로 applicability pairing
↓ scan task opens data + applicable position deletes
⑤ Row ordinal과 delete position merge
삭제되지 않은 live rows만 operator에 전달

번호별 요청·응답·상태 변화

  1. Read set: DELETE predicate가 partition/metrics로 candidate data files를 찾고 실제 matching rows와 물리 positions를 계산한다.
  2. Immutable output: Position delete file은 original data를 수정하지 않는다. Full path와 pos를 정렬해 쓰고 reserved field metrics를 남긴다.
  3. Linearization: Delete file object가 존재해도 table state가 아니다. New metadata pointer CAS가 성공해야 current snapshot에서 보인다.
  4. Planning: Reader는 delete manifests를 먼저 보고 query/data candidate에 붙을 delete를 정한다. Position delete는 same path와 partition, dataSeq ≤ deleteSeq 조건을 따른다.
  5. Execution: Data row ordinal이 delete positions와 일치하면 row를 숨긴다. Query predicate와 delete filtering 모두 통과한 row만 결과가 된다.
  6. Rewrite: Minor compaction은 delete files를 교체하는 새 optimistic commit이다. Old snapshot reader는 old files를 계속 읽고 new snapshot reader만 replacement를 본다.

4. CS 관점의 내부 동작

Control path와 data path를 분리한다

Control path: Catalog pointer → metadata JSON → snapshot → manifest list → delete/data manifests → scan tasks다. Data path: Object storage의 Parquet data/delete files를 열고 row group·positions를 decode해 live rows를 만든다. Planning latency가 느리면 control path, executor spill/OOM이면 data path를 먼저 의심한다.

왜 delete manifest를 먼저 보는가

Delete file이 어느 data file에 적용되는지 알아야 scan task를 완성할 수 있다. Manifest partition summary와 metrics가 query와 겹치지 않으면 delete manifest/file을 제외할 수 있다. 다만 inclusive pruning은 false negative를 금지하므로 실제 match가 없는 false positive는 실행 단계까지 남을 수 있다.

Position delete metadata를 읽는 법

files.content=1은 delete file 자체의 통계다. Target 관계는 position_deletes.file_path와 delete_file_path를 함께 봐야 분명하다. entries의 sequence numbers는 file 상대 나이를 보여 주고, deleted status는 과거 manifest entry이지 current scan 대상이 아니다.

EXPLAIN의 한계

Physical plan이 모든 delete file path와 applicability edge를 그대로 출력한다고 가정하면 안 된다. Spark/Iceberg version에 따라 node label과 metrics가 달라진다. Plan은 “Iceberg scan과 predicate pushdown이 있는가”를 보고, exact file graph는 metadata tables, runtime I/O는 Spark metrics/object-store logs로 교차 검증한다.

Rewrite의 state transition

Delete rewrite는 old delete files를 remove하고 logically equivalent new delete files를 add하는 snapshot을 만든다. New file의 data sequence는 replacement의 applicability를 보존해야 한다. Concurrent writer가 target graph를 바꾸면 latest snapshot에서 validation하고 replan해야 한다. CAS 전 crash는 orphan outputs, CAS response 유실은 unknown commit state를 만든다.

V2/V3 경계

이 lab은 format v2 position delete를 관찰한다. V3 writer는 새 position delete file을 추가할 수 없고 data file당 최대 하나의 DV에 기존 positions를 동기적으로 합친다. 따라서 같은 SQL이라도 format/engine에 따라 artifact가 달라질 수 있으며, test assertion은 feature-aware해야 한다.

5. 실무 설계 판단

Best practice 1 · Evidence bundle: Operation별 base/result snapshot ID, SQL/job ID, input predicate, added/removed data·delete files, sequence, key count/hash, object path를 한 run ID로 묶는다. 장애 시 재현 가능한 최소 단위가 된다.

Best practice 2 · Snapshot pin: Before/after 비교는 current를 두 번 읽지 말고 explicit snapshot ID 또는 branch/tag를 사용한다. Concurrent writes가 있으면 current 비교가 서로 다른 state를 섞는다.

Best practice 3 · Multi-level assertion: Row count만 같아도 값이 바뀔 수 있다. Count, sorted key set/hash, aggregates, duplicate key, null semantics, file applicability를 함께 검사한다.

Best practice 4 · Mode capability gate: Table property, format version, writer output artifact, reader support를 모두 확인한다. write.delete.mode=merge-on-read property 하나만으로 position delete 생성과 모든 reader 호환을 단정하지 않는다.

Best practice 5 · Maintenance canary: Small partition/branch에서 rewrite 후 golden query와 plan/I/O를 비교한다. Live row 불일치, unexpected global delete, conflict율 증가 시 확장을 중단한다.

Anti-pattern: Warehouse listing으로 current file을 추정, all_files duplicate를 current files로 오해, EXPLAIN 문자열만 golden test로 고정, delete object를 수동 삭제, rewrite 결과 0을 성공 개선으로 보고, count만 맞으면 compaction 안전하다고 판단하는 것이다.

Edge case: Predicate가 partition 전체를 정확히 지우면 metadata-only delete가 가능해 position delete가 생기지 않는다. Lab predicate는 개별 row를 겨냥해 이 경로를 피한다.

Version 차이: Spark 3.x procedure는 Iceberg SQL extensions가 필요하다. 1.11.0의 position_deletes, rewrite_position_delete_files를 기준으로 하며 최신 spec의 DV/v4 규칙을 그대로 1.11 runtime 결과로 기대하지 않는다.

6. 장애 대응 표

상황: DELETE 후 일부 row가 재등장하거나 compaction 뒤 count가 달라졌다.

증상삭제 row 재등장·과삭제, engine별 count 차이, position_deletes target path가 live data path와 불일치, rewrite 전후 key hash 차이, delete file 404, plan에 unexpected full scan, conflict/retry 반복.

1단계 · 여러 data file과 baseline 증거 만들기

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
CREATE NAMESPACE IF NOT EXISTS local.day34;
CREATE TABLE local.day34.events (
  id BIGINT, bucket STRING, payload STRING
) USING iceberg
TBLPROPERTIES (
  'format-version'='2',
  'write.delete.mode'='merge-on-read',
  'write.delete.granularity'='file',
  'write.delete.target-file-size-bytes'='65536'
);

INSERT INTO local.day34.events
SELECT id, 'A', repeat('a', 100) FROM range(1, 21);
INSERT INTO local.day34.events
SELECT id, 'B', repeat('b', 100) FROM range(21, 41);
INSERT INTO local.day34.events
SELECT id, 'C', repeat('c', 100) FROM range(41, 61);
INSERT INTO local.day34.events
SELECT id, 'D', repeat('d', 100) FROM range(61, 81);

SELECT count(*) AS rows_before,
       sum(id) AS id_sum_before,
       sha2(concat_ws(',', sort_array(collect_list(CAST(id AS STRING)))), 256)
         AS key_hash_before
FROM local.day34.events;

SELECT content, count(*) AS files, sum(record_count) AS records,
       sum(file_size_in_bytes) AS bytes
FROM local.day34.events.files
GROUP BY content ORDER BY content;
"

예상 관찰: 80 rows와 data file(content=0)만 보인다. Insert commit을 나눴어도 Spark/AQE에 따른 exact file 수는 환경마다 다를 수 있다.

6단계 · Minor compaction과 불변식 검증

docker compose exec -T spark /opt/spark/bin/spark-sql -e "
CALL local.system.rewrite_position_delete_files(
  table => 'day34.events',
  options => map('rewrite-all', 'true')
);

SELECT count(*) AS live_rows_after_rewrite,
       sha2(concat_ws(',', sort_array(collect_list(CAST(id AS STRING)))), 256)
         AS key_hash_after_rewrite
FROM local.day34.events;

SELECT content, count(*) AS files, sum(record_count) AS records,
       sum(file_size_in_bytes) AS bytes
FROM local.day34.events.files
GROUP BY content ORDER BY content;

SELECT committed_at, snapshot_id, parent_id, operation, summary
FROM local.day34.events.snapshots
ORDER BY committed_at;
"

통과 기준: Live rows 68, before/after key hash 동일, rewrite snapshot 추가, eligible delete files 감소 또는 재배치다. Procedure가 0 files를 rewrite했다면 threshold/runtime capability와 current graph를 확인하고 결과를 억지로 성공 처리하지 않는다.

7단계 · 동시성 실패 주입(선택, 10분)

  1. Terminal A에서 delete rewrite를 다시 실행하고 Terminal B에서 DELETE ... WHERE id=10을 실행한다.
  2. Commit 순서, conflict/retry, final parent chain을 snapshots에서 확인한다.
  3. 최종 live rows는 67이며 ID 10은 없어야 한다. Conflict가 발생하면 same output을 blind commit하지 말고 latest snapshot에서 rewrite를 재계획한다.

자주 나는 오류와 해결

  • Position delete가 없음: Format v2, MOR property, row-level predicate를 확인한다. Partition 전체 match면 metadata-only delete일 수 있다.
  • position_deletes table 오류: Iceberg 1.11.0 runtime과 SQL extensions를 확인하고 DESCRIBE local.day34.events.position_deletes로 schema를 본다.
  • Procedure not found: Catalog 이름과 Spark extension 설정을 확인한다. Spark 3.x에서는 extension이 필요하다.
  • Hash가 null/불안정: Empty table 여부와 collect order를 확인한다. sort_array 뒤 string join을 사용하고 같은 snapshot을 비교한다.
  • Exact file count가 문서와 다름: Spark partition/AQE에 따른 정상 차이다. Content, rows, applicability와 전후 상대 변화로 검증한다.
  • Concurrent lab이 너무 빨리 끝남: Data 규모를 키우거나 두 terminal에서 barrier를 두고 실행하되 운영 table에는 failure injection하지 않는다.

8. 놓치기 쉬운 함정

  1. files는 warehouse listing이다. Current snapshot manifest graph의 projection이며 unreferenced objects는 나오지 않는다.
  2. all_files row 수가 physical object 수다. 같은 file이 여러 snapshots에서 중복될 수 있다.
  3. DELETE SQL 성공 즉시 object가 안전하게 지워진다. Row-level delete는 새 metadata state를 만들고 old files는 time travel/retention 때문에 남는다.
  4. Plan에 delete path가 없으면 delete가 적용되지 않았다. Plan 표현은 version별로 다르므로 metadata/result와 교차 확인한다.
  5. Position delete file 하나는 target 하나다. V2 file은 여러 target paths를 담을 수 있다. File granularity 설정은 정책이지 spec 일반 불변식이 아니다.
  6. Rewrite 후 delete file 수는 반드시 1이다. Partition/file group, target size와 engine plan에 따라 여러 outputs가 정상이다.
  7. Count가 같으면 logical equivalence다. Key/value hash와 aggregates가 필요하다.
  8. V3에서도 같은 position delete lab 결과가 나온다. V3 writer는 새 position delete를 금지하고 DV를 사용한다.

9. 대기업 기술 면접 질문

  1. DELETE 한 건이 reader 결과에서 사라질 때까지 end-to-end 경로를 설명하라.
    좋은 답변 구조: Predicate/read set → position 수집 → immutable delete file → manifests/metadata → validation/CAS → reader snapshot pin → applicability → row filtering → failure windows.
  2. Compaction 전후 동일성을 어떻게 자동 검증할 것인가?
    좋은 답변 구조: Snapshot/branch pin → count+key/value hash+aggregates → file graph/sequence → golden multi-engine queries → canary threshold → conflict/unknown commit → rollback/forward repair.
  3. Query plan에는 delete details가 부족한데 production read amplification을 어떻게 측정할 것인가?
    좋은 답변 구조: Metadata tables로 graph 추정 → runtime scan metrics → object GET/bytes/cache → task memory/spill → p95/p99 SLO → delete/data rewrite 손익분기 → connector differences.

짧은 정답/채점 기준: ① Full data-file path + 0-based row position(3점). ② Object는 prepared artifact일 뿐, catalog pointer CAS 성공이 current state 공개 시점(3점). ③ Live key/value set·hash는 동일, physical data/delete paths/count/layout은 달라질 수 있음(4점). 8점 이상이면 통과.
