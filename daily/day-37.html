APACHE ICEBERG · WEEK 6 / DAY 37

REST catalog와 credential vending 경계

Catalog·Multi-engine·Streaming · 개념 45분 + 실습 35분

한 줄 요약
REST catalog credential vending은 engine이 catalog에 인증하면 catalog가 그 table의 storage prefix와 작업에만 유효한 짧은 수명의 자격 증명을 반환하는 권한 위임이다. Catalog token과 storage credential을 분리하고 scope·TTL·refresh·감사 경계를 지켜야 장기 static key 없이 metadata→data path를 열 수 있다.

1. 선수 용어 사전

REST catalogTable load·commit·namespace 작업을 HTTP API로 제공하는 control plane이다. Engine은 backend별 client 대신 공통 protocol을 사용한다.
Credential vendingCatalog가 client에 짧은 수명의 table-scoped storage credential을 빌려주는 방식이다. 장기 access key를 engine에 배포하지 않는 것이 목적이다.
Catalog tokenREST API에 “누가 어떤 catalog 작업을 요청하는가”를 증명하는 OAuth2 bearer token 등이다. S3/GCS/ADLS credential과 용도·audience가 다르다.
Storage credentialObject storage가 metadata·manifest·data/delete file read/write를 허용하는 임시 권한이다. 보통 prefix, operation, expiration으로 제한한다.
Scope · audience · TTLScope는 허용 동작/자원, audience는 credential을 받아야 할 서비스, TTL(Time To Live)은 유효 시간이다. 세 축이 권한 폭과 노출 시간을 결정한다.
Access delegationClient의 인증 결과를 storage access로 안전하게 이어 주는 protocol이다. Iceberg REST는 vended credential과 remote signing을 구분한다.
Remote signingCredential을 client에 넘기지 않고 catalog signer가 개별 storage request에 서명하는 방식이다. 요청당 제어가 강하지만 signer latency·availability 비용이 있다.
FileIOIceberg가 object storage bytes를 읽고 쓰는 계층이다. Load-table 응답의 table config와 vended credential이 여기 적용된다.

2. 왜 중요한가

Static storage key를 Spark cluster, notebook, CI worker, Flink task마다 배포하면 한 곳의 유출이 warehouse 전체로 번진다. 반대로 credential vending은 사용자의 catalog identity를 table 수준 policy로 평가한 뒤 필요한 prefix와 짧은 시간만 허용한다. 엔진은 data plane을 object storage와 직접 통신하므로 catalog가 모든 Parquet byte를 proxy하지 않아도 된다.

하지만 “REST 로그인이 됨”과 “table file을 읽을 수 있음”은 다른 성공 조건이다. Catalog token이 정상이어도 vended credential이 만료되거나 prefix·KMS scope가 빠지면 metadata JSON load 뒤 manifest에서 403이 날 수 있다. Long-running scan은 시작 시점의 credential TTL보다 오래 걸릴 수 있어 refresh endpoint, clock skew, retry 경계를 설계해야 한다.

핵심 불변식: REST authorization은 table operation을 허가하고, storage authorization은 실제 object request를 허가한다. 둘의 principal·scope·TTL·감사 correlation을 연결하되 credential 자체는 로그·Spark UI·event log에 남기지 않는다.

3. 아키텍처 그림과 요청 흐름

② REST catalog policy boundary

↓ LoadTableResponse: metadata location · config · storage-credentials
③ Table FileIO

④ metadata JSON → snapshot → manifest list → manifest → data/delete

번호별 요청·응답·상태 변화

  1. Catalog 인증: Engine은 REST service용 token을 얻는다. 이 token의 audience는 catalog이며 object storage request에 그대로 쓰지 않는다.
  2. Table authorization: Client는 table load와 access-delegation 지원을 요청한다. Server는 principal, namespace/table, read/write 의도를 policy로 평가한다. Server가 vending을 지원·허용하지 않으면 credential이 없을 수 있다.
  3. Delegation: Load-table 응답은 metadata와 table config에 더해 vended storage credentials를 담을 수 있다. Credential은 한 table의 storage prefix와 필요한 operation으로 제한하고 expiration을 가진다.
  4. Direct data path: FileIO는 credential을 적용해 metadata JSON→snapshot→manifest list→manifest→data/delete file을 직접 읽는다. Write는 immutable data/metadata artifact를 먼저 만든다.
  5. Refresh: Long-running job은 server가 제공한 credentials endpoint를 통해 fresh credential을 얻을 수 있다. Expired credential을 무한 retry하거나 catalog token을 storage credential로 대체하면 안 된다.
  6. Commit: Writer는 storage credential로 M1까지 쓰고 REST commit에 expected state와 updates를 보낸다. Server가 requirements를 검증하고 authoritative pointer를 바꾼 시점이 성공이다.
  7. Remote signing 대안: Server가 credential을 반환하지 않고 storage request를 원격 서명할 수도 있다. Secret 노출 면은 줄지만 signer가 data path control dependency가 된다.

4. CS 관점의 내부 동작

Capability token으로 보기

Vended credential은 “이 principal은 관리자가 맞다”는 신분증보다 “이 시간까지 이 prefix에서 GET/PUT을 해도 된다”는 일회성 출입증에 가깝다. 안전성은 credential 문자열의 난수성뿐 아니라 resource scope × action scope × TTL × audience의 곱으로 결정된다. 한 축이라도 넓으면 blast radius가 커진다.

성공 시점과 failure window

  • Load 성공: Catalog가 table metadata와 delegation 정보를 반환했다. 아직 모든 referenced object read 성공을 보장하지 않는다.
  • Scan 성공: Plan에 필요한 manifest와 data/delete object를 읽고 delete를 적용했다. 중간 refresh가 실패하면 partial task retry가 필요할 수 있다.
  • Write prepare 성공: Immutable file이 storage에 있다. 아직 table state가 아니다.
  • Commit 성공: REST server가 requirements를 검증하고 current metadata pointer를 새 root로 공개했다. 응답 유실 시 current pointer·operation identity로 확인한다.

Credential refresh는 cache invalidation 문제이기도 하다. 너무 일찍 refresh하면 auth service QPS가 폭증하고, 너무 늦으면 task 실행 중 만료된다. Client는 expiration과 clock skew를 고려해 미리 교체하되 같은 credential을 무제한 재사용하지 않아야 한다. Server는 revocation이 필요하면 짧은 TTL과 policy change 이후 신규 발급 차단을 조합한다.

5. 실무 설계 판단

Best practice 1 · 두 credential을 명시적으로 분리: Catalog OAuth token과 object-store credential의 issuer, audience, TTL, refresh, redaction rule을 각각 문서화한다. 같은 환경 변수나 Spark property에 장기 secret을 넣지 않는다.

Best practice 2 · 최소 capability: Read job은 GET/LIST와 decrypt만, writer는 필요한 prefix의 PUT와 제한된 delete만 허용한다. Table location 밖 warehouse root listing, 다른 namespace, unrelated KMS key는 거부한다.

Best practice 3 · 만료 budget: p99 scan/task duration, executor queueing, retry/backoff, clock skew를 더해 TTL·refresh lead time을 정한다. TTL만 길게 늘려 장애를 숨기지 않는다.

Best practice 4 · 감사 correlation: Principal, catalog request ID, table identifier, operation, vended session ID, storage request ID, snapshot/commit ID를 연결한다. Credential 값 자체는 어느 로그에도 기록하지 않는다.

Best practice 5 · capability matrix: REST server, Java client, Spark/Flink/Trino connector, FileIO 조합이 storage-credentials, refresh endpoint, remote signing을 실제 지원하는지 contract test한다. Protocol이 정의한다고 모든 배포가 구현한 것은 아니다.

Anti-pattern: Static cloud key를 cluster-wide config에 넣기, load response 전체를 debug log로 남기기, 403을 무조건 token refresh로 반복하기, read job에 delete 권한 주기, storage credential로 REST API를 호출하기, catalog outage를 우회하려 같은 location을 다른 catalog에 등록하기다.

Edge case: Table의 metadata와 data가 다른 bucket/region/KMS key에 걸쳐 있으면 한 credential scope로 충분하지 않을 수 있다. 각 storage credential의 prefix/scheme과 FileIO 지원을 확인하고, relocation 중 old/new prefix를 동시에 허용하는 기간은 짧고 감사 가능하게 둔다.

Version/engine 차이: 최신 REST protocol 문서는 storage-credentials, refresh endpoint, remote signing을 설명한다. 프로젝트 runtime은 Spark 3.5.8 + Iceberg 1.11.0이므로 최신 문서의 모든 동작을 자동으로 가정하지 않는다. Server endpoint discovery, client/FileIO의 vended credential 적용, connector별 secret redaction을 배포 version으로 재검증한다.

6. 장애 대응 표

상황: REST table load는 성공했지만 manifest/data read 또는 write에서 401/403·ExpiredToken이 발생한다.

증상Load table 200 뒤 metadata/manifest/data GET 401·403, ExpiredToken, KMS AccessDenied, long task만 반복 실패, reader는 되고 writer PUT만 실패, 다른 table/prefix만 실패, refresh endpoint 401/404/5xx.
먼저 수집할 증거/지표Secret을 제거한 exact HTTP/storage code, principal·catalog request ID·session ID, table/location/scheme/region, object path와 operation, credential expiration과 client/server clock, refresh endpoint/config 존재, FileIO/engine/server version, KMS key ID, retry count·elapsed time, commit current pointer.
가능한 가설Credential 만료·clock skew, 잘못된 prefix/action scope, server가 delegation을 생략, client/FileIO 미지원, refresh endpoint auth 실패, region/endpoint mismatch, KMS permission 누락, executor에 stale credential cache, table relocation 중 old prefix 누락, policy 변경/회수.
안전한 첫 조치Credential·token 값을 출력하지 말고 failing object/action을 식별한다. 새 load/refresh를 1회 수행해 expiration·scope가 바뀌는지 확인하고, clock·region·KMS·FileIO capability를 read-only로 검증한다. Writer는 commit 상태 판정 전 중지하고 reader는 검증된 snapshot을 pin한다.
rollback/복구Policy/prefix 오류를 최소 범위로 수정해 새 credential을 발급하고 affected task만 retry한다. Commit이 publish됐으면 성공 처리하고 checkpoint를 맞춘다. 미commit이면 latest snapshot에서 revalidate/replan하고 확정 orphan은 safety window 뒤 정리한다. Relocation이면 single-writer 하에 old/new scope를 단계적으로 회수한다.
하지 말아야 할 조치Static admin key 임시 배포, credential 원문 로그/티켓 첨부, bucket-wide 권한 부여, TTL 무기한 연장, 403 무한 retry, REST token을 storage에 재사용, commit timeout 뒤 artifact 삭제, evidence 전 cache·event log 삭제를 하지 않는다.

7. 35분 재현 실습

목표: 실제 secret 없이 table-scoped temporary capability를 모델링하고, prefix·action·audience·expiration 검증과 redacted audit log를 테스트한다. 예측→실행→failure injection 순서를 지킨다.

사전 조건과 실행 전 예측

  • Node.js 18 이상만 필요하며 cloud account나 실제 key는 사용하지 않는다.
  • GET metadata/...와 GET data/...는 ALLOW, 이웃 table path·DELETE·틀린 audience는 DENY여야 한다.
  • Expiration을 과거로 바꾸면 같은 path도 DENY여야 한다.
  • Audit output에는 credential 값 대신 session ID와 decision reason만 보여야 한다.

1단계 · In-memory vended credential policy 실행

node <<'NODE'
const now = Date.now();
const credential = {
  sessionId: 'vend-day37-001',
  secret: 'DO-NOT-LOG-example-only',
  audience: 'object-storage',
  prefixes: ['s3://warehouse/sales/orders/'],
  actions: ['GET', 'PUT'],
  expiresAt: now + 15 * 60_000
};

function authorize(c, req, at = Date.now()) {
  if (at >= c.expiresAt) return [false, 'expired'];
  if (req.audience !== c.audience) return [false, 'wrong-audience'];
  if (!c.actions.includes(req.action)) return [false, 'action-out-of-scope'];
  if (!c.prefixes.some(p => req.uri.startsWith(p))) return [false, 'prefix-out-of-scope'];
  return [true, 'allowed'];
}

const cases = [
  ['metadata-read', {audience:'object-storage', action:'GET', uri:'s3://warehouse/sales/orders/metadata/v2.json'}],
  ['data-read', {audience:'object-storage', action:'GET', uri:'s3://warehouse/sales/orders/data/0001.parquet'}],
  ['neighbor-table', {audience:'object-storage', action:'GET', uri:'s3://warehouse/sales/customers/data/0001.parquet'}],
  ['delete', {audience:'object-storage', action:'DELETE', uri:'s3://warehouse/sales/orders/data/0001.parquet'}],
  ['catalog-reuse', {audience:'rest-catalog', action:'GET', uri:'s3://warehouse/sales/orders/metadata/v2.json'}]
];

for (const [name, req] of cases) {
  const [ok, reason] = authorize(credential, req, now);
  console.log(JSON.stringify({name, sessionId:credential.sessionId, action:req.action, uri:req.uri, decision:ok?'ALLOW':'DENY', reason}));
}
console.log('secret-leaked=', JSON.stringify(cases).includes(credential.secret));
NODE

예상 관찰: 첫 두 case만 ALLOW이고 나머지는 prefix, action, audience 이유로 DENY다. 마지막은 secret-leaked=false여야 한다.

2단계 · Failure injection: expiry와 clock skew

node <<'NODE'
const minute = 60_000;
const issuedAt = Date.now();
const c = {
  sessionId:'vend-day37-expiry',
  audience:'object-storage',
  prefixes:['s3://warehouse/sales/orders/'],
  actions:['GET'],
  expiresAt:issuedAt + 5 * minute
};
const request = {audience:'object-storage', action:'GET', uri:'s3://warehouse/sales/orders/metadata/v2.json'};
function decide(at) {
  const refreshLead = 2 * minute;
  if (at >= c.expiresAt) return 'DENY expired';
  if (at >= c.expiresAt - refreshLead) return 'REFRESH before-use';
  return 'ALLOW';
}
for (const [label, at] of [
  ['t+0m', issuedAt],
  ['t+3m', issuedAt + 3 * minute],
  ['t+6m', issuedAt + 6 * minute],
  ['client-clock+4m', issuedAt + 4 * minute]
]) console.log(label, decide(at), request.uri);
NODE

예상 관찰: t+0m은 ALLOW, t+3m과 clock+4m은 REFRESH, t+6m은 DENY다. Refresh lead time은 “실패 후 재시도”가 아니라 만료 전 교체 budget이다.

자주 나는 오류와 해결

  • Node syntax 오류: Heredoc 시작/끝의 NODE는 들여쓰기 없이 한 줄로 둔다.
  • 모든 요청 DENY: URI scheme, trailing slash, case normalization을 확인한다. 문자열 prefix만으로 production authorization을 구현하지 말고 provider-native policy를 사용한다.
  • Manifest에서만 403: Table root만 허용하고 metadata/manifest prefix 또는 KMS decrypt를 빠뜨렸는지 본다.
  • Long job만 실패: TTL, refresh lead, executor cache, clock skew, credentials endpoint auth를 함께 본다.
  • Server는 지원하지만 engine이 실패: Connector와 FileIO가 vended credential/refresh를 실제 구현하는지 version matrix로 검증한다.

Cleanup

두 Node 실습은 파일·credential을 만들지 않아 별도 cleanup이 없다. 실제 환경에서 실험했다면 test principal/session을 revoke하고 temporary log를 secret scan한 뒤 정책을 원복한다. Secret이 로그에 노출됐다면 삭제만 하지 말고 먼저 credential을 revoke/rotate한다.

8. 놓치기 쉬운 함정

  • REST token = storage credential이 아니다. Issuer·audience·scope가 다르다.
  • Credential vending = data proxy가 아니다. Engine/FileIO가 storage와 직접 통신한다.
  • Load 200 = full scan 가능이 아니다. 뒤쪽 manifest·data·delete·KMS scope가 실패할 수 있다.
  • 짧은 TTL = 자동으로 안전이 아니다. Scope가 넓거나 로그에 남으면 TTL 동안 공격 가능하다.
  • Refresh retry = 무한 재시도가 아니다. 401/403 원인을 expiry, policy, audience, region, KMS로 분류한다.
  • Protocol feature = 모든 engine 지원이 아니다. Server·client·connector·FileIO 네 층을 함께 검증한다.
  • Credential expiry = commit rollback이 아니다. Current pointer를 확인해 published state와 orphan을 구분한다.

9. 대기업 기술 면접 질문

  1. 1만 명이 Spark·Trino로 공유 lake를 읽을 때 static IAM key 없이 table-level access를 설계하라.
    좋은 답변 구조: Identity/tenant 요구 → REST auth와 storage delegation 분리 → table/action/prefix/KMS scope → TTL/refresh 수치 → FileIO direct path → audit correlation → cache·revocation failure → remote signing 대안과 latency trade-off.
  2. 3시간 Spark scan이 70분마다 403으로 실패한다. 어디서부터 증명할 것인가?
    좋은 답변 구조: Exact object/action과 timeline → catalog token vs storage credential → expiration/clock/refresh endpoint → executor cache와 FileIO version → prefix/KMS/region → single refresh test → affected task retry → TTL 무작정 연장 금지.
  3. Credential vending과 remote signing 중 하나를 선택하라.
    좋은 답변 구조: Data request QPS·latency와 secret exposure 요구 → vended credential의 direct I/O·TTL risk → remote signer의 per-request control·availability bottleneck → outage/refresh/revocation 모델 → engine support → canary·fallback·SLO 수치.

짧은 정답/채점: ① Catalog는 name→current metadata pointer, warehouse는 immutable bytes를 소유한다. ② Authoritative pointer가 새 metadata root를 공개해야 state가 된다. ③ 두 pointer owner가 서로를 모르는 split brain이 된다. 상태 소유자와 성공 확정점을 말하면 만점.

오늘 내용 확인 3문제

  1. Catalog token과 vended storage credential을 네 가지 축으로 비교하라.
  2. Credential vending이 data proxy가 아닌 이유는 무엇인가?
  3. Load table 성공 뒤 manifest GET 403이면 안전한 첫 조치는 무엇인가?

짧은 정답/채점: ① Issuer/audience, scope, TTL/refresh, 사용 endpoint를 구분한다. ② FileIO가 vended credential로 object storage에 직접 요청한다. ③ Secret을 노출하지 않고 failing object/action, expiration, prefix/KMS/region, refresh/FileIO support를 증거로 확인해 새 credential을 1회 검증한다. Static admin key 확대를 거부하면 만점.
