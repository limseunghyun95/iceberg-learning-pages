Hadoop/Hive/REST/Glue/Nessie catalog

Catalog·Multi-engine·Streaming · 개념 45분 + 실습 35분

한 줄 요약
Iceberg catalog는 data를 저장하는 창고가 아니라 table 이름을 current metadata JSON에 원자적으로 연결하는 control plane이다. Hadoop·Hive·REST·Glue·Nessie의 핵심 차이는 그 pointer state의 소유자, compare-and-swap 또는 lock 방식, 인증 경계와 장애 범위다.

1. 선수 용어 사전

CatalogNamespace와 table 이름을 관리하고, 각 table의 current metadata location을 load·create·commit·drop하는 control plane이다.
WarehouseMetadata·manifest·data/delete file이 놓이는 base storage 경로다. Catalog와 같은 것이 아니며 다른 권한·SLA를 가질 수 있다.
Metadata pointerTable identifier가 현재 metadata JSON을 가리키는 작은 mutable state다. Commit의 선형화 지점이다.
CASCompare-and-swap. “Pointer가 아직 M0이면 M1로 바꿔라”는 조건부 갱신이다. 동시 writer의 lost update를 막는다.
Catalog cacheLoad 비용을 줄이기 위해 table metadata를 잠시 저장하는 client/server cache다. 성능을 높이지만 stale pointer라는 failure window를 만든다.
FileIOS3·GCS·ADLS·HDFS 등에서 metadata와 data bytes를 읽고 쓰는 계층이다. Catalog API 권한과 object storage 권한은 별개다.
ReferenceNessie의 branch·tag·commit hash처럼 catalog content state를 선택하는 이름 또는 immutable 지점이다.
Control/Data planeControl plane은 pointer·namespace·auth를, data plane은 metadata/manifest/data bytes 전송을 담당한다. 장애 대응에서 둘을 분리한다.

2. 왜 중요한가

같은 Parquet와 같은 Iceberg metadata를 사용해도 catalog가 달라지면 commit의 성공 조건과 장애 양상이 달라진다. Hadoop catalog는 warehouse path와 file-system primitive에 크게 의존하고, Hive는 HMS의 table state와 lock, REST는 HTTP service의 commit protocol, Glue는 AWS managed metastore와 optimistic update, Nessie는 branch/ref content state가 권위자다.

Catalog 선택은 단순 연결 문자열 선택이 아니다. Multi-engine 지원, object storage의 rename 특성, 인증·감사, write 빈도, branch/multi-table 공개 방식, 재해복구 절차를 결정한다. 특히 writer가 data file을 다 쓴 뒤 catalog 응답을 잃으면 “실패”와 “성공했지만 응답만 유실”을 구분해야 하므로 pointer owner의 status check 방법이 필수다.

핵심 불변식: Object storage에 M1·data file이 존재해도 catalog의 authoritative pointer/ref가 M1을 current로 확정하지 않았다면 table state가 아니다. 반대로 pointer가 M1을 가리키면 referenced object의 404는 catalog 문제가 아니라 committed graph 손상이다.

3. 아키텍처 그림과 요청 흐름

① Engine: Spark · Flink · Trino
table identifier + operation + expected current pointer
↓ catalog client / Thrift / HTTP / AWS API / Nessie ref
② Catalog control plane
Hadoop path · Hive HMS · REST server · AWS Glue · Nessie branch
↓ load current M0 · auth/config · namespace
③ Writer prepares immutable graph in warehouse
data/delete → manifest → manifest list → metadata JSON M1
↓ commit(expected=M0, new=M1)
④ Catalog-specific atomic state transition
rename/lock/CAS/version/ref commit · success 또는 conflict/unknown
↓ reader reloads authoritative pointer
⑤ metadata JSON → snapshot → manifests → data/delete files
control path가 고른 immutable data path만 읽음

번호별 요청·응답·상태 변화

  1. Resolve: Engine은 catalog name, namespace, table, 선택적 Nessie ref를 전달한다. Catalog는 current metadata location과 필요한 FileIO/config를 반환한다.
  2. Read: Reader는 load한 M0에 고정되어 snapshot→manifest list→manifest pruning을 수행한다. Catalog가 잠시 불가해도 이미 열린 scan task가 data 권한을 보유했다면 진행할 수 있지만 새 load·refresh는 실패할 수 있다.
  3. Prepare: Writer는 data/delete와 metadata graph M1을 warehouse에 먼저 쓴다. 이 단계 성공은 commit 성공이 아니다.
  4. Publish: Hadoop은 file-system 기반 pointer discovery/atomic primitive, Hive는 HMS table state와 lock, REST는 change-based HTTP commit, Glue는 managed catalog의 versioned/optimistic update, Nessie는 ref의 content commit으로 M0→M1을 확정한다.
  5. Conflict: Expected M0가 current가 아니면 writer는 latest state를 reload해 validation/rebase한다. Lock 획득은 semantic conflict가 없다는 뜻이 아니며 predicate/source-file validation은 별도다.
  6. Unknown: Catalog가 update를 처리한 뒤 응답이 유실될 수 있다. Operation identity와 current metadata/ref history를 조회하기 전 blind retry·artifact 삭제를 금지한다.

4. CS 관점의 내부 동작

Catalog별 상태 소유자와 trade-off

CatalogPointer owner / commit강점과 주요 failure domain
HadoopWarehouse의 table path와 metadata version discovery, file-system atomic primitive.별도 service 없이 단순. Path가 identity가 되기 쉬우며 object store에서 atomic rename/상호배제가 약하면 별도 lock과 검증이 필요하다.
HiveHive Metastore table parameter의 metadata location과 HMS lock/conditional update.기존 HMS·namespace 통합. Thrift/HMS DB·lock heartbeat가 control-plane failure domain이며 Hive positional schema 검증과 Iceberg field ID가 충돌할 수 있다.
RESTHTTP API 뒤 server가 pointer, validation, config를 소유하고 change-based commit 처리.언어·engine별 backend client 중복을 줄이고 auth/credential/remote planning을 중앙화. HTTP service·token·server compatibility가 새 failure domain.
GlueAWS Glue Data Catalog table state의 metadata pointer와 optimistic update/version.IAM·Athena/EMR/Lake Formation 생태계와 결합. AWS API throttling, region, IAM, Glue state와 S3 FileIO 권한의 이중 경계.
NessieBranch/tag/hash가 선택한 content state와 ref commit.Git-like branch·merge·history와 여러 table 변경 공개에 유리. Ref 선택·merge conflict·server availability가 추가되며 branch merge를 DB transaction과 동일시하면 안 된다.

세 개의 독립된 권한·가용성 경계

Catalog 권한은 이름·pointer를 load/update하고, FileIO 권한은 metadata와 data bytes를 GET/PUT/DELETE하며, KMS 권한은 encrypted file key를 해제한다. Catalog load가 성공해도 S3 403으로 scan이 실패할 수 있고, data read가 되더라도 catalog update 권한이 없으면 writer는 commit하지 못한다. REST credential vending은 이 경계를 연결할 수 있지만 내일 별도로 깊게 다룬다.

Consistency와 cache

Catalog cache는 load latency와 control-plane QPS를 줄이지만 stale M0를 늘린다. Reader는 한번 고정한 snapshot으로 일관된 결과를 낼 수 있지만, writer는 commit 직전 authoritative current를 확인하고 CAS/validation해야 한다. Cache TTL을 길게 만든다고 correctness가 깨져서는 안 되며 conflict rate와 freshness SLA가 비용으로 나타나야 한다.

Object storage와 lock

S3 같은 object storage의 read-after-write가 강하더라도 “두 writer 중 한 명만 pointer를 바꾼다”는 mutual exclusion/CAS 문제는 남는다. Apache 문서는 file-system 기반 HadoopTables/HadoopCatalog에 DynamoDB lock manager 같은 보조 lock을 사용할 수 있음을 설명한다. 반대로 Hive lock을 무조건 끄는 것도 위험하며 서버 patch와 모든 writer 버전·설정이 일치해야 한다.

5. 실무 설계 판단

Best practice 1 · Pointer owner를 한 문장으로 정의: “prod.orders의 current metadata location은 어느 시스템의 어느 record/ref가 소유하며, expected-old 조건은 무엇인가?”에 답하지 못하면 운영 준비가 안 된 것이다.

Best practice 2 · Catalog와 FileIO를 분리 테스트: Load/commit API, metadata GET, data GET/PUT, KMS, delete 권한을 별도 synthetic check로 둔다. 단일 SELECT 1 health check로 합치지 않는다.

Best practice 3 · 선택 기준: HDFS·작은 단일 engine 환경은 Hadoop의 단순성이, 기존 HMS 중심 환경은 Hive가, 다언어·서비스화·보안 중앙화는 REST가, AWS 관리형 거버넌스는 Glue가, branch·다중 table 배포는 Nessie가 유리할 수 있다. 실제 SLA·RPO/RTO·write QPS·engine matrix로 결정한다.

Best practice 4 · DR runbook: Catalog backup/restore와 object storage versioning을 함께 설계한다. Catalog만 복원해 pointer가 존재하지 않는 object를 가리키거나, storage만 복원해 current pointer를 잃는 반쪽 복구를 피한다.

Anti-pattern: Warehouse listing을 catalog로 사용하기, 같은 bucket이면 같은 table이라고 가정하기, Hive lock을 성능 때문에 일괄 비활성화하기, REST 5xx 뒤 blind append하기, Glue 권한과 S3 권한을 한 역할로 뭉개기, Nessie branch merge를 row-level serializable transaction으로 부르기다.

Edge case: 두 catalog가 우연히 같은 table location을 가리키면 각자 정상적으로 CAS하면서도 서로의 pointer update를 모를 수 있다. “Dual registration”은 migration 도중에도 single-writer fencing과 명확한 cutover 없이는 split brain이다.

Version/engine 차이: Iceberg 1.11.0 Spark configuration은 hive, hadoop, rest, glue, jdbc, nessie type을 열거하지만, 필요한 runtime module·auth option·server protocol 기능은 engine/connector 배포별로 다르다. 공식 예제를 복사하기 전에 현재 runtime과 backend 문서를 함께 검증한다.

6. 장애 대응 표

상황: Commit 중 catalog가 unavailable/timeout 상태가 되었고 data·metadata file은 이미 생성됐다.

증상HMS/REST/Glue/Nessie timeout·5xx·throttling, lock timeout, CAS conflict, Spark catalog load 실패, 새 object는 존재하지만 snapshot 미노출, 일부 reader는 old snapshot 지속, retry 후 중복 가능성.
먼저 수집할 증거/지표Catalog 종류·endpoint·region/ref, exact exception와 HTTP/AWS code, operation/batch ID, base/current metadata location, CAS expected/new 값, lock owner·lease·heartbeat, request/response timeline, snapshot summary, object path/ETag/time, cache age, engine/connector version, auth principal.
가능한 가설Catalog service outage, DNS/TLS/token expiry, IAM deny, throttling, stale cache, concurrent writer CAS 승리, lock heartbeat 만료, REST server는 commit했지만 응답 유실, 잘못된 Nessie ref, Glue region mismatch, storage는 성공하고 control plane만 실패.
안전한 첫 조치동일 operation의 blind retry와 orphan cleanup을 멈춘다. Writer traffic을 제한하고 artifact·로그를 보존한다. Catalog가 복구되면 cache를 우회/refresh해 operation ID, new metadata path, current ref를 read-only로 조회한다. Reader는 검증된 snapshot을 pin한다.
rollback/복구Current pointer에 operation이 있으면 성공 처리하고 checkpoint를 맞춘다. 명시적 미commit이면 latest state에서 revalidate/replan한다. Unknown이면 status 확인이 가능할 때까지 보류한다. 잘못된 pointer는 catalog-native restore/forward commit으로 고치고, 확정 orphan만 safety window 뒤 제거한다.
하지 말아야 할 조치Metadata JSON·HMS/Glue record·Nessie ref 수동 편집, 다른 catalog로 즉시 같은 location 재등록, timeout 뒤 새 batch ID append, lock 강제 삭제, future cutoff orphan cleanup, object listing으로 commit 성공 추정, evidence 전 snapshot expiration을 하지 않는다.

자주 나는 오류와 해결

  • metadata_log_entries column 오류: DESCRIBE local.day36.catalog_probe.metadata_log_entries로 runtime schema를 확인한다.
  • REST 실패가 오래 걸림: OS connect timeout 뒤 종료될 수 있다. 같은 실행에서 endpoint를 반복 호출하지 말고 첫 exception과 elapsed time을 증거로 남긴다.

  • Hive schema evolution 실패: HMS positional validation과 Iceberg field ID semantics를 구분한다. 검증 비활성화의 Hive direct-read trade-off를 문서화한다.

8. 놓치기 쉬운 함정

  • Catalog = warehouse가 아니다. 이름/pointer state와 immutable bytes는 다른 시스템이 소유할 수 있다.
  • Object exists = committed가 아니다. Authoritative pointer/ref의 reachability가 membership을 결정한다.
  • Lock 획득 = semantic conflict 없음이 아니다. Overwrite/delete의 source file·predicate validation은 별도다.
  • Strong consistency = atomic multi-writer commit이 아니다. CAS/lock이 여전히 필요하다.
  • REST = storage proxy라고 단정할 수 없다. Client-side/remote scan planning과 credential 방식은 protocol/server/version별로 다르다.
  • 같은 location의 dual catalog 등록은 migration이 아니라 split-brain risk다.
  • Nessie merge = 하나의 DB transaction이 아니다. Branch 위 개별 Iceberg commit과 ref merge의 가시성 의미를 분리한다.

9. 대기업 기술 면접 질문

  1. 하루 10만 commit, Spark·Flink·Trino가 공유하는 S3 lake의 catalog를 선택하라.
    좋은 답변 구조: Write/read QPS와 p95 SLA → pointer owner/CAS → engine·language matrix → IAM/credential boundary → throttling/cache → RPO/RTO와 backup pair → Hadoop/Hive/REST/Glue/Nessie trade-off → canary와 migration/fallback.
  2. Catalog timeout 뒤 data file은 보이지만 job은 실패했다. 정확히 한 번 처리를 어떻게 지키는가?
    좋은 답변 구조: Operation identity/checkpoint → base/current pointer → explicit/unknown state 분류 → read-only status check → committed면 성공 처리, 미commit이면 latest replan → orphan safety window → blind retry·수동 pointer edit 금지.
  3. HMS에서 REST catalog로 무중단 이전을 설계하라.
    좋은 답변 구조: Source of truth와 single-writer fencing → table/location inventory → metadata pointer·auth mapping → shadow read와 snapshot checksum → write freeze/cutover marker → atomic consumer config 배포 → rollback 기준 → dual registration 방지 → DR 검증.

짧은 정답/채점: ① Version은 최소 해석 계약이고 delete/DV write property는 실제 artifact 생성 선택이다. ② Later reader가 V1 artifact의 missing field를 spec default로 해석한다. ③ Metadata load, old delete read, DV read/write, type/default, maintenance 중 네 가지 이상. 계약과 구현을 구분하면 만점.

오늘 내용 확인 3문제

  1. Catalog와 warehouse의 상태 소유 차이를 한 문장으로 설명하라.
  2. Hadoop/Hive/REST/Glue/Nessie에서 pointer owner를 각각 말하라.
  3. Catalog timeout 후 가장 먼저 해야 할 일과 하지 말아야 할 일은?

짧은 정답/채점: ① Catalog는 table name→current metadata pointer, warehouse는 immutable bytes를 소유한다. ② Path/filesystem, HMS record, REST server, Glue table state, Nessie ref/content. ③ Operation identity와 authoritative current pointer를 read-only로 확인하고 blind retry·orphan 삭제를 하지 않는다. 성공 확정 시점을 언급하면 만점.
