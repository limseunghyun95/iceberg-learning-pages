APACHE ICEBERG · WEEK 1 / DAY 07 · 회상·복습

회상: “Parquet만으로 부족한 이유” 설명

Lakehouse와 Table Format 정신 모델 · 예상 학습 25분 + 실습 30분

한 줄 요약
Parquet는 한 파일 안의 row를 효율적으로 저장하는 형식이고, Iceberg는 여러 immutable 파일 중 무엇이 현재 table인지 원자적으로 전환·추적하는 table protocol이다. 둘은 경쟁재가 아니라 서로 다른 계층의 책임을 맡는다.

1. 선수 용어 사전

File format한 파일 내부의 column encoding, compression, page·row group과 statistics를 정의한다. Parquet가 대표적이다.
Table format여러 data/delete file의 membership, schema·partition, snapshot, commit과 evolution을 정의하는 metadata protocol이다. Iceberg가 대표적이다.
CatalogTable 이름을 current metadata JSON 위치에 연결하고 pointer 교체의 원자성을 제공하는 control-plane 구성요소다.
Snapshot특정 commit이 만든 immutable table state의 root다. Data 전체 복사본이 아니라 manifest list를 가리키는 metadata node다.
Atomic commit독자가 old state 또는 new state만 보고 중간 상태는 보지 않게 current pointer를 한 번에 교체하는 동작이다.
Optimistic concurrency미리 lock을 잡기보다 base state에서 새 state를 준비하고 commit 직전에 current가 바뀌지 않았는지 검증하는 방식이다.
PruningPredicate와 metadata statistics로 읽을 필요가 없는 manifest·file·row group을 미리 제외하는 최적화다.

2. 왜 중요한가

“Iceberg는 Parquet의 단점을 해결한다”는 말은 절반만 맞다. Parquet의 책임은 한 파일 내부의 columnar I/O다. 여러 writer가 만든 수천만 파일 중 현재 읽을 집합, rename된 column의 동일성, partition 변경 뒤 old/new layout, 원자적 overwrite와 rollback을 정의하는 것은 file format 바깥의 문제다.

책임 경계를 정확히 말하면 장애 대응도 달라진다. Parquet footer가 정상이어도 manifest에 없으면 Iceberg row가 아니다. Warehouse file이 모두 있어도 catalog pointer나 metadata JSON을 읽지 못하면 table을 load할 수 없다. 반대로 catalog가 살아 있어도 referenced object가 사라지면 scan은 실패한다. “어디가 source of truth인가”를 계층별로 답해야 한다.

면접용 핵심 문장: Parquet는 byte layout, Iceberg는 table state와 transaction protocol, catalog는 current-state pointer의 소유자, engine은 이 protocol의 실행자다.

3. 아키텍처 그림과 요청 흐름

① Engine
SQL parse·plan·read/write task 실행
↓ table identifier 조회 / commit compare-and-swap
② Catalog pointer
namespace.table → current metadata JSON
↓ control path
③ Metadata tree
metadata JSON → snapshot → manifest list → manifest
↓ live file path·partition·metrics·sequence
④ Data path
Parquet/ORC/Avro data file + delete file/DV
↓ column/page pruning·decode
⑤ Query rows
선택 snapshot에 일관된 결과

Read 요청·응답·상태 변화

  1. Engine이 table identifier를 catalog에 보내 current metadata location을 받는다. Warehouse directory listing으로 table을 재구성하지 않는다.
  2. Metadata JSON에서 current snapshot, schema field ID, partition spec ID와 properties를 읽는다.
  3. Snapshot의 manifest list에서 partition summary로 manifest를 pruning하고, manifest의 partition·field metrics로 data/delete file을 pruning한다.
  4. 남은 Parquet file의 footer·row group·column page를 읽고 file-level pruning을 더 적용한다. Row-level delete table이면 sequence number에 따라 equality/position delete 또는 deletion vector를 적용한다.
  5. Read는 선택 snapshot의 state를 관찰할 뿐 current pointer를 바꾸지 않는다. 이것이 data path와 control path의 분리다.

Write 요청·응답·상태 변화

  1. Writer는 base metadata location과 snapshot을 load한다.
  2. 새 immutable data/delete file을 쓰고 manifest, manifest list, metadata JSON을 차례로 만든다. COW는 data file을 다시 쓰고, MOR은 delete file/DV를 추가해 read 비용을 미룰 수 있다.
  3. Commit 전 append/overwrite/delete operation에 맞는 conflict validation을 수행한다. Concurrent state가 안전하게 병합되지 않으면 실패한다.
  4. Catalog pointer가 새 metadata JSON으로 원자 교체되는 순간 commit이 확정된다. Object storage rename이 table transaction의 필수 선형화 지점인 것은 아니다.
  5. 응답 전에 network가 끊기면 성공/실패가 불명확하다. Current snapshot과 operation identity를 확인하기 전 blind retry하지 않는다.

4. CS 관점의 내부 동작

CS 개념왜 Parquet만으로 부족한가 / Iceberg가 추가하는 것
Namespace & identityFile path/column name만으로 안정적 identity를 만들기 어렵다. Catalog identifier, table UUID, field ID와 spec ID가 rename/evolution 뒤 동일성을 보존한다.
Persistent data structure새 snapshot은 전체 byte를 복제하지 않고 immutable manifest/data object를 공유하며 새 root를 만든다. Time travel과 rollback 가능성의 기반이다.
Transaction여러 file 쓰기를 하나의 atomic table state로 묶고 optimistic validation과 pointer swap으로 isolation을 제공한다. Parquet file 자체는 cross-file commit을 정의하지 않는다.
Secondary indexManifest list와 manifest가 membership·partition·column metrics의 계층형 index다. Object store의 O(n) listing과 모든 footer open을 피한다.
MVCCMulti-version concurrency control처럼 reader는 선택 snapshot을, writer는 새 version을 다룬다. 기존 data byte를 in-place 수정하지 않아 reader/writer 간 간섭을 줄인다.
Garbage collectionSnapshot/ref reachability와 retention을 기준으로 expire·orphan cleanup을 한다. Directory mtime만으로 삭제하면 active writer나 rollback state를 파괴한다.

상태의 소유자와 불변식

  • Parquet: 한 file의 schema annotation, encoding, statistics와 row byte를 소유한다. Table current state는 소유하지 않는다.
  • Iceberg metadata: Schema/spec/sort order, snapshot lineage, manifest와 file membership을 소유한다.
  • Catalog: Table identifier와 current metadata pointer의 atomic update를 소유한다.
  • Engine/connector: Spec을 읽고 write/validation/delete/pruning을 실행한다. 같은 table을 읽는다고 모든 version/feature 지원이 같지는 않다.
  • Object storage: Byte durability·availability를 소유한다. Object 존재가 table membership을 의미하지 않는다.

핵심 불변식: Reader가 관찰한 snapshot에서 manifest를 통해 도달 가능한 data/delete file 집합은 일관돼야 한다. Writer가 만든 file은 catalog pointer swap 전까지 current state가 아니며, swap 후에는 새 reader가 새 state를 볼 수 있어야 한다.

5. 실무 설계 판단

판단Best practice와 이유
Raw vs tableLanding zone의 immutable raw file과 curated Iceberg table 계약을 분리한다. Directory scan과 table scan을 같은 dataset API로 섞지 않는다.
Commit 증거Job exit code 외에 base/current snapshot, operation summary, source batch identity와 added records/files를 기록해 ambiguous commit을 판정한다.
EvolutionSchema는 field ID, partition은 spec ID와 transform으로 관리한다. 변경 가능성과 downstream 의미 호환성을 별도 검토한다.
COW/MORRead/write 비율, update 범위, delete-file 누적과 compaction SLO로 선택한다. V3 DV는 spec 존재와 engine 지원을 구분한다.
MaintenanceSnapshot expiration, data/manifest rewrite, orphan cleanup을 각기 다른 transaction으로 취급하고 active reader/writer·refs·rollback window를 guardrail로 둔다.
Multi-engineSpark/Flink/Trino별 connector, format version, read/write/delete/DV, type mapping, refresh와 procedure 지원을 compatibility matrix와 test gate로 관리한다.

Anti-pattern: “ACID table”이라는 이름만 믿고 catalog·object storage 장애, commit timeout, small file, delete-file 누적과 maintenance race를 관찰하지 않는 것. Protocol의 성공 지점과 비용을 설명하지 못하면 기능 목록일 뿐이다.

Edge case: Parquet footer schema가 읽을 수 있어도 Iceberg field ID mapping·delete applicability·partition spec 해석을 우회하면 silent wrong result가 가능하다. Raw Parquet read로 Iceberg table을 검증하지 않는다.

6. 장애 대응 표

상황: Warehouse에 정상 Parquet가 있는데 Iceberg query 결과에서 일부 row가 보이지 않는다.

증상Raw directory read와 Iceberg table row count 불일치, engine별 결과 차이, 새 file은 보이나 snapshot/file metadata 증가 없음.
먼저 수집할 증거/지표Catalog identifier와 current metadata location, snapshot/history, manifests/entries/files/all_files, exact object URI·size·mtime, schema field ID/spec ID/sequence, writer batch·commit log, engine/connector/format version, catalog/object audit log.
가능한 가설Manual/raw copy, failed commit orphan, pointer swap 후 stale cache, 다른 catalog/namespace, missing manifest reference, field/spec mismatch, delete file/DV 적용, expired snapshot, referenced object 손실.
안전한 첫 조치Write와 cleanup을 멈추고 current metadata chain과 exact paths를 보존한다. 새 session에서 catalog를 refresh하고 metadata table을 read-only로 대조해 membership과 delete 적용을 확인한다.
Rollback/복구올바른 과거 snapshot이 retained됐으면 검증 후 rollback을 새 commit으로 수행한다. 미commit data는 정식 Iceberg write/add-files 절차로 새 snapshot에 포함하고, missing referenced object는 backup에서 복원한다. Orphan은 safety window 뒤 정리한다.
하지 말아야 할 조치Parquet가 읽힌다는 이유로 manifest/metadata JSON을 수동 편집하지 않는다. Directory mtime 기준 삭제, blind INSERT retry, active writer 중 orphan cleanup, raw read 결과를 source of truth로 삼지 않는다.

사전 조건과 실행 전 예측

  • 자료를 덮고 90초 동안 답한다: 문제 → 책임 경계 → read path → commit → failure/cost 순서다.
  • 예측한다: INSERT 후 Parquet를 하나 복사하면 raw directory row와 Iceberg table row는 각각 몇 개가 되는가?

1단계 · 기억에서 architecture 재구성

빈 종이에 적을 7개 상자
Engine → Catalog pointer → metadata JSON → Snapshot → Manifest list → Manifest → Data/Delete file
각 화살표 위에 “무엇을 요청하고 무엇을 돌려받는가”, 각 상자 아래에 “누가 상태를 소유하는가”를 쓴다.

채점: Parquet를 마지막 data-file 계층에 두고, catalog pointer swap을 commit 성공 시점으로 표시하며, warehouse listing을 catalog로 그리지 않으면 1차 통과다.

예상 관찰: Iceberg table은 여전히 2 row이고 files에 rogue copy가 없다. Raw Parquet directory read는 정상 file과 복사본을 모두 읽어 2 + 선택한 file의 record count row가 된다. 예시 runtime처럼 선택 file에 1 row가 있으면 raw 결과는 3이다. 같은 byte를 읽어도 scan contract가 다르다는 증거다.

3단계 · 90초 teach-back 다시 녹음/작성

  1. 요구사항: 수천만 file, concurrent writer, schema/partition evolution, time travel이 있다고 가정한다.
  2. 내부 경로: Catalog pointer부터 Parquet까지 7단계를 순서대로 말한다.
  3. Transaction: 새 immutable object 준비, conflict validation, pointer swap 성공 시점을 말한다.
  4. 장애: Data upload 후 commit 실패와 pointer swap 후 response 유실을 구분한다.
  5. Trade-off: Metadata/pruning 이득과 small file·manifest·maintenance 비용을 말한다.

자주 나는 오류와 해결

  • KNOWN_FILE이 비어 있음: INSERT와 files 결과를 확인하고 DESCRIBE TABLE EXTENDED의 실제 Location으로 경로를 수정한다.
  • Raw path가 없음: 이 프로젝트의 container mount는 /workspace/warehouse, host는 warehouse다. 다른 환경에서는 catalog warehouse 설정과 volume mount를 확인한다.
  • Raw row 수가 예상과 다름: Writer가 여러 file을 만들 수 있다. 결과는 원래 2 row에 선택한 file의 record count를 더한 값이어야 한다.
  • Iceberg row도 증가함: Raw path가 아니라 table identifier를 조회했는지, 같은 catalog/namespace인지와 files path를 다시 확인한다.
  • Permission/cache 오류: make smoke, Docker disk와 프로젝트 Ivy cache 설정을 확인한다.
  • 설명이 기능 나열에 그침: 상태 소유자, 불변식, 성공 확정, failure window와 비용을 문장마다 하나씩 추가한다.

8. 놓치기 쉬운 함정

  1. Iceberg가 Parquet를 대체한다. Iceberg table의 data file로 Parquet를 흔히 사용하며 두 형식의 계층이 다르다.
  2. Warehouse directory가 table이다. Catalog pointer에서 current snapshot을 따라 도달 가능한 file 집합이 table state다.
  3. Snapshot은 table 전체 복사본이다. Immutable metadata root이며 기존 manifest/data file을 공유할 수 있다.
  4. ACID는 object storage rename이다. 새 metadata를 준비하고 catalog pointer를 원자적으로 교체하는 protocol이 핵심이다.
  5. 모든 conflict는 retry하면 된다. Append, overwrite, delete의 validation scope와 idempotency가 다르다.
  6. Schema rename은 이름 문자열만 바꾼다. Stable field ID가 old/new file의 column identity를 보존한다.
  7. Time travel은 backup이다. 같은 catalog/storage와 retention에 의존하므로 독립 DR copy가 아니다.
  8. Spec 기능은 모든 engine 기능이다. Format v2/v3, MOR/DV와 procedure 지원을 connector별로 확인해야 한다.

9. 대기업 기술 면접 수준 질문

Q1. “왜 Parquet 파일만으로는 데이터 레이크 table을 운영하기 어렵습니까?”

좋은 답변 구조: 10PB·수천만 object·동시 writer·다중 engine 가정 → Parquet의 file-internal 책임 → cross-file membership/schema/partition/transaction 부재 → catalog→metadata→snapshot→manifest→file read path → optimistic commit/pointer swap → timeout/orphan → metadata/small-file 비용과 Delta/Hudi/DB 대안.

Q2. “Iceberg append가 atomic한 이유와 실패 창을 설명하세요.”

좋은 답변 구조: Base metadata load → immutable data/manifest/list/JSON 생성 → operation별 conflict validation → catalog compare-and-swap 선형화 → old/new snapshot isolation → upload 후 commit 전 orphan과 swap 후 response 유실 → batch identity 검증·retry·cleanup safety window.

Q3. “Raw Parquet와 Iceberg를 함께 쓰는 플랫폼 경계를 설계하세요.”

좋은 답변 구조: Landing/curated 소비자·SLO·RPO/RTO → raw immutability와 Iceberg table contract → ingestion idempotency/validation → schema/partition evolution → Spark/Flink/Trino compatibility → catalog/storage outage → COW/MOR·compaction/retention 비용 → governance와 migration 대안.

10. 어제 내용 회상 3문제

  1. CREATE, INSERT, SELECT는 각각 어떤 Iceberg persistent state를 바꾸는가?
  2. Writer가 만든 data file은 어느 시점부터 current table member가 되는가?
  3. Client timeout 뒤 동일 INSERT를 바로 반복하면 왜 위험한가?

짧은 정답/채점 기준

  1. CREATE는 catalog/최초 metadata, INSERT는 새 snapshot/pointer, SELECT는 table state 불변이라고 답하면 통과.
  2. 새 metadata JSON으로 catalog pointer swap이 성공한 뒤라고 답하면 통과.
  3. Swap은 성공하고 response만 유실됐을 수 있어 중복 append가 생긴다고 답하면 통과.

11. 오늘 내용 확인 3문제

  1. Parquet, Iceberg metadata, catalog, engine이 각각 소유하는 상태를 한 문장씩 말하라.
  2. Warehouse에 valid Parquet를 복사했는데 Iceberg row가 늘지 않는 이유를 read path로 설명하라.
  3. Iceberg가 추가하는 reliability와 그 대가로 생기는 운영 비용을 두 가지씩 말하라.

짧은 정답/채점 기준

  1. File byte layout / table metadata graph / current pointer / protocol 실행자로 구분하면 통과.
  2. Catalog→current snapshot→manifest에서 복사본 path에 도달하지 못해 membership이 없다고 답하면 통과.
  3. Atomic commit·snapshot isolation/evolution 중 둘, metadata planning·small files·maintenance/compatibility 중 둘을 trade-off로 답하면 통과.
