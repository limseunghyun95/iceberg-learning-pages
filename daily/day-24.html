APACHE ICEBERG · WEEK 4 / DAY 24

append/overwrite/delete conflict validation

Commit·Isolation·Concurrency · 예상 학습 40분 + 실습 35분

한 줄 요약
Iceberg의 conflict validation은 “table version이 바뀌었는가”만 묻지 않고, operation이 읽고 제거하려던 file·predicate 범위가 concurrent commit 뒤에도 유효한지 검사해 append는 합치고 안전하지 않은 overwrite/delete는 중단하는 의미 기반 transaction gate다.

1. 선수 용어 사전

Read setOperation이 결과를 계산하며 의존한 table state다. Row-level SQL에서는 matching predicate로 scan한 data/delete file 집합이 대표적이다.
Write set새로 추가하거나 제거할 data/delete file과 이를 가리키는 manifest·snapshot 변화다.
Validation predicateBase snapshot 이후에도 참이어야 하는 안전 조건이다. 예: 제거 대상 file이 여전히 live이고, 조건 범위에 충돌하는 새 file이 없다는 조건.
Append기존 file을 제거하지 않고 새 data file membership을 더하는 operation이다. Table Spec의 retry 분류에서는 요구 조건 없이 새 current에 재적용할 수 있다.
Overwrite / replace기존 file 일부를 제거하고 새 file로 바꾸는 변화다. Compaction, dynamic overwrite, COW update/delete가 이 패턴을 쓸 수 있다.
File delete / expression delete전자는 특정 file identity를 제거하고, 후자는 event_time < X 같은 조건을 current state에 적용한다. Retry 규칙이 서로 다르다.
COW / MORCopy-on-write는 영향받은 data file을 다시 쓰고, merge-on-read는 delete file을 추가해 read 시 합친다. 같은 SQL도 write set과 검증 대상이 달라진다.
Isolation levelConcurrent 변화 중 무엇을 conflict로 볼지 정한 계약이다. Iceberg는 row-level operation에 serializable과 snapshot isolation을 지원하며 Day 25에서 비교한다.

2. 왜 중요한가

Writer A와 B가 같은 base snapshot에서 출발해도 모든 동시 실행이 충돌하는 것은 아니다. 서로 독립적인 append라면 둘 다 보존하는 것이 옳다. 반대로 A가 file F의 row를 읽어 새 F′를 만들었는데 B가 F를 먼저 삭제·재작성했다면 A의 stale F′를 publish하면 B의 변경을 잃거나 삭제된 row를 되살릴 수 있다.

따라서 CAS 실패는 1차 신호일 뿐이다. 최신 metadata tree를 읽은 뒤 operation별 read/write set과 concurrent changes의 교집합을 검사해야 “재적용 가능한 경쟁”과 “업무 의미가 깨진 충돌”을 구분할 수 있다. 이 구분이 잘못되면 lost update, write skew, duplicate ingestion, delete 누락, maintenance race가 발생한다.

두 층을 구분하자: Table Spec의 commit retry 규칙은 metadata update를 새 current에 적용할 수 있는지 말한다. Spark의 row-level isolation 검사는 UPDATE/DELETE/MERGE predicate와 concurrent file 추가·삭제까지 검사한다. “Expression delete는 재적용 가능”만 보고 row-level semantic conflict를 무시하면 안 된다.

3. 아키텍처 그림과 요청 흐름

① Base S0 계획
catalog pointer → metadata JSON → snapshot → manifest list → manifest
↓ predicate projection·file pruning
② Read set R / write set W 고정
Append: add only · Overwrite/Delete: remove/replace 또는 delete file add
↓ immutable output 준비
③ W1 CAS 성공, current=S1
Concurrent file add/remove/delete-file change가 먼저 linearize
↓ W2 CAS 실패 → refresh
④ S0→S1 conflict validation
R/W, 대상 file 존재, predicate와 concurrent change 교집합 검사
↓ compatible: rebase / incompatible: abort·replan
⑤ 새 snapshot S2 CAS
CAS 성공 시에만 새 membership이 모든 reader에 보임

번호별 요청·응답·상태 변화

  1. Plan: Engine은 S0의 schema/spec/sequence와 manifest metric으로 matching data/delete file을 찾는다. Hidden partition transform은 predicate를 spec별로 투영한다.
  2. Prepare: Append는 새 data file을, COW overwrite/delete는 replacement data file을, MOR delete는 equality/position delete file을 unique path에 쓴다. 아직 current graph에는 연결되지 않는다.
  3. Concurrent commit: W1이 catalog CAS로 S1을 publish한다. S1에는 W2가 읽지 못한 data file, 제거된 source file, 새 delete file이 포함될 수 있다.
  4. Validate: W2는 S0 이후 snapshot lineage와 manifest entry를 비교한다. Append는 prepared add를 S1에 더할 수 있다. Replace는 제거하려던 source가 모두 live인지 확인한다. Predicate overwrite/delete는 isolation 수준에 따라 범위 안 concurrent add/delete를 검사한다.
  5. Commit or fail: Compatible하면 S1을 parent로 한 manifest list·snapshot·metadata JSON을 재생성하고 CAS한다. Incompatible하면 prepared bytes가 온전해도 operation을 실패시키고 latest state에서 다시 계획한다.
  6. Read visibility: Reader는 current pointer에서 도달 가능한 data/delete file만 읽고 sequence 규칙으로 delete applicability를 판단한다. Validation 실패 artifact는 orphan 후보일 뿐 committed row가 아니다.

4. CS 관점의 내부 동작

Operation별 validation matrix

Operation새 current에서 확인판정
AppendSpec retry 분류상 기존 file 제거 요구 조건이 없다.새 manifest를 current snapshot에 합쳐 retry 가능. 단, batch dedupe·PK uniqueness는 별도 문제다.
Replace제거할 source file이 모두 live인가?모두 존재하면 remove+add 재적용. 하나라도 사라졌으면 abort·replan.
Specific file delete지정한 file이 아직 table에 있는가?있으면 삭제 재적용, 없으면 stale intent이므로 실패.
Expression deleteSpec 수준에서는 current에 expression을 다시 적용할 수 있다.Engine row-level command는 isolation 계약에 따라 concurrent matching file을 추가 검사한다.
Predicate overwrite대상 file 존재 + base 이후 destination predicate 안의 add/delete.Serializability와 idempotency 요구에 따라 conflict 또는 재적용.

불변식과 성공 시점

  • Membership invariant: 새 snapshot의 live file 집합은 parent의 live set에 검증된 add/remove를 적용한 결과여야 한다. Concurrent commit의 file을 조용히 잃으면 안 된다.
  • No resurrection: Base 이후 제거·재작성된 source를 stale replacement로 되살리면 안 된다.
  • Predicate invariant: Row-level operation이 “조건에 맞는 모든 row”를 바꾼다고 약속했다면 isolation 계약이 허용하지 않는 concurrent matching add를 놓치면 안 된다.
  • Delete applicability: MOR/equality·position delete와 v3 deletion vector는 data file identity와 sequence semantics를 보존해야 한다. Validation은 byte 존재만이 아니라 적용 관계를 지킨다.
  • Linearization point: Validation 통과도 성공이 아니다. 새 metadata location의 conditional catalog swap이 성공한 순간에만 state transition이 확정된다.

Control path와 data path

Data path는 executor가 row를 읽고 shuffle하며 data/delete file을 쓰는 경로다. Control path는 driver가 base snapshot, read/write set, manifest, validation과 catalog CAS를 관리하는 경로다. Conflict validation이 control path에 있다고 해서 값싼 것은 아니다. Predicate 범위가 넓고 snapshot 사이 manifest가 많으면 validation planning 비용과 catalog stale window가 함께 커진다.

Object storage가 성공한 PUT을 보장해도 catalog commit이 실패하면 logical write는 실패다. 반대로 CAS 성공 응답이 유실되면 unknown commit state다. 이때 validation failure와 네트워크 timeout을 같은 retry로 취급하지 않는다.

5. 실무 설계 판단

Best practice 1 · operation identity: Pipeline은 batch ID, source offset 범위, target predicate와 base snapshot ID를 남긴다. Append의 metadata retry 가능성은 end-to-end idempotency를 대신하지 않으므로 duplicate batch를 별도로 차단한다.

Best practice 2 · scope 최소화: Full-table overwrite 대신 명시적 filter나 dynamic overwrite, row-level MERGE를 사용해 read/write set을 줄인다. 단, partition evolution 뒤 dynamic overwrite가 대체하는 partition 의미가 바뀔 수 있어 MERGE가 더 명확할 때가 있다.

Best practice 3 · conflict telemetry: Operation, base/current snapshot, validation type, matching concurrent file 수, predicate, source file 수, isolation property, retry attempt, maintenance job ID를 한 event로 기록한다.

Best practice 4 · maintenance coordination: Compaction은 replace validation을 통과해야 한다. Hot partition의 ingestion·COW delete·rewrite_data_files를 동시에 돌리지 말고 시간 또는 branch/WAP로 scope를 분리한다.

Spark 1.11.0 기준: Table property write.delete.isolation-level, write.update.isolation-level, write.merge.isolation-level의 문서 기본값은 serializable이다. DataFrame V2 overwrite의 write option isolation-level은 null이면 idempotent write용 no checks, serializable이면 destination partition의 concurrent insert/delete, snapshot이면 concurrent delete를 검사한다고 문서화되어 있다. 정확한 지원과 exception은 사용 중인 Spark/Iceberg connector 버전에서 검증한다.

Engine 차이: Table Spec이 append/replace/delete retry 불변식을 정의해도 Spark·Flink·Trino의 SQL surface, COW/MOR default, predicate projection, conflict exception과 지원 format version은 같지 않다. Multi-engine write 전에는 같은 table property와 concurrent test를 CI gate로 둔다.

Anti-pattern: Validation 실패를 transient CAS conflict로 보고 무한 retry하거나, isolation-level=null을 일반 overwrite 성능 옵션처럼 쓰거나, static overwrite에서 PARTITION 절 누락으로 table 전체를 교체하는 것이다.

Edge case: Snapshot expiration이 validation에 필요한 base lineage를 너무 일찍 없애거나, rewrite가 delete file/sequence를 고려하지 않거나, object store에 output만 남은 failed attempt를 즉시 orphan cleanup하면 안전한 복구가 어려워진다.

6. 장애 대응 표

상황: Overwrite/delete job이 validation conflict로 반복 실패하거나 성공했는데 기대한 row가 남거나 사라졌다.

증상ValidationException/CommitFailed 급증, “required files are missing”, conflicting data/delete file, COW rewrite 반복, 같은 predicate 일부 row 잔존, duplicate append, orphan 증가, maintenance·ingestion 동시 실패.
먼저 수집할 증거/지표Engine/connector/catalog/version, operation·COW/MOR·isolation, base/current snapshot과 lineage, predicate·partition spec ID, read/source file 및 concurrent added/removed data/delete file, sequence number, attempt별 log, snapshot summary, catalog latency/status, maintenance timeline, batch ID/offset.
가능한 가설같은 hot partition overwrite, delete predicate와 late data append 중첩, compaction이 source file 선점, partition evolution 후 overwrite scope 변화, snapshot/serializable 설정 오해, scheduler duplicate, stale table cache, sequence/delete applicability mismatch, catalog timeout의 unknown state.
안전한 첫 조치동일 predicate의 새 writer·maintenance를 잠시 멈추고 current snapshot을 refresh한다. 실패 attempt의 base, target file/predicate, concurrent diff를 보존하고 operation identity로 성공 여부를 먼저 확정한다. Latest state에서 canary 한 건을 재계획한다.
Rollback/복구Invalid operation은 latest state에서 source set을 다시 읽어 새 output을 만든다. 잘못 성공한 overwrite는 검증된 이전 snapshot/backup source로 compensating write하고, duplicate append는 batch identity로 dedupe한다. Failed artifacts는 safety window 뒤 orphan cleanup한다.
하지 말아야 할 조치Validation 비활성화, metadata JSON/manifest 수동 편집, stale file 강제 remove, 같은 SQL의 무한 blind retry, unknown state에서 duplicate append, 증거 전 snapshot expiration·orphan cleanup, isolation을 낮춰 장애를 숨기는 조치는 금지한다.

7. 35분 재현 실습

목표: Concurrent append는 합쳐질 수 있지만 같은 범위의 DELETE/INSERT는 isolation validation 대상이 되는 차이를 snapshot·log·metadata table로 관찰한다.

사전 조건과 실행 전 예측

  • Docker daemon과 프로젝트의 Spark/Iceberg 환경이 준비되어 있고 make smoke가 성공해야 한다.
  • 같은 날 partition에 DELETE와 INSERT가 겹칠 때 가능한 결과를 먼저 적는다: 한쪽 validation 실패, 또는 실행이 직렬화되어 둘 다 성공.
  • 둘 다 성공하면 최종 row가 어떤 commit 순서를 반영할지 예측한다.
  • 학습용 local Hadoop catalog의 timing은 production REST/Glue/Hive catalog를 대표하지 않는다.

자주 나는 오류와 해결

  • DELETE syntax/extension 오류: Spark session에 Iceberg SQL extensions가 설정되었는지 프로젝트 구성과 make smoke를 확인한다.
  • 모든 job 성공: Scheduler가 직렬화했을 수 있다. Row를 늘리거나 round를 늘리고 snapshot parent 순서를 확인한다.
  • 모든 append 실패: Retry 0 contention 결과일 수 있다. Log에서 CAS와 validation을 구분하고 retry 4로 같은 append를 새 ID에 실행한다.
  • Table property 무시: Connector version과 row-level mode 지원을 확인하고 SHOW TBLPROPERTIES 결과를 보존한다.
  • Files table column 차이: Engine/version별 metadata table projection이 다르면 DESCRIBE local.day24.conflict_lab.files 후 존재하는 column만 조회한다.
  • Production과 결과가 다름: Hadoop catalog timing과 실제 catalog의 conditional update, cache, throttling을 동일시하지 않는다.

8. 놓치기 쉬운 함정

  1. CAS conflict면 business conflict다. Append처럼 semantic하게 합칠 수 있는 change도 pointer 경쟁은 발생한다.
  2. Append는 중복이 없다. Metadata retry 가능성과 batch idempotency·PK uniqueness는 별도다.
  3. Expression delete는 항상 안전하다. Spec retry 가능성과 row-level isolation의 concurrent matching add 검사는 다른 층이다.
  4. Overwrite는 table 전체 교체다. Filter/dynamic partition/file replacement 등 scope가 다르며 static mode 오설정은 실제 전체 교체가 될 수 있다.
  5. Source file 존재만 보면 충분하다. Delete file과 sequence applicability, predicate 범위의 concurrent add도 operation에 따라 중요하다.
  6. COW와 MOR validation은 같다. 제거·추가되는 artifact와 read-time merge 책임이 다르다.
  7. Isolation을 낮추면 성능만 좋아진다. 허용되는 concurrent 결과가 달라지므로 업무 invariant 검토가 먼저다.
  8. Validation 실패 artifact는 corruption이다. Current metadata graph에서 unreachable한 prepared output은 보통 orphan 후보다.

9. 대기업 기술 면접 질문 3개

  1. 두 append와 두 overwrite가 같은 base에서 시작했다. 어떤 쌍을 retry할 수 있는지 설명하라.
    좋은 답변 구조: 요구사항·operation 정의 → read/write set → CAS와 semantic conflict 구분 → append add-only → overwrite source/predicate validation → rebase/abort → idempotency 대안.
  2. Late event ingestion과 GDPR DELETE가 같은 날짜 partition에서 경쟁한다. Isolation과 운영 방안을 설계하라.
    좋은 답변 구조: SLO·삭제 보장·late rate 수치 → matching predicate → serializable/snapshot 결과 → COW/MOR 비용 → conflict metric·backoff → window 분리/branch/compensation.
  3. Compaction이 계속 “required file missing”으로 실패한다. 원인과 복구를 방어하라.
    좋은 답변 구조: Source file identity assumption → concurrent rewrite/delete/sequence → snapshot·manifest 증거 → latest replan → maintenance scope 조정 → orphan/snapshot retention 안전선.

10. 어제 내용 회상 3문제

  1. CAS conflict 뒤 data file을 재사용해도 반드시 새로 만들어야 하는 metadata는?
  2. Rewrite retry가 안전하려면 source file에 대해 어떤 가정이 유지되어야 하는가?
  3. Commit contention을 키우는 두 변수 λ와 T는 무엇인가?
짧은 정답/채점 기준
  1. 최신 parent를 반영한 manifest list, snapshot, metadata JSON과 CAS attempt. Metadata rebase를 말하면 정답.
  2. 제거하려던 source file이 모두 current table에 live여야 한다. No stale replace가 핵심.
  3. λ는 table commit rate, T는 base load부터 CAS까지 stale window다. 빈도×시간을 말하면 정답.

11. 오늘 내용 확인 문제 3개

  1. Append CAS conflict와 overwrite semantic conflict의 차이는?
  2. Specific file delete와 expression delete의 retry validation은 어떻게 다른가?
  3. Validation 통과가 commit 성공이 아닌 이유는?
짧은 정답/채점 기준
  1. Append는 add-only라 새 current에 합칠 수 있지만 overwrite는 source/predicate의 concurrent 변화가 lost update를 만들 수 있다. Read/write set 교집합이 핵심.
  2. Specific file delete는 대상 file이 여전히 live인지 검사하고, expression delete는 current에 재적용 가능하되 row-level isolation은 concurrent matching change를 추가 검사한다. Spec/engine 층 구분을 말하면 정답.
  3. 새 metadata pointer의 conditional catalog swap이 아직 남아 있으며 다른 writer가 먼저 이길 수 있다. CAS=linearization point가 핵심.
